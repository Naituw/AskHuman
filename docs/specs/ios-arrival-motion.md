# iOS 新请求到达动效：原型设计

2026-10-31：用户已确认手机能播放 MP4，选择方向 A，并在对比顶部曲线修订后决定先使用原轨迹。随后批准正式接入，实施见 [计划](../plans/ios-arrival-motion.md)。

## 已确认的要求

- 提问、权限确认、Stop 确认都播放；Agent 完成等消息继续普通提示。
- 继承 Mac 的柔光瓷面、蓝色镂空问号、两次弹跳及弯曲飞行。每条独立完整播放，允许并发，不合批、不排队。
- 覆盖所有 App 页面，包括键盘输入中、sheet 与全屏页面。纯装饰层完全透过触摸，不导航、不关闭弹层、不收起键盘，不改变焦点、光标、选区或输入法组合态。
- 气泡替代新请求的大横幅，Agent 完成等其他横幅保留。无导航标题的全屏页也在安全区顶部显示短暂收件提示，不延后到退出全屏。

## 触发时机（2026-11-01 修订）

用户反馈回到 App 时收件箱刷新补出的请求也弹跳，确认保留**前台收件箱实时新消息的弹跳**，只排除回来刷新和同步补齐。

| 场景 | 到达动效与原有到达震动 |
|---|---|
| App 持续活动，某台 Mac 的收件箱已同步，随后收到有效的实时新增 | 播放，收件箱列表与其他页面一致 |
| 冷启动、回到前台、点击推送、下拉刷新时同步出的请求 | 不播放，列表、未读和数量照常更新 |
| 重连、Mac 恢复在线或增量缺口修复后，从快照补出的请求 | 不播放；即使请求刚创建，也不把快照还原成实时到达 |
| 短暂失活或后台期间的到达事件，回到活动状态后才被 UI 消费 | 丢弃提醒，不补播 |
| 已打开／已处理的同一请求、补齐正文、重复消息 | 不播放 |
| 动画中失活或离开 App | 清除，回来不续播 |

不设置“回来后禁播几秒”的时间窗口。同步完成后的下一条有效实时新增立即获得播放资格；各 Mac 独立同步，互不压制。
动画和到达震动采用同一资格；动画结束不标记已读、不处理请求、不改草稿。轨迹、并发和各页面的落点沿用原设计。

## 原型里的两个落点方向

**A：优先飞入现有收件箱。** 底部标签可见时落在收件箱图标，轻柔亮起一次；待处理数量仍由实际 inbox 驱动。底栏不可见时，在导航标题区域显示短暂的「收件箱 · 数量」小收纳提示，承接气泡后淡出。单行标题轻移 6pt 腾出副标题位置；已有文件名／页码等双行标题保留，提示放在导航栏下沿，不盖住返回／取消／提交按钮、输入内容或键盘。无导航栏使用安全区顶部。

**B：统一落在标题区。** 无论底栏是否可见，始终落入同一收纳提示。空间更一致，但主页面多出一个收件指示，目的地与实际收件箱标签之间的关系较弱。

用户已选择 A 和原轨迹；B 仅保留为首轮对照。

### 宽屏分栏：飞进那一行的蓝点（2026-11-07）

用户在 iPad 上发现：收件箱列表可见时来了新请求，气泡弹跳之后没有飞到那一行的蓝点上，与 Mac 的设计不一致（Mac 把气泡收成一个 10px 蓝点、飞进侧边栏新行的蓝点位置，蓝点在气泡落下之前不显示）。原因是手机的落点只有「收件箱标签」与「导航标题」两种，没有行这个目标。

| 情形 | 落点 |
|---|---|
| 窗口宽到收件箱列表是一栏（分栏），新请求的行已在列表里、蓝点落在列表可见区域内 | **那一行的未读蓝点**：气泡收成 9pt 蓝点飞进去，落地时蓝点原位出现（落下前保持隐藏，不提前闪一下），同一位置柔光一次 |
| 行不在屏幕上（列表滚走了）、当前不是收件箱页、窗口是单栏（手机、窄窗口） | 沿用原设计：收件箱标签图标，没有标签栏时导航标题 |
| 减少动态效果 | 不隐藏蓝点；在那一行的蓝点处亮一下静态柔光（有标签栏时与标签处的静态提示同理） |

- 位置每帧重新测量：列表可以在气泡飞行中滚动，行的出现也晚于气泡起跳；落点用同一个平滑系数跟随，不会突然跳位。多个请求并发时各飞各的行；有的行看得见、有的看不见，各自按上表选落点。
- 不为了让气泡有地方落而去滚动列表：新请求的行在列表顶部，列表在顶部时一直看得见；用户正翻到别处时不抢他的位置，气泡落到标签图标。
- 蓝点的隐藏由动画自己的状态决定：气泡落地、动画被打断（失活、离开页面、减少动态效果）或请求已被打开时立即恢复，不会留下一个永远不显示的蓝点。

## 动作与质感

- 使用 Mac 的现有 `inboxArrival.ts::arrivalFrame` 轨迹，220ms 浮现、1000ms 第一跳、616ms 第二跳、750ms 勾线飞入；不依赖通用 spring 近似，保持空中减速、触地轻压及向飞行连续衔接。
- 手机底板约 70pt（Mac 88px 的 0.8 倍），保留柔光瓷面渐变、近远双层阴影、轻微压缩和镂空问号。飞行时底板淡去、问号闭合、气泡收成小蓝点。
- 普通页面从可用内容中央出现；输入时起点在键盘以上，避免从键帽或当前输入框里弹出。
- 并发气泡小幅水平错位，各自拥有时间轴和飞行，不用数量气泡替代请求。大量同时到达的遮挡风险需要用原型评估，不能擅自改为合批。
- 标题收纳提示不提供点击；动画本身也不提供任何手势。此轮不新增声音或震动设计。

### 顶部曲线的对比结论

用户初轮反馈顶部像直接折返，因此比较过侧向展开再上行的曲线；看过前后对比视频后，最终要求「还是先用原轨迹吧」。当前原型已恢复 Mac 的原轨迹，不启用侧向展开方案。

## 正式实现

`PhoneEngine.onInboxSnapshot` 只同步请求，不生成到达事件；`onRequestNew` 仅对按序接收的、此前未知的前台实时请求生成事件。事件携带手机的单调时钟接收时刻，`AppStore` 将其与本轮活动期起点比较，过滤跨失活周期排队的旧事件；不依赖 Mac 的时钟或新增线协议字段。

`AppStore.requestArrivals` 保留每条符合资格的新请求。`presentArrivals()` 处理事件先于状态的情况，等请求进入 inbox 后再一起释放动画和到达震动；活动资格直接跟随 scene 生命周期，避免独立状态流中较早的前后台快照误丢新事件。重复的 active 更新不会重置本轮起点。打开／处理／离开活动状态清理相应动画，短暂完成不改未读或草稿。原来的“只显示最新请求横幅”已替换，其他种类横幅保留。

`ArrivalSceneHost` 绑定根视图所在的 `UIWindowScene`，用透明装饰 UIWindow 承载。`canBecomeKey` 恒为 false，`hitTest` 恒返回 nil，窗口和子树禁用交互，装饰元素对辅助功能隐藏；不调用 `makeKeyAndVisible`，不改变 first responder。仅 Debug mock 验证时开放诊断标识和真实 UITextInput marked-text 测试 fixture，正式后端不启用。

`ArrivalLayout` 读取真实可见底栏、导航标题、键盘和安全区；键盘／页面切换时锚点平滑跟随。已有输入区域避让，已有双行标题不挪动。没有标题时，收件提示优先使用导航按钮之间剩余的宽空隙；不足时放到导航栏下沿，避免覆盖请求快切箭头和更多菜单。减少动态效果显示静态提示；后台／scene 失活清理 display link。顶部收纳在落位后保留 950ms，再用 450ms 淡出，避免气泡结束时提示与标题突然跳回。

分栏列表的行落点：`InboxRow(landsArrival:)` 在宽屏的分栏列表里给自己的蓝点放一个看不见的 `ArrivalDotMarker`，登记到主线程上的 `ArrivalDots`（请求 id → 弱引用的标记视图，同时记下「气泡已落地」的请求）；`ArrivalSceneController` 每帧用 `ArrivalDots.center(of:in:)` 取标记在窗口里的位置，且要求它在最近的滚动视图的可见区域内才算数，然后把该请求的落点从标签换成它。诊断串里 `destination=row` 与 `target=x,y` 表示这条气泡正飞向行的蓝点，供 UI 测试与屏幕上的行对照。

当前 App 只启用单 scene，装饰层仍按来源 scene 绑定并过滤其他 scene 的失活通知。此项不改变 MQTT／APNs 或线协议。

## 第一帧：被画出来之前不可见（2026-11-12）

用户反馈：手机收到新消息时，动画先在角上出来，然后闪到中间。他说的是右上角；录像里我抓到的是窗口的左上角（见下），两者是同一个机制，不论落在哪个角，修法一样。

**原因**：气泡是一个新建的 `UIView`，加进装饰窗口时落在窗口原点 (0, 0)，不透明度 1；装饰窗口也在同一刻显示。而 display link 的第一次回调要等下一个 vsync，才由 `tick` 把它摆到起点并从 0 渐显。两者之间只要有一次画面提交，屏幕上就先有一个完整不透明的气泡停在窗口左上角，随后才跳到中间。屏幕录像（`simctl io recordVideo`，逐帧看）：iOS 26.2（iPhone 17）和 iOS 27.1（Duo 外屏）上每次到达都有 2 帧（约 50 ms）的角上气泡；iOS 18.5（iPhone 16）那一次没有抓到——提交与 vsync 谁先谁后不由我们定，所以不是只有个别系统才会出现，主线程忙时（到达与列表刷新撞在一起）第一次回调更晚，角上停得更久。另一个相关的小毛病：起跳时刻原先从气泡创建起算，第一次回调来得晚时，220 ms 的渐显被吃掉一截，气泡直接「闪」进中间。

**规则**（动效本身的轨迹、时长与落点不变）：

- 气泡创建时 `alpha = 0`，并在加进窗口之前就摆在第 0 毫秒那一帧的位置与形变上（起点、透明），所以在被画出来之前，屏幕上什么也看不到。
- 动效计时从**第一次画出它的那一帧**起算，不是从气泡创建起算；第一帧来得晚，也不会跳过渐显。
- 显示装饰窗口之前，先把窗口与画布的 frame 对齐到来源窗口当下的位置与大小（创建窗口时的 frame 可能已过期：旋转、折叠展开、改变窗口大小之后）。
- 诊断串新增 `stray=<n>`：第一次画出来时就已经可见的气泡个数，正确的实现恒为 0。`AskHumanArrivalUITests.testABubbleIsNotSeenBeforeItsFirstFrameIsPainted`（三条并发气泡）守着它；旧实现下这条用例是红的（`stray=3`）。

**证据边界**：`stray` 量的是「第一次画出来之前气泡的透明度」，是这个机制的模型层判据；逐帧看屏幕的证据是上面的录像，修复后的录像见 [实施记录](../plans/ios-arrival-motion.md)。XCUITest 不能逐帧取屏幕，所以没有「屏幕上第一帧在哪」的断言。
