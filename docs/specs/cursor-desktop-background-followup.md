# Cursor Desktop 后台完成自动续跑控制

状态：2026-10-16 已按用户授权恢复默认关闭的实验功能，加入原生行为预检并完成安装与六窗口验证。
恢复实施与安装验证见 [恢复计划](../plans/cursor-desktop-restoration.md)；先前的撤回决定与理由保留于
[可靠性复审](../investigations/cursor-background-reliability.md)。本机偏好保持关闭（2026-11-07 起本机已开启，
已在 Cursor 3.27.22 的 Agents 窗口生效）。

2026-11-07 修订（**已实现，待落地观察**）：同一个开关下增加第二个守卫「运行中会话保护」，防止长时间运行的首轮
失败后被 Cursor 误归档、首条消息被删除；见 [§7](#7-修订2026-11-07已实现同一开关下增加运行中会话保护)，
实现与验证记录见 §7.12。§1–§6 的后台完成守卫不变。

## 1. 目标与已确认决策

Cursor 的后台 Shell 或子代理结束后，可以通过完成通知重新启动模型，即使用户已点击 Stop，
或通过 AskHuman 同意结束本轮。调查与原型证据见
[`../investigations/cursor-background-followup.md`](../investigations/cursor-background-followup.md)。

用户已确认：

- 采用全局策略：阻止所有后台完成通知自动启动新一轮模型，包括尚未明确结束的会话。
- 不维护逐会话的结束、恢复状态，不识别人类输入来解除会话静音。
- 增加独立开关，默认关闭；仅 Cursor 的 AskHuman 自动集成为 CLI/MCP 时运行。
  切至 None 停止接入，保留该开关偏好。
- 首版正式范围为 **macOS Cursor Desktop 的 Cursor Agents 和普通 IDE 窗口**，两条运行路径
  都必须通过验收，不能用一条路径的结果替代另一条。
- 普通启动自动接入；按实用优先，不为消除启动、重载期间的短暂接入过程增加启动接管机制。
- 用户随后授权按本规格开始实现；Cursor CLI 仅作静态分析，禁止实测。

这里的 CLI/MCP 是 **AskHuman 的提问集成模式**，不表示该功能支持终端里的 Cursor CLI。

## 2. 行为契约

| 输入或动作 | 开关开启且已接入时的行为 |
|---|---|
| 后台 Shell 成功、失败或被中断 | 正常记录真实结果与输出，确认完成通知，不自动启动模型 |
| 后台子代理完成 | 正常维护完成状态与原生确认台账，不因通知自动启动父会话模型 |
| 已排队、尚未进入模型的后台完成通知 | 通过原生完成处理收敛，不重排，不产生模型请求 |
| 模型正在显式 Await 的任务完成 | 正常返回该工具调用的结果，不能破坏等待者或挂死当前轮次 |
| 用户点击 Stop / 在 AskHuman 同意结束 | 沿用原有停止语义；已生效的全局策略持续阻止后台完成续跑 |
| 主动发送新消息，或选择 AskHuman 的继续 | 沿用原有提交与 continuation，不被此开关阻断 |
| 开启前已经进入模型的一轮请求 | 不追溯取消；原生 Stop 仍可停止它 |
| 关闭开关或切至 None | 恢复原生后续行为；不回放此前已确认的通知 |

全局范围覆盖接入 Cursor Desktop 进程中的所有本地工作区和会话，不要求会话使用过 AskHuman，
也不依赖它是否打开、位于前台、属于当前项目或显示过结束标记。

不终止后台命令或子代理，不改变其输出文件、退出状态和权限审批；不归档、隐藏、删除聊天。
正常工具结果不能伪装成成功：原型中的 `completed` 是“完成通知已处理”的内部返回值，
任务本身的 success/error/aborted 状态仍取原生结果。

本节的后台完成守卫只控制后台完成通知（同一开关下的第二个守卫见 §7）。Goal、订阅、定时任务、用户设定的自动化及远端 Cloud Agent 自身的
调度不在范围内；不得将 UI 文案写成“禁止一切自动运行”。本地父会话收到子代理完成时，仍需
按本节契约处理，不能借 Cloud Agent 的非目标范围遗漏本地完成通知。

## 3. 设置、状态与偏好

- 设置入口位于 Cursor 自动集成卡，建议文案为 **“禁止后台完成后自动续跑”**（2026-11-07 起标题与说明以 §7.5 为准）。
- 简短说明：**“对所有本地 Cursor Desktop 会话生效。后台任务照常执行，完成后需主动发消息
  才会让模型继续处理；不影响当前轮次的 Await。”**
- 与“结束时确认”、生命周期追踪分开保存和启停，不增加第二条 Stop Hook，也不更改现有
  Stop / whats-next 输出协议。
- 偏好使用现有配置保存机制，建议字段为
  `cursorDesktop.suppressBackgroundCompletionFollowUp`，缺失时为 `false`。
  具体字段归属在实现时按配置约定确定，不形成第二份配置真值。
- macOS 且 CLI/MCP 集成有效时可开启；None 隐藏运行开关但保留偏好。Windows/Linux 显示
  暂不支持，不执行 macOS 接入逻辑。
- “偏好已开启”与“当前已生效”分开表达。沿用设置页现有状态样式，简要显示等待 Cursor、
  正在接入、已生效或接入失败；失败原因进入现有诊断入口，不增加日常弹窗。
- 只有目标运行路径的契约检查及挂载均成功，才能显示已生效；部分窗口失败不能显示全局成功。
- 2026-11-07 修订（§7.5）：设置项文案改为覆盖两个守卫，状态按守卫分别报告，新增「部分生效」。

## 4. 运行与接入边界

### 4.1 所有权与普通启动

由 Daemon 独占管理接入；GUI/CLI 只读状态、保存偏好和发出既有 IPC 管理请求。
不要求用户改变 Cursor 的日常启动方式、手工加调试参数、打开 DevTools 或修改安装包。

运行约定：

- 开关有效时，Daemon 保持运行并发现后续启动的 Cursor；关闭后恢复既有闲退规则。
  不改写用户的 `general.daemonLifecycle`，登录启动沿用现有设置。
- AskHuman 尚未运行时不宣称保护有效；开启开关会启动所需 Daemon。
- 覆盖 Cursor 先启动、AskHuman 先启动、Cursor 重启、新窗口和窗口重载。
- 接入时点为 `发现 Cursor 进程 → 等待窗口内部服务就绪 → 安装拦截 → 后续完成通知不再启动模型`。
  Cursor 已运行时开启开关，当场接入已有窗口；开关有效后发现新进程便开始接入，新建或重载窗口
  自动重新挂载。Stop 或 AskHuman 结束不是接入触发点，正常工作时拦截应已就绪并持续有效。
- 已接入窗口的拦截能独立处理完成通知，不把每次通知转交 Daemon 等待，不依赖短命 Ask 进程。
  Daemon 换新时优先接管已有接入，避免主动拆掉仍有效的拦截。手动停止 Daemon 不作为还原
  开关；已有保护可继续驻留，关闭能力开关或切至 None 才明确还原。
- 启动或重载后先等待运行环境就绪，再自动挂载；允许短暂的重新接入过程。
  失败有界重试并给出状态，不阻止正常对话，不自动杀任务，也不自动重启 Cursor。

### 4.2 适配契约

- 将后台工作结果更新、完成通知确认和“启动新一轮模型”分开。
  首选保留原生账务与队列处理，只跳过自动进入模型的步骤。
- Cursor Agents 的 legacy runtime 与普通 IDE 的 Agent Host 分别检测、分别验收。
  不能仅拦截共用提交入口、Stop Hook 或一段提示词来声称完成支持。
- 接入需覆盖窗口内已存在和后来创建的工作区服务实例，不只覆盖前台或已加载聊天。
- 同一进程、窗口和服务代际只挂载一次；重载后替换旧代际，过期回调不能修改新代际。
- 定位依赖经过检查的服务与行为契约，不依赖压缩类名、源码行号或整堆扫描。
  记录 Cursor 版本、构建和适配器版本；契约不匹配时停止该路径的修改并报告不可用。
- 结构检查后，先解除 provider 调试暂停，再创建隔离的原生 store / service 和虚拟 composer
  运行行为预检。预检不接触真实队列、聊天和文件服务，模型调用边界一律拒绝；验证原生同步
  ACK / nack、六种任务结果标识、Await 排除、活跃轮次排队和停止后的结算。存在 paired inbox
  时还检查原生游标排序和缺口保护；3.14 的直接 ACK 契约需明确匹配，不无条件跳过检查。
- 每次窗口代际的激活必须先通过预检。调用次数与等待时间有界，超时 / 还原会取消激活并释放
  隔离资源；晚到的 Promise 不能重新安装 guard。只有预检通过、当前原型未变且 owner / revision /
  lease 一致，才修改真实原型。任何窗口未验证都不能报告全局 active（两个守卫的状态聚合见 §7.5）。

### 4.3 接入资源与恢复

初始候选沿用已验证的 macOS 进程附加方式，具体实现仍需审查：临时连接主进程 Inspector，
建立用户私有的有限控制桥，再关闭仅由 AskHuman 打开的 Inspector。

- 确认进程属于当前用户及目标 Cursor 安装，并核对端点所有者；端口冲突不能误连或操控其它进程。
- 控制桥仅接受固定管理操作，要求随机认证；目录/端点使用用户私有权限，不能暴露任意代码执行入口。
- 不关闭用户已有的调试连接，不遗留公开调试端口，不读取认证 token 或用户消息正文作诊断。
- 重复接入、Daemon 重启及旧端点清理必须校验进程身份与所有权，不能误清其它实例资源。
- 显式关闭开关、None 或卸载时还原自己的拦截、释放资源；还原前确认当前包装仍归自己所有，
  不覆盖后来安装的其它包装。Cursor 已退出时清理对应记录即可。
- 稳态不调用模型，不反复扫描大文件或堆，不做高频忙轮询；重试和诊断日志有界。

## 5. 验收标准

### 5.1 不消耗模型 Token 的自动化验证

| 类别 | 必须覆盖 |
|---|---|
| 配置 | 默认关闭；旧配置兼容；CLI/MCP 切换保持偏好；None 停止；重新集成恢复偏好；保存失败可见 |
| 独立性 | 生命周期和 Stop 开关任意组合不改变本能力；现有单一 Stop handler 与输出协议保持 |
| 队列 | Shell/子代理的 success/error/aborted；批次、重复、在途回收、重试与原生确认台账 |
| Await | 等待期间成功/失败结果正常返回；已消费结果不再唤醒；并发等待与完成不死锁 |
| 会话范围 | 多聊天、多工作区、多窗口、旧待处理通知、新建空白聊天触发重扫仍不续跑 |
| 生命周期 | 两种运行路径的普通启动、窗口新增/重载、Cursor/Daemon 重启与版本换新；幂等挂载和还原 |
| 故障 | 端口占用、身份不匹配、服务暂未就绪、契约漂移、桥接断开；状态准确且正常任务可继续 |
| 卸载 | 关闭开关/None/卸载后无自有包装和临时调试资源；已确认通知不回放；未运行任务不被杀 |
| 回归 | 主动消息、AskHuman 继续、普通工具结果、权限审批及明确不在范围内的其它调度正常 |

### 5.2 真实 Desktop 验收

功能实现后按项目要求运行相关检查和 `./scripts/install.sh`，再使用新安装的 AskHuman 继续确认。
两种运行路径分别建立可追溯记录，不能只凭 UI 停转、最终文本或等待一段时间判为通过：

1. 按普通方式启动 Cursor，在空临时工作区确认模型为 **Grok 4.7**，尽量减少消息和 Token。
2. 让一个真实 Shell 在主轮次结束后完成，证明拦截收到了完成事件、原生状态/输出正确、
   通知已确认且队列清空，并用请求日志证明没有自动模型请求。
3. 至少一条极短的主动消息证明仍可正常继续；不用重复对照组复现已知问题。
4. 真实子代理与 Await 至少各覆盖一条有意义的流程，检查原生等待、完成与确认账务；
   优先共用少量场景，不能用纯模拟替代两条运行路径的真实核心验收。
5. 验证 Stop 和 AskHuman 明确结束后的后台完成不会再请求模型；可以共用测试会话，
   不伪造用户同意结束的标记。补验正常启动、窗口重载与关闭开关后的还原。
6. 检查没有改变全局模型偏好、没有隐藏/归档聊天、原 Cursor 仍正常运行，临时接入资源已清理。

**Cursor CLI 禁止实测。** 不为补齐表格启动 CLI 会话、发送模型请求或擅自升级 CLI。
若未来要支持终端 CLI，需要单独授权和适配规格，本功能不得显示它已受保护。

## 7. 修订（2026-11-07，已实现）：同一开关下增加「运行中会话保护」

本节在**不新增开关**的前提下，为同一个设置项增加第二个守卫。它与 §1–§6 的后台完成守卫互相独立：
各自预检、各自还原、各自报告状态。**评审已通过（见 §7.10），已实现（见 §7.12）。**

它取代了 2026-11-07 当天口头确认过的方案（在实验服务读取配置处关闭 Cursor 的「隐藏会话气泡驱逐」实验）。
调查中发现那个方案对已发生的事故路径无效，原因与替代方案见 §7.1、§7.2；评审时已重新确认（§7.10 D1）。

### 7.1 现象与机制

**现象。** 本机（两个工作区合计）自 2026-10-25 起至少 8 次：Cursor Agents 窗口里一个长时间运行的**首轮**
（8–12 小时，主要在等 AskHuman 回答）因传输重试用尽而最终失败后，该会话从侧栏消失，首条用户消息被删除，
提示词被放进一个新的「New Agent」草稿（10-25 ×2、11-04 ×4、11-07 ×2）。这 8 个会话各持久化了 1142–4587 条气泡，
不是小会话。同期另有 9 个失败过、**没有**被归档的会话，同样巨大（1613–8778 条），它们都有 ≥2 条用户气泡
（失败后被续跑，首条消息还在）。所以「会话大小」不是区分因素。

**机制**（静态阅读 Cursor 3.27.22 Agents 窗口代码；Cursor 官方没有说明过，不是文档化行为）：

1. 首轮提交开始时，Cursor 记下「这是第一条消息」。最终失败时，Agents 窗口的错误回调用
   `getLoadedConversation()` 判断「这条用户消息之后是否已经有 AI 回复」。
2. `getLoadedConversation()` 只返回从会话**末尾向前连续已加载**的气泡，遇到第一个未加载的就停止。
3. 用户气泡不在这段连续尾部、或其后没有 AI 气泡，回调就认为「这次提交什么都没产出」：删除这条用户气泡，
   并因为它是首条消息而执行「中止并还原输入」命令——归档会话，把提示词还原进新草稿。
   判定成立（尾部里有用户气泡且其后有 AI 气泡）时则只显示错误并带「Resume」，会话保持原样。
4. 气泡被卸载（从内存里的 `conversationMap` 删除）有两条路径，**都经过同一个方法
   `ComposerDataService.unloadBubblesByIds`**：
   - **A 滚动卸载**（常驻，没有开关）：会话的转录视图可见时，视口及其前后各 6 行、已挂载的行、贴底时的末尾 8 行、
     生成中与活动工具气泡之外的 **AI / 工具气泡**，在 750 ms 后被卸载。用户气泡不会被它卸载，
     但中间的气泡没了，用户气泡就不再与末尾连续。其参数是写死的常量，不读任何实验配置。
   - **B 隐藏会话驱逐**（实验 `composer_hidden_bubble_eviction`，服务端灰度，本机账号缓存值为开启）：卸载
     **不可见、未选中且不忙**的会话的全部气泡（传入 `conversationMap` 的全部 key）。它**跳过生成中的会话**。

   该方法自己只会跳过 `generatingBubbleIds` 里的气泡（正在写的那一两个），**不保护同一会话里的其它气泡**，
   所以生成中的会话仍会被 A 裁剪；这正是本节守卫要补的地方。
5. 因此，一个很长的首轮只要被看过（A 把中间的气泡卸掉了），之后失败就会被误判；从没被看过的会话保持全部加载，
   失败时判定成立，只显示错误。这与「同样巨大、有的被归档有的没有」相容。

**确定与推断。** 1–4 是对源码的直接阅读，且在下表的 7 个构建里一致。「每次事故具体由 A 还是 B、会话是否被看过」
**没有直接证据**：Cursor 不记录可见性与卸载事件，持久化数据里也没有卸载过的痕迹。第 5 条是与数据相容的推断，不是证明。

### 7.3 目标与非目标

目标：开关开启且守卫生效时，Agents 窗口里**正在生成的会话不再被卸载气泡**，使 §7.1 第 3 步的判断对运行中的回合
得出正确结果。

非目标：

- 不修 Cursor 的错误处理，不拦截删除、归档与还原；
- 不改变非生成中会话的卸载（含 B 的行为，含回合结束后 A、B 的恢复）；
- 不修复守卫生效前就已经出现缺口的在途回合（§7.7 只报告它们）；
- 不读写 Cursor 的状态库或存储，不触碰其实验覆盖接口，不为此改任何实验 / 灰度配置；
- 不阻止失败本身（预防是 S6，另议），也不自动取消归档（S5，另议）。

### 7.4 行为契约

| 输入或动作 | 开关开启且守卫生效时 |
|---|---|
| 卸载请求作用于**生成中**的会话（`status === "generating"`，或 `generatingBubbleIds` 非空，或 Cursor 自带的忙碌判定为真） | 忽略整个请求：不卸载任何气泡，也不做其附带的表头改写；计数 +1 |
| 卸载请求作用于其它会话 | 原样透传：全部实参、返回值、`this` 与异常不变 |
| 守卫自身读状态失败 | 视为非生成中并透传；守卫不得向调用方抛出异常 |
| 回合结束 | 之后的卸载按 Cursor 原样进行；回合期间保留的气泡不主动补卸 |
| 关闭开关或切至 None | 还原原方法；不回放被忽略的请求，已保留的气泡由 Cursor 之后的卸载自行处理 |
| 窗口重载 / Cursor 重启 | 内存状态丢失，按 §4 重新接入；回合期间已经存在的缺口不会因此恢复 |

**范围：仅 Agents 窗口**（`isGlass`）。普通 IDE 窗口的错误回调没有那个破坏性分支，不安装此守卫，
它的状态是「不适用」。

**代价：** 生成中的会话（含当前可见的那个）在回合期间占用更多内存，上界是它自己的全部气泡——与 Cursor 对
「后台生成、从未被看过」的会话本来的处理一致。可见的超大会话在生成期间的界面流畅度**没有实测**
（行的 DOM 虚拟化与气泡数据的卸载是两层，预期只影响内存），落地后要观察（§7.8），异常时关开关即还原。

**状态。** 每个窗口分别报告两个守卫：`completion`（沿用现有字段）与 `retention`（新增：

- 每个窗口的 completion 守卫都已验证，且每个 Agents 窗口的 retention 为 `active`、IDE 窗口为 `notApplicable`
  → `active`（含义与现在一致）；

### 7.6 接入与契约

沿用 §4 的所有权、lease、revision、窗口代际与还原规则；本节只写新增。

- **目标**：Composer 数据服务原型上的 `unloadBubblesByIds`（该服务就是适配器已经拿到的那个对象）。
- **结构检查**（任一不满足：该守卫「不可用」，不修改任何原型，另一个守卫不受影响）：
  - 是函数，且原型上的属性可配置、可写；
  - 源码形态：函数体里第一个对 `getComposerData` 的调用以**第一个形参**为实参，并出现 `generatingBubbleIds` 与
    `conversationMap`。
  - 守卫只依赖「第一个参数是会话句柄」与「Cursor 自己也据此保护生成中的气泡」，**不依赖参数个数**；
    包装一律用不定参数透传（该方法的参数个数 3.9.16 起变过两次）。
- **预检**（隔离，不触碰真实会话与存储）：用包装函数加一个计数用的假原函数，在虚拟服务实例上验证：生成中
  （`status`、仅 `generatingBubbleIds`、Cursor 忙碌判定，三种各一）→ 不调用原函数；其它状态 → 以相同的 `this`
  与全部实参调用一次并返回其返回值；原函数抛出 → 异常原样抛出；读状态抛出 → 透传、不抛出。
- **激活后复核**：原型上的属性就是自己的包装；否则还原并报告「不可用」。
- **依赖面**：1 个方法名 + 2 个数据字段（`status`、`generatingBubbleIds`）。Cursor 自带的忙碌判定
  （`_composerDataIsBusy`，3.22.12 起）存在时与这两个字段取并集，它改名时字段判定仍然有效。
  不需要实验服务，不需要 Inspector 之外的新能力。

### 7.7 观测

每个 Agents 窗口在内存里保留（不落盘、不含会话 ID 与消息内容），经现有状态通道进入 `AskHuman doctor --json`：

- `skipped`（被忽略的卸载请求数）、`skippedBubbles`、`passed`（被透传的请求数）、`lastSkippedAt`；
- 最近 20 次被忽略的请求：时间、气泡数、范围 `all`（请求覆盖该会话当前全部已加载气泡，B 的特征）或
  `partial`（A 的特征）。用来回答「到底是哪条路径在生成期间尝试卸载」。

**可选：在途风险量表（D5）。** 尽力而为地报告「当前生成中的会话里，已加载的连续尾部够不到最后一条用户消息的有几个」
——这些会话若此刻失败就会被误判。它让上面的前提在你的机器上**可以直接观察**，也如实暴露存量限制
（守卫生效前已出现缺口的在途回合不受保护，结束后消失）。每 30 秒至多计算一次、至多 50 个会话；计算失败只显示「未知」，
绝不影响守卫本身。额外依赖：`loadedComposers.byId`、`getHandleIfLoaded`、`getLastHumanBubbleId`、`getLoadedConversation`。

**自动化（不消耗模型）**

**落地后的观察（不是验收门槛）与证伪**

- 观察生成中的可见会话的内存与滚动手感；异常时关开关即还原。
- 下一次自然出现首轮失败时核对：会话是否仍在侧栏、首条消息是否还在、`skipped` 与最近记录在该回合期间是否有内容。

### 7.9 风险与限制（如实）

- **依赖私有方法，没有「数月不失效」的承诺。** 证据是该方法与「第一个参数为句柄」的形态在 7 个构建（06-27 至 10-27，四个多月）里保持，
  而参数个数变过两次、守卫已按此设计。失效时的表现：方法改名或形态改变 → 结构检查失败，守卫「不可用」，设置页显示部分生效
  （安全）；Cursor 改用别的卸载入口 → **静默无效**，只能靠 §7.7 的计数（生成中的会话 `skipped` 长期为 0）和 §7.8 的
  证伪条件发现。
- **不修复缺陷本身。** Cursor 的错误处理在气泡缺口存在时仍会误判；守卫生效前就已有缺口的在途回合不受保护，
  它们结束后风险消失。
- **重试期间的会话状态未实测。** 守卫只在会话「生成中」时生效。传输层重试（日志里 `retries` 通常为 10）期间会话的
  `status` 是否一直保持 `generating`，只是静态阅读的判断；若重试间隙曾短暂离开该状态，A 在这个间隙里仍可卸载。
  §7.7 的计数与 §7.8 的证伪条件会暴露这种情况。
- **内存与界面**：见 §7.4。
- **共用接入通道**：Inspector / `__SSG_COMPOSER_PROVIDER__` 失效会让两个守卫同时不可用。
- **推断不是实锤**：见 §7.1。

## 8. 延长无入站消息的等待与重试窗口

2026-11-07 用户确认 **单次停滞阈值 5 分钟，连续停滞重试窗口 10 分钟**，沿用「Cursor 会话防护（实验）」开关。Cursor 3.27.22 的实现已接入主工作树，日常机安装验收待完成。

1. macOS 的 Agents 和普通 IDE 窗口启用后，新回合单次无入站消息中止阈值从本机原生的 90 秒延长到 300 秒，保留原生的预警设置。开启时若原生未启用停滞检测或已配置更长的单次等待，沿用该配置并报告实际状态。
2. 连续停滞重试窗口从第一次因停滞失败且决定重试时开始计时。以后仅在再次发生停滞失败时检查。原生为 180 秒，配套调整为 600 秒。连续三次完整停滞的场景通常在约 15 分钟加退避时间后停止，仍遵守 Cursor 原有的重试次数、无进展及 Stop 判定。
3. 两项计时作为一个能力验收。仅在窗口和对应 Agent Host 的接入均已验证时启用。关闭或切至 None 后，新回合取原生计时。在途回合使用其启动时取得的计时策略。超时能力不可用时报告部分生效，由其它会话守卫独立决定自身状态。
4. Cursor 3.27.22 两类窗口都从 `nal_stall_detector_timeout_config` 读取预警和单次失败阈值。连续重试窗口在两类窗口代码与 Agent Host 各有一份原生常量。离线提取三份分类函数的夹具已验证 180 秒和 600 秒的边界、传输重试次数上限、运行时挂载及还原。产品接入后仍须验证跨运行路径的策略快照、开关状态及退出隔离。
5. 原生预检使用独立 Cursor 配置与隔离环境，不启动 Agent 任务，不触发计费。验收包括 30 秒预警、跨过 90 秒、300 秒中止、第二次停滞允许重试、600 秒连续停滞边界，以及关闭、窗口重载和不兼容版本时的行为。预检通过后才接入产品开关。

### 8.1 原生预检记录

2026-11-07 至 08 在另一台 macOS 上验证 Cursor 3.27.22。该机的 Agent Host、普通 IDE 和 Agents 的脚本分别与日常机 SHA-256 一致。独立配置没有登录，macOS 外层沙箱拒绝公网和本地代理连接、拒绝读取日常用户目录、只允许写入测试目录。测试使用模拟钥匙串和本地测试开关。全部调用为只读配置与合成错误判定，没有启动 Agent。

- 在普通 IDE 和 Agents 两种真实窗口，确认原生配置 30 秒预警与 90 秒中止。临时覆盖后，预警仍为 30 秒，中止为 300 秒。两种窗口的原生分类函数都通过 180/600 秒边界及传输重试次数上限检查，撤销后回到 90/180 秒。
- `cursor-agent-host` 实际加载在每个窗口的 `agent-exec` 扩展宿主。通过本机已加载模块定位原生分类函数，无需调用扩展激活。该函数通过相同边界与还原检查。

### 8.2 每回合策略

2026-11-08 用户确认在本机窗口与 Agent Host 之间传递每回合标记，以覆盖关闭开关时已经排队的回合。渲染器仅在当前窗口和对应宿主均验证后才扩展新回合的快照。直接在窗口运行的回合使用该快照。发往本机 Agent Host 的消息保留原生超时值，并另带宿主专属的短标记。宿主读到自己的标记后同时启用 300 秒和 600 秒，随后移除标记。宿主更换后，旧标记对应的回合使用成对的原生值。预热模板使用原生值，不带标记。

关闭时停止生成新快照。宿主的轻量解码与重试包装随原进程保留，以便同一进程中已排队的回合仍能解码。无标记的回合直接使用原生行为。Cursor 的 Stop、次数上限和其它错误由原生分类器处理。调试端口仅在安装对应宿主的包装期间临时打开，在报告生效前关闭。设置页分别报告三个能力，`AskHuman doctor` 会列出停滞能力的状态和仍采用的原生超时。

在 `.19` 的两种断网实例，用实际窗口编码器、原生 Agent Host 解码器与产品代码验证了成对接入、关闭后的排队回合、新回合恢复、后续发送、预热模板、原生 300 秒不误判和重复开关。合成失败覆盖原生 180 秒和扩展 600 秒的边界。两轮测试只使用空的合成本机消息、假预热回调和本机调试接口，没有调用 Agent 或模型。日常安装与自然故障验证另记。
