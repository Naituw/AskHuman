## 1. 背景与目标

2026-10-26 用户提出：

> 「我们之前在实现 iOS 渠道的时候，增加了 MQTT 的设施，我在想是不是可以通过这个来实现不同 Mac 设备之间的通信。比如说我公司和我家里分别有一台 Mac，我把它们配置到一个通道之后，我就可以在公司的 Mac 上回答我家里 Agent 的提问。帮我分析一下。」

分析结论：可以，而且不需要新的服务器。iOS 渠道已经有 EMQX、端到端加密、在线状态、断线补发与「多设备首答胜出」，这些对「另一台 Mac」同样成立。真正缺的是四件事：两台 Mac 不在一起时怎么配对、对方的提问怎么进本机作答窗口、这些提问与渠道自动激活是什么关系、多对多分发时怎么控制流量。本文把这四件事定下来。

**一句话**：每台 Mac 的 Daemon 既是「提问方」（现有 Gateway：把本机 Agent 的提问发出去），又是「答题方」（新增：把其他 Mac 的提问放进本机的合并作答窗口，答案送回去）。

**目标**

1. 在任意一台 Mac 上回答其他所有已配对 Mac 上 Agent 的提问（含权限 / Stop 确认），与本机提问**同在一个合并作答窗口**，草稿、附件预览、稍后答、按项目分组都和本机一致。
2. 多台 Mac 全互通（家 / 公司 / …）：任何时候在其中一台上工作，都能收到其他所有 Mac 的提问。
3. 复用 iOS 渠道现有设施：同一个 EMQX 账号、同一套端到端加密；不新增服务器、不用推送中继、不改 iOS App。
4. 两台 Mac 不在一起也能配对（晚上在家操作一下，白天在公司操作一下）；新增一台 Mac 只需要批准一次。
5. 通道流量克制：其他 Mac 先收到摘要，只有在那台 Mac 上点开才拉取正文。

**为什么不直接用 IM**：用户第 1 轮的结论——IM 卡片没有合并作答窗口、草稿与附件预览，体验不够。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 提问方 | Agent 所在的 Mac。它的 Gateway 持有请求的权威状态，Coordinator 裁决首个终态 |
| 答题方 / 答题端 | 回答别的 Mac 的提问的那台 Mac，及其 Daemon 里新增的答题引擎。一台 Mac 同时是提问方和答题方（M3） |
| 对端 | 与本机配对过的另一台 Mac |
| 圈子 | 经引荐互相配对的一组 Mac（全网状：任意两台之间都有独立的一对密钥） |
| 邀请码 | `ahmac1.…`：圈内一台 Mac 生成、给新 Mac 用的一次性凭据；24 小时有效，**不含 broker 密码** |
| 安全码 | 6 位数字，两台 Mac 各自从密钥协商结果算出；一致才说明中间没人替换密钥。沿用 iOS 渠道的校验码（ios D5） |
| 批准卡 | 「批准新 Mac 加入」确认卡：邀请方收到加入请求后生成，可在邀请方本机、其已配对手机、圈内其他 Mac 上点「允许 / 拒绝」 |
| 引荐 | 新 Mac 获批后，批准方代新 Mac 向圈内其他成员转交一次性票据，让新 Mac 与他们各自完成配对 |
| 摘要 | 提问方发给对端的轻量到达通知（不含正文、选项、缩略图、附件） |
| 远端条目 | 答题方作答窗口里来自对端的请求，分「未加载 / 加载中 / 已加载」 |
| 电脑出口 / 远程出口 | 渠道激活里的两类投递面：电脑出口 = 本机弹窗 + 所有在线对端 Mac；远程出口 = IM（只有它还受活跃槽管辖）。手机不属于这两类：它始终投递，只由「推送时机」规则决定要不要提醒（M6、§6.4） |
| 弹窗网 | 本功能的别称：多台 Mac 的作答窗口连成一张网 |

## 3. 已确认决策（用户经 AskHuman 定案）

以下来自 2026-10-26 ~ 27 的第 1–6 轮问答（题目与用户原话见 §17）。

| 编号 | 决策项 | 结论 |
|---|---|---|
| M1 | 形态与动机 | 每台 Mac 的 Daemon 新增「答题端」，对端的提问进入**同一个合并作答窗口**，带 Mac 名称标签、按「Mac + 项目」分组（第 1 轮：IM 卡片没有合并作答窗口 / 草稿 / 附件预览，所以不走 IM） |
| M2 | v1 范围 | 只回答提问（与手机一致：多问题、选项、附件查看、回复附件）+ 权限 / Stop 确认。**不做**远端 Agent 列表、实时观察、插话、新建任务；因此对端不进入 Watch 并集，`autoEndWatch` 不受影响 |
| M3 | 方向 | 双向对称：每台 Mac 既是提问方又是答题方（家里 Mac 也能回答公司 Agent 的提问） |
| M4 | 网络前提 | 用户确认公司网络可连 EMQX（「公司发的提问，我的手机可以收到」）。v1 不再设网络门禁；这是用户口头确认，没有用探针量化，也没有区分 8883 / 8084 / 中继域名 |
| M5 | 到达呈现 | 对端提问到达时与本机提问**完全一致**：到达气泡、提示音、非激活前置。不做「静默入列」，也没有「接管」概念（用户第 2 轮选了「始终同等对待」，没有采用推荐的「静默入列 / 接管」） |
| M6 | 与渠道激活的关系 | 投递面分两类。**电脑出口永远参与**：本机弹窗 + 所有在线、未暂停接收的对端 Mac，与本机弹窗同待遇，**不受 `channels.autoActivation` 与活跃槽管辖**；只有**远程出口**（IM）按活跃槽选择；手机已由并行需求 `ios-alert-timing` 移出活跃槽（§6.4）。联动：在任一台 Mac 上作答视同「人在电脑前」→ 提问方活跃槽 = `popup`（开着自动激活时 IM 静下来）。对端不使用 `slot.take` / `slot.state`，也没有反激活提示。每个对端留「暂停接收」开关（默认开）。批准卡不是 Agent 提问：发给弹窗网里所有 Mac 与所有已配对手机，不看活跃槽、不改活跃槽（用户第 4 轮：「我任意时候在一台 Mac 工作，都应该可以收到其他所有 Mac 的消息」；第 5 轮选「永远参与」） |
| M7 | 配对方式 | **异步邀请 + 手机 / 本机代批**（像 Apple ID 新设备登录批准）：家里 Mac 生成邀请码（24 小时、仅限一次、不含 broker 密码）→ 公司 Mac 粘贴并显示「等待批准」+ 6 位安全码 → 家里 Mac 生成批准卡，同时出现在家里 Mac 本机与已配对手机上（及圈内其他 Mac），谁先点谁生效 → 用户在公司用手机核对安全码后点「允许」→ **一次批准双向生效**。保留「人工核对安全码 + 明确点允许」这道门（ios D5）。两台 Mac 须已用同一个 EMQX 账号（连接串导入）并开启 iOS 渠道 |
| M8 | 圈子引荐进 v1 | 新 Mac 经**一次批准**加入整个圈子，圈内成员自动互相配好（用户第 5 轮选了更难的这一项，没有采用推荐的「两两配对」）。已接受的代价：信任集中到已批准成员（任一成员被攻破，可借引荐给圈子加人），配套「被引荐设备通知 + 一键撤销」 |
| M9 | 密钥结构 | **两两独立密钥（全网状）+ 票据转交式引荐**：新成员 P 获批后，引荐人 M 通知其他成员 X；X 各出一张一次性票据，**经 M 转交给 P**；P 与 X 自己走一遍配对握手（X 因信任 M 自动批准）。M 只转交票据、**不参与密钥协商**，事后被攻破也解不开 P↔X 的流量。一个成员泄露只暴露它自己的通道。不采用圈子共享密钥 |
| M10 | 广播 | MQTT 话题扇出只用于在线状态（`s/+`，保留消息 + 遗嘱）。内容消息是两两密钥，**每个收件人各封一份、各发一次**（现有手机路径同样如此）；**不用群密钥广播** |
| M11 | 摘要先行 | 对 Mac 对端，提问方先发**摘要**，用户在对端「查看」时才拉取正文；附件原文件仍点开才拉；回复附件只发提问方；作答后其余端清理。手机路径不变（仍发完整 `request.new`）。权限 / Stop 确认必须先拉过完整内容才能决定（用户第 5 轮提出，第 6 轮选定） |
| M12 | 流程 | 设计无异议后先写需求与计划供评审；**评审通过前不写代码**（第 6 轮）。评审已于 2026-10-27 通过（第 7 轮），开工条件见 §17 |
| M13 | Daemon 常驻 | 存在已配对对端且 iOS 渠道启用时，Daemon **不因空闲而退出**（视同常驻，不改写 `general.daemonLifecycle` 的设置值；沿用 Cursor Desktop 集成「独立保活」的先例）。理由：Mac 无推送唤醒，Daemon 退出 = 对其他 Mac 离线（第 7 轮 Q1，首次未答，单独再问后选 (b)） |
| M14 | 撤销通知 | 圈内某台 Mac 撤销一台设备后，向其他成员发通知并**自动生效**（各端删除对应记录；第 7 轮 Q2） |
| M15 | 新 Mac 已有圈子 | v1 **不合并**：新 Mac 只加入批准方的圈子，要合并就再配对（第 7 轮 Q3） |
| M16 | 在对端工作与手机推送 | v1 **不做**「在对端 Mac 上工作 → 提问方不向手机推送」，记为已知限制（§6.4 第 3 点、§15），归入后置的「在席过滤」（§12）（第 7 轮 Q4） |

## 4. 总体架构

```
┌──────────── Mac A（家）───────────┐            ┌─────────── Mac B（公司）──────────┐
│ Agent → CLI → Daemon              │            │ Agent → CLI → Daemon              │
│   ├ 本机弹窗 / IM / 手机           │            │   ├ 本机弹窗 / IM / 手机           │
│   ├ Gateway（提问方）──────────────┼─ MQTT ─┐ ┌─┼─ 答题端（答题方）                 │
│   └ 答题端（答题方）───────────────┼─ MQTT ─┼─┼─┼─ Gateway（提问方）               │
└───────────────────────────────────┘        │ │ └───────────────────────────────────┘
                                  EMQX Serverless（同一账号；端到端加密；两两独立密钥）
```

- **同一个 EMQX、同一份 broker 凭据**：所有 Mac 与手机共用（ios D3），设备之间靠端到端加密隔离。
- **每对 Mac 之间有两条互相独立的「提问方 → 答题方」通道**：A 提问 B 答、B 提问 A 答，各有一对方向密钥；一次批准同时建好（共 4 把方向密钥 + 1 把校验码密钥）。
- **消息路径等同手机路径**：`request.new` / `request.get` / `request.full` / `answer.submit` / `confirm.decide` / `asset.*` / `upload.*` / `request.resolved`。对端在提问方 Gateway 里只是一种新的设备类型（「手机」「Mac」两类），提问方的 Coordinator、首答胜出、幂等日志都不变。
- **权威状态仍在提问方**：答案是否被采纳以提问方 Coordinator 的 `try_submit` 为准；答题方只是遥控与展示端。
- **答题端不转发**：对端的提问只进本机作答窗口，不会再发给本机的 IM / 手机，也不会发给第三台 Mac，所以不会成环。
- **并入现有 iOS 渠道**：同一份 broker 配置、同一张设置卡片；但投递面独立，不占用活跃槽里的渠道 id（见 §6）。

## 5. 配对与圈子

### 5.1 前提：两台 Mac 用同一个 EMQX 账号

沿用 iOS 渠道现有流程：在一台 Mac 上「复制连接串」，在另一台上「导入连接串」（连接串含 broker 密码，由用户自己搬运），并在两台上都开启 iOS 渠道。**邀请码里不含 broker 密码**——手机没有 broker 配置所以二维码要带，Mac 已经有导入连接串的办法，邀请码只负责「谁邀请的你」，不负责给你凭据，被截获的损失更小。

### 5.2 异步邀请与代批（M7）

两台 Mac 不会同时在场，所以整个过程允许任何一方在任何一步离线，最终一致。

1. **家里 Mac（H）**：设置 → 实验 → iOS 渠道 → 设备 →「添加 Mac」→「邀请另一台 Mac」，得到邀请码：24 小时内有效、仅限一次、不含 broker 密码，带一个 broker 指纹（让加入方在本地先核对「是不是同一个 EMQX 账号」）。邀请的临时私钥与票据秘密落盘，Daemon 重启不丢。
2. **公司 Mac（O）**：设置 → 添加 Mac →「加入」，粘贴邀请码。O 本地校验（版本、未过期、broker 指纹与本机一致）后把加入请求发给 H，然后显示「等待『家里 Mac』批准」和一个 6 位**安全码**。
3. **H 收到请求**（H 当时不在线也不丢：请求保留在 broker 上，H 上线后处理；H 离线时 O 显示「家里 Mac 目前离线，上线后会收到你的请求」）→ 生成**批准卡**。卡片文案要点：新 Mac 的名称、同一个 6 位安全码、「允许后它可以回答你所有 Mac 上 Agent 的提问，包括批准权限请求」。批准卡**同时**出现在 H 的本机作答窗口、H 已配对的所有手机、以及圈内已配对的对端 Mac 上，谁先点谁生效，其余处自动消失。没配手机时卡片只在 H 本机等（24 小时内，过期自动作废）。
4. **用户核对**：在公司拿手机（或任一台已配对设备）看批准卡上的安全码，与 O 屏幕上的对一下，一致点「允许」；不一致或不认识点「拒绝」。
5. **批准后**：H↔O 两个方向的通道一次建好；O 显示「已加入」；如果 H 的圈子里还有别的 Mac，自动走 §5.3 的引荐，不再需要任何人点「允许」。O 批准时若离线，结果保留在 broker，O 下次上线自动完成。

手机上的批准卡就是一张普通的权限确认卡（`ConfirmView`：标题、几行上下文、「允许 / 拒绝」两个选项），**预期不需要改 iOS App**（计划 P0 验证）。

### 5.3 一次批准加入整个圈子（M8、M9）

用户视角：新 Mac P 经 M 批准后，圈里其他 Mac X 上会各出现一条通知「M 引荐了新 Mac P」（带「撤销」按钮）；P 与每台 X 之间自动完成配对，不需要再有人点「允许」。

```
P（新）                 M（批准方）                X（圈内其他）
 │── peer.request（M 的邀请码）─▶│
 │◀──────── 批准 ───────────────│
 │                               │── circle.intro（P 是谁）──▶│
 │                               │◀─ circle.ticket（X 的一次性票据）─│
 │◀─ circle.relay（X 的票据）────│
 │── peer.request（X 的票据）────────────────────────────────▶│  X 自动批准
 │◀──────────────────────── peer.accept ─────────────────────│
 P↔X 各自用临时密钥协商并派生密钥；M 看得到票据，但没有任何一方的临时私钥，解不开 P↔X 的流量
```

- **离线**：引荐是「至少一次」的持久化消息；X 离线时 M 排队，X 上线后补发；P 离线同理。全过程最终一致，不要求三方同时在线。引荐票据的有效期比邀请码长（7 天），因为 X 可能几天后才上线。
- **撤销**：任何成员撤销某台 Mac，都会向圈内其他成员发撤销通知，各端删除对应记录；离线成员下次上线补收，撤销方排队；收到撤销通知的成员**自动删除**对应记录并提示用户（M14）。被撤销的 Mac 在各端的通道一并失效。
- **为什么不用圈子共享密钥**：一个成员泄露则圈内全部流量暴露、成员之间可互相冒充；撤销需要全圈换钥；链状配对一旦中间断了会整体失效。两两独立密钥的代价只是每对多一次握手，由引荐自动完成。
- **只加入批准方的圈子**：新 Mac 自己如果已经有别的对端，不自动合并两个圈子（M15）。

### 5.4 解除、撤销与恢复

- 任一方可随时解除某个对端：两个方向的通道一起删除（本机记录、密钥、待发消息、该对端的所有远端条目）；对方收到 `unpaired` 后同样清理（离线则下次上线）。
- 解除后若要恢复，重新走邀请流程。
- 邀请码可在生成方随时取消；已被使用或过期的邀请码不能再用。
- 重装 / 换机：新 Mac 标识不同，等同新增一台；旧记录用撤销清理。

### 5.5 异常与边界

| 情形 | 表现 |
|---|---|
| 邀请码过期 / 已被用 / 已取消 | O 显示「邀请码已失效，请在家里 Mac 重新生成」 |
| O 与 H 不是同一个 EMQX 账号 | O 本地比对 broker 指纹，直接提示「两台 Mac 需要使用同一个 EMQX 账号，请先导入连接串」，不发请求 |
| H 离线 | O 显示「家里 Mac 目前离线，上线后会收到你的请求」；邀请有效期内都能完成 |
| 有人抢先用了同一个邀请码 | H 的批准卡上的安全码与 O 屏幕上的不一致 → 用户拒绝；H 发现同一邀请码收到不同的请求时，标注「同一邀请码收到多个请求，可能被他人使用」，并让该邀请码作废 |
| 同名 Mac | 列表里附加短标识；可本地重命名 |
| 圈子已满（超过 8 台） | 拒绝并提示 |
| 引荐时 X 或 P 的 Daemon 重启 | 邀请 / 票据 / 待发队列落盘，重启后继续 |

## 6. 渠道语义（提问方）

### 6.1 两类出口（M6）

| | 电脑出口 | 远程出口 |
|---|---|---|
| 成员 | 本机弹窗；所有在线、已握手、未暂停接收的对端 Mac | 飞书 / 钉钉 / Telegram / Slack（手机不在此列，见 §6.4） |
| 参与规则 | **永远参与**（自动激活开 / 关都一样），与本机弹窗同待遇 | 沿用现有：自动激活关 → 都参与；开 → 仅「活跃槽 ∪ Watch」 |
| 作答的效果 | 视同「人在电脑前」：开着自动激活时，活跃槽 = `popup`（IM 静下来） | 沿用现有：赢家渠道成为活跃槽 |
| 兜底 | 存在在线对端就算「有电脑出口」：本机无弹窗时**不**触发「全发 IM」兜底 | 沿用现有：Popup 不可用且候选为空才全发 |

### 6.2 投递与抢答规则

1. **在线判定**：对端在线状态为在线、已完成 hello、且没有暂停接收。离线 / 暂停的对端不投递：请求留在待答表，对端上线并 hello 时由快照补齐（已看过的不重复提醒）。
2. **首答胜出**：本机弹窗、IM、手机、各对端任一端先答，其余端收到「已在别处回答」（对端：摘要或已加载内容自动消失，已打开的窗口显示与本机被抢答相同的结束态）。
3. **来源名称**：对端作答的来源 = 对端的 Mac 名称，进回复历史与回执文案（「由『公司 Mac』回答」）。
4. **批准卡**不是 Agent 提问：发给弹窗网里所有 Mac 与所有已配对手机，不看活跃槽，也不改活跃槽；对手机的推送不等 Mac 空闲（§6.4）。
5. **对端只能回答提问**：提问方 Gateway 对「Mac」类设备按白名单放行消息类型（hello、在线状态、取正文、已收到 / 已看过、提交答案、提交确认、取附件、上传回复附件、解除配对），其余（Agent 列表、Follow、Watch、插话、新任务、`slot.take` 等）一律拒绝。对端也不进入 Watch 并集。
6. **Broker 不可达 / 无设备**：沿用 ios §7.5——投递时 5 秒内仍未连上 broker 则按「投递面丢失」处理；没有任何在线对端不算丢失（请求照常留在待答表）。

### 6.3 与现有激活机制的联动

- 自动激活**关**（默认）：每个提问发所有已启用的 IM + 手机 + 本机弹窗 + 所有在线对端，行为就是现状加上对端。
- 自动激活**开**：本机弹窗、手机与在线对端始终参与；IM 只发给「活跃槽 ∪ Watch」。在任一台 Mac（本机或对端）上作答后，活跃槽落到 `popup`，之前的 IM 被切走（沿用现有的切槽流程：持久化、给旧 IM 的反激活文字、`autoEndWatch`、补推在途请求）。
- 对端**不是**活跃槽里的一个值：不存在「槽在家里 Mac」这种状态，所以也没有「接管」。这样多台 Mac 全互通时槽不会互相抢占。

### 6.4 与 iOS「推送时机」的衔接（`ios-alert-timing`）

并行需求 `docs/specs/ios-alert-timing.md`（2026-10-26 已批准、实现中）改了手机这一侧的规则，本文以它落地后的语义为准：

- 手机**不再受活跃槽管辖**：每道待答题（含确认）无条件进已配对手机的待答列表；`channels.autoActivation` 只管 IM。
- 手机推送只在**提问方 Mac** 空闲 ≥ D（默认 15 分钟，`channels.ios.alertAfterSecs`）、手机不活跃、且这道题没被打开过时才发；每部手机每道题最多一次，不再提醒。
- 它是本需求的前置：两者改的是同一批代码（活跃槽候选筛选、`Host` trait、Gateway 的 `deliver()`），本需求在它合并之后开工。

对本需求的影响：

1. 「在任一台 Mac 上作答 → 活跃槽 = `popup`」现在只让 IM 静下来；手机的安静来自「这道题已被答，不再待通知」。
2. **对端点开某题 = 手机上的「已打开」**（§13 第 17 条）：提问方收到对端对这道题的 `request.get` 后记为已看过，手机不再因它推送。只收到摘要、没点开的不算。
3. **已知限制**：提问方的「空闲」只看提问方自己的键鼠。你在公司 Mac 上工作时，家里那台通常是空闲的——家里 Agent 的提问会在公司 Mac 上弹出，手机也照常收到推送；你在公司 Mac 上答完后，手机上已送达的通知会被「已在 X 回答」的替换推送改写（沿用现有行为）。要让「在任一台 Mac 前工作」都算「人在电脑前」，需要对端上报「正在使用」，即「在席过滤」，v1 不做（M16）。
4. **批准卡对手机立即推送**，不等 D（§13 第 18 条）：发起加入的人正在等，而批准方（家里 Mac）的空闲读数并不反映你在哪。

## 7. 摘要先行与广播（M10、M11）

### 7.1 有没有广播

MQTT 本身有话题扇出，但我们只在「在线状态」上用它：所有设备订阅 `s/+`（保留消息 + 遗嘱）。内容消息是**每个收件人一份**：每对设备各有独立密钥，所以提问方给 3 台对端各封一份、各发一次（手机路径今天同样如此）。不采用群密钥广播：它省的流量不到每月 6 MB（见 7.3），却要承担群密钥分发、轮换与泄露面扩大的代价。

### 7.2 摘要先行流程

1. 提问方对**每台对端**发 `request.new{full:false}`，视图比现有 `light_view` 再轻一档，是**摘要**：Agent、项目、类型（提问 / 权限 / Stop）、问题数、附件数、首行预览（≤120 字）、内容大小；**不含**正文、选项、缩略图与附件。每个对端可设「摘要里不带预览」（默认带；预览首行在端到端加密里，broker 看不到）。手机路径不变。
2. 对端收到摘要：到达提醒与本机提问相同（气泡 / 提示音，文字取摘要）；作答窗口主窗格先显示**摘要卡**。
3. 用户在对端「查看」（Sidebar 点选，或主窗格点「查看并回答」）才发 `request.get`；提问方回 `request.full`（正文 + 选项 + 缩略图，**只发给这一台**）。设置里「收到摘要后自动加载」默认关；打开后收到摘要即自动加载。
4. 附件原文件仍然点开才拉（`asset.get`）；回复附件走 `upload.*`，只发给提问方。
5. 一端作答后，提问方向其余所有端发 `request.resolved`；各端丢弃摘要，清理已拉取的内容与临时文件。
6. **权限 / Stop 确认必须先拉过完整内容才能决定**：提问方拒绝没拉过完整内容就提交的 `confirm.decide`（答题端界面也不允许在未加载时决定）。
7. **拉取失败**（提问方睡眠 / 离线）：保留摘要，显示「家里 Mac 离线，稍后重试」；若已被别处作答则收到 `request.resolved`，条目自动消失。
8. 远端条目有三种加载状态（未加载 / 加载中 / 已加载）加一个失败态；顺带收益：没点开的对端根本收不到正文。

### 7.3 流量估算

假设：每天 100 个提问、平均完整请求 20 KB、3 台对端、三分之一在对端被查看；EMQX 按「发布 + 投递各算一次」；免费额度每月 100 万连接分钟 + 1 GB 流量（入站 + 出站）。

| 方案 | 每天 | 每月 |
|---|---|---|
| 完整内容发给每台对端 | ≈12 MB | ≈360 MB |
| **摘要先行（本方案）** | ≈0.6 MB 摘要 + ≈1.3 MB 被点开的内容 | **≈60 MB** |
| 摘要先行 + 群密钥广播 | 摘要再省 ≈0.2 MB | 再省不到 6 MB |

连接分钟：每台常驻 Mac ≈4.3 万 / 月；3 台 Mac + 1 部每天前台 1 小时的手机 ≈13 万；8 台 ≈35 万，都在额度内。

## 8. 答题端：本机作答窗口里的远端提问

### 8.1 呈现

- **同一个合并作答窗口**：远端条目与本机条目并列；Sidebar 按「Mac + 项目」分组，行内带 Mac 名称标签（沿用手机端 Mac 标签的视觉语言）；未查看蓝点、稍后答、草稿、小窗「待答 N」与本机条目一致。
- **到达提醒**与本机相同（M5）；Mac 休眠后醒来的批量补发只提醒一次（「N 个来自『家里 Mac』的提问」），不逐条弹气泡。
- **主窗格**：未加载 → 摘要卡（Mac 标签 · 项目 · Agent · 时间 · 预览 · 「3 个问题 · 2 个附件 · 18 KB」·「查看并回答」）；加载中 → 进度；已加载 → 与本机提问同一套表单（多问题、选项、推荐、草稿、附件预览），顶部一行「来自『家里 Mac』· Agent · 项目」。
- **权限 / Stop 确认卡**顶部突出「此操作将在『家里 Mac』上执行」，避免把远端的权限请求当成本机的。确认卡用手机路径同款的简化视图（只下发推荐变体，带按选项显示的输入框，如拒绝理由），不含本机独有的编辑能力。
- **隐藏本机独有的入口**：聚焦终端、打开项目目录、Git 信息、「在访达中显示」等（远端路径在本机不存在）。远端附件只读预览，不自动打开。

### 8.2 作答

- **提交**：答案经加密发给提问方（`answer.submit` / `confirm.decide`），提问方 Coordinator 采纳后回执；采纳前条目显示「发送中」。终态由提问方裁决：回执 `accepted` → 条目关闭；`lost` → 「已在别处回答」；`expired` → 「已过期」。
- **回复附件**：压缩与限额沿用手机路径（图片长边 ≤ 2048 px 的 JPEG、单文件 ≤ 10 MB、每题 ≤ 5 个），分块上传到提问方。
- **失败**：提交时对端离线 → 拒绝提交、保留草稿并提示「家里 Mac 离线」；提交后 30 秒无回执 → 显示失败、可重试，重试沿用同一个客户端消息标识（提问方持久化去重），不会重复提交。
- **草稿**：沿用本机草稿机制，按请求保存，请求结束后清理。

### 8.3 与本机子系统的边界

| 子系统 | 远端条目的行为 |
|---|---|
| 回复历史 | 答题端不记录，由提问方记录（来源写答题端 Mac 名称） |
| whats-next 待办与出队 | 不适用：待办在提问方；选项里的待办随请求下发，出队由提问方在采纳答案时做 |
| 重复提问收敛 | 只在提问方做（会话键是本机概念） |
| 项目卡 Git 信息、聚焦终端、打开项目目录 | 不显示（路径在本机不存在）；项目键带 Mac 命名空间，避免两台 Mac 上同路径的仓库混为一组 |
| Agent 注册表、等待徽标、「工作中兜底」 | 不进答题端（Agent 不在这台 Mac 上） |
| `ask-received` 等本机 hook | 不在答题端触发（属于提问发生的那台 Mac） |
| 闲退守卫 | 有远端条目时 Daemon 不闲退；存在已配对对端且 iOS 渠道启用时也不闲退（M13） |
| 托盘「待答」 | 列出远端条目（带 Mac 名），点击定位 |
| IM / 手机 | 不转发 |

### 8.4 离线、睡眠与重连

- **Mac 没有推送唤醒**：休眠 = 离线。提问方对离线对端不投递，提问留在待答表；对端醒来（在线状态变为在线、完成 hello）后收到快照，补齐尚未结束的提问；睡眠期间已被别处作答的不会补出来。
- **答题端 Daemon 重启**：待发的答案落盘重发（同一标识，幂等）；已提醒过的摘要不重复提醒。
- **提问方 Daemon 重启 / 换新**：对端看到其在线状态变化后重新 hello；未结束的提问在提问方请求重建后重新出现（沿用 iOS 渠道的 epoch / rev 对齐机制）。
- **对端 `daemon stop`**：其远端条目随之取消（不算作答），提问方的请求仍在，等对端回来补齐。

## 10. 协议与安全概述

> 逐字段协议、密钥派生、消息目录与幂等规则见 `docs/plans/mac-mesh.md` §3。

- **信任等级**：对端 Mac = 手机：能回答提问，**也能批准权限 / Stop 确认**——也就是能决定另一台 Mac 上的 Agent 能否执行命令。配对门、引荐与撤销都按这个等级设计。
- **加密**：每对 Mac 一次批准派生 4 把方向密钥（A→B 与 B→A 两条「提问方 → 答题方」通道各一对）+ 1 把校验码密钥；X25519 + HKDF-SHA256 + ChaCha20-Poly1305，沿用 ios §8；邀请与引荐票据就是一次性票据（用票据密钥封装配对请求）。
- **不同角色的密钥互相独立**：`A→B` 通道的密钥与 `B→A` 通道的密钥不同，一把泄露不影响另一条。
- **异步配对靠「保留消息」**：加入请求与批准结果以 MQTT 保留消息放在配对话题上，对方上线订阅即可收到；用完立即清除。邀请 / 引荐里的时间戳窗口按票据有效期放宽（仍有下限与上限），不放宽正常通道的 15 分钟防重放窗口。
- **防护**：对端消息类型白名单（§6.2）；邀请 24 小时、一次性、无 broker 密码；同一邀请码收到多个请求即作废；每个对端待答条目上限 20（超出丢弃新到的摘要并在设置页提示）；远端 Markdown 沿用本机渲染的清洗，远端附件只读预览。
- **可见元数据**：broker 可见话题（含随机标识）、消息大小与时间、各 Mac 是否在线；看不到 Mac 名称、问题、答案、项目、附件。
- **兼容**：线协议号 `PROTO` 保持 1，只新增可选字段与 Mac 专用消息类型，iOS App 无需修改；Daemon ↔ 弹窗的 IPC 预计需要 +1（计划 P0 评估，尽量用加字段规避）。

## 11. 性能、流量与成本

- **延迟口径**（沿用 ios D10 的方法，拆段记录，不混成一个数字）：①提问方发出 → 对端摘要出现；②点「查看」→ 正文可作答；③作答提交 → 提问方持久化回执。两台未校时的 Mac 单向耗时不当精确值，用往返估算并同时报告原始数据。
- **流量**：见 §7.3，典型场景每月约 60 MB（对比不用摘要 ≈360 MB）。本机流量统计沿用 iOS 渠道，按「发布 + 投递各计一次」折算 EMQX 额度占比，对端流量计入。
- **EMQX 免费额度**：消费上限保持 0（额度用尽即停，不自动付费）；不创建管理 API Key。
- **无新增费用**：不新增服务器与中继调用。

4. **首答胜出**沿用 Coordinator 语义；作答来源写对端 Mac 名称。
5. **合并窗口按「Mac + 项目」分组**；Mac 标签沿用手机端 Mac 标签的视觉语言。
6. **远端作答不写入答题端的本机历史**，由提问方记录。
7. **唤醒补发批量只提醒一次**。
8. **确认卡用简化视图**：远端权限 / Stop 确认只显示手机路径同款的视图（只下发推荐变体，带按选项显示的输入框），不含本机独有的编辑能力；顶部强调「此操作将在 X 上执行」。
9. **摘要默认带首行预览**（≤120 字），可按对端关闭；预览在端到端加密之内。
10. **撤销通知自动生效**：已由你在评审时确认（M14）。
11. **对端名称**：默认用对方 Mac 名称，可本地重命名；重名时附加短标识。
12. **存储兼容**：设备记录新增 `kind`（`phone` / `mac`），旧记录默认 `phone`，不迁移；降级到旧版本时，Mac 记录会被当成没有推送句柄的手机显示，无害。
13. **提交与发布**：沿用 iOS 渠道——所有提交带 `Release-Note: skip`，直到你决定对外发布。
14. **测试方式**：用两个 Dev Instance（各自 `ASKHUMAN_HOME`、各自 Mac 标识）在同一台机器上模拟「家」与「公司」，最后由你在两台真实 Mac 上验收；真实 Agent 的启动 / 发 prompt 测试必须先经你批准。
15. **公司设备政策**风险由你把握：全程端到端加密，broker 只见密文与在线状态，可随时撤销或关闭渠道。
16. **以 `ios-alert-timing` 落地后的语义为准**（§6.4）：手机不受活跃槽管辖、推送由提问方 Mac 空闲时长决定；该需求先合并，本需求在它之上做。M6 对 Mac 的决定不受影响。
17. **对端点开 = 已看过**：提问方收到对端对某题的 `request.get` 后，视同手机「已打开」，手机不再因它被推送；只收到摘要的不算。
18. **批准卡对手机立即推送**，不等「Mac 空闲 D」；需要 `ios-alert-timing` 的推送路径支持按请求覆盖（计划 P0.9 确认）。

## 14. 评审问题与结论（2026-10-27 已答复）

评审时的问题（每条列了推荐项）与你的结论，均选了推荐项；结论已写入 §3 的 M13–M16。Q1 第一次没收到回答，单独再问后选了 (b)。

1. **Daemon 常驻**：答题端要求 Daemon 在线（Mac 无推送唤醒，休眠 = 离线）。
   - (a) 只在设置页提示，与 iOS 渠道一致；
   - (b) **推荐**：存在已配对对端且 iOS 渠道启用时，Daemon 不闲退（视同常驻，不改写你的设置值）。理由：「任何时候在一台 Mac 工作都能收到其他所有 Mac 的消息」依赖答题端 Daemon 在线，闲退后这台 Mac 对其他 Mac 就是离线；代价是空闲时 Daemon 常驻，仅保持一条 MQTT 连接。
   - **结论：(b)**（M13）。
2. **撤销通知**：某台 Mac 撤销圈内一台设备后——
   - (a) **推荐**：向圈内其他成员发通知并**自动生效**（圈子本就是互信集合；单点被攻破的代价已写进 §15）；
   - (b) 仅提示，各端自己确认后才删。
   - **结论：(a)**（M14）。
3. **新 Mac 自己已有圈子**：
   - (a) **推荐**：v1 只让新 Mac 加入批准方的圈子，不合并两个圈子（要合并就再配对）；
   - (b) 双向合并（批准一次，两个圈子的所有 Mac 互相配好；信任面与实现 / 评审成本都更大）。
   - **结论：(a)**（M15）。
4. **你在对端 Mac 上工作时，要不要让提问方不向你的手机推送？**（与 `ios-alert-timing` 的衔接，§6.4 第 3 点）
   - (a) **推荐**：v1 不做，记为已知限制（§15）。理由：手机多推一次只是打扰，题不会丢；做它要让每台 Mac 上报「正在使用」（在线状态加可选字段）并改 `ios-alert-timing` 的推送判断，是一块独立的范围，可并入后置的「在席过滤」（§12）。
   - (b) v1 就做：对端在线状态里带「空闲时长」，提问方只要有任一在线对端「正在使用」就不推手机——在任一台 Mac 前工作都算人在电脑前，与「多台 Mac 全互通」一致；代价：多一个状态字段与一处推送判断，计划要多一个阶段，且要先改 `ios-alert-timing` 的实现。
   - **结论：(a)**（M16）。
5. **P4（第一个用户可见版本）之后是否设用户 gate**：先给你两个 Dev Instance 的演示截图 / 录屏，看过最大的 UI 变更再继续做 P5–P7。
   - **结论：要**（计划 P4）。

## 15. 风险与已知限制

| 风险 | 处理 |
|---|---|
| 信任集中：任一已批准成员被攻破 → 可借引荐给圈子加人，也能批准权限请求 | 被引荐设备通知（含「撤销」）、圈内撤销通知、邀请 / 票据短时效且一次性、批准卡写明来源；撤销后密钥即失效（M8 已接受） |
| 对端与手机同等权限：能批准另一台 Mac 上的权限请求 | 配对门（安全码 + 明确点允许）；确认卡写明「此操作将在 X 上执行」；对端白名单；用户可随时「暂停接收」或撤销 |
| **不在场的 Mac 醒着也会弹窗 / 响铃**（M5 + M6 的已知代价） | v1 靠「暂停接收」手动兜住；「在席过滤」留作后续（§12） |
| 睡眠 = 离线，且无推送唤醒 | Daemon 常驻（M13）；离线对端不投递，醒来补发；设置页显示对端状态 |
| 公司设备政策（公司电脑向外部 broker 发加密流量） | 用户把握；全程端到端加密；可撤销 / 关闭渠道 |
| 公司网络端口 | 用户口头确认可用（M4），没有量化；若某个网络封 8883，Gateway 沿用自动退到 WSS 8084 |
| 邀请码泄露 | 24 小时 + 一次性 + 无 broker 密码；仍需邀请方点「允许」并核对安全码；同一邀请码收到多个请求即作废 |
| 保留消息在 EMQX Serverless 上的行为（补收、清除、容量） | 计划 P0 在真实 EMQX 上实测（用户在自己的终端运行探针）；不可用则停下问用户 |
| EMQX 额度 | 摘要先行后约 60 MB / 月；N 台常驻 Mac 约 N × 4.3 万连接分钟 / 月；沿用本地流量统计与预警 |
| 并发过多的远端提问刷屏 / 恶意对端 | 每对端待答上限 20；唤醒补发批量提醒；对端白名单 |
| 远端内容渲染安全（Markdown / 附件） | 沿用本机渲染的清洗；远端附件只读预览、不自动打开；远端路径不可用于「打开 / 在访达显示」 |
| 两台 Mac 复制同一份 `~/.askhuman` 导致标识冲突 | 沿用 iOS 渠道的提示与冲突检测 |
| 时钟偏差 > 15 分钟 | 沿用防重放窗口与提示；邀请 / 引荐的保留消息用「创建时刻 − 15 分钟 ~ 现在 + 15 分钟」窗口 |
| IPC 协议号变化 | 计划 P0 评估，尽量用可选字段；确需新增变体时 +1 并按 overview「IPC 协议号」同步文档 |
| 与并行需求 `ios-alert-timing` 改同一批代码（候选筛选、`Host` trait、`deliver()`）、语义上也依赖它 | 它先合并；开工前核对合并后的接口（计划 P0.9）；本需求不重复实现它的任何规则 |
| 你在对端 Mac 上工作时，手机仍会被推送（§6.4 第 3 点） | v1 已知限制；对端点开 / 作答后沿用「已看过 / 已答」规则；「在席过滤」后置（M16） |

## 16. 验收标准

1. **配对**：两台 Mac（家 / 公司，不同时在场）用邀请码完成配对：24 小时 / 一次性生效；安全码不一致可识别并拒绝；H 离线、O 离线、批准时对方不在线都能最终完成；批准卡同时出现在 H 本机与 H 的手机，任一处点击生效、另一处自动消失；Daemon 重启后邀请与待批准不丢。
2. **圈子**：三台 Mac 的圈子——第三台经一次批准加入后，与圈内所有 Mac 自动互配（含离线成员上线后补齐）；被引荐设备通知与一键撤销可用；撤销后各端通道失效、旧密钥不再被接受；测试证明引荐人解不开 P↔X 的流量。
3. **提问**：任一台 Mac 的提问（单题 / 多题 / 推荐 / `selectOnly` / `single` / 附件 / whats-next 待办）出现在其他所有在线 Mac 的合并作答窗口（Mac 标签、按「Mac + 项目」分组、到达提醒与本机一致）；对端作答后 Agent 的 CLI 输出与本机作答一致。
4. **摘要先行**：未查看的对端只收到摘要（不含正文、选项、缩略图）；点「查看」才拉取；自动加载开关生效；附件点开才拉；作答后所有端清理；权限 / Stop 确认未拉取完整内容时被提问方拒绝。
5. **抢答**：本机弹窗、IM、手机、各对端同时作答，首个终态获胜，其余端收到「已在别处回答」；回复附件上传到提问方并出现在 CLI 输出里。
6. **激活**：自动激活开 / 关两种配置下，对端始终收到提问；在对端作答后活跃槽 = `popup`，IM 静下来（手机不看活跃槽，按 `ios-alert-timing`：已被答的题不再推；对端点开视同已看过；批准卡对手机立即推）；本机无弹窗但有在线对端时不触发「全发 IM」兜底；暂停接收后不再投递、恢复后补齐；批准卡不看活跃槽也不改活跃槽。
7. **离线与恢复**：对端睡眠 / 断网 / Daemon 重启、提问方重启、回执丢失、broker 断开，都不重复提交、不静默丢失；提交时对端离线保留草稿；唤醒补发只提醒一次。
8. **隔离**：远端条目不写答题端本机历史、不触发本机待办出队、不显示本机 Git / 终端入口；答题端不转发（不成环）；对端无法使用 Agent 列表 / 插话 / 新任务 / `slot.take`（测试证明被拒）。
9. **流量与成本**：典型场景落在 §7.3 的预算内；EMQX 上限保持 0；全程不创建管理 API Key；日志 / 命令输出 / 文档 / 提交里不出现 broker 密码、邀请码、票据秘密与方向密钥。
10. **测试与交付**：自动测试（Rust、前端）与端到端（两台一次性 Mac + 本地 broker）通过；每阶段交付前跑 `./scripts/install.sh` 并用新装 `AskHuman` 验证；最后由用户在家 / 公司两台真实 Mac 上验收。

## 17. 反馈意见

### 2026-10-26 ~ 27 设计问答（第 1–6 轮，经 AskHuman）

- **第 1 轮（需求分析后）**：动机选「IM 卡片体验不够：没有合并作答窗口 / 草稿 / 附件预览」；形态选「有 / 会装，希望远端提问和本机提问在同一个作答窗口」（→ M1）；范围选「只回答提问 + 权限 / Stop 确认（风险最小，最快验证价值）」（→ M2）；方向选「双向对称：家里 Mac 也能答公司 Agent 的提问」（→ M3）；补充：「公司网络早就验证过了，公司发的提问，我的手机可以收到。」（→ M4）
- **第 2 轮**：到达呈现选「始终同等对待：和本机提问一样弹出（到达气泡、提示音、非激活前置）」，没有采用推荐的「静默入列 / 接管」（→ M5）；补充：「我觉得需要设计一种，针对这种 Mac 不在一起的情况的配对方式。因为 Mac 不像手机，我是拿着手机在和 Mac 配对，但是 Mac 可能是我晚上在家里操作一下，然后白天又在公司操作一下。不能用传统的配对方式。」
- **第 3 轮**：配对选「方案 1：异步邀请 + 手机 / 本机代批」（→ M7）；追问：「这个机制和我们的渠道激活的机制是什么关系？你需要设计一下。」
- **第 4 轮**：用户指出：「如果你用 Mac 做一个特殊的渠道，那这个渠道什么时候激活呢？你可以考虑一下，如果我有多台 Mac 的情况，它们应该是全都可以互通的。我任意时候在一台 Mac 工作，都应该可以收到其他所有 Mac 的消息。」——据此否决了「每台 Mac 一个渠道 id 放进单活跃槽」的设计（单槽表达不了多 Mac 全互通，还会逼用户先接管 / 作答才能收到别的 Mac）。
- **第 5 轮**：激活选「永远参与」（→ M6）；圈子选「v1 就做『圈子引荐』：新 Mac 经一次批准就加入整个圈子，圈内成员自动互相配好，批准次数恒为 1」，接受信任集中到已批准成员的代价，没有采用推荐的「两两配对」（→ M8）；追问：「我觉得还有一个问题，现在相当于是多对多的事件分发了，我们的通道有广播的机制吗？还是说我必须每一个消息都给所有的 Mac 单独发送一次？然后其次，我们是不是发送可以有一个特殊的处理，就是我只发一个摘要或者是通知，只有我在对端 Mac 去查看这个提问之类的操作，我才实际接收它的内容。避免在我们的通道里面去直接传输大量的数据。我觉得你可能需要设计一下这些方面的问题如何解决。」（→ M10、M11）
