## 1. 背景与目标

iOS 端要开放给更多用户，初期只提供免费版，靠 TestFlight 或用户自己编译分发。要解决两件事：

1. **不和某一家 broker 绑定。** 作者和 EMQX 没有利益关系，只推荐它会像在给它打广告。
2. **推送中继的成本不能随用户数失控。** 所有推送都经作者那一个部署，用的人多了，成本会涨，而这是个免费产品。

约束（来自用户的回答）：

- 用户以中国大陆为主；成本口径是「每月几块钱可以接受，100 就太高」；增长不确定，希望自然扩大。
- 有已备案的域名，所以中继绑自定义域名没有障碍。
- 措辞中立，不用特意强调「无商业关系」；只把实测兼容的 broker 写成「已实测」；**不只推荐一家**。
- 已排除：方案 A（给 Mac 下发短时效 APNs JWT）；完全自建（要付费 Apple 账号，门槛太高）。

## 3. 总体设计

```
Mac ──MQTT(TLS/WSS)──► 用户自选的 Broker（EMQX / flespi / 自建 / 其它实测兼容的） ──► iPhone
 └──HTTPS──► 公共推送中继（腾讯云 SCF·香港，自定义域名，并发封顶）──► APNs ──► iPhone
```

不变量（均为现状，本需求不改）：

- 消息端到端加密：broker 只见密文与主题名。中继无状态、什么都不存；它只在登记与推送时经手设备 token（登记后以加密句柄的形式存在于 Mac 上）和固定的告警文案键。
- 中继 `register()` 拒绝 `bundleId` 不等于自己的 `APNS_TOPIC`：它不能被当成通用 APNs 代理。所以自己编译、换了 Bundle ID 的人，默认中继会拒绝他们的登记，他们要用自己的中继（向导里的「使用自己的中继」，文档给出自建指南的入口）。
- 手机的中继地址来自**配对二维码**，没有下发通道；所以**老配对继续用旧函数 URL**，旧 URL 要一直保留，直到所有老配对自然迁走。

## 4. 公共中继：成本模型与护栏

### 4.1 价目与合法用户的成本

账号是腾讯云**国内站**（早先按国际站价目写的数字已作废）。价目取自官方文档「云函数基本能力产品定价」（2025-03-24 版）、「计费项说明」「计量原则」「欠费与停服说明」，2026-11-22 检索；实际扣费**以费用中心的明细账单为准**。

| 计费项（Web 函数） | 价格 |
| --- | --- |
| 资源使用量 | ¥0.00011108 / GBs（配置内存 × 实际运行时长，毫秒计） |
| Web 函数调用次数 | ¥0.0133 / 万次（每次 ¥0.00000133） |
| 外网出流量、Web 函数响应出流量（中国香港） | ¥1.00 / GB（中国大陆与新加坡等 ¥0.80，美国与曼谷 ¥0.50） |

- **没有免费额度可指望**：官方免费额度只给开通后的前三个月，而且不含 Web 函数响应流量；本账号早已过了免费期（费用中心里云函数已有实际扣费）。下面的数字一分一厘都按上表算。
- **结算**：后付费，整点结算上一小时的费用；明细账单里一般要过 1.5–3 小时才出现；单个计费周期不足 ¥0.01 不出账，只在月度精度调整里体现。

一次推送的函数内运行时间，2026-11-28 用上线后一周的真实流量核对过（函数监控逐分钟数据，11-22 12:00 起 968 次推送；出流量 ≥ 0.4 KB 的调用才是推送，只有推送会向 APNs 发请求）：**平均 419 ms**，比原先估的 0.3 s 高约 40%。热调用 0.1–0.3 s，冷调用 1.0–1.4 s（要新建到 APNs 的连接），孤立的单次推送里冷调用占 25%（上线前的老函数是 42%、平均 620 ms）。每次推送的成本：资源 128 MB × 0.419 s = 0.0524 GBs ≈ ¥0.0000058，调用 ¥0.0000013，约 1.27 KB 的外网出流量 ≈ ¥0.0000012，合计约 **¥0.0000084**（约 ¥0.0084 / 千次推送）。每天 20 次（偏高）× 30 天 = 600 次，**每用户每月约 ¥0.005**；1,000 / 5,000 / 10,000 个用户约 **¥5 / ¥25 / ¥50 每月**。预期用量下，这就是「每月几块钱」。

账单实际收的比这个少：11-22 起一周的明细账单是调用 3,197 次 ¥0.0043 加出流量 1.2 MB ¥0.0012，共 ¥0.0054（11-28 当天还有几个小时没出账），**没有资源使用量的行**（三个云函数 28 天都没有；监控估算同一周约 54.2 GBs，按价目 ¥0.0060）。账号里有一个 SCF 资源包（备案资源包，用量几乎没动，有效期很长），官方说明资源包可抵扣资源使用量，很可能就是原因，但「抵扣明细」页的产品下拉里没有云函数，**没有证实**。所以模型继续按价目把资源一项计入，当作上界。实例多并发（4.3）下资源按实例的忙碌时间计费，重叠的请求只算一次，同样的流量不会比单并发更贵（监控的 `MemDuration` 与重叠模型在单并发、2、8 并发下的误差都在 0.2% 以内）。

### 4.2 最坏情形：被人刷

「拒绝类」请求（无效句柄，几毫秒返回）每次约 ¥0.0000017：调用 ¥0.0000013，运行几毫秒约 ¥0.0000001，约 0.3 KB 的响应流量约 ¥0.0000003。**并发超限的请求（HTTP 432）由平台直接拒绝，函数不执行，账单里也不收钱**：官方「计量原则」写明这类请求「未执行、不计量、不产生费用」，预发上单台笔记本把它打到约 1,500–1,900 次 / 秒也没有被网关限速；明细账单核对过——2026-11-22 凌晨两个整点里监控记到 61,500 次受限（432），账单的调用次数行只有成功执行的 4,477 次，没有为 432 收调用费，也没有出现响应流量的行（§7 第 7 条）；2026-11-28 在生产上再核对一次：14 天里 11 天的账单调用次数与「监控调用次数 − 432」完全相等，另外 3 天只差 2–9 次，880 次 432 一分钱没收。所以烧钱速度由「实例数 × 每个实例的 CPU 上限」决定，**和槽数没有直接关系**：被刷时每个实例的 0.1 vCPU 先跑满（平台对每个请求有约 20–35 ms 的固定开销），单并发的实例约 22–33 次 / 秒，多并发的约 45 次 / 秒，攻击连接从 40 加到 60 也没抬高，说明瓶颈在实例端而不是攻击端。2026-11-28 在临时函数上实测（公网上一台笔记本，被执行的无效句柄请求，每组几十秒到几分钟）：

| 配置（最大独占配额 × 每实例并发 = 槽数） | 被刷时每秒被执行的请求 | 每小时 | 持续 8 小时 |
| --- | --- | --- | --- |
| 512 MB × 1 = 4 个槽（2026-11-22 起的旧配置） | 88–132 | ¥0.54–0.81 | ¥4.3–6.5 |
| 1,024 MB × 1 = 8 个槽 | 约 218 | 约 ¥1.3 | 约 ¥10.7 |
| 512 MB × 2 = 8 个槽 | 约 155 | 约 ¥0.95 | 约 ¥7.6 |
| 128 MB × 8 = 8 个槽 | 46–53 | ¥0.28–0.32 | ¥2.3–2.6 |
| **256 MB × 8 = 16 个槽（现配置）** | **约 89** | **约 ¥0.55** | **约 ¥4.4** |

换算：每「每秒一次」的持续攻击每小时约 ¥0.0061（¥0.0000017 × 3,600）。这是一台笔记本的短时压测，只当量级，不是账单；更强的攻击机能不能压出更多，没有测过。早先写的「143 次 / 秒 ≈ ¥0.9 / 小时」与「上界 400 次 / 秒 ≈ ¥2.4 / 小时」作废：后者的「每实例 100 次 / 秒」没有依据，实例的 CPU 先到顶。**槽数可以加得比速度快**：256 MB × 8 把槽数从 4 提到 16，被刷时的速度仍落在旧配置的区间里；抬高速度的是实例数（配额 ÷ 128 MB）。再往上加的路径是 512 MB × 8 = 32 个槽、4 个实例，约 ¥1.1 / 小时。**按「每小时一块钱以内」想。**

合法容量看的是**同一时刻在途的推送有几条**，不是每秒能处理多少条。配额满了不排队（函数 URL 上的「请求缓冲队列」实测无效，§7），平台直接拒绝：那条推送丢了，手机上没有任何提示；守护进程遇到 432 不重试，Owner 2026-11-28 决定不靠延迟重试去补，靠槽数留足余量。一条推送占一个槽，平均约 0.42 s（冷调用约 1–1.4 s）。按「每用户每天 20 次、高峰是平均的 10 倍、推送独立到达」估算（真实推送会成簇，只会更差），高峰时被拒的比例（Erlang B 公式）：

| 用户数 | 4 个槽 | 8 个槽 | 16 个槽 |
| --- | --- | --- | --- |
| 1,000 | 1.4% | 0.0007% | ≈ 0 |
| 2,000 | 8.9% | 0.073% | ≈ 0 |
| 3,000 | 19.7% | 0.7% | ≈ 0 |
| 5,000 | 38.7% | 6.4% | 0.004% |
| 10,000 | 63.8% | 32.5% | 1.9% |

高峰被拒低于 1% / 0.1% 时能服务的用户数：4 个槽约 900 / 450，8 个槽约 3,200 / 2,100，16 个槽约 9,100 / 6,900。假设（每条占用 0.2–1.0 s、峰值倍数 3–10）一变，4 个槽的容量在约 190–3,000 个用户之间摆动，所以**槽数要跟着用户数涨，不是常数**。早先写的「4 个实例每秒能处理约 20 次真推送……按 10 倍峰值估算够几千个用户」是错的：它算的是吞吐，没算同时在途的占用，4 个槽只够约 900 个用户。真实流量已经碰到过：上线后一周里有 1 次真推送被拒（11-25 17:11，6 个请求几乎同时到达，其中 1 个被 432），近 15 天里一分钟内有 3–6 个推送的有 13 次。

容量不足的信号只有 **HTTP 432 的次数**（监控指标 `Http432`）：HTTP 432 告警要连续 5 个 1 分钟都有 432，孤立的容量型拒绝触发不了它（它抓的是持续满速的刷），所以要定期看监控曲线；每天都有、或成串出现，就按 4.3 加配额（512 MB × 8 = 32 个槽）。**不要用 `ConcurrentExecutions`（并发执行次数）判断槽数**：多并发下它不反映在途请求数（实测：同时到达 6 个推送、那一分钟共 61 次调用，它仍显示 1）。没有为容量另配告警（Owner 2026-11-28 决定先不加）。

**没有「到钱就停」的硬封顶**：腾讯云云函数是后付费，做不到。账号层面唯一的硬停是余额耗尽——官方「欠费与停服说明」：欠费后 24 小时内仍可用，超过 24 小时云函数服务停止；这个账号上其它按量付费的产品也受欠费影响，所以不能当防线（见 4.4）。本需求用「封顶速率 + 告警 + 熄火」逼近硬封顶，最坏损失 = 速率 × 反应时间。

### 4.3 护栏

1. **最大独占配额 256 MB + 每实例 8 个并发 = 16 个并发槽**（官方定位就是「费用管控、避免费用失控」；2026-11-28 由 512 MB × 1 = 4 个槽改成这样，依据在 4.2 与 §7）：封顶烧钱**速率**与同一时刻在途的请求数。槽数 = 配额 ÷ 128 MB × 每实例并发数。配额是函数级设置，函数的所有 URL（旧 URL、别名 URL、自定义域名）一起生效，超限返回 HTTP 432、不排队，发布新版本不会动它。**每实例并发数是版本级设置，随发布的版本固定下来**（API `UpdateFunctionConfiguration` 的 `InstanceConcurrencyConfig`：`DynamicEnabled = FALSE`、`MaxConcurrency = 8`、`InstanceIsolationEnabled = FALSE`、`Type = Request-Based`），别名指向的版本是几，实例就按几个并发算。所以**每次发布新版本之前，先在 `$LATEST` 上把它设成 8，发布后读回新版本的 `InstanceConcurrencyConfig` 确认是 8，再移别名与 `$DEFAULT`**；漏了就退回 1，16 个槽缩成 2 个。432 的正文里报的是「配额 × 每实例并发」（256 × 8 显示成 2048MB），别读成配额被改了。回滚到版本 1 或 2（并发 1）时，要把配额同时设回 512 MB 才能保住 4 个槽。**不能用 128 MB / 1**：在预发上设成 128 MB / 1、做过一次「设为 0 → 再设回」之后，函数一直返回 432，把配额整个删掉才恢复；512 MB / 4 没有这个问题。
2. **告警与预算**（2026-11-22 已在 Owner 的云监控与费用中心建好；阈值按预期用量留 5–6 倍余量，上线一周后按实际调整）：
   - `askhuman-relay-并发触顶-HTTP432`：云函数 / 版本，资源超过限制（HTTP 432）> 0 次，1 分钟粒度、连续 5 次满足，每 1 小时提醒一次。
   - `askhuman-relay-调用量异常`：云函数 / 版本，调用次数 > 1,700 次 / 5 分钟、连续 2 次满足，每 1 小时提醒一次（约 2 万次 / 小时）。
   - 费用中心预算「askhuman-relay 云函数月预算」：¥30 / 月，范围「云函数 SCF」，实际费用达 50%（¥15）与 100%（¥30）各提醒一次，提醒时段 08:00–22:00；预算进度约有 2 小时延迟。
   - 告警对象选「全部对象」（新建的版本与别名约 30 分钟后自动纳入），通知用系统预设模板（主账号邮箱 + 短信）。代价是账号里其它函数也会触发这两条告警：**在这个账号里新建临时函数做 432 实验会触发真告警**（2026-11-28 的实验就触发了一次，短信与邮件都收到），做之前先在云监控里把告警对象排除，或事先告知 Owner。**删掉那个临时函数后，这条告警记录不会自己恢复**：平台要等到「之后又出现一个正常的数据点」才判恢复，函数删了就不会再有数据，记录一直停在「告警中」，而策略设的是每小时重复提醒，短信与邮件会一直发（2026-11-28 实际发了 19:24、20:24 两条，到 21:12 才处理）。处理办法（2026-11-28 21:12 经 Owner 同意做过）：把该策略关闭再开启（API `ModifyAlarmPolicyStatus`，`Enable` 设 0 再设 1，这次关了 14 秒）；旧记录当即变成「已失效」（API 里是 `NO_CONF`，控制台写「21:12:03 结束」），开启后没有回到「告警中」。代价是关闭期间这条策略对生产函数也不判定，开启后「连续 5 次」的计数从零开始。不建议把告警对象收窄成生产函数：告警对象的粒度到版本号（`appid#函数名#命名空间#版本`），每发一个新版本都得重选，漏选就没有告警。
   - 2026-11-28 一周复核（Owner 决定两条阈值都不改）：一周里没有误报。HTTP 432 告警只抓持续满速的刷（孤立的容量型拒绝触发不了它，见 4.2）；调用量告警的阈值是真实推送 5 分钟峰值（13 次）的 131 倍、一周里最大突发（770 次 / 5 分钟，11-23 08:45）的 2.2 倍，而现配置被满速刷约 89 次 / 秒 ≈ 26,700 次 / 5 分钟，连续两个窗口、10 分钟内必响。降到 1,000 次 / 5 分钟也仍高于最大突发，但没有收益，所以不动。
3. **熄火 / 恢复**：控制台把该函数的「最大独占配额」设为 0，或 API `PutReservedConcurrencyConfig`（`ReservedConcurrencyMem = 0`），生效约 3–5 秒，之后所有 URL 都返回 432、函数不执行；恢复时设回 256（2026-11-22 在 512 上演练时立即恢复；每实例并发数是版本级设置，熄火动不到它），设回后若仍持续返回 432，就把配额删掉再重设。手动，写成清单；2026-11-22 在生产函数上演练过一次（§7）。云函数概览里的「冻结」能停整个账号的云函数，会把账号里其它函数一起停掉，不当作熄火手段。
4. **函数内的限流（公平性，不是成本护栏）**：注册按客户端 IP 分桶（每个 IP 突发 30 次、每秒补 0.5 次，最多记 5,000 个 IP），再加全局兜底（突发 200 次、每秒 10 次）；推送仍按句柄编号限速（突发 10 次、每秒 2 次）。桶在各实例的内存里，各实例各算一份（多并发后请求集中在更少的实例上，桶更接近这里写的数）；它防的是「一个 IP 把所有新用户的注册挤掉」，防不了账单。客户端 IP 取 `X-Forwarded-For` 从右数第三项（见 §7）。

预发验证过：函数 URL 与自定义域名都**没有**可配的限流，所以没有「被限流的请求到不了函数、不计费、也不占并发」这一道闸（§7）。

### 4.5 业界怎么防「被刷」，和这里的差别

ntfy.sh 按访问者 IP 限速（请求令牌桶、匿名每 IP 每天条数、每 IP 订阅数、附件配额，异常请求罚分后交给 fail2ban），主题名就是密码；Bark 对成功请求不限，对错误请求按 IP 计数后封禁，文档写「QPS 超过 200 请自建」。它们的防护都发生在请求**到达服务器之后**，而服务器是固定月费，被刷只是变慢、不多花钱。这里为了「固定成本为零」选了按调用计费的云函数，**请求一到就计费**，函数里再按 IP 限速也省不了调用费，所以必须有平台层的东西封顶（4.3），再加告警和熄火。一致的部分：句柄不可伪造（相当于主题名 / 设备 key），错误请求便宜。

两点局限，如实告知用户：

1. 并发封顶下，攻击者占满并发会把真用户挤掉：被刷期间推送可能发不出（App 前台仍可用）。平台没有可配的限流（§7），要避免只能靠边缘层。没有攻击时，用户多了高峰也会自己把槽挤满（4.2），那一刻的推送同样发不出，所以槽数要跟着用户数涨。
2. 边缘层（腾讯云 EdgeOne：被拦截的请求不计费）免费版目前限量内测、要兑换码，且定位是静态内容加速；个人版约 $4.2 / 月，超出预算，所以不作为默认，被刷、告警频繁触发时再评估。

中继是**尽力而为的免费服务**，不承诺可用性；这是事实，但设置里的说明不强调它（Owner 2026-11-22）。

### 6.3 测试连接的隔离自检（OA10）

现有「测试连接」（`commands::ios_test`，设置页与 CLI `channel ios` 共用，内部 `ios/transport.rs::probe`）连上后给自己发一条、收到回声。成功后追加：订阅自己命名空间之外的一个随机主题，向它发布一条 QoS 1 非保留消息，等约 1.5 秒看有没有回声；有回声就警告「这份凭据能读写自己命名空间之外的主题」；被 broker 断开连接也算「已隔离」。警告级，不挡保存与配对。`ios_test` 的返回由单个字符串改为「消息 + 警告列表」的结构（Tauri 命令返回值，**不是 IPC 消息**，不涉及 `PROTOCOL_VERSION`）。不做大消息等重检查（会吃用户的免费流量），那些留给离线套件。

### 6.4 向导与错误提示（OA11）

`src/views/settings/iosBrokers.ts` 是纯数据的服务商目录（名称、主机名后缀、默认端口、要点、文档锚点）；设置卡顶部是服务商下拉与要点块。不新增配置字段，按主机名后缀识别服务商，认不出就是「自建 / 其它」。认证失败 / 超时按服务商给针对性提示（例如 flespi：用户名填 token 编号、密码填完整 token）。

## 7. 风险与未验证项

- **预发验证结果**（2026-11-21～22，临时函数 `askhuman-relay-verify`，香港，不动生产函数；压测只用了一台笔记本，样本小，数字只当量级）：
  1. **最大独占配额**：Web 函数支持。超限返回 HTTP 432（正文 `Function [<函数名>] concurrency exceeded reserved quota`），函数不执行；旧 URL、别名 URL、自定义域名三种入口表现一致；设为 0 即熄火，生效约 3–5 秒。128 MB / 1 用不了（见 4.3），512 MB / 4 可用，恢复立即。**432 不计费，明细账单核对过**（第 7 条）。
  2. **自定义域名**：能映射到别名，但**每个版本 / 别名要有自己的函数 URL**（建 URL 时取消「参数兼容」），否则域名映射里选不到它。HTTPS：免费证书（TrustAsia，90 天）托管在 SSL 证书服务里，打开托管与「自动续期」两个开关后，到期自动续期并自动部署到 SCF 的自定义域名；已开强制 HTTPS。
  3. **客户端 IP**：`X-Forwarded-For` 是 `真实客户端, 网关, 函数宿主`（后两项是内网地址），所以真实 IP 在**从右数第三项**，环境变量 `TRUSTED_PROXY_HOPS` 可调（默认 2）。平台还会把 `x-scf-private-environment`、`x-scf-uin` 等头带进代码，里面有账号标识，**公共端点不得回显请求头**（预发的调试端点回显过，所以预发函数验证完要删）。
  4. **「仅供测试」**：压测（十几秒、被拒请求约 1,500–1,900 次 / 秒）里，默认 URL、别名 URL、自定义域名都没有被限速或下线。官方没公开限速与下线的条件，所以这是「没观察到」，不是「没有」。
  5. **单实例吞吐**：成功请求每实例约 23–38 次 / 秒（4 个实例合计约 143 次 / 秒），受单台笔记本经公网的往返限制，只能当下限。（2026-11-28 重测后修正：瓶颈在实例的 CPU，不在笔记本；「只能当下限」作废，见下面「上线一周复核与并发改造」第 4 条。）
  6. **可配限流**：函数 URL 与自定义域名都没有可配的 QPS 限流，OA14 里「再加一道」不成立，熄火仍然只有手动这一个办法。
  7. **432 不计费（明细账单核对，2026-11-22 04:55 读数）**：函数监控里「调用次数」= 成功执行 + 「受限次数」（HTTP 432）。01:00–01:59 调用 30,661、受限 29,381、执行 1,280；02:00–02:59 调用 35,316、受限 32,119、执行 3,197（逐分钟读自监控曲线，相加）。明细账单里这两个整点的「HTTP 函数调用次数」是 1,280 与 3,197，**正好等于执行次数**：61,500 次 432 没有产生调用费，两个整点一共只收了 ¥0.006（4,477 次）。预发函数在账单里**没有外网出流量的行，也没有资源使用量的行**：监控里外网出流量全程为 0（这条指标看起来是函数主动访问外网的流量，生产函数平均每次调用约 1.3 KB，与它向 APNs 发的请求相符，不是给调用方的响应），所以 61,500 次 432 响应与 4,477 次成功响应都没有响应流量费；本账号三个云函数 11 月的账单里也从没出现过资源使用量的行，原因没查。价目表里的这两项在 4.1、4.2 里仍然计入，当作偏保守的上界。样本只有这两个整点，响应流量一项的结论只是「没有看到」。
- **生产切换与验证结果**（3c，2026-11-22，生产函数 `askhuman-relay`，香港；Owner 在场，文件选择框由他操作，其余在浏览器控制台里点，验证全部来自外部 `curl`）：
  1. **怎么切的**：现有代码先发布为版本 1（`$DEFAULT` 固定在它上面，当回滚目标），新代码上传到 `$LATEST` 并发布为版本 2；别名 `live` 指向版本 2，有自己的函数 URL；自定义域名 `/*` 只映射到 `live`；最大独占配额 512 MB / 4（2026-11-28 起是 256 MB × 每实例 8 并发，别名与 `$DEFAULT` 指向版本 3，见下面「上线一周复核与并发改造」）；外部验证通过后 `$DEFAULT` 也指到版本 2，旧函数 URL 因此也跑新代码。版本 1 保留，回滚就是把别名或 `$DEFAULT` 指回去。预发函数 `askhuman-relay-verify` 已删除（它的调试端点会回显请求头）。
  2. **功能**（自定义域名，真实 SCF）：`/v1/health` 返回 200 且 `apns: true`；HTTP → HTTPS 301；未知路径与错误方法 404；注册的错误路径 400；无效句柄的推送 401，格式正确的伪造句柄也是 401；用合成的设备 token 注册后再推送，Apple 接受了中继用真实密钥签的 JWT，回 `BadDeviceToken`，中继映射成 410（说明到 APNs 的链路、签名与 topic 都对）；在旧函数 URL 上登记的句柄经自定义域名推送同样有效（同一个函数、同一把句柄密钥），所以老配对的 Mac 改用默认中继不必重新配对。
  3. **限流**：桶在各实例自己的内存里，结果取决于请求落在几个实例上。只有一个热实例时，同一客户端连续注册第 35 次起返回 429（突发 30 个，加上发送期间补充的几个），在 `X-Forwarded-For` 前面伪造别的地址换不出新的桶；压测、演练之后有了多个热实例，同样的 45 次连续注册（自定义域名与旧函数 URL 各一遍）全部 200；之后闲置二十多分钟、多余的实例被回收，同一段脚本复测，又回到第 37 次起 429，伪造前缀仍绕不过。代码与入口都没变，变的只有热实例数，所以是实例数在起作用。这正是 4.3 里「公平性手段、不是成本手段」的实测例子：每个实例各算一份，一个 IP 在各实例上能拿到的突发是单实例的倍数。
  4. **客户端 IP 的层数**：生产函数不回显请求头，所以是在删预发函数之前，用它的调试端点量的（自定义域名经临时加的探测路径、别名 URL、旧函数 URL 三个入口）：`X-Forwarded-For` 都是 3 项 `真实客户端, 内网网关, 内网宿主`，从右数第三项是真实客户端，和第一次预发一致；生产函数在同一套网关后面。
  5. **432**：512 MB / 4 上并发压测，超限的请求返回 432，压测一停立刻恢复。
  6. **熄火 / 恢复演练**：把配额设为 0，约 7 秒内三个入口都返回 432；设回 512 MB / 4，约 6 秒内都恢复 200，整个中断约 20 秒；恢复后并发 4 的 60 次请求全部 200。
  7. **真机推送**：Owner 的手机（配对时用旧代码登记的句柄，3b 没有改句柄编解码）经新代码收到了推送通知；Mac 端记这台手机的推送状态是 `ok`（守护进程只在中继返回 2xx 时才记 `ok`，中继只在 Apple 返回 200 时才回 2xx）。函数监控里这几次真实推送的运行时间是：热调用 202、217、217 ms，冷调用 956、965 ms（要新建到 APNs 的连接），每次向外网发出约 1–2 KB；切换前用合成 token 测过一次冷推送约 1,160 ms。冷热比例要看上线后的真实流量。函数没有配日志投递，控制台里看不到调用日志与实例列表，只有监控曲线可用。
  8. **原始函数 URL 也接受明文 HTTP**：只有自定义域名强制 HTTPS，所以默认地址与文档一律写 `https://`。
  9. **腾讯云 2027-01-01 起停止新建的功能**（Node.js 6.10 / 8.9、Custom Runtime、Serverless 应用、AI 与 Agent 应用、K8s 托管模式）不含 Node.js 20.19 的 Web 函数；官方写明范围外的功能暂无下线计划，存量资源不受影响（[迁移指南](https://cloud.tencent.com/document/product/583/138985)，2026-11-22 查）。
- **上线一周复核与并发改造**（2026-11-28，Owner 在场逐项答复。复核窗口是 11-22 00:00 起的 6.8 天，其中 11-22 上午是我们自己的验收与压测；函数没有日志，用量与来源都读自监控曲线与明细账单，来源判断是推测）：
  1. **用量**：切换后共 4,138 次调用，实际执行 3,258 次，被 432 拒绝 880 次；其中真推送（出流量 ≥ 0.4 KB 的调用）968 次，每天约 110–190 次。本机 `daemon.log` 里 11-22 起有 124 次推送（约 20 次 / 天，全发往 Owner 的那一台手机），与「每用户每天 20 次」的假设一致，中继总量约相当于五到九个这样的用户（粗估，中继没有日志，分不出用户数）。运行时长与账单见 4.1。
  2. **880 次 432 的来源**：377 次落在 11-22 验收、压测与熄火演练的时间点上（时间吻合，不是日志证据）；502 次是两个一分钟的突发（11-23 08:46、11-24 04:45），毫秒级、没有出流量、不是推送，像自定义域名上线后被扫描（推测，证实不了），配额把它们挡在函数外、不收费；1 次是真推送被拒（11-25 17:11，见 4.2）。HTTP 432 告警要连续 5 个 1 分钟，这些孤立的 432 都触发不了它。
  3. **临时函数上的实验**（`askhuman-bufftest`，香港，做完已删除；生产函数在改造前没有动）：① 「请求缓冲队列」（`OverClockConfig.TimeOut`）在函数 URL + 最大独占配额上无效，5 组对比，超限请求全部立即 432。② 每实例并发数可行：版本级设置，别名 URL 认版本里的值，默认 1。③ 计费：单并发按各请求运行时间之和，多并发按实例的忙碌时间（重叠只算一次），监控的 `MemDuration` 与这个重叠模型在 1、2、8 并发下相差 0.2% 以内；`Duration` 是每次调用的平均毫秒数。④ 中继代码本身不挡多并发：`adapters/scf.js` 每个进程、每个 APNs 环境共用一个 HTTP/2 会话（同步创建，多路复用），本地实测处理一次推送的 CPU 约 0.05–0.22 ms，远小于平台在 0.1 vCPU 上对每个请求的固定开销（约 20–35 ms）。
  4. **被刷速度的重测**（一台笔记本经公网，每组几十秒到几分钟）：4.2 的表。结论是速度由实例数 × 实例 CPU 决定，和槽数无关；攻击连接从 40 加到 60 速度不变。

  6. **验证**：公网域名上用合成 token 验证：6 个同时到达的推送（Apple 回 BadDeviceToken，中继映射成 410）全部拿到应答、没有 432；20:57 复测一次，9 组 × 6 个同时请求（health、无效句柄、合成 token 各三轮），状态码只有 200、401、410，合成 token 的推送最慢 1.6 s（差异主要来自 APNs 对错误 token 的响应时间）；监控里改造后 `Http432` 全为 0。**没有用真机推送验证**：原计划用一次真实的 AskHuman 推送收尾，但守护进程日志里 18:51 以后没有 iOS 推送发出，所以换成合成 token，手机没有被通知；下一次真实推送是第一次真实验证。
