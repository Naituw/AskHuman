# AskHuman 项目级开发验收

> 状态：已按项目级方案重做并安装 Dev；自动验证范围见实施计划，真实渠道与本机界面由用户明确后置。2026-10-31 用户要求重新设计并在补充工作树准备、远程连续性及渠道测试边界后明确批准实施：这是 AskHuman 自身的开发机制，不能改变普通用户的规则、MCP 与使用流程。
> 已确认：开发 rules 和 MCP 均采用项目作用域；保留借用正式渠道，仅显式开发请求使用内部投递能力。
> 本方案取代先前的全局路由与集成迁移方案。PR #27 已按本文重做；新版验证范围见对应计划，旧测试结果不代表新版验收通过。

使用 Dev Instance 开发 AskHuman 时，主开发会话通过正式版讨论需求，由项目专用工具验收本工作树的构建。
开发规则和 MCP 只在 AskHuman 仓库及其工作树中生效。普通用户无需更新规则、调整 MCP、选择路由模式或执行迁移。

## 1 范围与边界

| 范围 | 新方案 |
| --- | --- |
| 普通用户级 rules、MCP 注册与普通工具目录 | 保持既有内容与行为；不增加开发说明或 `dev_ask` |
| 普通设置、日常问答、权限、Stop 与待办 | 保持既有流程；不增加开发页或开发模式选择 |
| AskHuman 仓库及其工作树 | 项目规则、项目开发 MCP、显式安装与验收入口 |
| 每棵工作树的运行时 | 私有程序、home、daemon、构建记录、测试 profile 和结果 |
| 正式版参与开发验收 | 仅为显式请求提供受限渠道转送，不切换日常会话归属 |

不再建立账户级 `legacy / explicit` 路由状态、正式程序注册表和全局 Agent 集成迁移器。
开发专用指令不进入供普通用户安装的交互协议模板。已有普通用户集成继续按其现有方式管理。

## 2 实际使用流程

首次在某工作树准备开发环境时，将项目准备并入已有 `dev enable`，不新增独立 setup 步骤。
每棵工作树分别准备；同一树继续开发、切换分支或重新安装无需重新初始化，删除后重建则视为新树。
普通用户级 AskHuman 配置无需改动。常规开发默认借用正式远程出口，不再逐树询问是否另配 channel；
仅明确测试渠道实现时，才询问专用 bot／配对和预设。

是否使用 Dev Instance 沿用 AGENTS 原有的任务与工作树约定，不要求主工作树或每个开发任务启用 Dev。
已经使用 Dev Instance 的任务按项目说明执行幂等准备命令；自动识别不到客户端时才手动传 `--agent`。
程序检查本树 manifest、配置版本和所需项目文件；齐全时不重复写入，缺失或升级时才补齐。
准备成功与验收就绪分别显示；`dev status` 给出构建和当前投递方式的检查结果。旧正式端不支持转送时，
明确指出需要兼容的正式安装，不能用反复重建 Dev、刷新 MCP 或提前替换日常正式端来声称完成验收。
不让 Agent 依赖对话记忆判断是否已准备。写入项目文件与客户端实际加载分开记录，未加载时明确返回待刷新状态。

之后以修改弹窗为例：

1. Agent 使用日常 AskHuman 讨论需求，回答走正式版和用户惯用渠道。
2. 在本树修改并运行 `./scripts/install.sh`，程序安装到 `.askhuman-dev/bin/`。
3. MCP Agent 调用项目连接 `askhuman-dev` 提供的 `dev_ask`；CLI Agent 使用仓库开发验收命令。
4. 本树 Dev 显示带工作树、构建身份的测试卡片；回答和附件返回原开发会话。
5. Agent 继续通过普通 AskHuman 讨论；无需切回实例。

Windows 使用对应安装脚本。首次加载项目 MCP 需要按客户端要求信任项目、刷新连接或重新打开会话；
不修改正在等待的请求，也不把一次配置刷新描述成运行中会话已经切换。

仓库统一入口拟定为 `node scripts/dev.mjs`，Node 已是本仓库构建前提，命令在三平台使用同一语义：

```bash
AskHuman dev enable                     # 幂等准备当前工作树，补齐项目规则与 MCP
./scripts/install.sh                     # 安装当前工作树的 Dev 构建
# MCP: askhuman-dev.dev_ask(...)          # 回答直接回到当前 Agent
node scripts/dev.mjs ask -- "请验收这次修改"  # CLI Agent 的同等入口
node scripts/dev.mjs ui                  # 打开本树 Dev 工作台
node scripts/dev.mjs session codex       # 完整集成测试，使用独立 profile
```

项目 MCP 由仓库工具提供，绑定 enable 时的绝对工作树路径；连接本身不依赖被测程序已经构建成功。
未安装时工具可正常列出，但验收明确报告缺少构建。安装新构建后委托新程序，避免开发 server 自身仍运行旧构建而冒充验收。
这些接口由本仓库提供；原生客户端加载、真实渠道和登录后会话须分别保留验收证据。

## 3 项目规则与 MCP

### 规则

`AGENTS.md` 是本仓库开发流程的主入口。首次准备所需的最小客户端规则适配文件也随仓库提交，
引用同一份开发说明，避免复制多份交互协议。说明在启用前即可读取，不增加“每次功能任务必须 enable”的要求。

项目规则只补充：普通讨论使用日常 AskHuman；安装后验收使用项目开发工具；完整集成测试使用独立 profile。
验收例外及开发工具用法只随项目连接提供，不写入用户级 `CLAUDE.md`、`AGENTS.md`、全局 skill 或全局规则。
不改变既有普通交互协议的提问、等待、`show_last` 和结束交接要求。

### MCP

项目连接使用独立名称 `askhuman-dev`，提供开发验收工具。普通 `askhuman` 连接和它的工具保持原样，
不覆盖同名全局注册，不代理或重新实现日常 `ask`、`whats_next`、待办和原生身份绑定。

开发 server 在启动时绑定明确的工作树。`dev_ask` 只能操作该树，不能因 server 的 cwd、请求参数或 marker 变化
转向另一棵树。调用 Dev 时移除日常原生 session、内部 profile 和一次性凭据，不临时修改 server 的全局环境。

项目适配采用客户端原生作用域：

| 客户端 | 项目开发规则 | 项目 MCP 配置 |
| --- | --- | --- |
| Codex | 根 `AGENTS.md` | `.codex/config.toml`，需受信任项目 |
| Claude Code | `CLAUDE.md` 导入开发说明；支持时可直接读取 `AGENTS.md` | 根 `.mcp.json`，使用 project scope |
| Cursor | 根 `AGENTS.md` 或 `.cursor/rules/askhuman-development.mdc` | `.cursor/mcp.json` |
| Grok | 根 `AGENTS.md` | `.grok/config.toml` |
| Pi | 根 `AGENTS.md` | 沿用 CLI 验收，不虚构 MCP 支持 |
| Antigravity | 工作区规则适配，按实际客户端版本检测 | `.agents/mcp_config.json`，按版本与连接验证开放 |

Codex 的项目配置优先于用户配置，但只加载受信任的项目层；Claude、Cursor、Grok 也有项目级 MCP。
以上是原生配置能力，不能替代对本机已安装版本的加载验证。Antigravity 的工作区 MCP 与其完整原生会话启动能力分开判定。

共享开发说明与模板入库。带本机路径的生成配置仅保存在当前项目，运行状态放 `.askhuman-dev/`；
不提交机器路径或凭据。enable 只维护自己的连接与规则区块，保留项目中的其他服务器和自定义内容；
已有同名自定义 `askhuman-dev` 视为冲突，不覆盖。只有新生成的本机文件加入精确的项目排除项，
不把整个客户端配置目录静默加入忽略列表。客户端自身的项目信任由客户端交互确认，工具不代改用户级信任文件。

## 4 工作树选择与旧开发标记

新开发环境使用本树版本化的私有 manifest，显式记录 Dev 程序、home、构建和正式投递入口。
它不使用旧的 `.askhuman-dev/enabled` 作为普通命令自动改道标记。

项目 enable 遇到旧标记时，只在当前工作树完成开发设施升级：检查活动 Dev 会话和旧 MCP 连接，
保存旧标记并切换为新 manifest。活动连接未清理时给出具体原因，不强杀当前主开发会话。
此操作不扫描并改写账户内所有客户端配置，也不改变别的工作树。

普通命令不会因为新 manifest 自动进入 Dev。已有旧标记在显式 enable 升级前保留原开发机制，
因此新旧开发设施的识别必须分开：安装脚本可以识别两种布局，普通旧自动路由只认旧标记。
不能简单让旧 cwd 路由把新 manifest 也当成 enabled。对祖先旧标记或嵌套工作区的歧义直接报告冲突。

MCP 的普通连接与 Dev 连接均在生命周期内固定目标；enable 后需要刷新的旧连接明确标为未生效。
这属于开发者当前项目的准备过程，普通用户不需要迁移。

## 5 构建与请求隔离

Dev 工具校验实际程序、构建输入快照和实际 daemon 指纹。源码变化未重建、缺失或旧程序、错误 home、
错误 daemon、继承上下文冲突均明确失败，不回退到正式版充当验收结果。
内部子进程继承同一 Dev 目标，不能重新根据 cwd 选树。项目开发 server 可保持连接，验收时检查并委托本树新安装的构建。

每次验收拥有独立 ID、构建身份与终态。取消、超时、发起执行器退出和迟到回答不能成为另一次测试的答复。
结果重取不重发，拒绝错构建；附件归入该 Dev 的私有验收目录，保存后不受原文件后续修改影响。
保留已实现的有界留存、并发及附件预算，不把开发结果写进日常 `show_last` 或待办队列。

## 6 正式渠道转送

用户已选择保留正式渠道借用。拟定默认由正式版已有远程渠道转送，不要求每棵树另配 Dev channel。
纯本机弹窗及 Dev 自有渠道作为显式测试选项，不能因远程不可用而静默退成本机等待。
投递偏好属于当前工作树，不增加普通设置中的全局开关。

转送覆盖所有支持远程作答的 AskHuman 开发交互：验收问答、独立测试会话的问答、权限与 Stop。
不能仅实现 `dev_ask` 转送，就让其余交互停在本机弹窗。客户端自身的项目首次信任、登录等原生步骤单独报告。

启用与发起前检查正式版的所需能力及远程出口，投递失败向发起 Agent 返回明确状态。
不把配置中的 enabled 或平台接受发送等同于人类已收到。不让日常的本机活跃槽阻断显式远程转送；
对权限／Stop 等同步交互，还须处理日常通知延迟导致请求超时的情况。即时提醒限定于该次显式 Dev 投递，
不改变正式日常请求的空闲门槛或默认通知策略。

正式版仅处理本次开发请求的受限投递：验证请求关联、工作树、构建、有效期与授权；使用自己已有的渠道连接，
将回答和附件回传 Dev。权限决定、记忆范围和 Stop 后续动作均由原 Dev 会话处理，正式版不代为执行。
它不接管测试会话，不执行日常待办，不给 Dev 日常会话控制能力，不复制生产凭据。
临时转送状态有界且与普通历史分开；没有显式开发请求时，日常路径沿用原行为。

正式版不支持所需内部投递能力时，报告需要兼容正式版，不替换正式程序、不触发错误的 daemon 互顶、
不把普通提问伪装成开发转送，也不擅自降级为其他投递方式。

借用正式渠道只证明转送链路。验收渠道实现本身仍使用 Dev 专用 bot／独立配对；验收 Mac 弹窗外观仍需实际 Dev 窗口。

正式渠道的连接始终由正式 daemon 唯一持有。各 Dev 经本机 IPC 委托投递，不读取正式凭据，
不为同一个正式 bot 另建连接。请求、回答和取消按独立 ID 对应。

修改渠道实现时，主开发沟通继续走稳定正式端；真实验收请求明确投到 Dev 自身的测试渠道，
不走正式代理作为成功路径，也不在失败时自动回退正式渠道。使用已有预设前检查独占租约，
不同 Dev 并行连接需不同测试身份，不得复用正式 bot。无法配置专用渠道时可完成单测和模拟，
但真实渠道验收保留未完成状态。被测渠道故障由独立的正式沟通路径报告。

修改正式端转送实现时，另起私有 home 的测试转送端并使用测试渠道；不能为了验收候选代码替换正在沟通的正式 daemon。

## 7 独立 Agent 测试会话

保留独立 profile，用于验证 MCP、生命周期、权限、Stop、恢复、Watch、插话与子任务继承。
profile、认证和 Hook 仅放在 `.askhuman-dev/clients/` 及本工具拥有的测试工作区内，不改用户级集成。

项目开发主会话与完整测试会话是两个环境：前者的日常 AskHuman 属于正式版，后者所有受测入口属于同一 Dev。
测试启动器不能把主会话项目 MCP、日常 Hook 或开发例外再次加载进测试 profile，导致原生调用逃回正式版。
按各客户端已验证的隔离参数和中性工作区策略启动；无法保证时限制能力，不借机写全局配置。
不复制认证；首次登录由用户在该私有 profile 中完成。新建／Fork 继承测试 profile，无法确认归属时拒绝。

保留当前客户端能力限制：Claude／Codex CLI／Grok／Pi 按实际隔离能力开放；Cursor 与 Antigravity
的项目 MCP 能力不等于完整原生会话隔离能力，不能因此直接开放未验证的启动器。

## 8 开发界面与安装

普通设置页删除开发测试 tab、路由迁移、重试和回退入口。
需要图形界面时，由仓库开发命令打开仅属于本树 Dev 的工作台，展示构建、投递偏好、测试 profile 和 Dev 窗口入口。
它不托管在正式 GUI Host 中，不提供修改日常集成的按钮。Dev 卡片与窗口继续明确显示开发身份。

工作树安装只更新本树程序，正式安装保留原有用途，不注册新的全局开发状态。
开发机制通过显式项目入口启用；构建选项及打包检查确保普通发布不暴露开发设置、开发 MCP 工具或开发规则。
正式版新增的开发支持仅为渠道转送所需的内部协议能力。安装后继续按仓库规范验证新程序，不能仅测试工具本身。

## 10 验收门槛

1. 普通发布的规则、MCP 普通工具、设置及默认流程与本任务前一致，不新增本方案的开发入口或迁移要求；原有开发设施保留旧标记的兼容路径。
2. 对真实全局配置做内容及权限快照；项目 enable、安装、验收、重连、清理后保持不变。
3. 原生客户端实际加载项目规则和 `askhuman-dev`；其他项目不出现它；保留自定义项目配置，重启要求清晰。
4. 新旧开发标记切换、两个工作树、子目录启动、server cwd 不可靠、旧程序和 stale build 均有真实进程回归。
5. 同一主开发会话普通／Dev／普通分别到达正式／Dev／正式，答案回到原调用，普通历史与待办不串入测试。
6. 不配 Dev channel 时，问答、权限与 Stop 都可由正式远程出口回答；本机活跃槽、通知延迟、断线、旧正式版、取消、超时、重启、附件和迟到回答均有明确结果。真实渠道与配置模拟分别记录。
7. 私有测试会话的所有受测入口固定 Dev，不读取或改写日常原生会话；项目开发配置不污染测试 profile。
8. macOS、Linux、Windows 完成适用编译与自动化；原生图形和登录后 Agent 会话依实际证据记录，不以 CI 代替。
