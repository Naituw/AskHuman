## 1. 背景与目标

**背景**（实测，出处 [同步流量收敛 §9](ios-traffic-reduction.md#9-实测2026-11-21)）：

- 同步流量收敛落地后，**附件分块占落地后总字节的约 92%**：附件约 167 MiB/天（两端合计），同步约 12.5 MiB/天；11 月到 11-21 已计费 1.67 GB。EMQX 每月免费 1 GiB，成本红线是「消费上限保持 0」（[总览](../overview-ios.md#不变量与注意点)「成本红线」）。
- 手机每打开一张图，EMQX 上是文件大小的约 **3.56 倍**：字节先 base64 放进 JSON 明文（×1.33），加密后密文再 base64 放进信封（×1.33），合起来 ×1.78；EMQX 对「发布」与「投递」各计一次，再 ×2。查看器还会同时去取左右相邻页的原图。
- 这台 Mac 上还读得到的 81 个不同图片文件（共 179.5 MB）：中位约 1.7 MB、p90 约 5.3 MB、最大 7.1 MB；74 个 PNG（界面截图、设计稿）、7 个 JPEG；≥ 1 MB 的 56 个占字节 94%，< 400 KiB 的 12 个只占 1.6%。
- iOS 通道发过 81 次附件，其中 25 次是此前发过的相同内容（至少 31%：另有 13 次的文件已删，没法比对；只算还读得到的 68 次，是 37% 的次数、约 47% 的字节）。手机按 `assetId` 缓存，而每条请求的 `assetId` 都是新生成的，所以同一份内容出现在新请求里就要重新下载。Mac 没有按来源的计数，分不开「重复下载」到底有多少，所以才要加本地计数（AT5）。

**目标**：把整月用量压回 EMQX 免费的 1 GiB 以内（按 §10 的估算约 0.58 GiB），同时：

1. 看图仍然清楚：界面截图和设计稿至少看得清整体；要看细节随时能拿到原图（AT1）。
2. 分享、拖出、保存拿到的永远是原文件（AT3）。
3. 旧手机、旧 Mac 的互通一点不变（§8）。

**非目标**：见 §12。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 原图（original） | Agent 附带的原文件，按现在的方式原样分块下发 |
| 预览（preview） | 手机要的时候 Mac 现做的派生图：AVIF，长边 ≤ 1600 px，固定质量 76。只在 Mac 内存里，不落盘 |
| 变体（variant） | `asset.get` / `asset.chunk` 里说明传的是预览还是原图的字段（AT14）；缺省 = 原图 |
| JSON 信封 / 二进制信封 | 现在的信封（JSON + base64）/ 以字节 `0xA1` 开头、字段按字节排布的新信封（§5.1） |
| blob 帧 | 明文不是 JSON、而是「头 JSON + 原始字节」的格式，只给 `asset.chunk` 与 `upload.chunk` 用（§5.2） |
| 内容哈希 | 原文件整体的 SHA-256（小写十六进制），线上是 `AssetRef.sha256` |
| 能力位 | `Hello.binary`、`Caps.binary`、`Caps.assetPreview`；对端声明了才用（§5.3） |

## 4. 用户视角

- **打开一张图**：点附件里的图片，查看器先显示**预览**——同一张图的整体画面，约 75 KB（Mac 现做约 0.3 秒，再加传输），比下载几 MB 的原文件快得多。左右滑到相邻页，同样只取预览。
- **看细节**：当前页是预览时，工具栏多一个「原图 · 7.1 MB」按钮（大小是原文件的）；点它下载原图并**原位替换**，下载时按钮显示进度，好了就消失；失败沿用查看器现有的错误提示与重试。
- **分享、拖出、保存**：永远是原文件。原图还没在手机上时，点分享先下载原图（带进度），好了再打开分享面板；拖出沿用现在的行为（接收方来要文件时才下载原图）。
- **不做预览的图**：小于 400 KiB 的、GIF 等动图、带透明像素的、Mac 解不开的（如 HEIC）：和现在一样直接是原图，没有「原图」按钮。
- **已经有原图的**（之前下载过）：直接显示原图，没有按钮。
- **同一份内容再次出现**（Agent 又发了同一个文件，`assetId` 是新的）：手机按内容哈希认出，不再下载。
- **旧 Mac / 旧手机**：和现在一样（§8）。没有设置开关。
- 非图片附件（文本、代码、PDF 等）、请求里的缩略图、会话历史卡片上的缩略图都不变。

## 5. 线协议

Rust `ios/wire.rs` · `envelope.rs` 与 Swift `AHProtocol` 同一批改动、共用 `ios/Fixtures/wire-v1/`（§5.6）。JSON 键 camelCase，可选字段缺省不发。

### 5.1 二进制信封

```
偏移  长度  内容
0     1     魔数 0xA1
1     1     flags：第 0 位 = 明文是 raw DEFLATE（相当于现在的 `z:1`）；第 1–7 位必须为 0
2     2     kid，u16 大端
4     16    发送方 id 的 16 个原始字节
20    12    nonce
32    n+16  密文 ‖ Poly1305 标签
```

- 首字节 `0xA1` 不可能是 JSON 的 `{`（0x7B），也不是合法 UTF-8 的开头，接收方凭它区分两种信封；以 `{` 开头照旧按 JSON 信封解析。
- **加密语义不变**：ChaCha20-Poly1305、同一把方向密钥、同一个 nonce 规则；AAD 沿用文本串 `ah1|<主题>|<发送方>|<kid>`（压缩时末尾追加 `|z1`，推送域是 `ah1|push|…`），其中发送方由 16 字节重新编码成 26 位小写 base32。所以现有测试向量里的密文照样能打开，压缩位同样受认证。
- 固定部分 32 字节加 16 字节标签；JSON 信封的固定部分约 76 字节，密文还要再 base64（×1.33）。
- 压缩位的规则与 [同步流量收敛 §3.3](ios-traffic-reduction.md#33-c消息压缩mac手机) 完全一致：只有 Mac→手机、只有列表类消息、只有手机声明了 `compression`；手机发给 Mac 的信封带压缩位 = 畸形、拒收；推送信封永远是 JSON、永远不压缩；解压后明文 ≤ `MAX_PLAIN_BYTES`（512 KiB）。
- 严格解析：总长 ≥ 48 且 ≤ `MAX_ENVELOPE_BYTES`（900,000）；魔数不对、flags 有未知位、截断一律是畸形，静默丢弃、照旧只记「被拒」计数。
- **仍是 JSON 的三处**：配对通道（票据密钥，发生在协商之前）、presence（本来就是明文 JSON，不是信封）、推送信封（走 APNs 载荷，通知扩展只认 JSON 信封）。配对通道与推送的接收方不接受二进制信封。

### 5.2 blob 帧

只有两种消息可以用：`asset.chunk`（Mac→手机）与 `upload.chunk`（手机→Mac）。明文是

```
0x01 | 头长度（u32 大端） | 头 | 原始字节
```

- **头**是现在明文的 JSON `{"i","t","ts","b"}`，其中 `b` 里**没有 `data`**（`asset.chunk` 的 `b` 是 `assetId, index, total, size, sha256?, variant?`；`upload.chunk` 的 `b` 是 `uploadId, index`）。字节放在尾巴上，不再 base64。
- 接收方看解密后明文的首字节：`{` 是 JSON 明文，`0x01` 是 blob 帧，其它一律畸形。类型注册、按 `i` 去重、按 `ts` 的重放窗口、按 `t` 的流量台账都不动。
- 严格解析：明文 ≥ 5 字节；头长度 ≤ 4 KiB 且不超过剩余长度；头必须是合法的 `{i,t,ts,b}`；`t` 只能是上面两种，且 `b` 里不得出现 `data`；原始字节 ≤ `ASSET_CHUNK_BYTES`（192 KiB）；整份明文 ≤ `MAX_PLAIN_BYTES`。头长越界、尾部长度不符、截断都当畸形帧丢弃。
- 两种消息的 JSON 形式（`data` 为 base64）继续有效：没协商的对端收到的与今天逐字节相同。
- blob 帧不压缩（AT15）。

### 5.3 协商

| 位置 | 字段 | 语义 |
|---|---|---|
| `hello`（手机→Mac） | `binary: bool`（缺省 false，false 时不发） | 手机能打开二进制信封与 blob 帧 |
| `hello.ack` 的 `caps`（Mac→手机） | `binary: bool`（同上） | Mac 能打开二进制信封与 blob 帧 |
| `hello.ack` 的 `caps` | `assetPreview: bool`（同上） | Mac 会按 `variant: preview` 生成并发送预览 |

- **Mac→手机**：以手机**最近一次 `hello`** 为准（与 `compression` 一样不持久化）；手机下线（presence 变 offline）时随 `hello_at` 一起失效，下一次 `hello` 重新给。手机在 `hello` 里已经声明了，所以对这个 `hello` 的 `hello.ack` 与随后的快照就可以是二进制信封（新手机两种格式都认）。
- **手机→Mac**：以**本次握手**的 `hello.ack.caps.binary` 为准；`hello` 本身与握手完成之前一律发 JSON，每次握手开始时「对方懂二进制」重置为否；多台 Mac 各自独立。
- 对方没声明，或 AT16 的条件不满足，就发 JSON 信封；接收方永远两种都认。没有任何协商之外的降级路径。

### 5.4 附件字段

| 位置 | 字段 | 语义 |
|---|---|---|
| `AssetRef` | `preview: bool`（缺省 false，false 时不发） | 这个文件可以要预览（Mac 按类型与大小判断，AT10）；运行时仍可能回原图 |
| `AssetRef` | `sha256: string?` | 原文件整体的 SHA-256（小写十六进制）；只给请求附件、非 `tooLarge`（AT13）。手机的缓存键 |
| `asset.get`（手机→Mac） | `variant: string?` | `preview`；缺省 = 原图；Mac 不认识的值按原图 |
| `asset.chunk`（Mac→手机） | `variant: string?` | 实际发出的是哪种（`preview` 或 `original`）。**只在 `asset.get` 带了 `variant` 时回显**；不带 `variant` 的原图请求，回的 chunk 与今天逐字节相同 |

- `asset.chunk` 的 `index` / `total` / `size` 都按**实际发出的那份字节**算（预览就是预览的字节数和块数）；`sha256`（首块）的含义不变：实际发出那份字节的整体哈希，手机用它校验。
- 手机要预览但收到 `variant: original`（AT10 的运行时回退）时照单收下，当原图缓存，工具栏不再出现「原图」按钮。
- 旧 Mac 对 `asset.get.variant` 与 `Caps` 之外的新字段一概忽略（`wire.rs` 没有 `deny_unknown_fields`），所以新手机即使误发也只会拿到原图。

### 5.5 不动的东西

`PROTO`（手机线协议）、`PROTOCOL_VERSION`（本机 IPC）、恢复存储与它的 SQL 夹具、消息类型注册（没有新消息类型）、令牌桶、`MAX_ENVELOPE_BYTES` / `MAX_PLAIN_BYTES` / `ASSET_CHUNK_BYTES` / `MAX_ASSET_BYTES` / `MAX_ASSET_CHUNKS_PER_GET` 等限额常量、`THUMB_MAX_BYTES`。附件仍只能取登记过的文件、单个 ≤ 10 MiB。

### 5.6 夹具

`ios/Fixtures/wire-v1/` 只**追加**，既有样本原样保留：

- `crypto.json`：二进制信封向量（由 Rust 用固定密钥与固定 nonce 生成，二进制是确定的，两边逐字节比较；含压缩位那一条按「能打开」比较，同 `compressedEnvelopes`）、blob 帧向量（含 AAD 绑定主题）、一组畸形二进制信封与畸形 blob 帧（两边都必须拒收）。
- `messages.json`：带 `binary` 的 `hello`、带 `binary` / `assetPreview` 的 `hello.ack`、带 `preview` / `sha256` 的 `AssetRef`、带 `variant` 的 `asset.get` 与 `asset.chunk`（带与不带各一条）；证明缺省字段不进 JSON。

## 6. Mac 端行为

### 6.1 二进制收发（`ios/envelope.rs`、`ios/gateway/mod.rs`）

- 发送（`send_value`）：手机已握手（`hello_at` 有值）、最近一次 `hello` 带 `binary`、AT16 的条件满足 → 封成二进制信封；`asset.chunk` 同时用 blob 帧。否则与今天完全一样。按实际发出的字节计台账与 `trafficBreakdown`，自动受益。
- 接收（`open_up`）：JSON 信封与二进制信封都认；blob 帧只接受 `upload.chunk`，其它类型的 blob 帧是畸形。解析入口分「配对通道只认 JSON」与「主题上两种都认」。

### 6.2 建请求视图（`ios/views.rs`、`ios/history_view.rs`）

- 请求附件（`asset_for`）：对非 `tooLarge` 的文件读一次，算 `sha256`（同时记进 `AssetSource`，生成预览时核对，AT19）；图片再按 AT10 的类型与大小设 `preview`。历史里的图（`picture_ref`）按同一规则设 `preview`，不算哈希（AT13、AT17）。读不到（文件刚被删）就不带 `sha256`。
- 建视图（`ask_view`）本来就在阻塞上下文里做：它已经为请求里前 `MAX_REQUEST_IMAGES`（20）张图整份读取、解码并做缩略图；其余图片和所有非图片附件现在不读文件。加哈希后，每个非 `tooLarge` 的附件都要整份读一遍（≤ 10 MiB；SHA-256 约 3 GB/s，主要成本是磁盘读取）。附件很多的请求建视图会慢一点，实现后量一次再决定要不要给哈希设一个文件数上限（§15）。

### 6.3 取图（`ios/gateway/assets.rs`）

`on_asset_get` 解析 `assetId` 的顺序不变（待答请求 → 网关的历史图缓存 → `Host::history_picture`），拿到 `AssetSource` 后：

1. `variant` 缺省或不认识 → 原图，行为与今天一字不差。
2. `variant: preview` 且这个文件按 AT10 可做预览 → 经 `spawn_then` 在阻塞线程里取或生成预览（§6.4、§6.5），再按预览的字节分块发送，`asset.chunk` 回显 `variant: preview`；`index` / `total` / `size` / 首块 `sha256` 都按预览字节。
3. 运行时发现不能做（透明、动图、解码失败或超限、预览不比原图小、原文件的哈希与建请求时记下的不同，见 AT19）→ 发原图，回显 `variant: original`；不是错误。
4. 原图仍须 ≤ 10 MiB（超过的今天就回 `tooLarge`，这一版不变）。窗口规则（`from` / `count ≤ 8`）、`notFound` / `tooLarge` / `internal` 错误不变。

### 6.4 预览生成

输入是原文件（≤ 10 MiB）读一次；输出是一个 AVIF 文件：

0. 建请求时记下了 `sha256` 的文件（请求附件），对读到的字节算 SHA-256 并比较，不同就放弃（AT19）。
1. 解码（`image`：PNG / JPEG / WebP），应用 EXIF 方向；解码有内存上限，超限按解码失败。
2. 检查：带 alpha 通道时扫描像素，真有透明就放弃；动图放弃（AT10）。
3. 长边 > 1600 px 时用 Lanczos3 缩到长边 1600（保持比例，不放大）；非 sRGB 的 ICC 先转成 sRGB（AT11）。
4. 编码：`ravif`，4:4:4，质量 76，速度 6，开 `threading`、不用汇编（构建机没有 nasm）；常量集中放在一处。
5. 结果字节不小于原文件就放弃。

**代码放哪、怎么编译（AT20）**：步骤 1–5 放进一个独立的 crate（路径与名字实现时定，§15），对外只有一个非泛型函数，进出的都是字节和普通结构体，`image` 的图像类型、`ravif` 的泛型与迭代器都不出这个 crate。`Cargo.toml` 里对这个 crate 和它依赖的编解码 crate（`rav1e`、`ravif`、`image`、`png`、`zune-jpeg`、`moxcms`、`rayon` 等，清单实现时用 `cargo tree` 定）在 `release` 与 `local-install` 两档各设 `opt-level = 3`。两处缺一不可，原因与实测见 §10.3：被调用的泛型代码会实例化在调用方的 crate 里，编码调用若写在主 crate（`z` 或 0），整个编码器就按主 crate 的等级编译，依赖设成 3 也救不回来；反过来只设这个 crate、不设它的依赖，解码与缩放仍是慢的。

### 6.5 缓存与并发（AT12）

- 缓存键 = 路径 + 大小 + 修改时间（文件变了就不命中）；值是预览字节，或「这个文件做不了预览」的结论（同一文件不重复尝试）。几十个条目、几十 MiB 封顶，满了丢最旧的；不落盘；Daemon 重启即清空。
- 同一个键的并发请求共享一次生成（后来者等同一个结果）；生成在阻塞线程里，网关的其它消息不受影响。同时在做的预览数有上限（§15）。
- 一次 `asset.get` 常常是三张图一起来（查看器同时开当前页与左右相邻页），每张各自生成。

### 6.6 本地计数（G，AT5）

沿用已实现的 `TrafficBreakdown`（[T6](ios-traffic-reduction.md#7-决定)，只存本机、只进 `AskHuman channel ios status --json`、不上线）。要能直接读出下面几个数（键名实现时定；要求同一字节只算进一个键，各键之和等于现有的 `out:asset.chunk` 总量）：

- 预览分块与原图分块各自的条数与字节；
- 其中「同一部手机已经完整取过同一份内容」的重复取的条数与字节（请求附件按 `sha256`、历史图按 `assetId` 判断；记忆只在内存里、有上限、重启即清空）；
- `asset.get` 按来源分开：待答请求的附件 / 历史里的图。

手机一侧没有单独的计数（与 T6 一致）。

## 7. 手机端行为

### 7.1 引擎（`AHProtocol`、`AHCore/PhoneEngine*`）

- `hello` 带 `binary: true`（`hello` 自己是 JSON）；每台 Mac 在 `hello.ack` 后按 `caps.binary` 决定发什么格式；握手前、断线后不用二进制。`upload.chunk` 在协商后用 blob 帧。收到的信封与 blob 帧两种都认。
- 下载（`PhoneEngine.download(macId:asset:progress:)`，经 `Backend` 协议与 `AppStore`，`MockBackend` 同步）的 `downloads` 从按 `assetId` 分键改成按「`assetId` + 变体」分键：同一 `assetId` 的预览与原图可以同时在途；每个 `asset.chunk` 靠回显的 `variant` 归位（没有 `variant` 的 chunk 属于原图）。Mac 对预览请求回成原图（回显 `original`）时，这次下载就当原图收完；同一资产的原图下载已经在途时两者并成一次，到了的原图同时满足等着预览的一方。
- 取哪种变体由调用方决定：**查看器**在 `AssetRef.preview` 与 `Caps.assetPreview` 都为真时要预览；**分享、拖出（`downloadForExport`）、保存、非图片文件**一律原图。
- 缓存（`config.assetDirectory`）：预览与原图各一份，已有原图时预览请求直接用原图；`AssetRef.sha256` 存在时先按哈希找缓存（预览也按原文件哈希），命中就不发 `asset.get`；哈希缓存的诚实规则见 AT19。已有的按 `assetId` 命名的缓存文件继续有效。
- 预览解不开 → 自动改取原图（AT18）。

### 7.2 查看器（`ios/AskHuman/Views/Attachments/` 下的 `ImageGallery.swift`（`ImageGalleryViewer`）、`ImageViewers.swift`（`ZoomableImage`）、`AssetViews.swift`）

- 每页先取预览；当前页是预览且原图还没在手机上时，工具栏有「原图 · <大小>」按钮（`accessibilityIdentifier` 实现时定）：点了下载原图（显示进度），到了原位替换并去掉按钮。相邻页只取预览。
- 现在工具栏的 `ShareLink` 分享的是 `arrived[assetId]`，也就是已下载的那一份；换成预览之后它**必须分享原文件**：没有原图时先下载（带进度）再进分享面板。
- 保存、拖出沿用现有路径（始终原图）。
- 会话历史卡片与「历史」标签详情页里的图用同一个查看器，行为相同（AT17）。
- 查看器的布局（整张 sheet 大小的 `GeometryReader`、`ZoomableImage` 的 `contentInset`）一行不动；只换图的来源与工具栏的一个按钮。

## 8. 兼容

| 组合 | 表现 |
|---|---|
| 旧手机 + 新 Mac | 手机的 `hello` 没有 `binary`：Mac 发 JSON 信封；手机不发 `variant`：Mac 发原图；`AssetRef` 多出的 `preview` / `sha256` 被旧手机的解码忽略 |
| 新手机 + 旧 Mac | `hello.ack` 没有 `caps.binary` / `assetPreview`：手机发 JSON 信封、要原图；`AssetRef` 没有 `preview` / `sha256`：缓存仍按 `assetId`。旧 Mac 对多出的 `hello.binary` 与 `asset.get.variant` 一概忽略 |
| 新 + 新 | 全部生效 |
| 旧 + 旧 | 现状 |

同一个手机线协议号 `PROTO = 1` 下，一台 Mac 本来就可能服务不同构建的手机（反之亦然），所以「同号」必须继续意味着「能通话」：任何新能力对端没声明就关闭，没有新的必要字段，没有新的消息类型。

## 9. 隐私与安全

- **加密与密钥不变**。封装格式本身不在认证范围内，但它承载的一切——主题、发送方、`kid`、压缩位（AAD）和消息体（含 `i` 与 `ts`）——都受认证；把同一份密文换一种信封格式重投，得到的是同一条消息，被按 `i` 的去重挡住。
- 解析严格（§5.1、§5.2）；解压上限不变；blob 帧头长度有上限；畸形一律静默丢弃，不记内容。
- 预览是 Mac 内存里的派生物，不落盘；它由像素重新编码，**不带原图的 EXIF（含位置）**；它与原图内容同属一条请求，没有新增暴露面。
- 预览生成吃的是 Agent 指给 Mac 的文件：解码有内存上限，超限按失败处理，防图片炸弹；同时在做的预览数有上限。
- `AssetRef.sha256` 把原文件哈希告诉手机；手机本来就会收到文件内容，broker 只见密文，没有新增暴露。
- 附件的访问规则不变：只能取登记过的文件（待答请求的附件、历史里记过的图）、单个 ≤ 10 MiB。

## 10. 预期效果与实测依据

### 10.1 一张图的流量

典型的 3 MB 截图，EMQX 计费（发布 + 投递各一次）：

| | 手机收到 | EMQX 上合计 |
|---|---|---|
| 现在 | 3.0 MB × 1.78 | 约 10.7 MB |
| 只做二进制（D） | 3.0 MB × 约 1.00 | 约 6.0 MB |
| 预览 + 二进制（要预览时） | 约 75 KB | 约 0.15 MB（−98.6%） |
| 预览 + 点了「原图」 | 75 KB + 3.0 MB | 约 6.2 MB（比现在少 42%） |

满块（192 KiB 原始字节）在线上：JSON 信封约 350 KB → 二进制 blob 帧约 197 KB（×1.78 → 约 ×1.00，−44%）。同步类消息只去掉外层 base64，约少 25%，且没有哪种消息变长。

### 10.2 整月用量（估算）

输入：附件每天被取走的原文件字节 R ≈ 46.9 MiB（实测 167 MiB/天 ÷ 3.56）；同步 12.5 MiB/天（二进制后约 9.4）。**p** = 看过的图里还要再取原图的比例，没有数据，取 10%；**C** 取「重复内容的 25% 不再下载」（低于观察到的重复占比，因为只有之前看过的才在手机缓存里）；**s** = 预览字节占原图字节的比例，81 张实测 4.8%（≥ 400 KiB 的 69 张是 3.3%，加上 12 张原样发送的小图是 4.8%）。附件每天 = R × (1 − C) × (s + p) × 2。

| 方案 | 合计 MiB/天 | 整月 GiB（30 天） | 月费（超出 1 GiB 的部分 × ¥1.5/GiB） |
|---|---:|---:|---:|
| 现在 | 179 | 5.3 | 约 ¥6.4 |
| 只做 D（二进制，不做预览） | 103 | 3.0 | 约 ¥3.0 |
| **本规格：AVIF 1600 / q76 + C + D** | **20** | **0.58** | **0** |

对 p 的敏感度：p = 0% 约 0.37 GiB；10% 约 0.58；30% 约 0.99；100%（每张都看原图）约 2.4 GiB，仍比现在少一半以上。整月回到 1 GiB 以内，「消费上限保持 0」的红线就能守住（这只是结果，规格不涉及也不改 EMQX 的任何设置）；之后同步（约 0.27 GiB/月）反而成了大头，再往下压没有意义。AT2 的两个常量提高一档的代价：2048 px 整月多约 0.02 GiB，q85 约 0.01 GiB。

### 10.3 实测依据

- **语料**：这台 Mac 上还读得到的 81 个不同图片文件（74 PNG、7 JPEG，中位 1.7 MB）；≥ 400 KiB 的 69 个；81 张里 8 张带 alpha 通道（3 张真有透明像素）、8 张带 ICC、1 张带 EXIF 方向。
- **编码选型**（24 张抽样，每张调到与现在的 JPEG q75 同一 SSIMULACRA2 画质分，JPEG 基线分中位 79.9）：同等画质下相对 JPEG 的字节（中位 / 按字节加权）——优化 JPEG 0.86 / 0.89、HEIC（macOS 自带）0.67 / 0.69、WebP 0.53 / 0.57、AVIF（macOS 自带）0.52 / 0.56、**AVIF（rav1e，速度 6）0.45 / 0.50**、AVIF（速度 4）0.34 / 0.40（慢 2.2 倍、再小约 15%，不值）。HEIC 只有 macOS 能编；JPEG XL 没有成熟的纯 Rust 编码器，没测。
- **规格对比**（3 张真实附件，旧 JPEG 1600 q75 / AVIF 1600 q76 的 KB 与画质分）：页面截图 176 / 79.4 → 86 / 79.6；App Store 主图 214 / 81.2 → 103 / 78.9；竖图渐变 145 / 78.6 → 73 / 75.7。其余几档：1280 / q70 肉眼可见偏软，不建议；q85 约 +14% 字节、画质分高约 3 分；2048 px（q76）这 3 张上约 +34–44% 字节（81 张整体是 +27%，见下一条）。
- **字节比例**（81 张、实际编码，1600 px，≥ 400 KiB 的 69 张）：q76 预览合计是原图字节的 3.26%，中位 75 KB、p90 133 KB、最大 255 KB（只有这 1 张超过一个 192 KiB 的块）；q85 3.72%（×1.14）；2048 / q76 4.13%（×1.27）；2048 / q85 4.72%（×1.45）。
- **现做的耗时**（整条流水线：读文件 + 解码 + 转正 + Lanczos3 缩放 + AVIF 速度 6 编码；`ravif` 开 `threading`、不用汇编。这台 Mac 是 18 核（6 个性能核 + 12 个能效核），测的时候后台还有约 4 的负载。**下面这几条都是 opt-level 3 编译的数字**，仓库自己的两档不是，见紧随其后的「编译配置」一条）：
  - 81 张在一个进程里连着做：中位 0.27 s（≥ 400 KiB 的 69 张 0.28 s），p90 0.34 s，最大 0.45 s；解码中位 16 ms、缩放 32 ms、编码 208 ms。
  - 另取 12 张（≥ 400 KiB，0.4–7.1 MB，按大小均匀抽取），每张单独起一个进程，用 `RAYON_NUM_THREADS` 限线程数来模拟核少的机器：默认线程中位 0.33 s（0.22–0.46 s）；8 / 4 / 2 线程中位 0.48 / 0.62 / 0.92 s（2 线程最慢的一张 1.6 s）。CPU 总量（含进程启动）每张中位约 1.6–1.8 个核·秒、最大约 3.1，不随线程数变，只是铺开的时间不同。
  - 查看器同时要三页时（三个进程并发，4 组）：默认线程下三张都到齐的中位 0.62 s（最慢一组 0.77 s）；每个限 8 线程 0.70 s（最慢 0.77 s）；限 4 线程 0.93 s（最慢 1.06 s）。
  - 都在这台 Mac 上量的；没在真机上量，也没在真正核少的 Mac 上量过。
- **编译配置（AT20）**：仓库的 `release` 档是 `opt-level = "z"`，`local-install` 档（`./scripts/install.sh` 装机用）是 `opt-level = 0`，上面的数字却是 opt 3 量的。写规格时补测了这两档（一个一次性小工程，档位与仓库的定义一致；同一批 12 张图，每张每个配置各起一个进程、配置之间交替运行，所以后台负载对各配置一样，当时负载约 9–12）：

  | 配置 | 总耗时中位数 | 相对 opt 3 | CPU 核·秒（中位数 / 最大） |
  |---|---|---|---|
  | 全程 opt-level 3（对照，上面几条用的） | 0.31 s | ×1.00 | 1.9 / 3.2 |
  | `release` 原样（`z`） | 1.19 s | ×3.9 | 5.9 / 9.7 |
  | `release`，只给预览 crate 设 3 | 0.82 s | ×2.7 | 2.9 / 4.9 |
  | **`release`，预览 crate 与编解码依赖设 3（AT20）** | **0.32 s** | **×1.03** | **1.8 / 3.2** |
  | **`local-install`，同上（AT20）** | **0.31 s** | **×1.02** | **1.8 / 3.3** |
  | `local-install`，只给预览 crate 设 3 | 2.45 s | ×8.0 | 10.0 / 17.0 |
  | `local-install` 原样（0；另测的 4 张图，同批对照 0.26 s） | 5.4 s | ×21 | 44 / 57 |

  成因的另一组对照：依赖都设成 3 时，编码调用留在主 crate（`z`）里是 0.56 s（×1.8），主 crate 也改成 3 就回到 0.30 s；`panic = abort`、`codegen-units` 都没有影响。依赖留在 `z` 时，缩放一项从 46 ms 变成约 430 ms。结论：必须让预览代码自己所在的 crate 和它的依赖都按 3 编译（AT20）。
  构建代价（干净构建，各档位各一次）：`local-install` 档 6.9 s → 10.6 s（只在依赖第一次编译或清理后发生，增量构建不重编依赖）；二进制 `local-install` 档 5.8 MB → 1.8 MB（打开优化后反而更小），`release` 档 2.06 MB → 1.78 MB。这几个数是小工程的，真实工程里依赖与别的 crate 共用，实现时要重量（§15）。
- **哈希**：SHA-256 在这批文件上 3.2 GB/s（Python / OpenSSL，文件都在系统缓存里：81 个文件共 179.5 MB 约 56 ms，最大的 7.1 MB 约 2.2 ms）；Mac 的网关用 Rust `sha2`，没单独量，但 `serve_asset` 本来就对每次 `from == 0` 的 `asset.get` 整份算一遍 SHA-256。
- **解码（手机）**：macOS ImageIO 一张样图 22 ms；iOS 18.5 模拟器 ImageIO 解 `ravif` 产出的 AVIF：1600 px 约 15 ms、2048 px 约 22 ms（跑在 Mac 的 CPU 上，真机会慢几倍）。
- **固定质量的取舍**（24 张样本，固定 q76 对旧 JPEG q75）：字节是旧 JPEG 的 0.45（中位）/ 0.47（按字节加权），画质分中位低 0.3 分，13/24 张不低于旧 JPEG，最差低 7.4 分（照片拼图）；界面截图与设计稿往往高 3–4.5 分，照片、夜空、光晕渐变这类低 1–7 分。q80 是 20/24，q85 是 24/24（最差 −0.4、中位高 4.8 分）。画质分只衡量压缩损失，不含缩小损失。

## 11. 已知局限

- 预览是有损的 1600 px：放大看比原图软；固定质量在照片、渐变、夜空一类图上比旧 JPEG 低 1–7 分（AT2，Owner 知情并接受）。真机上看着不满意就改常量。
- 第一次要预览时 Mac 现做：中位约 0.3 s，核少的 Mac 更慢（限 2 线程模拟时中位约 0.9 s）；一张图约 1.8 个核·秒的 CPU，笔记本上会短暂占满几个核。这些数以 AT20 的编译配置为前提；不设的话，装机版（`local-install`）每张约 5 s、发布版约 1.2 s。
- 非 sRGB（如 Display P3）的图在预览里会截掉 sRGB 放不下的饱和色；原图不受影响。
- 超过 10 MiB 的图仍显示「太大」、不能下载（范围不变，见 §12）。
- 先在请求里看、之后在「历史」里再看同一张图，仍各下载一次（AT13）。
- 旧手机、旧 Mac 仍付现在的价钱；二进制与预览都要对端声明。
- 手机端缓存没有清理代码（现状，与流量无关）。

## 13. 验收标准

1. 协商后，满块 `asset.chunk` 在线上 ≤ 200 KB（现在 350 KB）；同样一批同步消息总字节少约 25–30%，没有任何一种消息变长；没协商的对端收到的与今天逐字节相同。
2. 点开一张 ≥ 400 KiB 的 PNG / JPEG：手机只收到预览（AVIF、长边 ≤ 1600、通常几十到一百多 KB），没有下载原图；当前页工具栏有「原图 · <大小>」。
3. 点「原图」：下载并原位替换，哈希与 Mac 上的原文件一致，按钮消失；失败有错误与重试。
4. 分享、拖出、保存拿到的字节与原文件逐字节相同；原图还没下载时分享先下载再打开面板。
5. 不做预览的图（小图、动图、带透明像素、解不开的、预览不比原图小）：发原图，查看器没有「原图」按钮；Mac 回 `variant: original` 时手机照单收下。
6. 查看器相邻页只取预览。
7. 同一份内容出现在两条请求里（`assetId` 不同、`sha256` 相同）：第二次不发 `asset.get`，预览也一样；`AssetRef.sha256` 与实收哈希不符时不进哈希缓存；建请求之后原文件被改过的，Mac 发原图并回显 `original`，不会有预览进哈希缓存（AT19）。
8. 预览解不开时自动改取原图，不弹错误。
9. 兼容矩阵四格（旧 / 新手机 × 旧 / 新 Mac）各有一条端到端用例通过；`PROTO`、`PROTOCOL_VERSION` 不变；既有夹具原样保留、新夹具两边通过。
10. 畸形帧（§5.1、§5.2 列的每一类）被丢弃，既不崩溃也不影响后续消息。
11. 生成预览期间网关的其它消息照常收发；同一文件的并发请求只生成一次。
12. `AskHuman channel ios status --json` 的 `trafficBreakdown` 能读出 §6.6 的几个数。
13. 真实 Mac + 手机（或模拟器）上，一张典型 3 MB 截图打开一次，台账里的流量增量与 §10.1 同量级（预览约 0.15 MB 而不是约 10.7 MB）。
14. 深色、最大字号、iPad、VoiceOver 下查看器的行为不退化（既有 UI 用例全绿，加预览 / 原图的新用例）。
15. 用 `./scripts/install.sh` 装出来的 Mac 版本（`local-install` 档）和 `release` 档构建，一张典型图（≈ 3 MB 的 PNG 截图）从 `asset.get` 到达到预览发出，耗时与 §10.3 全程 opt 3 的数同量级（不超过约 1.5 倍），CPU 总量没有成倍增加（AT20）。

## 17. 实现与规格的差异

2026-11-21 实现完成后补。逐阶段的记录、测量与对照实验在[计划的「实施记录」](../plans/ios-attachment-traffic.md#实施记录)；下面只列实现与上文写法不同的地方，以实现为准：

- **AT19 的核对挪到「用的时候、按请求」**（§6.4 第 0 步）：缓存与合并按文件身份（路径 + 大小 + 修改时间），同一个身份下可以有记着不同 `sha256` 的请求，所以比对放在每个等待者拿结果的那一刻；可观察的行为与第 0 步相同。「做不了预览」的结论仍被记住，但不记原因。
- **AT20 的配置**：`local-install` 继承 `release` 的包级覆盖，清单只写一份（51 项），不是两份；另外给 `src-tauri/Cargo.toml` 加了 `[workspace]`（预览 crate 是成员与默认成员，`vendor/*` 在外），否则 `cargo test`、`clippy` 覆盖不到它。
- **计数**（§6.6）：`TrafficBreakdown` 多一个 `assets` 视图，七个固定键：`chunk.preview`、`chunk.preview.repeat`、`chunk.original`、`chunk.original.repeat`、`get.request`、`get.history`、`get.unresolved`；`kinds` 原样不动，四个 `chunk.*` 之和恒等于 `kinds["out:asset.chunk"]`。「重复」指这部手机已经被发完过同一份内容、同一类（预览或原图）的全部块；Mac 看不到手机是否真的收到，所以可能偏高。`get.*` 数的是网关处理了的 `asset.get`。
- **手机缓存**（§7）：哈希索引就是缓存目录本身（`<sha256>`、`<sha256>.preview`，同一份字节的第二个名字是硬链接）；同一个请求里内容相同的两个附件同时在途时各取一次。
- **查看器**（§7）：预览直接读引擎的缓存文件，不拷成 `.avif`；原图下载失败用 `.alert`（标题、「重试」「取消」），预览与按钮留着，而不是整页错误——这是对「沿用现有错误提示与重试」的一种读法；辅助功能字号下按钮只写「原图」，大小留给 VoiceOver（`accessibilityLabel` 始终带大小）。
- **线协议**（§5）：`AssetChunk.data`、`UploadChunk.data` 解码时缺省为空，序列化规则不动；blob 帧的头部是「消息去掉 `data` 键」，空文件仍发一块零字节的数据。
- **没做**：给 `sha2` 及其依赖（`digest`、`block-buffer`、`crypto-common`、`generic-array`、`cpufeatures`）设 opt 3（装机版里算附件哈希会快约 13 倍，但超出 AT20，留给 Owner 决定）；出 Mac 版本与 TestFlight 构建；真机核验（§15）。
