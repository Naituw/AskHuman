# Daemon 即时换新与在途请求恢复

用户决定及体验目标见 [实施计划](../plans/daemon-live-update.md) §2。本文定义恢复路径，
旧协议客户端的让位、显式停止和强制操作继续参照 [优雅排空](daemon-graceful-drain.md)。

## 请求与调用身份

CLI 在提交前生成调用 UUID 和独立恢复密钥。首次提交、未收到 Accepted 的重试、
收到 Accepted 后的重连均使用同一身份。Daemon 保存密钥哈希、完整原始任务、规范化后的
展示载荷、创建时间、等待关系、胜出答案和最终结果。

一张题卡可有多个合流调用。每个调用独立取消和领取结果，最后一个真实等待者离场且尚无
人类决定时才取消题卡。短暂 IPC EOF 保留等待关系。存活证明包含 PID 和操作系统进程
创建标识，以识别 PID 复用。CLI 析构时额外写私有取消标记，daemon 暂不可达时仍可接收取消。

同一存活 CLI 只输出一次终态，原 stdout 格式、stderr 和退出码沿用既有契约。
未领取结果保留到等待者取消或确认交付，已交付结果至少保留到原五分钟重放窗口结束。
重启后的内容重放沿用原终态时间。手机提交回执按既有 journal 的数量和三十天期限保留。

## 私有恢复存储

`state/requests.sqlite3` 使用 SQLite 事务与 `synchronous=FULL`，目录权限 0700、文件 0600。
当前保存格式为 schema 5，依序包含请求/调用/渠道检查点、元数据/手机回执、终态时间、
调用方进程创建标识，以及早期恢复数据库缺失的取消记录表和调用属性修复。
每次迁移在事务内完成；已有版本的迁移不能代替新的迁移，数据库结构变更必须增加版本，
并回归已有数据库升级后的待答题、已答结果和渠道检查点。遇到高于本程序支持的格式保留原数据并重试恢复。

| 记录 | 权威内容 |
| --- | --- |
| requests、completed | 原题、展示载荷、首个可靠决定、不可变终态及时间 |
| calls、cancelled_calls | 恢复凭证哈希、合流关系、调用方、取消与交付事实 |
| checkpoints | 渠道路由、原卡、逐题进度、选择、文字、附件事件及已处理事件 |
| receipts | 手机 clientMsgId、手机与载荷哈希、已接受回执 |
| metadata | Popup 宿主租约、iOS 通知和上传、Telegram 消费位置、daemon 自持消费状态 |

受理成功以前保存调用，确认答案成功以前保存首个决定。手机答案和对应接受回执在同一
SQLite 事务中提交。保存失败时保留原题和提交等待，程序重试。暂时失败只写内部日志，
用户继续在原界面看到简短更新或重连状态。

历史以请求 ID 去重。恢复后的回复图片沿用确定路径并核对原字节，避免重复生成文件。
待办交付在首个决定内保存，恢复跳过重复物化，出队按原待办身份执行。
更新交接必须等待已经开始的决定完成指令、权限记忆、渲染和终态保存。

## 恢复协议与兼容

`StatusInfo.recoveryVersion` 为带默认值的可选能力，当前为 1。支持端先读取 Status，
只有能力匹配才发送 `ClientMsg::Recover`。恢复信封独立版本化，操作包括 Submit、Resume、
Cancel、Delivered，以及共享和独立窗口的恢复认证。响应使用 `ServerMsg::Recovery` 信封。

协议号仍为 5。旧 daemon 不声明能力，因此新客户端走旧入口。旧客户端发送原有消息，
新版服务只向已经使用恢复入口的连接返回恢复信封。窗口更新事件只在全部在途窗口均
具有恢复租约时发送，旧窗口不会收到新增枚举。今后扩展信封内容时继续按恢复版本协商，Task 语义不兼容时也必须调整恢复版本。
旧 Hello 的严格协议号和多安装 hold 规则继续适用。

目标程序通过隐藏的 `--recovery-capabilities` 输出恢复版本与 schema 范围，交接前由旧
服务验证。恢复连接依据稳定能力重连，并使用 ReuseAlive 启动策略，避免旧 CLI 将新版
后台替换回自己的映像。

旧 CLI 和旧窗口已经运行的代码无法补充重连能力。首次上线仍需一次安全排空。
新版 daemon 遇到缺少恢复能力的在途调用或窗口时保留原服务并继续受理兼容新题，
待旧调用结束再交接。显式 stop/restart 和协议不兼容让位仍有其排空边界。
Windows 安装 worker 先检查恢复能力。支持时保持旧服务受理，事务式替换与校验后由后台触发交接；
旧服务不支持时沿用显式 stop 的安全排空。文件共享冲突继续按原有界重试处理，兼容旧服务仍可继续接题。
Windows/Linux 原生换代验证分别保留，macOS 的结果不能代替。

## 交接与自动恢复

1. 检测安装入口变化，验证目标版本、保存格式、全部请求和窗口的恢复能力。
2. 建立有界受理屏障，给原窗口和手机发布更新状态，暂停四个 IM 入站读取。
3. 请求 actor 保存已经排队的输入，保留原卡，等待附件处理和答案提交等机器操作结束。
4. 刷新全部检查点，保存手机投递/推送事实及同步后的上传文件，关闭旧渠道和监听资源。
5. 复用 Unix exec 或 Windows 接班进程，取得同一用户实例的服务所有权。
6. 恢复原题、终态、宿主租约和路由，接收新题，各渠道独立重试连接。

受理屏障和单轮交接准备有界。保存或准备失败时撤销交接并恢复原服务，之后自动重试。
Unix exec 失败时保留单实例锁，在当前映像中重新建立服务并恢复保存的请求。
显式停止优先于更新，正常停止取消待答请求，已接受的人类决定仍按不可变终态处理。
受控交接不会执行普通取消清理。任意崩溃后的系统级自动拉起仍沿用现有运行环境的能力。

Daemon 自持错误卡和 Codex 原生请求使用稳定消费身份，答案可等后继程序消费。
只有已经领取的原生操作阻止交接。原生发送结果不确定时保存 Unknown，沿用现有
原生操作回执策略。接管程序依据错误卡清单和已连接的原生权威快照撤销失效请求。
短暂原生断连保留等待。

## Popup

共享 Host 与独立 Helper 保持原进程及挂载的表单，通过私有租约重连。
相同请求 ID 的恢复 Show 不重建组件，因此保留草稿、附件、选区、滚动和批注。
未确认提交保留在桥接层，重连后重新发送 Ready 和原答案，收到接受或终态回执后收尾。
旧连接的迟到 EOF 只能清理属于自己的发送端，不能影响已重连窗口。
窗口程序在空闲时更新。已就绪表单重连后不重复置前，独立窗口的焦点仲裁状态随交接保存，并只恢复仍存活的原窗口。

## iOS

Gateway 的快照屏障以恢复存储中仍需 iOS 投递的请求为准，只有这些原题已挂接后才发送
inbox snapshot，避免恢复过程的空列表提前结束手机缓存的题卡。
手机按 Mac 显示 pending、updating、recovering，更新期间保留草稿及原 clientMsgId 的 outbox。
新的 epoch 完成同步后自动续送。旧手机忽略可选状态字段，继续使用原协议。

每题每手机的 ACK、已看、MQTT 投递和推送事实跨交接保存。原题恢复沿用这些事实，
避免再次发到达通知。上传保存原身份、范围、路径、块位置和哈希，恢复时核验私有路径，
重建部分文件哈希，完成文件再次核验。答案可靠接受后才消费上传附件。
新旧字段的跨语言夹具覆盖 `Caps.liveUpdate`，Presence 的可选 `u` 表示更新状态。

## 四个 IM 渠道

普通题和确认卡均保存原消息 ID、目标和路由凭据哈希，接管时重新挂接原卡。
已完成的前题、当前选择和文字、附件事件及处理去重事实继续使用原身份。
附件下载完成与事件完成检查点一起保存。交接收尾保留卡片，普通取消仍显示原取消结果。
原确认期限跨交接保持，恢复不续期。

Telegram 保存 getUpdates offset，先挂接保存的原卡路由再恢复轮询。
飞书、钉钉和 Slack 暂停唯一 reader 后，让各题 actor 处理已入队事件，再保存交接状态。
平台编辑框内尚未发送到 Mac 的输入继续由平台持有。

## 验证入口

恢复存储、窗口桥接、iOS gateway、Swift engine 与原渠道回归覆盖独立边界。
`scripts/daemon-update-handoff-smoke.mjs` 使用私有 HOME、真实 daemon 和 loopback Telegram
验证同 PID 换代、未回答 A 与新增 B、原卡选择、确认卡、停止优先和坏目标恢复。
真实渠道、手机和原生窗口的最终体验需在安装后的环境验收，跨平台结果分别记录。
