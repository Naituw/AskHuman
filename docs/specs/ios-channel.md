# 需求：iOS 原生渠道（AskHuman Mobile）

> 状态：已于 2026-10-25 获用户批准并实现为可用原型（模拟器与本地 broker 验证通过）；真实 EMQX / 中继 / APNs 与真机验收待进行，进度见 `docs/PROGRESS.md`。实现与计划的差异见 `docs/plans/ios-channel.md` §13。本文是 2026-10-25 多轮 AskHuman 问答后的定稿。
> 关联计划：`docs/plans/ios-channel.md`
> 前置资料：`docs/investigations/native-ios-channel-handoff.md`（2026-10-24 交接：EMQX 杭州实测、Mac / iOS 交互原型、费用模型）
> 依赖：Daemon 渠道体系（`Channel` / Coordinator）、统一作答窗口（`popup-request-inbox.md`）、IM watch（`im-watch.md`）、插话（`agent-interject.md`）、IM 创建任务（`im-agent-task-launch.md`）、「实验」设置 Tab。
> 平台：Mac 端沿用现有 Daemon（首期只在 macOS 验证）；手机端为 iPhone，iOS 17+，中 / 英双语。

## 1. 背景与目标

现有渠道（弹窗、飞书、钉钉、Telegram、Slack）要么是桌面窗口，要么受限于第三方 IM 卡片：多问题合并窗口、
原生草稿、附件预览、Agent 实时观察这些体验在 IM 里无法还原。本需求新增一个**原生 iOS 应用**，作为 AskHuman
的新通信渠道 `ios`，与飞书等渠道并列：

1. **回答提问**：覆盖 Mac 弹窗的核心语义（多问题、推荐项、仅选择、单选、附件、Markdown），并以手机原生交互呈现；
2. **响应确认**：Agent 的权限请求与 Stop 确认；
3. **多 Mac**：家里一台、公司一台……多台 Mac 上的 AskHuman 与**同一部手机**配对，手机统一收件箱；
4. **观察 Agent 与结果通知**：可选择性实时观察某个 Agent；从手机创建的任务做完 / 出错时收到通知；
5. **发消息**：向工作中的 Agent 插话；
6. **创建任务**：从手机在某台 Mac 上启动新的 Agent 任务（与 IM `/new` 同语义）；
7. **端到端加密**：消息与推送预览只有 Mac 与手机能解密；
8. **按量成本**：不引入固定月费服务器；EMQX Serverless 与推送中继均在免费额度内运行。

非目标见 §11。

## 2. 术语

| 术语 | 含义 |
|---|---|
| Mac | 运行 AskHuman Daemon 的电脑（Windows / Linux 代码路径同源，首期不验证） |
| 手机 | 安装 AskHuman iOS App 的 iPhone |
| Broker | EMQX Serverless 实例（MQTT 服务器）；所有 Mac 与手机共用一份凭据 |
| 配对 | 一台 Mac 与一部手机之间建立的、独立的端到端密钥关系 |
| 中继 | 极小的无状态 HTTPS 服务，持有 APNs 密钥，代 Mac 向苹果推送；部署在腾讯云云函数 |
| 句柄 | 手机向中继登记后得到的不透明推送凭证；Mac 只持有句柄，看不到设备 token |
| Follow（通知集） | Mac 上记着的「这部手机要被通知结果」的 Agent：从手机创建的任务启动成功后进入，第一次做完 / 出错时通知手机并移出（一次性；推送要等 Mac 空闲，见 `docs/specs/ios-follow-narrowing.md`）。App 里没有手动加入的入口；与「打开详情实时观看」不同 |
| Watch（实时观察） | 手机打开某 Agent 详情期间的实时推流，仅前台 |

## 4. 总体架构

```
┌───────── Mac A（家）─────────┐     ┌───────── Mac B（公司）────────┐
│ Agents / CLI / 弹窗           │     │ 同左                           │
│        │                      │     │                                │
│  Daemon ── ios Gateway ───────┼─┐ ┌─┼─ ios Gateway ── Daemon         │
└───────────────┬───────────────┘ │ │ └───────────────┬────────────────┘
                │ HTTPS：句柄+密文  │ │ MQTT（TLS/WSS）  │
                ▼                  ▼ ▼                  ▼
        推送中继（腾讯云云函数）   EMQX Serverless（杭州）
                │ HTTP/2 + JWT            ▲
                ▼                         │ MQTT（TLS/WSS）
              APNs ── 推送 ─────────► iPhone（AskHuman App）
                                          └ 通知扩展：用配对密钥解密预览
```

- **实时通道**：Mac 与手机通过 EMQX 收发端到端加密的消息；手机只在**前台**保持连接，退到后台即断开（App 仍在屏幕上、只是被控制中心 / 通知中心 / 多任务界面 / 系统弹窗盖住的 `inactive` 不算离开，超过 10 秒才断开，见 §15 2026-10-26）。
- **后台通知**：手机不在前台时，Mac 经中继调用 APNs；通知只携带密文，点击后打开 App，由前台连接补同步权威状态。
- **权威状态在 Mac**：请求、答案是否被采纳、Agent 状态都以 Mac Daemon 为准；手机是遥控与展示端，「首个终态获胜」沿用 Coordinator 现有语义。
- **每台 Mac 一个独立 ios Gateway**，手机侧把多台 Mac 聚合成一个收件箱 / Agent 列表。

## 5. 配对与多 Mac

### 5.1 Mac 一次性配置

在「设置 → 实验 → iOS 渠道」（或 CLI）填写：Broker 主机 / 端口 / 用户名 / 密码、中继地址、Mac 名称（默认取主机名，手机上显示）。
为了避免第二台 Mac 重复手填，第一台 Mac 提供「复制连接串」，其它 Mac「导入连接串」一次性填入 broker 与中继信息。
密码进入系统钥匙串，不写 `config.json`。

### 5.2 配对流程

1. Mac：点「添加手机」→ 显示二维码（同时提供「复制配对码」文本，供无摄像头或模拟器使用），5 分钟内一次性有效；
2. 手机：扫码（或粘贴配对码）→ 连接 broker → 发送配对请求；手机显示「请在 Mac 上确认」与 6 位校验码；
3. Mac：弹出确认，显示**手机名称 + 6 位校验码**；用户核对两端一致后点「允许」（或「拒绝」）；
4. 允许后两端各自得到配对密钥；手机向中继登记推送句柄并加密发给这台 Mac；
5. 两端显示配对成功；Mac 的手机列表出现该手机，手机的 Mac 列表出现该 Mac。

安全要点：二维码含 broker 凭据与一次性票据，5 分钟失效、仅可使用一次；不能只靠二维码完成配对——Mac 端的人工确认与校验码是第二道门，
旁观者拍下二维码也无法在用户不核对的情况下配对成功；配对密钥由双方临时密钥交换得到，之后的消息密钥与 broker 密码无关。

### 5.3 多 Mac 与多手机

- 手机对每台 Mac 重复上述流程，每个配对有独立密钥；撤销 / 重新配对互不影响。
- 一部手机在 v1 只支持**一份 broker 配置**（所有 Mac 使用同一个 EMQX 账号）。扫到使用不同 broker 的二维码时，手机明确提示并要求先「重置」才能切换。
- 一台 Mac 可以配对多部手机（自己的或朋友的）：请求同时投给所有已配对手机，**首个答案生效**，其余手机收到「已在 X 回答」。
- Mac 名称在手机上显示为标签，可在 Mac 端或手机端重命名（手机端重命名仅本机显示）。

### 5.4 解除与恢复

- 任一端都可解除配对：解除后立即删除本端密钥，并尽力通知对端；对端若离线，则在下次连接时发现并提示「该 Mac 可能已移除此手机」。
- 手机的配对密钥存放在钥匙串（`AfterFirstUnlockThisDeviceOnly`，不同步、不进备份）。由于 iOS 钥匙串可能在 App 删除后保留，重装后若发现遗留配对，App 提示「保留上次配对 / 清除」。
- App 提供「忘记所有配对」，用于清空本机全部配对数据。
- 手机重装、系统恢复或推送 token 变化后，App 自动重新登记推送句柄，并通过加密通道通知各 Mac 更新。

## 6. 手机端功能

### 6.1 导航结构

底部四个标签：**收件箱**、**Agents**、**历史**、**Mac**（配对与设置）。「新任务」入口在 Agents 页右上角的「＋」与各 Mac 卡片中。仅支持 iPhone。

### 6.2 收件箱

- 汇总所有已配对 Mac 的待答请求（提问与确认），**按项目分组**，组内与组间按最近到达时间排序；每行带 Mac 名称标签、Agent 官方 logo（品牌色底 + 白色 logo）+ 名称、摘要、相对时间、未读蓝点、草稿徽标。
- 筛选：全部 / 提问 / 确认（配对多台 Mac 时再加「按 Mac」），收在导航栏左上角的菜单里，**不在列表上方固定一条筛选栏**：iOS 26 的顶部滚动边缘效果会把固定在那里的内容裹进模糊带，让导航栏高到三倍。筛选生效时图标高亮、列表顶部出现一行「已筛选：xx · 清除」；未筛选时不占高度。Agents 页同理。
- **加载与空状态**：打开 App 时 Mac 还没应答，不能显示「没有问题」。列表有三种就绪度：加载中（有上次留下的请求就照常显示，没有就显示骨架行，不显示空状态）→ 已就绪（此时才可能显示「已全部处理」）→ 全部 Mac 确实连不上（显示「连不上你的 Mac」）；15 秒仍无应答才显示「等待 Mac 响应」。Agents 页同理（此前正在连接时会被误报成「Mac 连不上」）。
- **同步提示**：同步在后台进行，只在导航栏标题位上延迟约 0.6 秒淡入「正在更新… / 正在连接…」（转圈 + 次要色文字），很快完成的刷新不出现，列表不被推动；不用橙色横幅、不给行着色。列表顶部只在**需要处理**时出现一张中性提示卡（只有图标着色）：Broker 拒绝连接、时钟偏差、流量将尽 / 已尽、某台 Mac 离线且有它的待答请求；连不上 Broker 的提示持续约 10 秒后才出现。
- 行内摘要显示第一题的正文（去 Markdown 标记）、题数、是否含「仅选择」「推荐」「附件」。
- 新请求在 App 前台到达时：轻触觉反馈 + 应用内横幅；未读蓝点在打开请求后消失；每个请求的草稿相互独立。
- 请求被其它渠道（Mac 弹窗、飞书、另一部手机）回答或被调用方取消时：列表项短暂标注「已在 X 回答 / 已取消」后移出；若用户正在填写，则保留草稿区并在顶部提示「该请求已结束」。
- 提交成功（Mac 确认收到）后：当前页先显示全页回执（大号 ✓ +「已发送」+ Agent / 项目，约 0.7 秒）并给成功触感，再切到下一条待答请求（新页从右边滑进来盖住回执，回执略向左让，约 0.45 秒；栈里始终只有一页），顶部浮出提示条「已发送 · 还剩 N 条」（约 2.5 秒）；下一条总是从顶部开始、按自己的阅读进度显示「下一题 / 发送」，不沿用上一页的滚动位置与状态；「返回」直接回到列表。自动跳转可在设置关闭；关闭或已无待答请求时回到列表；全部清空显示空状态。回执期间用户自己离开了该页，则取消这次切换。
- 下拉刷新 = 向 Mac 请求权威快照；转圈至少停留约 0.6 秒，并保持到列表同步完成（最长 8 秒）。

### 6.3 作答（提问请求）

整页纵向长表单，结构与 Mac 弹窗一致：

- 头部：Agent、项目、Mac、提问时间；共享 Message 以 Markdown 渲染，随请求的 `-f` 附件以缩略图 / 文件胶囊展示。
- 每个问题一张卡：题号、Markdown 正文、选项列表、自由文本框、回复附件区。
- 选项：多选用复选框，`single` 用单选；AI 推荐项带「推荐」徽标，**绝不预选**；提交值始终是选项原文。
- 「仅选择」（`selectOnly`）：隐藏自由文本与回复附件；每题至少选一项才能发送；仍可取消请求。
- 非「仅选择」时可以不选直接发送（与 Mac 一致）；一题被视为「已答」当且仅当选了选项、写了文字、或带了图片 / 文件。
- 底部固定操作条：显示「已答 n/N」与主按钮。**多题时主按钮先是「下一题」**，**最后一题的底部进入屏幕后才变成「发送」**，与 Mac 弹窗一致，防止没看到后面的题就误发。「下一题」按屏幕**当前位置**走（与弹窗 `goNext` 一致）：第一张底边还在可视区下方的题卡，放得下就整张露出，放不下先对齐它的顶部、再按一次看底部；不看「看过」的历史，往回滑后再点不会跳过看过但没答的题（2026-10-28 改，此前按「第一个还没看过的题」走，会跳过）。「看过」只决定「发送」何时出现：= 题卡底部进入过可视区（滚过去的也算，一旦看过最后一题就不再收回）；已作答的题视为看过；整张表单一屏放得下时直接是「发送」；「发送」出现后屏幕下方还有题时，旁边仍留一个「下一题」图标按钮；单题请求不受影响。内容规则不变：非「仅选择」时有未答题也可发送（点击前不额外弹窗），「仅选择」每题都要选才行，没选全时计数下的提示可点，直接跳到第一道没选的题。详见 `ios-answer-flow.md`。
- 取消请求在更多菜单里，需二次确认。
- 草稿（选择、文字、附件）按请求独立自动保存，App 被杀后恢复；请求结束后草稿丢弃。
- 长文本：Markdown 支持标题、列表、引用、代码块（可横向滚动、可复制）、表格、链接（用应用内浏览器打开，打开前显示目标域名）、内联图片、Mermaid 图、本地图片（见 §6.5）。**提问页的 Message、确认页与历史详情的正文由网页渲染**（与 Mac 弹窗同一套 markdown-it + Mermaid，可选字、软换行换行；2026-10-28，见 `ios-web-markdown.md`），题干与列表摘要等仍是原生渲染；网页不可用时自动回落原生，那时 Mermaid 图按代码块展示。
- whats-next 请求：正常渲染其 TODO 选项（含 `⚡` 自动待办标记）；选中后的 TODO 出队由 Mac 的 Coordinator 照旧处理。

### 6.4 确认类请求（权限 / Stop）

- 以单独的确认页呈现：标题、上下文字段（命令、路径、时间等）、详情（Markdown）、操作按钮。
- 按钮语义由 Mac 下发（允许 / 拒绝 / 记住前缀等），与 IM 一致只展示推荐的那一档变体；推荐项高亮、**不预选**；若存在需要补充的输入（如拒绝理由），按 Mac 下发的可见规则显示输入框。
- 有时限的确认显示倒计时；到期或被 Mac / 别处处理后立即收敛为终态。
- 确认的取消 / 关闭语义沿用 `dismissActionId`（即「视为拒绝」类默认动作）。

### 6.5 附件

**AI → 手机（请求附带 `-f` 文件、Markdown 里引用的本地图片）**

- 请求到达时只带元数据与缩略图（图片小缩略图随请求下发）；点开才从 Mac 分块拉取原文件。
- 预览支持：图片（缩放 / 平移）、文本与代码（等宽、可选择复制）、Markdown（原生渲染）、diff（+/- 着色）；其它类型提供「用其它应用打开 / 分享」。
- 只能拉取**属于当前可见请求**的文件，且单个文件有大小上限；拉取失败显示明确错误并可重试。
- Markdown 正文里引用的本地图片（绝对路径或项目相对路径）随请求登记为可拉取资源；拉不到时显示占位而不阻塞阅读。

**手机 → Agent（回复附件）**

- 每题可添加：拍照、相册、文件；图片在手机端压缩后再传；文件按原样传。
- 上传分块进行，带校验和与进度；成功后作为附件随答案提交：图片进入答案的图片字段，非图片文件落到 Mac 临时目录并把路径放进答案的文件字段（与 Mac 弹窗一致）。
- 「仅选择」请求不提供附件入口。

### 6.6 Agent 列表与结果通知

- Agents 页按 Mac 分组列出 Agent（与 Mac「Agents 控制台」同源）：类型、项目、标题、状态（工作中 / 空闲 / 等待你 / 已结束）、当前工具、待送达插话标记；默认只显示未结束会话，可切换显示最近结束；
  有多台 Mac 时工具栏有按 Mac 过滤的菜单（只有一台 Mac 时不出现）。
- **结果通知（通知集）**：只有**从手机创建的任务**会通知：任务成功启动后，该会话进入这台 Mac 上这部手机的通知集（每台每部手机最多 5 个；名额已满则不进入，新任务进度页会说明）。
  通知集里的 Agent **第一次出结果**时通知手机，之后自动移出（一次性）：
  - **完成**：一轮工作结束；
  - **出错**：该轮以失败结束（见 D19；Codex 不提供）。

  手机在前台时是应用内横幅；不在前台时是推送，但和提问一样要等 Mac 键盘 / 鼠标空闲满 `alertAfterSecs` 才发，你在此前回到 Mac（有了新输入）就作废、不再补推
  （`docs/specs/ios-follow-narrowing.md`）。原有的「等待你」通知已删除：每道提问本来就在手机收件箱里。
- **App 里没有手动关注的入口**（星标、「已关注」过滤、名额提示都已去掉）。会通知你的 Agent 只读地标出来：列表行上的小铃铛，详情页一行说明；
  结果被处理后（推出 / 手机正在看 / 你回到 Mac）铃铛随之消失。引擎里的 `setFollow` 与 `follow.*` 线消息保留，兼容旧版 Mac / 旧版 App。
- 通知点击直达对应请求或 Agent 详情；同一台 Mac 的通知按 Mac 折叠分组。点开提问通知时请求往往还没到手机，页面先用通知里的文字占位、转圈等它到达，不说「不可用」（见 §15「2026-10-27 推送点开与会话标题」）。

### 6.7 Agent 详情：实时观察与插话

- 打开详情即开始实时观察（仅前台）：阶段徽标、已用时、当前工具、最近步骤（成功 / 失败）、待办列表、最近一段 Markdown 文本；内容只在变化时推送，约每 2 秒一次。离开详情或退后台立即停止。
- 同一时刻最多打开 2 个实时观察，避免流量与名额浪费。
- 插话：底部输入框发送文字（可带图片 / 文件）；仅对「工作中」且支持插话的 Agent 可用，其余显示原因。插话先排队，Agent 在下一次工具调用前交付；界面区分「已入队」「已送达 Agent」，并保留「待送达气泡 + 撤回」（与 Mac 控制台一致）。
- 若该 Agent 正在等待回答，详情页顶部提供「去回答」跳转到对应请求（若该请求投到了手机）。（原设计里请求没投到手机时还有「接管提问」入口；自 D11 修订起 iOS 不受活跃槽约束，每个提问都在手机上，这个入口不再需要。）

### 6.8 新建任务

与 IM `/new` 同语义，流程：选 Mac（仅显示已连接且已开启「Agent 任务」的）→ 工作目录（置顶优先，其余按最近使用；隐藏的不出现）→ Agent（只列就绪的，不可选的给原因）→ 权限（按 Mac 设置：每次询问 / 总是默认 / 总是 YOLO；询问时二选一、不预选、YOLO 显示风险说明）→ 任务输入（可选项目 TODO，最多 10 条，自动待办标 `⚡`；默认「直接输入新任务」；任务 ≤ 3000 字符）→ **Face ID / 设备密码** → 提交。

提交后显示进度：已提交 → 终端已启动 / Codex 已创建 → 等待 Agent 注册 → Agent 已在运行（并说明做完 / 出错时会通知你，Mac 空闲一阵后；这台 Mac 的名额已满时说明不会通知）；60 秒内未匹配到会话时明确告警（Agent 仍在运行，只是没能加入通知集）。启动失败原样显示 Mac 的原因。
Mac 未开启「Agent 任务」或终端不可用时，入口置灰并说明如何在 Mac 上开启。

### 6.9 本地历史

仅存手机，不同步：保存已回答 / 已取消请求的摘要、所选答案与时间，最多保留 500 条或 90 天（先到者）；可搜索、可单条删除、可「清空」。附件只存元数据，不保存文件内容。

### 6.10 Mac 管理与设置（手机端）

- Mac 列表：名称、连接状态（已连接 / Mac 离线 / Broker 未连接 / 推送不可用 / 需要重新配对）、最后在线时间、当前活跃槽、重命名、解除配对。
- 「接管提问」开关：原设计是把本 Mac 的活跃槽切到手机并补推在途请求。自 D11 修订起 Mac 端对手机恒报「不使用自动激活」，App 因此恒显示「所有提问都会发到手机」而不出开关；App 内的开关代码保留但不会出现（`docs/specs/ios-alert-timing.md` D1）。
- 通知权限状态与引导；Face ID 设置说明；本月流量估算（本机统计）；「添加 Mac」「忘记所有配对」。
- 提交类操作（回答、确认、插话、新任务）要求对应 Mac 在线；Mac 离线时按钮置灰并说明，草稿保留，不做离线排队。

### 6.11 通知

- 类型：提问、确认、Follow 的完成 / 出错；统一以 `thread-id = Mac` 分组。
- 时机：提问 / 确认的推送只在手机没在看、且 Mac 键盘 / 鼠标空闲满 `alertAfterSecs`（默认 15 分钟，`0` = 立即）后才发，每题每手机最多一条，不重复提醒；你还在用 Mac 时不推，问题仍在 App 的收件箱里。详见 `docs/specs/ios-alert-timing.md`。Follow 的完成 / 出错通知遵守同一规则（§6.6）。
- 文案：系统层只有通用占位（本地化的「AskHuman 有新的提问」等），通知扩展解密成功后替换为「Mac · Agent · 项目」+ 摘要。
- 请求被别处处理后，对应通知被一条低调的替换通知（无声、被动级别）改写为「已在 X 回答」，并在 App 回到前台时清理已失效通知。
- App 图标角标 = 待答请求总数（App 活跃时更新）。
- 首次配对成功后再请求通知权限，并解释用途。

## 7. 渠道语义（Mac 端）

1. **可用条件**：`channels.ios.enabled` 且 broker 与中继已配置且至少有一个配对手机。
2. **投递**：
   - **不受活跃槽与 `autoActivation` 约束**（D11 修订）：所有请求都挂给所有已配对手机；手机一连上就由 hello 快照拉到，不依赖通知。
   - 手机前台已连接 → 经 MQTT 直达，3 秒内无应用层确认再补发推送；
   - 手机不在前台 → 请求等在它的收件箱里，推送要等 Mac 键盘 / 鼠标空闲满 `channels.ios.alertAfterSecs`（默认 15 分钟，`0` = 立即）才发，每题每手机最多一条、不重复提醒；你还在用 Mac 时不推（手机回到前台后由连接时的快照补齐）。细则见 `docs/specs/ios-alert-timing.md`。
3. **抢答**：手机的答案走 Coordinator 的 `try_submit`，首个终态获胜；落败的手机收到「已在 X 回答 / 已取消」；Mac 对答案先校验（`selectOnly` / `single` / 附件限制），拒绝非法答案。
4. **确认请求**：作为 Confirm 渠道接入现有确认链路，按钮、默认动作、时限与终态沿用。
5. **Broker 不可达**：投递时若 5 秒内仍未连上 broker，则按「投递面丢失」处理（与 IM 一致：其它渠道仍可答；全部丢失则请求以「无可用渠道」结束并给出原因）；请求等待期间连接断开不判丢失，恢复后手机的同步会拿到该请求。
6. **活跃槽**：手机不参与活跃槽的投递筛选（见第 2 条）；手机作答或新任务创建成功后，活跃槽仍沿用既有「在哪个渠道说话就把它设为活跃槽」的规则——这只影响 IM 的投递，不影响手机。
7. **Daemon 生命周期**：iOS 渠道**不强制 keepalive**。Mac 端设置页提示「想让手机随时看到这台 Mac，请把 Daemon 设为常驻」；手机打开 Agent 详情期间 Daemon 不会因空闲退出；「新任务」依赖「Agent 任务」功能（该功能已强制 keepalive）。
8. **离线表现**：Mac 休眠或 Daemon 退出时，手机看到「Mac 离线」（Daemon 正常退出立即显示；休眠等异常断开要等保活超时，最长约 1 分钟）；缓存的收件箱标记为过期，不能提交。
9. **Dev Instance**：使用各自独立的 Mac 标识与配对，首期不支持用渠道预设（preset）自动带入。

## 8. 协议与安全概述

> 逐字段协议、密钥派生、消息目录与幂等规则见 `docs/plans/ios-channel.md`。

- **标识**：Mac、手机各有随机生成、长期不变的标识；配对由 (Mac 标识, 手机标识) 唯一确定。
- **话题隔离**：每台 Mac、每部手机各有私有收发话题；EMQX 用「每个用户名一条 `ah/<用户名>/#` 允许规则 + 全部用户 `#` 兜底拒绝」把不同用户名彼此隔离（已实测），共享凭据内的设备靠加密隔离。
- **加密**：X25519 临时密钥交换 + 一次性票据作为 HKDF 盐，派生方向独立的两把 ChaCha20-Poly1305 密钥与校验码；每条消息随机 nonce，认证数据绑定话题、发送方与密钥编号；预留密钥轮换字段（轮换功能 v2）。
- **可见元数据**：broker 可见话题（含随机标识）、消息大小与时间、手机是否在线 / 在前台（保留的在线状态）；看不到问题、答案、Agent 名称、项目、附件。中继可见设备 token、推送时间与大小。
- **泄露面**：共享 broker 凭据泄露 ⇒ 对方能看到元数据与制造流量，但读不到内容、也不能冒充已配对设备；配对二维码泄露需在 5 分钟内且用户在 Mac 上放行才可利用；推送句柄泄露 ⇒ 只能让手机收到通用提示，且 180 天过期。
- **幂等与恢复**：答案、确认、插话、新任务都带客户端消息标识，Mac 持久化去重；同标识不同内容拒绝；任何重启 / 断线 / ACK 丢失后手机用快照对齐状态，不会重复提交也不会静默丢失。
- **防重放**：每条消息带时间戳，与接收方时间相差超过 15 分钟的会被丢弃；握手带随机数，手机只接受本次握手对应的状态快照；即使有人拿到共享的 broker 凭据并录下密文，也无法重放旧的「新任务」等操作。
- **四种「已送达」要区分展示**：手机已保存 → Mac 已持久接收 → Coordinator 已采纳 → Agent 已消费（插话尤其明显）。MQTT PUBACK 与 APNs 200 都不代表后两者。

## 10. 性能、流量与成本

- **延迟**：按 D10 的四条口径验收，延迟拆成「状态产生 → 发布」「网络 / 持久 ACK」「UI 展示」「Agent 消费」「APNs 展示」分别记录，不混成一个数字；两台未校时设备的单向耗时不当精确值，用 RTT 估算并同时报告原始数据。
- **EMQX 免费额度**：每月 100 万连接分钟、1 GB 流量（入站 + 出站）、100 万规则动作（本方案不用规则动作）。一台常开 Mac + 手机每天前台 1 小时约 4.5 万连接分钟，远低于额度。
- **流量预算目标**：典型使用（每天 100 个请求、每天实时观察 1 小时）每月 ≤ 300 MB；Watch 帧签名变化才发、每会话最多每 2 秒一帧、单帧 ≤ 8 KB；附件按需拉取；Mac 与手机都在本机统计流量并在接近预算时提示。EMQX 上限为 0 意味着额度用尽服务即停，App 对「认证失败 / 额度可能用尽」给出明确说明。
- **中继费用**：每月约 1 千到 2 万次调用，只占腾讯云云函数免费额度的百分之几（以用户账号的计费规则为准，部署前先核对，避免意外的固定月费）。

### 2026-10-27 推送点开与会话标题

用户提了两点：从推送点进一条提问，先显示「此提问不可用」，过一会才出来；iOS 上的提问需要显示 Agent Session 的标题。经 AskHuman 逐项确认，方案采用推荐项（第一项的页面形态、标题要出现的位置与取名规则都由用户逐项选定）：

- **点开推送的等待页**：根因是推送比 MQTT 快（冷启动时更明显），页面在请求到达手机之前就打开了，却把「手机上暂时没有这条请求」一律当成「不可用」。现在页面区分三种情形：Mac 还没答复（刚启动、还在连）→ 「正在载入完整提问…」；Mac 连不上（Mac 离线 / broker 不通）→「连不上你的 Mac，连上后会自动出现」；Mac 已答复并确实没有这条（已在别处回答或取消，或那台 Mac 已解除配对）→「请求不可用」。前两种的页面先用通知里已有的文字占位（标题 = Agent · 项目，副标题 = Mac，正文 = 问题预览），请求到达后原地换成表单（约 0.2 秒淡入）；「已在别处处理」类通知不带占位文字，`follow.*` 通知仍直接打开 Agent 页。占位文字只存在于这次点开，页面关闭即丢弃。
- **会话标题**：Agent 会话在它自己那里叫什么（原生名称，没有就用首条用户消息，与 Agents 页和 Mac 弹窗取名规则一致）随请求送到手机，出现在五处（用户逐项选定）：
  - 收件箱行：标题直接替代 Agent 名做第一行，不加行（Agent 靠左边的 logo 认）；没有标题时仍显示 Agent 名。
  - 提问页：页头卡片里标题做主标题（最多两行），下面一行小字「Agent · 项目 · Mac」，再下面是时间；没有标题时页头保持原样。点开推送的占位页仍用通知里的文字，标题来自通知里的那行。
  - 应用内顶部横幅：标题 = 会话标题（没有就是「Agent · 项目」），副标题 = 问题预览。
  - 历史：列表行与收件箱行一致（项目挪到结果那行），详情页头与提问页一致；历史搜索也搜标题。
  - 推送通知：见下一条。
- **推送排版**（用户担心显示不下，把优先级交给我排；可调）：锁屏的标题与副标题各只有一行，放不下就被截断，所以按「最能认出这条提问的放最前，最不要紧的放最后」排——标题 = 会话标题（没有标题时仍是「Agent · 项目」，和以前一样）；副标题 = 「Agent · 项目 · Mac」（没有标题时仍只写 Mac）；正文 = 问题预览，不变。Mac 名放最后，窄屏最先被截掉的是它。推送里的标题最多 60 字符，超出加省略号。提问通知被「已在别处回答」之类的更新原地替换时，标题与副标题保持原样，只有正文变。
- **何时取标题**：请求送达手机时由 Mac 取一次——先看守护进程已经记住的名称，再做一次有时限的原生读取（最多多等约 0.3 秒，超时就用已记住的，再没有就不带标题；弹窗与其它渠道的送达不受影响）；之后不跟随改名，手机上已有的请求保持送达时的标题（与 Mac 弹窗「已打开的请求不订阅重命名」一致）。标题压成一行、最多 120 字符。提问和确认都带。
- **协议**：`RequestView.sessionTitle?`、`RequestSummary.sessionTitle?`、推送明文 `session?` 都是可选字段，没有时不出现在线上：旧手机忽略，旧 Mac 不发，不升级 iOS 协议号（与 D19 同一先例），也不改 Mac 的 IPC。`contentHash` 由最终的视图 JSON 算出，带不带标题都会让摘要与全文保持一致。
- 验证：Rust 全量测试、Swift 包测试，以及模拟器 UI 测试（含带 / 不带标题的收件箱行、提问页页头、历史列表与详情、历史搜索、应用内横幅）；通知排版的逻辑（`PushPlain.headerLines`）在 Swift 包里单测。

### 2026-10-27 换页的闪烁与空状态跳动

用户在真机上用了一阵，提了两点：答完一题后自动跳到下一题，有时会再闪一下「已发送」，闪完后页面的滚动位置不对、不在顶部；从提问页返回首页时，空内容提示的位置会跳一下，他猜与 TabBar 的显示有关。用户当时去午休、不能回答问题，两点都由我按判断自行处理，这里记下根因与取舍：

- **换页的闪烁与滚动位置是同一个根因**：旧做法先把下一条压在已发送页上（栈 `[a, b]`），推完再把 `a` 拿掉（`[b]`）。`NavigationStack` 按位置认页面，拿掉 `a` 等于把第 0 位那页「改成」`b`：那页被收起时最后一帧是 `a` 的回执，重新露出来时先闪两帧回执再淡掉；它的滚动偏移与 `@State` 也被沿用——`b` 从 `a` 滚到的位置开始（模拟器里量到标题在屏幕上方 668 pt 处），底栏还写「发送」而不是「下一题」（多题表单「看到最后一题才能发送」的阅读状态被带了过来，等于绕过了闸门）。把一条长表单滚到底答完、再换到另一条长表单时稳定复现；短表单没有滚动，只剩回执闪一下。
- **现做法**：栈里始终只有一页，`a → b` 是一步（`inboxPath = [b]`），每条请求一个独立页面（`RequestScreen` 上 `.id`），所以不会沿用任何状态。系统对这种原地替换在 iOS 27 上只有交叉淡入、没有位移，所以位移由页面自己做（`Arrival`）：回执的一份副本留在原地并略向左让，新页从右边滑进来盖住它，约 0.45 秒；新页的版面第一次排好后才开始动（长表单首次排版要几十到几百毫秒，动画先开始会被吞掉）。「减少动态效果」下改成淡入。回执自己记着是谁问的（`SentReceipt.summary`）与换到了哪一页（`next`），因为请求一关闭，页面就不再有它的详情；`settle` 由 1.5 秒缩到 0.8 秒（只管回执在换页 / 返回动画期间不被拿掉）。
- **空状态跳动**：请求页与 Agent 详情页都隐藏 TabBar，返回时列表先出来，TabBar 约 0.5 秒后才回来，底部安全区因此增高约 48 pt，居中的空状态上跳约 24 pt（录屏里标题行 475–492 pt → 451–468 pt）。猜想对了一半：是 TabBar 的出现时机，不是它的显示。`emptyState`（`ListChrome.swift`）记住这个宽度下见过的最大底部边距，一直按「TabBar 在」来居中；收件箱与 Agents 都用它。返回的全程位置不变（录屏量到 451–468 pt 不动），最终位置与以前相同。
- 我自行决定：换页动画放进页面、不再用系统推入；Agents 的空状态一并改；回执期间的 `settle` 缩短；新增两个模拟器场景（`single` 只有一条待答、`longs` 两条长表单）与回归用例（`testTheNextRequestStartsAtItsTopAndIsNotReadYet`、`testTheNextRequestTakesTheSentOnesPlaceAndTheReceiptOutlivesTheMove`）。
- 验证：iOS 27.0 模拟器用 `simctl io recordVideo` 逐帧核对（长表单 → 长表单、短表单 → 长表单、最后一题返回列表、「减少动态效果」各一次），iOS 18.5 模拟器核对了长表单 → 长表单；Swift 包测试与 UI 测试（英文整套、中文相关几条）通过。iOS 26 没有可用的模拟器，没测。真机（iPhone Air，Debug 构建，当晚装机；从电脑发两条带三道题的长提问让用户在手机上答）：用户在手机上答完了两条（先答第二条、后答第一条），反馈那一页「从顶部开始」「底栏是下一题」「切换时没有再闪」，换页手感选「自然」，要不要再改什么选了「都不改」。滑入是自己写的曲线（0.45 秒，慢起慢收），手感与系统推入不完全一样，但用户觉得自然。返回首页时空状态是否还跳，用户没有明确答复（待办里留着这一项）。

### 2026-10-28 请求正文改网页渲染、选项手感与「下一题」

用户在真机上用过之后提了三类意见：提问页的 Markdown 渲染没有 Mac 弹窗好（格式不一样、流程图画不出来、不能选字）；答案选项手感怪（选中是「渐变」出来的，显得软）；「下一题 / 完成」的逻辑与弹窗不一样（看过一些题没回答、往回滑，再点「下一题」会跳过它们）。第一类先做了 WebView 原型，在 iPhone Air 上实测延迟与内存，用户经 AskHuman 选定「正式实现：请求消息正文改用 WebView（一页一个；题干、列表卡片、实时卡片保持原生），先写 spec / plan 再做」，并在同一条回复里补上后两类，说明 spec / plan 只给我自己梳理思路、做记忆用，随后去休息，要求「全部弄好，明天早上查收」。所以下面的取舍都是我自行决定、用户还没看过，可否决，验收时一并处理：

- **网页渲染**（需求 `ios-web-markdown.md` W1–W17）：提问页的 Message、确认页的详情、历史详情里的同两处改由网页画；题干、列表摘要、Watch 卡片、附件预览仍是原生。同一套 markdown-it（`html:false, linkify:true, breaks:true`）+ Mermaid，版本取根 `package.json`、随 App 打包、完全离线；一个页面一个 `WKWebView`（每个都占一个 WebContent 进程，所以一页只放一个）。页面无特权：CSP 禁网、锁死导航、只有五个消息能回到 App；图片只显示内联 `data:` 的，网络与本地路径的图显示成「图片说明」胶囊（不联网取图，防止 Agent 的文本借图片泄露谁在看）；链接点了先弹域名确认。选字、复制整块代码、深色模式、Dynamic Type（含现场切换）都跟系统走。**与 Mac 的差别**：Mermaid 用 `securityLevel:'strict'` + CSP + 锁死导航，而 Mac 用 `sandbox` 重封装 iframe（Mac 那个页面带 Tauri 的特权接口，手机上这个页面没有）；对齐 `sandbox` 另案。页面加载不了 / 进程反复被回收 / 5 秒（模拟器 30 秒）没给出高度时回落原生渲染，页面照常可答；加载中页面整个透明、沿用同一段文字上次的高度，超过 0.6 秒才出现一个小转圈。Message 排好版之前多题表单不统计「看过」（否则 Message 还只有一行高时下面的题卡会被当成已在屏幕上、一下就能发送），等待上限 = 看门狗时间 + 1 秒。
- **原生渲染顺带修**：软换行改为换行（与 `breaks:true` 一致）、行内代码加浅底、文字可选。
- **选项手感**（需求 `ios-answer-flow.md` O1–O6）：根因是 `.plain` 按钮样式在按下时整行变淡再淡回，SF Symbol 换名又是交叉淡入，合起来就是「渐变选中」。现在自定义 `ButtonStyle`、指示器自绘、去掉继承的动画：按下立刻加深并下压，抬手一帧内翻转；选中行有强调色描边 + 淡底 + 实心指示器，未选行是中性灰底（一眼分得出）；每次点按一次触感（单选换项不响两下）。
- **「下一题」与「发送」**（F1–F11，对照弹窗 `usePopupCore.ts` 的 `goNext`）：「下一题」改成只看**位置**——落到第一张底边还在屏幕下方的题卡（放得下就整张露出，放不下先对齐顶部、再按一次看底部），不再看「看过」的历史，所以往回滑后不会跳过看过没答的题；落点那张卡闪一下（「减少动态效果」下不闪）。「发送」何时出现不变（最后一题底部进过屏幕，一旦出现不收回）。新增：「发送」出现后屏幕下方还有题时，旁边留一个次要的「下一题」图标按钮；「仅选择」没选全时计数下的提示可点，跳到第一道没选的题并闪一下；辅助字号下底栏改成上下排，按钮占满整行。
- 验证：Swift 包测试（`QuestionNavigator` 的位置 / 长卡片两步 / 无法量位置时的回退、`AnswerComposer` 闸门与草稿、Markdown 解析）；模拟器 UI 测试——作答流程的整套用例（新增「往回滑后再点下一题不跳题」「次要下一题按钮」「提示可点」「选项点按立刻翻转」；这一套一律用原生渲染，因为网页晚到几秒会把版面整体推走、点按落空）和网页渲染的一组用例（由网页画、原生回落、看门狗回落、点链接出域名、长按选字、确认详情、最大 Dynamic Type、深色、中文页面文字、Message 排版前不出现「发送」——做过变异验证，去掉等待后这条会失败——、从高 Message 走到最后一题），网页的一组在 iOS 27.0 与 18.5 两个模拟器上都通过；另外用 `simctl ui` 现场切换了 Dynamic Type 与深浅色，页面都跟着重排 / 重绘。
