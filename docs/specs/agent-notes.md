## 1. 背景与目标

Agent 手上常常还排着很多后续任务，这时它想先把一个结论告诉你——比如回答你之前问的一个问题——并不需要你做任何决定。现在只有两条路：发一个普通提问（它会停下来等你，耽误后面所有的活），或者不发（你不知道结果）。

更麻烦的是读完以后：对它的结论有疑问，现在只能先记在脑子里，或者记进待办。

目标：让 Agent 能发一条**不阻塞的留言**。它发出就继续干活；你在弹窗和手机上看到一张标明「无需回复」的卡，看完点「已收到」就行；有疑问就当场在卡里回复，回复会像插话一样送到 Agent，而不是留在你脑子里。

Cursor 的离开汇报（待阅汇报）本质上就是留言：Agent 发一份汇报，你回来再读。第四期把它迁到留言上，不再有单独的一套。

**非目标**：

- 不是聊天：没有 Agent 对留言再回复的会话线程；你的回复就是一次插话（D17–D21）。
- 不限次数，不加设置开关，不提供静音（D3）。
- IM 渠道不能回复，只能「已收到」（D9）。
- 不改普通提问、`--whats-next` 和插话的既有入口；不改中继（D4）。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 留言（Note） | Agent 发出的、不阻塞、不需要你回答的消息；由 Message 与附件组成，没有问题和选项。英文界面叫 Note |
| 无需回复 | 卡片标签「留言 · 无需回复」里的后半句：没有谁在等你这条的答案 |
| 已收到 | 留言的确认：点了只是告诉自己「看过了」，Agent 什么都收不到 |
| 插话 | 已有的功能（`agent-interject.md`）：把一段话在 Agent 下一次调用工具前送到它面前。留言的回复就走这条路 |
| 唤醒 | Agent 这一轮已经结束、但有原生续聊通道时，把回复发过去、开启新的一轮 |
| 续聊通道 | 能给「已空闲」的会话发消息的原生入口：Codex Desktop、Cursor Desktop、Pi、Antigravity App（以 `agent_control` 当前支持的为准） |
| 待答 | 列表标题里等你回答的提问数；留言不算待答 |

## 3. 决策记录

「第 N 轮」指第 N 轮 AskHuman 问答，原话与选项见 §10。

### 3.1 范围与语义

| 编号 | 决策项 | 结论 | 理由 / 否决后的代价 |
|---|---|---|---|
| D1 | 功能 | Agent 可以发一条留言：发出即返回、不等回复；内容只有 Message 与附件。弹窗和 iOS 把它显示成一张「无需回复」的卡 | 用户提出（原话 §10）。让 Agent 在有后续任务时能把结论先告诉你，又不拖慢它 |
| D2 | 名称 | 中文「留言」，英文 Note；卡片标签「留言 · 无需回复」，确认按钮「已收到」。Agent 侧的开关仍叫 `--async`（MCP：`ask` 加 `async: true`） | 用户觉得「异步消息」过于技术（第 2 轮批注），选了「留言」（第 3 轮 Q1）。`--async` 只有 Agent 看，它读到「不阻塞」最直接（§9 第 1 项请你确认） |
| D3 | 防滥用 | 宽松：不设次数上限，不加设置开关，不提供静音；只在 `--agent-help` 里写明「只用于不需要用户回答或决策的消息」 | 用户定（第 1 轮 Q3 选宽松；他对「数量上限」的追问是：长会话里很容易超过 3 条，所以不设上限） |
| D4 | 到达方式 | 和普通提问一样：弹窗展开并置前、桌面气泡；iOS 推送也和普通提问一样，中继不改 | 用户定（第 1 轮 Q4、Q5：「异步只是异步而已，和普通的没太大区别」） |
| D5 | 回复框 | 弹窗和 iOS 的留言卡都有回复框，也能加附注、图片和文件；什么都不写、只点「已收到」是最常见的用法 | 用户定（第 2 轮 Q1：「我觉得还可以有回复框」）。有疑问当场问，是这个功能存在的原因 |
| D6 | 主按钮随状态变 | 回复框是空的 → 「已收到」，淡色描边，点了 Agent 什么都收不到；写了字、或加了附注 / 附件 → 「插话」，实心强调色；Agent 这一轮已结束、有续聊通道 → 「唤醒」，点它先弹确认（D7）。状态表见 §4.1 | 用户定（第 2 轮 Q1：「发送按钮做区分，本来正常是已收到。当我做了附注，或者是写了回复，就变成插话。然后如果是已经空闲的，你再帮我想一个词」）；词「唤醒」是第 3 轮 Q2 选的 |
| D7 | 唤醒确认 | 点「唤醒」弹确认：标题「重新唤醒 Agent？」，正文「它这一轮已经结束了。发送后会开启新的一轮，会产生新的用量。」，按钮 [取消] [唤醒并发送]。从不在没有确认的情况下给空闲的 Agent 发消息 | 用户定（第 2 轮 Q1「点击就弹一个提示，说会重新唤醒之类的」；第 1 轮批注：Cursor 按次计费，「这种情况如果发出去，就要再扣费一次了。所以它和正常的提问回答也是有区别的」） |
| D8 | 回不了的会话 | 会话已结束，或没有续聊通道（Grok、认不出的会话）：回复框置灰停用，按钮仍是「已收到」；不写原因，也不加「存为待办」 | 用户定（第 1 轮 Q2：「我们现在在这些提问里面不是都可以添加待办吗？所以不需要额外的存为待办。如果你能禁用按钮，你就直接禁用就行了」）。弹窗的每张卡和 iOS 的每个请求页本来就有「添加待办」，留言卡照旧保留（§4.1、§4.3 的图里都能看到） |
| D9 | IM 渠道 | 只显示留言和一个「已收到」，不能回复 | 用户定（第 2 轮 Q1：「IM 通信渠道我觉得就不要给这种回复的能力了。就只给已收到就行」） |
| D10 | 旧版兼容 | 不认识留言的旧弹窗 / 旧 App 看到的是一条只有「已收到」一个选项的普通请求：能读、能点掉，没有回复框，也没有留言的样子 | 与现在的 Cursor 待阅汇报同一个形态（§3.7）；不为旧版让新功能降级 |

### 3.4 回复怎么送到 Agent

| 编号 | 决策项 | 结论 | 理由 / 否决后的代价 |
|---|---|---|---|
| D17 | 总规则 | 回复就是插话：送到「这个会话的 Agent」，并带上被回复那条留言的开头（让它知道你在回哪一条）。按 Agent 当下的状态走不同的路（D18–D21），**不会隐式开启计费的新一轮** | 用户定（第 1 轮 Q1：「我还是希望我的回复能送达 Agent，除非它已经结束了」，见 §10） |
| D18 | Agent 在工作 | 进插话队列，在它下一次调用工具前，用现有的 `[USER INTERJECTION]` 包装送达（多一段 `<in_reply_to>`，见 §4.4）。几条回复**依次追加**，不互相覆盖 | 现有机制，不动（`agent-interject.md`）。追加而不覆盖：回复是各自对着不同留言写的（N8） |
| D19 | Agent 正卡在另一个请求上 | 回复**并进那个请求的答案**一起交给 Agent，同时从插话队列里拿掉，不再等它下一次调用工具。这条规则对**所有来源的插话**都一样，不只是留言的回复 | 用户定（第 1 轮 Q1：「这个时候如果我插话了，也应该相同处理吧？」）。这个时候 Agent 正等着你的答案，它读到答案时最该一并读到你另外说的话 |
| D20 | 对 `agent-interject.md` D6 的修订 | D6 写的是「排队消息若未被消费就留队等下一回合，因为 Agent 结束前必调 AskHuman」。保留「回合内没有工具调用就留队」，**新增**：队列里有消息、而 Agent 正等着一个 AskHuman 请求的答案时，不再留队，而是随这个答案送达（D19）。具体边界见 N9 | 同 D19 |
| D21 | Agent 已空闲 | 有续聊通道 → 主按钮是「唤醒」，确认后经原生通道发送，开启新的一轮（D7）；没有 → 回复框停用（D8）。确认发生在客户端，Daemon 发送时再核对一次：Agent 已重新开始工作就按 D18 送达；客户端以为在工作、实际已空闲就拒绝并让客户端补确认 | 用户定（第 2 轮 Q1）；核对是为了不在竞态下悄悄计费 |

### 3.7 协议与兼容（按仓库既有规则做出，不是用户逐项确认的）

| 编号 | 决策项 | 结论 | 理由 |
|---|---|---|---|
| E1 | 请求上的标记 | 新增 `note: bool`，带 `#[serde(default, skip_serializing_if = "std::ops::Not::not")]`：CLI 交给 Daemon 的 `TaskRequest`（`ipc/mod.rs`）、`AskRequest`（`models.rs`）、手机 `AskView`、历史条目。弹窗前端用它推出列表里的类型「note」，**不新增 `PopupRequestKind` 变体** | `docs/overview.md`「IPC 协议号」：可选字段不 +1；新增枚举变体旧端可能收到就要 +1，所以不用变体 |
| E2 | 线上的回退形态 | 留言在线上仍带一个问题（题干为空）和唯一的选项「已收到」，并置 `select_only` 与 `single`——和今天的 Cursor 待阅汇报（`report_task`）同一个形态。认识 `note` 的新端隐藏这个问题、放开自由文本、画主按钮；不认识的旧端和 IM 渠道原样显示这一个选项 | D9、D10 靠它成立：IM 与旧端不用改就能读、能点「已收到」 |
| E3 | 不抬协议号 | `PROTOCOL_VERSION` 与 iOS `PROTO` 都不动。一种混用要说清：**新 CLI 对旧 Daemon** 发 `--async`，旧 Daemon 不认识 `note`，会把它当普通的单选项提问，Agent 会被挡到有人点「已收到」。这只会出现在新旧构建换代的窗口里（同协议号不同构建的互通是既有约定，`docs/overview.md`；换代时的排空与让位见 `daemon-graceful-drain.md`）；不为它 +1（§9 第 5 项请你确认） | `docs/overview.md`：能用可选字段解决的不要 +1 |
| E4 | 恢复存储 | 留言用现有的 owned 请求存储，不改 SQLite 结构、不动 `SCHEMA_VERSION`。`TaskRequest.note` 为 false 时序列化与原来逐字节相同（`skip_serializing_if`），已有任务的哈希不变；`src-tauri/src/daemon/recovery/fixtures/` 里已有的夹具不改 | `AGENTS.md`「Changing recovery storage」 |
| E5 | 手机的确认与回复 | 确认 = 选唯一的选项「已收到」（旧 App 也能做）；回复 = 一次不带选项、带文字 / 附件 / 附注的回答，另加可选字段 `wake: bool`（用户在客户端确认过唤醒）。`AskView.note` 与新的回复字段都缺省为空；新增能力位 `Caps.notes`，没有它的 Mac 不会发留言给手机 | `ios/wire.rs` 现有的可选字段与能力位做法（`Caps.annotations`） |
| E6 | 回复模式由 Daemon 算 | Daemon 按会话当下状态算出回复模式（插话 / 唤醒 / 停用），随请求发给客户端，会话状态变化时更新；规则复用 `agent_control::can_send_with`（`CanInterject`：未找到 / 控制通道启动中 / 空闲不支持 / 不支持 / 已结束 / 不在工作）。客户端只负责画，不自己判断 | 弹窗和 iOS 已经在为「发送消息」按钮收这些状态；留言只多一个消费者 |

### 3.8 我加的默认（用户没有单独确认过）

| 编号 | 默认做法 | 理由 |
|---|---|---|
| N1 | 回执：`[async_message_delivered]` 一行标记加一小段话，说明已送达、无需等待、回复会怎么到达（文本见 §4.4） | 要让 Agent 明白可以接着干活，也不要重发 |
| N2 | 离开模式下留言照常到达：不被自动回复拦下（它本来就不阻塞），弹窗、气泡、手机推送与普通提问一致 | 离开时人多半在手机上，留言正好推过去 |
| N3 | 历史：确认过的留言进历史，带「留言」标签，回复过的显示回复内容与送达方式（插话 / 并进答案 / 唤醒）；`--show-last` 不变 | 和提问一样可追溯；不给 `--show-last` 加新内容 |
| N4 | 页脚只留主按钮（和「附注 N」）：留言没有取消、稍后、快捷回复；`Esc` 只是关窗，不算取消 | 没有可取消的东西（§9 第 2 项） |
| N5 | 关窗、不点「已收到」：留言留在列表里，下次打开仍在，不自动清理，也不设 7 天自动归档 | 先不做自动清理，积压了再说（§9 第 3 项） |
| N6 | 角标：托盘、Dock、iOS 收件箱的角标把留言也算进去（都是还没处理的东西）；只有标题里「待答」单独数 | 看到角标就知道有东西没看（§9 第 4 项） |
| N7 | 键盘：主按钮就是 ⌘↵（或设置里的发送键），和提问的「发送」同一个位置；`Enter` 在回复框里照常换行或发送，由现有设置决定 | 不新增快捷键 |
| N8 | 回复的排队是「追加」：同一会话的几条回复各自带着被回复留言的开头，依次送达 | 弹窗的插话是「整体覆盖」，但留言的回复各自指向不同的留言，覆盖会丢话 |
| N9 | 并进答案（D19）只对 AskHuman 的提问和 What's next 生效；权限确认、Stop 确认的答案是交给 hook 的决定，不并入，消息继续留队（和今天一样）。What's next 里选了「结束」又带着并入的插话：不批准结束，只把话交给 Agent（沿用 `message-annotations.md` D5 的「结束 + 文字 = 继续」） | 避免把话塞进不读文字的决定；与附注一致 |
| N10 | 并进答案的写法：文本区块 `[user_interjection]`（标记恒英文、不本地化），被回复的留言开头放在 `>` 引用行，随后是正文与附件路径；JSON 顶层多一个 `user_interjections` 数组，每项 `{ "in_reply_to", "message", "attachments" }`，没有时不出现 | 与 `[user_annotations]` 同一套约定 |
| N11 | 被回复留言的引用：取留言正文的前 200 个字符，换行与连续空白压成一个空格，超出处用「…」 | 够 Agent 认出是哪一条，又不把长文再搬一遍 |
| N12 | 留言不参与重复提问收敛（`ask_dedup`）：回执明确说已送达，Agent 不应重发 | 留言没有问题可比较 |

## 4. 用户视角

### 4.1 弹窗里的一张留言卡

![弹窗里的留言卡：空回复、写了回复、唤醒确认、回复框停用](../assets/agent-notes/popup-card.jpg)

四张图是同一张卡的四个状态（浅色；深色已在原型里看过，同样成立）。

| 状态 | 回复框 | 主按钮 | 点击后 |
|---|---|---|---|
| ① 刚到，什么都没写 | 空，占位「回复这条留言」 | 「已收到」，淡色描边，带对勾 | 这条留言收起；Agent 什么都收不到 |
| ② 写了字，或加了附注、图片、文件；Agent 在工作 | 有内容 | 「插话」，实心强调色 | 送达 Agent（D18 / D19），这条留言收起 |
| ③ 写了内容；Agent 这一轮已结束，有续聊通道 | 有内容 | 「唤醒」，实心 | 先弹确认（D7）；确认后发送并开启新的一轮 |
| ④ 会话收不了回复 | 灰色、停用 | 「已收到」 | 同 ① |
| IM 渠道 | 没有回复框 | 「已收到」 | 同 ① |

### 4.3 iOS

![iOS：收件箱里的留言行、留言页、写了回复、唤醒确认](../assets/agent-notes/ios-flow.jpg)

- ① 收件箱：留言是一行，带一枚「留言」标签，和提问同一个列表；角标数的是收件箱里有几条（N6）。

- ④ Agent 这一轮已结束、可唤醒：按钮是「唤醒」，点它弹系统提示框，两个按钮并排；确认后发出。

### 4.4 Agent 看到的文字

**回执**（`--async` 返回，建议文本）：

```
[async_message_delivered]
Your message was delivered to the user. No reply is expected from this call: continue your work.
If the user replies, it reaches you as a [USER INTERJECTION] before your next tool call,
or together with the answer to your next AskHuman question.
```

**`--agent-help` 新增的一节**（英文版；中文版对应翻译）：

```
Non-blocking message (--async):
  AskHuman --async "<message>" [-f "<file>" ...] [--stdin]
  Use only for a message the user does not need to answer or decide on, e.g. answering a question
  they asked earlier while more work is queued. It returns immediately; do not wait for a reply.
  Not for asking questions, requesting decisions or reporting task completion (use a normal
  question or --whats-next). Takes no -q/-o/--select-only/--single/--output.
```

MCP `ask` 的描述多一句：`Set async: true to send message (and files) as a non-blocking note that needs no answer; it returns immediately.`

**回复送达（Agent 在工作）**：现有的插话包装，多一段被回复留言的开头：

```
[USER INTERJECTION] The user sent you the message below while you were working.
This tool call was blocked only to deliver it — the tool is not forbidden; re-issue
the same call if still appropriate.

<in_reply_to>
你之前问的「请求超时之后为什么没有自动重试」，我查完了： - `PairingClient` 的超时分支直接抛出…
</in_reply_to>
<user_message>
幂等键大概要改几处？如果不多，这一轮顺手做掉吧。
</user_message>

Adjust your plan if needed. If anything is unclear, ask the user as instructed.
```

**回复并进答案（D19）**：在该请求的结果里多一个区块：

```
[user_interjection]
> 你之前问的「请求超时之后为什么没有自动重试」，我查完了： - `PairingClient` 的超时分支直接抛出…
幂等键大概要改几处？如果不多，这一轮顺手做掉吧。
```

**唤醒**：经原生通道发出的新一轮消息同样带 `<in_reply_to>`（新一轮没有上下文，更需要它），其余按各通道现有的写法（例如 Antigravity 的 `[USER MESSAGE]` 包装）。

## 10. 讨论记录

**原话**（第 0 轮，你提出这个想法的两段）：

> 这个问题是我之前的一个想法。不过刚才我想到一个问题，就是Agent给我发一个这种消息的时候，如果我对它发的这个结论有什么疑问，我肯定是要立即回复给它的。要不然这个疑问我就需要记在我的脑子里，或者记在待办里了，这就很难受。所以这种异步的消息，我还是希望我的回复能送达Agent，除非它已经结束了。你帮我分析一下。

> 我想支持一个异步模式，就是当Agent有后续的很多任务等待执行的时候。它可以用异步的方式发起一个Ask Human提问，这个提问只是比如说回答我之前提出的一个问题，但是并不需要我做任何决策。然后我也不希望Agent滥用这个，只有真的是给我不阻塞的消息的时候才使用。然后这种消息在我们的弹窗还有iOS端都有特殊的表现。就是表达出来，这并不是等待我再回复的，是一个异步消息。可能需要设计一下UI，做的好看一点。另外我们现在Cursor在离开模式有一个待读报告，其实和这个类似。等这个做完了之后，待读报告也迁移到这个上面。就是待读的这种模式就自动变成一个异步消息，然后不去加额外的那些文字。

**第 1 轮**（七问）：

- Q1 回复怎么送：选「并进正在等的答案」，并补一句「这个时候如果我插话了，也应该相同处理吧？」→ D19，规则推广到所有插话。
