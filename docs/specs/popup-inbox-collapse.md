## 2. 现状与约束（来自代码，非假设）

### 2.1 窗口模型

- 合并窗口由左 Sidebar、正文和可选的右侧原生附件预览组成。**正文一次只显示一条请求**；Sidebar 从
  第 2 条请求起出现，之后保留到队列清空（D5）。Sidebar 通常 180–600、默认 240。
- 窗口是 transparent + Overlay 标题栏（保留红绿灯）+ 隐藏标题，材质 Solid / Blur / Glass 三态。
  原生最小尺寸 420×480（`popup_size`），Sidebar / 预览展开时更宽（`Allocation::minimum_width`）。
  小窗必须临时绕开这些下限。
- macOS 使用固定原生画布（`swift/PopupCanvas.swift`）：WebKit 视口固定，窗口裁切与画布原点在同一
  原生事务提交，不逐帧 resize WebView、不用截图交接。Sidebar / 预览的展开收起现在是 **0ms 即时提交**
  ——用户曾因抖动明确要求取消慢速展开动画（主规格 §17）。因此本需求的缩小 / 展开动画是这条路径上的
  **新增动画**，必须先在独立原生窗口原型验证，浏览器截图不能代替（主规格 D17、§9）。
- 导航顺序：`inboxGroups` 按项目分组、组内按到达序；`nextInboxRequest` 实现 D6「答完选下一条，当前
  项目优先，末尾循环」。「跳过次要」只需给它增加一个排除集合。
- 底栏当前是「取消（左）+ 发送（右）」，多题为「取消 + 上一个 / 下一个 / 提交」；请求级动作放在这里，
  窗口级动作（置顶、设置等）在顶栏右侧。

### 2.2 置顶

- 置顶初值是 `general.alwaysOnTop`（默认开）；顶栏图钉按钮可改（`setAlwaysOnTop`），状态由
  `PopupInboxView` 的 `pin` 在各请求之间共享，每轮结束重置。每轮首次呈现时宿主再按配置设置一次。
- 小窗若与展开态是同一个原生窗口，置顶自动沿用；若另起窗口，必须同步同一状态。

### 2.3 会被牵动的现有机制

| 机制 | 现状 | 需要回答的问题 |
|---|---|---|
| 到达气泡 | 第 2 条起，从作答区中央飞入 Sidebar 的 10pt 蓝点 | 小窗来新提问会自动展开（C4），气泡是否还需要 |
| 未读蓝点与 ripple | 按请求独立，真正显示正文才清除 | 次要请求的未读提示是否继续；小窗里是否展示 |
| 草稿、选区、阅读状态 | 按请求独立保留（D9） | 缩小 / 展开往返必须无损 |
| 答完换题（D6、§18） | 发送成功后自动选下一条并 300ms 接替 | 改为跳过次要；剩余全次要时缩小 |
| 关闭确认层 | 窗口内确认层（⌘W / 原生关闭） | 小窗下不可见，需约定入口 |
| 右侧原生附件预览 | PDF / Quick Look 是画布子视图 | 缩小时隐藏，展开恢复位置与阅读状态 |
| 托盘「聚焦待答」/ 外部终态（D13） | 选中并前置指定请求；当前请求被远端终结则切下一条 | 小窗下需展开 / 跳过次要 |
| 尺寸记忆 | `persist_popup_size` 过滤预热、最大化、收尾事件 | 小窗尺寸**绝不能**当成偏好写盘，需新增过滤 |
| 空队列 | 窗口隐藏，按 popupPrewarm 保留或退出宿主 | 标记与小窗位置随本轮结束重置 |

### 2.4 平台

固定画布与逐帧原生几何目前只有 macOS；Windows / Linux 沿用离散几何提交（主规格 §6），其实机绘制验收
本来就是延期 gate。

## 3. 分析结论

1. ~~正文一次只显示一条，所以「部分折叠」在视觉上没有区别。~~ **已作废（第 1 轮后）**：这是把「折叠」
   误解为「收起正文」得出的结论。用户的真实意图是给每条提问打「次要」标记，标记有实际作用：决定窗口
   是否缩小、答完换题跳过谁、新提问是否触发展开。逐条标记是必需的（C1、C2）。
2. **动画走已验证的技术路线**：沿用固定画布 + 原生裁切，WebView 视口不变、正文不 reflow；窗口裁切与
   画布原点由原生 display-link 逐帧一次提交，内容用 DOM 不透明度交叉淡化。公开 API 即可，不需要私有
   WindowServer 接口（上一轮提醒动画用过，生产路径已移除）。这是技术假设，需在原型里用真实 NSWindow
   测量与目测确认。
3. **置顶无新增设计**：小窗跟随当前窗口置顶状态即可（C7）。
4. **数据与视图分两层**：每请求的次要标记是数据；窗口「展开 / 小窗」是由标记派生的视图状态。唯一的显式
   例外是用户主动打开某条次要提问浏览时窗口保持展开（见 §4 Q7）。
5. **「占用可控」与「显眼」互相牵制**：列表要有行数上限才可控；要显眼就需要强调色、持续未读提示等。
   两者的取值适合在原型里用档位调，而不是现在拍数字。

### 5.1 暂定规则（C8：用户授权先按建议推进，原型阶段复核）

- R1 状态：每条待答请求是「主要」或「次要」，新请求默认主要。标记只改变本地呈现，不取消、不发送，
  不改变各渠道抢答和 Daemon 终态契约，草稿原样保留；普通提问、权限、Stop 都可标记。
- R2 窗口：存在任一主要请求时窗口展开；所有待答请求都是次要时缩成小窗。窗口因浏览或答完跳转而在「全部都是次要」时保持展开
  （peek），激活窗口离开 AskHuman 后缩回小窗（R11）。
- R3 标记当前请求：还有其他主要请求时，正文切到下一条主要请求（顺序同 D6，跳过次要）；否则缩成小窗。
  当前请求已经是稍后答时底栏按钮是「取消稍后答」：只取消标记，窗口和正文不动（C24）。
- R4 答完换题：发送成功后选下一条主要请求；没有主要请求时，**用户在场**则跳到下一条稍后答（顺序同 D6，窗口保持展开），
  窗口已是小窗、或远端终结而没人在看则缩成 / 保持小窗（C22；第 5 轮前的原文是「没有主要请求就缩成小窗，即使还有次要请求」）。
- R5 新提问：默认主要。窗口已缩小时自动展开并显示它；窗口已展开时沿用 D7，不切换当前正文。
- R6 外部终态与托盘聚焦：当前请求被远端终结按 R4 处理（「用户在场」取决于 AskHuman 是否为激活应用）；托盘等入口显式聚焦某条（含次要）时展开并打开它。
- R7 次要请求可随时浏览与回答，作答、草稿、选区、阅读状态与主要请求完全一致；未查看的次要请求，
  蓝点和 ripple 继续保留直到真正显示其正文。浏览时标记保留（C9）。
- R8 小窗：占用可控（迷你列表宽度沿用用户拖出的 Sidebar 宽度、行数有上限并可滚动；胶囊固定尺寸）、
  显眼（按置顶设置保持置顶、未读蓝点与 ripple 继续、强调色描边 / 光晕）；具体档位在原型里调。
- R9 本轮结束：队列清空窗口隐藏，所有标记和小窗位置重置；下一轮首条仍是普通弹窗。
- R10 尺寸记忆：小窗尺寸绝不写入窗口尺寸偏好；展开时恢复缩小前的尺寸。
- R11 切走缩回（C23）：窗口展开、没有主要请求（全部稍后答）、激活应用不再是 AskHuman → 缩回小窗；有主要请求时不缩，窗口已是小窗时无动作。
- R12 手动缩回（C27）：peek（窗口展开、没有主要请求）时 Sidebar 标题栏有「缩回小窗」图标，点击缩回小窗；有主要请求或窗口已是小窗时没有这个入口 / 无动作。
- R13 拖入文件（C28，C31 修订）：拖着文件在**小窗**上停留（默认 500ms）→ 展开成 peek，打开指针所在行的请求（标题 / 空白处：默认目标）；展开后文件在**另一条** Sidebar 条目上停留（默认 250ms）→ 正文切到该请求（不改标记）；等待中的行有进度条。
  松手**不等任何停留**，按指针下的目标立即投放：落在条目上 → 该请求（当前题），落在正文上或别处 → 当前请求（窗口原本是小窗则投给默认目标），小窗上直接松手 → 展开并附加；投放后显示接收文件的请求。
  拖进来又拖走没松手 → 若这次拖拽展开了窗口且没有主要请求，宽限后缩回。
- R14 新一轮不漂移（C30，正式实现要求）：一轮结束后下一轮首条请求的正文出现在上一轮结束时正文所在的位置（用户中途拖动过则以拖动后的为准），多轮循环后 x 不变。窗口位置以「正文锚点」为准，不以带 Sidebar 窗口或小窗的左缘为准；
  小窗被拖动后，本轮内展开以小窗为锚（C5），但下一轮仍回到锚点（产品现有 `reset` 语义）。原型不处理（用户确认原型里这样没事）。
- R15 多题落点（C32）：落点是「某请求的某一题」。顺序布局只有当前题可选（底栏「上一个 / 下一个」切换，拖拽中不选题）；纵向布局落到指针下的卡片，卡片之外落当前题；条目 / 小窗上松手落该请求的当前题（没看过的请求就是第一题）。
  提示：整块正文或那张卡出现虚线框，胶囊写「松手添加到第 N 题」（单题请求写「松手添加到当前请求」）。
- R16 边缘自动滚动（C31）：拖拽中指针进入 Sidebar 列表或正文区域上 / 下边缘 56px 内 → 该区域朝那个方向自动滚动，越靠边越快（平方曲线，上限约 900px/s）；离开边缘区、松手、拖走即停；
  滚动期间指针下的目标随内容变化（行 / 卡高亮跟着变），停留切换的计时随之重来。

### 6.4 第 3 轮反馈的处理（2026-10-17）

原话见 §1.4。

**① Sidebar 出现时界面跳动（原型与生产不等价）**

- 生产是怎么做到不跳的（读代码确认，`PopupCanvas.swift`、`popup_canvas.rs`、`popup_inbox_geometry.rs`、`PopupInboxView.vue`）：
  WebView 在固定画布里，画布左侧**永久**预留一块屏幕外区域；正文永远钉在画布 x = `canvas.left`，Sidebar 在它左边。
  Sidebar 出现时前端先把当前使用宽度冻结（`prepare`），下一帧再提交（`commit`）：原生在**同一个无隐式动画的事务**里把窗口
  向左加宽、把画布右移同样距离，被揭开的那一列在屏幕外早已画好；正文的画布坐标全程不变，也没有任何 reflow。
- 原型旧做法的问题：布局用流式宽度，`prepare` 把视口加宽时 DOM 还是旧布局，正文被重新排版并位移了至少 2 帧；Sidebar 还带
  176ms 淡入，行进入有过渡。这解释了用户看到的「跳一下」，也说明原型没有评估到生产的真实体验。
- 现在的做法（原型与生产同一套协议）：页面把正文和 Sidebar 都用 CSS 变量 `--v`（窗口左缘在画布里的 x）定位，正文固定在
  `--v + --span`，小窗列表 / 描边 / 胶囊都相对 `--v`。每轮起点 `canvasV = 屏幕外预留 − Sidebar 额外宽度`。Sidebar 增长分两步：
  ① 页面先切换到最终布局（`canvasV` 减去额外宽度、新列在屏幕外，视口大小不变，所以可见内容不变）；② 一次原生 0ms 提交：窗口向左长出
  额外宽度、画布右移同样距离。折叠 / 展开期间画布原点保持不变。Sidebar 的淡入与行进入过渡在增长期间关闭。
- 原生新增：`PopupCollapse.swift` 的动画驱动支持画布原点起止值，并保证进入时保留已有的屏幕外预留。
- 验证：新增「窗口自截图」能力——用 CoreGraphics 的窗口图像接口（运行时 `dlsym` 取符号，只截本应用自己的窗口，macOS 27 上不需要
  屏幕录制 / 辅助功能权限）拿到真实合成像素（含 WebKit 与材质），并对指定屏幕区域做逐像素对比。Sidebar 增长时：偏屏外布局步骤后
  可见区域 0.000% 像素变化；提交前后正文区域 0.000% 变化（平均差 0.33 / 255，属抗锯齿噪声）；被揭开的 Sidebar 列在提交瞬间已有内容
  （亮度标准差 18.6）；窗口恰好增宽一个 Sidebar 宽度、高度不变、正文位置不动。人工看了前后对照拼图，没有错位。

**② 行内按钮不直观**

原因：已次要的行显示的是「展开」类图标，而用户这时正在浏览这条已收起的提问，图标语义与处境相反。原型现提供 3 种样式（控制器
「行内按钮」切换，默认是文字，直接说明动作）：文字胶囊（「暂时收起 / 取消收起」）、时钟 / 撤销箭头、下沉 / 上浮双箭头。均已截图
目视确认悬停态不遮挡标题。该入口的最终样式由用户选定。

**③ 小窗状态新提问到达后没有气泡**

原型原先在窗口展开后不播放气泡。现在直接复用产品的 `InboxArrivalNotice` 与同一套时序和几何（气泡从作答区中央出现、弹跳两次、
飞入 Sidebar 行的蓝点、落点闪一下），在小窗展开动画结束后立即播放；气泡期间蓝点保持隐藏，收起或终结会取消。已在原生窗口里抓取
弹跳、飞行、落点三个时间点确认。需要用户决定的语义（控制器「展开后正文」）：

- 显示新请求（C4，默认）：展开后正文就是新请求，气泡落在已选中的那一行，作用主要是「提示它来了」；
- 保持原正文：展开后正文是小窗本来会打开的那条，新请求保持未读，气泡落在未读行，与窗口已展开时的 D7 一致。

**④「原型一旦出现边栏就出现不了收起的状态了」**

没有复现。已排查并用脚本验证：有 Sidebar 时用鼠标逐条标记 / 恢复 / 底栏收起 / 小窗列表打开与恢复；小窗期间新提问到达使 Sidebar
出现后再次收起；7 种外观组合下的收起 → 展开 → 再收起；全部都能到达小窗。同时发现测试脚本本身的一个缺陷（点击处理函数启动的
切换在页面状态变为「动画中」之前，状态读到的仍是「空闲」），已修为「有未完成的结果即视为进行中」，不影响交互行为。
可能的理解有几种：有 ≥2 条主要请求时底栏「暂时收起」只会切到下一条（R3），要全部标记才缩成小窗；行内图标看不懂所以没能把
每一条都标记；或是旧版 Sidebar 出现路径上的问题。已列入下一轮提问请用户确认。

**⑤ 点击切换请求时的正文动画**

用户认可原型里点击 Sidebar 条目切换请求时正文带的淡出 / 滑入动画，要求正式实现时加到合并窗口（C17）。

### 6.5 第 4 轮反馈的处理（2026-10-17）

原话见 §1.5。

**① 行内按钮：归档盒（C18）**

- 同一个位置、三种外观：主要请求的行悬停时是文件盒图标（`暂时收起`，Lucide `archive` 风格）；点击后该位置变成常驻的
  「▣ 已收起」灰色小标签；悬停这一行时标签交叉淡化成强调色的「⤓ 取消收起」按钮（`archive-restore` 图标）。两段文字叠在同一个网格
  单元里，所以切换时按钮不变宽。已用原生窗口截图目视确认静止态与悬停态（`.askhuman-dev/popup-collapse-shots/rowaction-archive*.png`）。
- 细节：标签会压到标题行尾，所以展开态里次要行的标题右侧让出 70px（标记那一刻标题会重排一次）；原先元信息行里的「已收起」小标签在
  该样式下隐藏（信息重复）；小窗里所有行都是次要，不显示常驻标签，只在悬停时出现「取消收起」，保证小窗列表不被标签占位。
- 控制器「行内按钮」多了「归档盒」并设为默认；旧的 localStorage 里存的「文字」会跟随新默认。

**② 新一轮首条请求不出窗（C20）**

根因：一轮结束时原型把窗口隐藏，但之后到达的请求只更新了页面模型，既没有重新起一轮也没有重新显示窗口；第二个请求才走「前置」路径把

显示窗口）；`endRound` 的延迟隐藏在宽限期结束时先检查是否已有新一轮，避免新请求刚显示就被隐藏。S13 覆盖这三种情形。

**③ 小窗到达后的展开状态（C19）**

原型现状已满足：窗口已展开时新请求只播放气泡与未读提示，不换正文、不动窗口；窗口由小窗展开时显示新请求并播放气泡。只做了确认。

**④ 窗口折叠 / 展开过程偶发跳动：排查记录**

用户：「不是每次都有但挺容易出现」。以下是花了较多时间建立的显示器层面测量和结论，供下一轮判断与后续取舍。

- 测量工具（均在原型里，`./scripts/popup-collapse-demo.sh --video`）：作答窗口后放一个纯品红背景窗口，另一个独立进程
  `scripts/popup-collapse-frames.swift` 用 ScreenCaptureKit 取该区域的每一帧（带显示时间戳，不经过视频编码），统计每帧里非品红像素的
  包围盒＝窗口大小。指标：**gap**（相邻两个运动帧间隔 >1.5 个 vsync，显示器这一拍没有新内容）、**repeat**（运动中连续两帧窗口大小相同再接一个双倍步长，即
  肉眼可见的顿一下）。每次切换里驱动还逐帧记录：回调到达时刻、放置结束时刻、目标显示时刻、放置的窗口大小（`lates / ends / targets / widths / heights`），
  用 `ASKHUMAN_DEMO_QUERY="cycles=…&rounds=…&variants=…"` 选变体，`rounds` 让变体轮流穿插，避免机器负载的缓慢变化只落在某个变体上。对照变体有 `ctl-driver`
  （同一套逐帧 `setFrame`，但窗口里没有网页）、`ctl-appkit`（AppKit `animator().setFrame`）、`ctl-layer`（窗口不变，只用 Core Animation 动画一个图层）。
  `--burst`（自己的窗口自截图）会明显干扰主线程，只能看撕裂，不能用来判断流畅度。
- 发现 1（时序）：驱动原先只统计 display-link 的**调度时间戳**间隔，所以「掉帧 0、间隔恒 16.7ms」并不能说明画面是均匀的。逐帧时序显示：`NSWindow.displayLink`
  的回调在自己的 `targetTimestamp` 前约 1ms 才到（距唤醒它的 vsync 约 15.3–17.8ms），此时放置的窗口大小**首次出现在目标时刻之后的第 2 个 vsync**（中位延迟 33.8ms，
  恒定的 2 帧延迟本身不可见）。放置结束时刻与结果的关系（557 个 tick）：结束在 19ms 内的约 4–6% 会晚一个 vsync，19–22ms 约 18%，22–24ms 约 38%，
  24–28ms 约 69%，≥28ms 100%。晚一个 vsync 的 tick 会被下一个 tick 覆盖，表现为「同一帧显示两拍，再跳两格」＝repeat。正常相位正好落在这个槽位的中央
  （两侧各约 8ms 余量），所以平移相位换不来更多余量，剩下的杠杆只有减少每帧耗时与抖动。
- 发现 2（同条件对比）：把变体轮流穿插后，负载高的时段里所有窗口动画机制都会卡——本弹窗、同样逐帧 `setFrame` 的纯窗口（`ctl-driver`）、AppKit 自己的
  `animator().setFrame`（`ctl-appkit`）每次切换都有 1–5 次 gap / repeat，页面是否可见、有无阴影、有无页面动画、窗口材质 blur / solid / glass 之间的差别都淹没在运行间波动里
  （单次运行每切换 0.0–6.8 次事件）。唯一从不出现 repeat 的是「窗口不变、图层做 Core Animation」（`ctl-layer`），但它依赖窗口外框不随动画变化，
  原生 titled 窗口的圆角 / 阴影 / 材质都绑在窗口 frame 上，用不了。
- 发现 3（环境）：机器安静的那几分钟里，本弹窗连续 8–10 次切换 **0 次**卡顿（共 4 次这样的运行，Blur 与 Solid 材质各 2 次）；繁忙时（本机 WindowServer 常驻 70–85% CPU，
  同时跑着 Xcode、iOS 模拟器、画中画 / 录屏类应用，load average 10–20）连纯窗口对照都是每次切换约 5 次。**更早那轮「页面可见内容 / 阴影 / 动画是主因」的结论作废**：
  当时各变体是依次而不是穿插运行的，卡顿的单调下降只是恰好赶上机器变安静。测量用的屏幕流本身也会给 WindowServer 加负载。
- 结论：动画驱动本身在机器安静时是流畅的；用户看到的「不是每次都有」与负载尖峰一致，但**需要用户在自己的环境里确认**（出现时机是否与其他重负载应用、录屏 / 画中画有关）。
  若确认与负载无关，候选补救（均未做，需用户同意）：① 精简逐帧放置（去掉 `displayIfNeeded()` / `CATransaction.flush()`，收益小、可能带回撕裂）；
  ② 动画期间用不变大小的无边框代理窗口 + Core Animation 播放快照，结束时再换回真窗口（唯一测到不重复帧的机制，但阴影 / 圆角 / 材质 / Glass 保真度与实现复杂度都要权衡）。

**⑤ 对正式实现的提示**

  悬停也不会切换请求。要满足「一次拖拽到达任何待答请求」，正式实现需要新增：小窗进入即展开、Sidebar 条目作为投放目标（含悬停切换）、
  向非当前请求投放（目前每个请求各有自己的 popup core 实例，只有当前那个在监听）。
- 原型实现（`CollapseStage.vue` 的 `onDragDrop`，沿用同一套 Tauri 原生拖放事件）：
  - 进入（`enter`）：〔第 7 轮起改为停留展开，见 C31、§6.8 ①〕小窗状态 → 展开成 peek，打开默认目标（同点击小窗）；已展开则不变。拖拽期间整个窗口进入「拖拽态」：所有请求行有淡描边，指针下的行高亮为投放目标，
    小窗的强调描边变成实线加粗；指针在正文上时整块正文出现虚线框和「松手添加到当前请求」。
  - 悬停（`over`）：展开窗口里，文件在**另一条**请求的行上停留 `dragSwitchMs`（默认 250ms，控制器 0–800ms，0＝立即）→ 正文切到它（同点击，不改标记，窗口不动）；中途移到别的行会重新计时。
  - 松手（`drop`）：落在行上 → 文件加到那条请求（**不等**切换完成：快速划过再松手也投到松手那一行）；落在正文上或别处 → 加到当前请求（窗口是小窗则加到默认目标）；
    随后显示接收文件的请求（小窗会因此展开），提示条「已添加 N 个文件到「…」」。
  - 拖走没松手（`leave`）：如果这次拖拽展开了窗口、且没有主要请求，600ms 宽限后缩回小窗；宽限内重新拖回则取消；控制器「拖走后缩回」可关。
    （因为 peek 是在 AskHuman 不是激活应用时打开的，没有「切走」事件会再来收它，不缩回的话它会一直占着屏幕。）
  - 松手后 AskHuman 前置并取得焦点（控制器「松手后前置」可关）：同样为了让之后的「切走」能触发缩回（C23），也方便接着打字。拖拽进行时不触发「切走缩回」。
  - 附件的呈现：正文底部一排附件条（文件名 + 移除），Sidebar 行的元信息里有「附件 N」，附件算「已有内容」（可以只带附件发送）。原型只列文件名，不读文件，不限制类型。
- 一个会咬到正式实现的坐标坑（读 wry 源码，原型里用 `demo_info` 修正）：wry/macOS 的落点 y 是 `webview.frame.height − draggingLocation.y`（x 是窗口坐标，只需要加画布原点），

  展开动画中也一样（差值逐渐减小到 0）。原型在窗口未稳定（小窗或动画中）时读 `viewH − 窗口高` 修正；稳定后 WebView 与窗口等高，不需要修正。

  松手投放到任意行（含从未切换到的行）与正文、附件条与「附件 N」、拖走缩回 / 宽限内拖回 / 关闭开关 / 期间到达主要请求不缩、直接松手在小窗的行上。
  **真实的 Finder → 窗口原生拖放无法脚本化（不碰鼠标），需要用户亲手试**；原生事件能否在小窗的固定画布上正常送达，要在这次体验里确认。

**⑤ 新一轮窗口位置漂移（C30，正式实现要求，原型不改）**

- 现象（用户看原型自动测试时发现）：Sidebar 出现时窗口向左长出一个 Sidebar 宽度（D5，正文不动）。原型一轮结束后，下一轮没有 Sidebar 的窗口沿用的是带 Sidebar 窗口的 x，
  所以正文每轮往左挪一个 Sidebar 宽度，连续几轮后窗口逐渐跑到屏幕左边。用户明确：原型里这样没事，**正式实现不能这样**。
- 产品现状（读 `popup_inbox_geometry.rs` / `commands.rs`）：几何控制器以正文锚点 `anchor`（正文左上角）为准，Sidebar 出现时窗口 x = `anchor.x − Sidebar 宽 − 分隔线`；
  用户拖动窗口时 `moved()` 把 `anchor` 更新为 `窗口 x + Sidebar 宽 + 分隔线`；一轮结束时 `popup_inbox_idle` 调 `reset`（`prepare(sidebar=false, preview=false)` + 提交），
  窗口回到 `anchor.x` 后清空控制器状态，下一轮的锚点从这个（无 Sidebar 的）窗口重新取。所以产品今天不漂移。
- 对正式实现的要求：新增小窗后这条不变量不能破——小窗里 Sidebar 列的左缘和小窗左缘重合（小窗宽 = Sidebar 宽），所以小窗被拖动时 `anchor` 必须按「小窗 x + Sidebar 宽 + 分隔线」同步
  （或统一改成记录窗口左缘再换算）；缩小 / 展开 / Sidebar 在小窗期间才出现 / 一轮在小窗状态下结束，几种路径结束时都要让 `reset` 把窗口放回正文锚点，而不是放回当时的窗口左缘。
  验收要有「多轮循环（含 Sidebar 增长、缩小为小窗、小窗拖动、在小窗状态结束一轮）后，下一轮首条正文 x 不变」的自动化覆盖。

**⑥ 拖进小窗不展开（第 6 轮试用发现的缺陷，已修复）**

- 现象：用户用 Finder 真拖，文件进了小窗但窗口不展开。第 6 轮的自动测试没有发现，因为它们逐条 `await` 事件，而真实事件是连发的。
- 原因（用自动测试复现过：小窗仍是 `260×290`）：原生事件形态是 `enter`，约 1ms 后第一个 `over`，之后每几 ms 一个 `over`。旧的 `onDragDrop` 对每个事件并发处理，
  每个事件先 `await` 一次读窗口几何（`demo_info`），读完后发现自己已被更新的事件取代就直接丢弃——**`enter` 总被紧跟的 `over` 取代而被丢弃**，
  而只有 `enter` 会展开窗口，`over` 不会，窗口于是永远不展开。
- 修复：原生拖放事件按顺序一次处理一个（`dragChain`），堆在慢步骤（展开动画）后面的 `over` 合并成最新的一个（只有最新位置有意义）；`enter` 和 `over` 都能开窗
  （首个事件是 `over` 也行，万一漏了 `enter`）；`leave`、`drop` 不会被丢弃，并且排在展开之后（松手时窗口还在展开，会在展开完成后按当时的布局落点）。
  `--auto` 的 S17 新增「`enter` + 连发 `over`、不 `await`」和「只有 `over`」两种用例：修复前失败，修复后通过（现 312 项）。
- 诊断：交互运行（非 `--auto`）时，页面把拖放过程写进 `.askhuman-dev/popup-collapse-demo.jsonl`（`label: "drag"`：事件类型、原始坐标、画布原点、y 修正量、视图、命中目标；
  `over` 只在命中目标变化或每 400ms 记一条），下次真拖有问题时可以直接读回，不用用户描述。
- 对正式实现的提示：产品的 `onDragDropEvent` 处理同样要按序处理 / 合并，不要在每个事件里并发 `await` 后再用「是否被取代」丢弃（产品现在的处理是同步的，没有这个问题）。

**⑦ 多问题请求怎么落点（用户第 6 轮试用提出；第 7 轮已回答并实现，见 §1.8、C31、C32、§6.8）**

- 用户的问题：「如果一个消息有多个问题，我无法选择问题？」——要求一次拖拽能落到**某个请求里的某一道题**，不止到请求这一级。
- 产品现状（读 `usePopupCore.ts`、`SequentialPane.vue`、`docs/specs/multi-question-vertical.md` §I1）：一个请求可以有多道题，附件、回答都按题归属（`imagesByQ` / `replyFilesByQ`）。
  - 顺序布局（默认）：一次只显示一道题，底栏「上一个 / 下一个」切换；拖入的文件落到**当前题**。
  - 纵向布局（实验开关 `experimental.verticalQuestions`，默认关）：所有题的卡片纵向平铺；拖拽时高亮指针下的那张卡，松手落到那一题（`dropTargetQ`、`questionAtPoint`）。
  - Sidebar 条目是请求一级，没有题的概念。
- 结论：用户要的是 Finder 式的「停留展开 + 边缘滚动」，顺序布局只拖到当前题，纵向布局靠边缘滚动够到各张卡，在小窗标题上直接松手则展开并附在第一题（C31、C32）。

### 6.8 第 7 轮：Finder 式弹簧加载与多题落点（C31、C32，2026-10-17）

原话见 §1.8。

**① 停留展开 / 停留切换 / 边缘滚动（C31，R13、R16）**

- 小窗上：`enter` / `over` 落在某一行 → 这一行成为「等待目标」，`dragExpandMs`（默认 500ms，控制器 0–1500ms，0＝立即）后展开成 peek 并打开那一条；落在标题、空白、描边上 → 等待目标是默认目标
  （`defaultOpenTarget`：记住的上次浏览 → 第一条没看过的 → 第一条）。匆匆划过（等待没到就移开 / 离开）什么都不开。
- 展开后：落在**另一条** Sidebar 条目上，`dragSwitchMs`（默认 250ms，0＝立即）后正文切到它；等待中的那一行底部有一条随时间填满的进度条（`.dwelling`）。
- 防连环：某次停留触发展开 / 切换时记下指针位置，指针移动不足 4px 不开始新的等待（展开后窗口布局变了，原位置下可能换成另一行，不应该紧接着又切）；动画进行中也不开始新的等待。
- 边缘滚动（R16）：Sidebar 列表和正文的上 / 下边缘 56px 内，每帧按平方曲线推进 `scrollTop`（上限约 900px/s，浮点累加，避免低速时被取整吃掉）；指针移出边缘区、`drop`、`leave` 即停；
  每次滚动后重新对指针下的目标做命中判断（行 / 卡高亮跟着内容走）。
- 松手：不等任何等待，按松手瞬间指针下的目标投放（见 ②）；松手在小窗上 → 展开并附加。
- 事件处理沿用 §6.7 ⑥ 的串行 + 合并；等待用定时器，不占事件链，`leave` / `drop` 随时能取消它。

**② 多题请求与落点（C32，R15）**

- 原型新增「多问题请求」：控制器「多问题提问 +1（3 题）」产生一个三题请求（「发布前的三个确认」：选环境 / 要不要迁移数据 / 补充说明）；回答、附件都按题归属，每个请求记着自己的当前题。
- 「多题布局」旋钮（控制器）：
  - **顺序**（默认，同产品）：一次一道题，页眉「第 i / n 题」，底栏「上一个 / 下一个」；拖拽中**不选题**，文件落当前题；
  - **纵向**：所有题是卡片，纵向平铺，当前题的卡有淡强调色；拖拽时指针下的卡有虚线框和胶囊「松手添加到第 N 题」；卡外落当前题；够不到的卡靠边缘滚动。
- 落点表（松手瞬间指针下是什么 → 文件去哪）：

  | 指针下 | 文件去哪 | 之后 |
  | --- | --- | --- |
  | 小窗上的某一行 | 该请求的当前题（没看过的请求就是第一题） | 展开并打开它 |
  | 小窗上的标题 / 空白 | 默认目标的当前题 | 展开并打开它 |
  | 展开后某条 Sidebar 条目 | 该请求的当前题 | 正文切到它 |
  | 正文（顺序布局 / 单题请求） | 当前请求的当前题 | — |
  | 纵向布局的某张卡 | 那一题 | 该请求的当前题改为那一题 |
  | 纵向布局的卡外 | 当前请求的当前题 | — |

  提示条：「已添加 N 个文件到「标题」的第 q 题」（多题）/「已添加 N 个文件到「标题」」（单题）。

**③ 验证**：见 §6.2 的第 7 轮记录。真实的 Finder → 窗口拖放（尤其是小窗上固定画布里的原生事件送达、停留的手感）无法脚本化，需要用户亲手试；交互运行会把拖放过程写进 `.askhuman-dev/popup-collapse-demo.jsonl`（`label: "drag"`），有问题可以直接读回。

**④ 派生细节（用户试用后：第 2 项明确选了「当前题」，等待时间 / 边缘滚动 / 手感选了「合适，保持默认值」，其余没有异议，按现状进入实施）**

1. 「小窗口标题」的理解：停留在**某一行**上 → 展开那一行的请求；停留在标题 / 空白处 → 展开默认目标。
2. 直接在小窗上松手附在「当前题」而不是字面的「第一题」（没看过的请求两者一致，请求已被翻到后面的题时才不同）。
3. 两个等待默认值 500ms / 250ms、进度条样式、防连环的 4px 阈值。
4. 边缘区宽度 56px、最高速度约 900px/s、平方曲线。
5. 纵向布局里松手后，该请求的当前题改为落点那一题。
6. 提示胶囊的位置：顺序布局在正文中央，纵向布局在卡片右上角。

**⑤ 对正式实现的提示**

- 产品里每个请求各有一个 popup core 实例，只有当前请求监听 `onDragDropEvent`；要做到「一次拖拽到达任意请求」，需要窗口级的一个监听者按落点把文件交给对应请求的 core（含当前没显示的请求），并在其中做停留展开 / 切换、进度提示、边缘滚动和命中判断。
- 按题落点复用产品已有的 `imagesByQ` / `replyFilesByQ` 与 `addDroppedPaths(paths, qIndex)`；顺序布局落「当前题」，纵向布局沿用 `questionAtPoint`。
- 命中判断的 y 要按 §6.7 ② 的 wry 坑修正（小窗 / 动画中 WebView 比窗口高）；事件要串行 + 合并（§6.7 ⑥）；等待用定时器、不占事件链。
- 边缘滚动要同时给 Sidebar 列表和正文区域；产品的纵向布局现在没有这个能力，是新增。
- 小窗的拖放高亮（实线描边）、行上的进度条、胶囊提示是新增 UI，需要进 i18n。
- 小窗期间的「停留展开」窗口仍是小窗，不应抢焦点；拖拽展开后放弃要缩回（§6.7 ②）。
- 新一轮窗口位置不得漂移（C30）对小窗拖动 / 小窗里结束一轮同样适用，见 §6.7 ⑤。
