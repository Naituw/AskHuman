# iOS 待答消息快速切换

2026-10-31 设计定稿。用户在手机上反馈：多条问题消息之间只能返回收件箱再进入，要求优化。已通过 AskHuman 确认 G 原生外观及下列交互；随后用户授权正式接入；已在当前工作树实现，验证与安装记录见 `../plans/ios-request-switching.md`。

## 1. 入口与外观

- 详情页右侧依次为：**左右箭头共用的系统 Liquid Glass 组 → 独立的更多菜单**。更多保留在原最右位置。左侧系统返回继续回收件箱。
- 左箭头打开上一条，右箭头打开下一条，一次点按完成。普通提问、权限、Stop 共用入口。
- 不增加底部栏、常驻编号、抽屉入口或整页横滑；表单内原来的“下一题／发送”保持其含义。
- 首尾对应箭头禁用，不循环。只有当前一条可查看请求时隐藏整组；当前请求已结束而还有其他待答时，仍提供离开当前项的箭头。
- iOS 26 起交由系统工具栏提供玻璃、图标尺寸、触摸范围与间距；更早版本采用系统普通工具栏，保留相同位置与动作。使用 leading／trailing 语义适配语言方向。
- 更多菜单和箭头按功能分组，保持中性系统外观。无独立主色底板，不把玻璃再套在工具栏的系统玻璃之上。

## 2. 手动浏览范围与顺序

用户已确认：**列表入口沿用筛选；其他入口用全部待答；本次浏览顺序稳定，新到消息追加队尾。**

1. 从收件箱列表进入，捕获当时筛选条件，按列表当前实际顺序展开 ID 队列（沿用 Mac／项目分组和组内顺序）。
2. 从通知、Agent 或现有发送后自动前进入口打开，建立全部待答的手动队列。通知内容尚未到达时保留当前占位，后续补齐，不把占位误报为已经结束。
3. 在详情之间手动往返时保持同一个队列；符合捕获范围的新请求追加在末尾，不改变已有邻居。按稳定请求身份去重。
4. 返回列表再打开时重新建立队列。App 在后台后回来可继续当前浏览，进程重启不要求恢复这份临时队列；既有草稿持久化规则继续有效。
5. 他处处理或取消的其他请求从可导航目标中移除。当前正在看的请求若结束，保留现有结束说明与阅读内容，并保留它的位置锚点，让箭头跳到相邻仍待处理项，不自动跳走。
6. 未发送、发送失败与仍在发送的请求都可手动查看；离线不阻止浏览本机已有内容，提交可用性仍由目标 Mac 状态决定。
7. 仅实际打开当前请求才标记已读，不能因建立队列或准备相邻内容而把其他请求标为已读。

自动前进会建立全部待答的手动队列，因此即使它按原规则跳出了先前的列表筛选，新的箭头也有明确范围；此时用户是经自动入口打开新请求，而非继续原筛选列表的手动浏览。

## 3. 草稿、阅读与键盘

- 文字、选项、回复附件、确认表单的选择与补充文字按 `macId/requestId` 隔离；手动切换前 flush，切回来继续，不弹离开确认，不发送或清除任何答案。
- 回到已查看的请求恢复本次浏览里的阅读位置与已看题状态；首次查看从顶部开始。自动前进到新请求继续现有的顶部起始规则。
- 滚动位置属于每条请求。记录稳定题卡／正文锚点和相对偏移，等 Markdown 与附件布局就绪后恢复；失效锚点回退到有效位置或顶部，不继承另一条请求的滚动或“发送”闸门。
- **用户主动点箭头时收起键盘，新请求不自动弹键盘。** 离开前先把输入法组合内容落实到原请求草稿，避免丢字或串到下一条。回来后点输入框继续。
- 保存草稿不等于请求仍有效；结束请求维持既有不可发送、可阅读的状态。

## 4. 发送与切换互不抢占

用户明确选择：**上传或等待确认时允许切换，后台继续，完成不抢后来打开的页面；自动前进仍按全部收件箱的原逻辑。**

- 附件处理、上传与发送操作归属于原请求，而不是当前可见 View。切走不取消操作；处理结果只能更新原请求／原题的草稿，不得落入新请求。
- 切回发送中的请求能看到其实际进度；其他请求可正常阅读、填写和提交。
- 用户在一次发送期间主动切换过，随后成功或失败都不能触发导航、覆盖另一条的表单、显示另一条的全页回执，或清除另一条的草稿。
- 成功清理原请求；失败保留原草稿与该请求的重试状态。必要的提示需说明来源，不自动重试、不把用户拉回错误页。
- 用户一直停留在发送页时，继续现有回执、成功触感、自动前进开关与 `nextPending` 目标选择；自动前进仍从**全部收件箱**选取，不限定为手动队列，也不改成队尾顺序。
- 手动切换本身不产生“已发送”回执。连续快速点按以已提交的请求身份为准，避免旧页面的延迟回调改变后来打开的页面。

## 5. 页面与现有动效

- 手动切换替换唯一详情页，不把每条请求压入系统返回栈；返回始终直接到列表。
- 为每条请求保持独立 View 身份，不能继承另一条的选项、焦点、滚动位置或阅读状态。使用轻量页面过渡；减少动态效果时用淡入／即时切换。
- 新请求继续既有到达动效与未读提醒，不因到达而替用户切页。临时收件提示需避开右侧工具栏分组。
- 图片查看器、系统附件选择器或确认弹层在前面时维持各自交互；不把这些界面的动作解释为消息切换。
- 大字号、窄屏、深色、减少透明度、减少动态效果均采用系统可访问性规则。VoiceOver 为左右箭头提供明确的“上一条消息／下一条消息”和禁用状态。

## 6. 实施落点与验证

当前实现落点如下；自动化证据与尚未验证的边界见实施计划。

- `AppStore.requestNavigation`／`RequestNavigation` 保存本次范围与稳定 ID 队列；逐请求阅读位置存于非观察缓存，不让每帧滚动触发页面重绘。
- `InboxScreen` 保留原有 NavigationLink；首次 `inboxPath` 入栈捕获当前筛选和 `inboxSections` 展开顺序。显式 `open` 和自动前进建立全部范围，返回列表清理浏览缓存。
- `RequestScreen` 安装唯一的右侧工具栏和手动换页流程，继续单页 `.id(id)` 隔离；现有 ask／confirm 的更多菜单保留动作并统一位置，避免重复菜单。
- `AnswerComposer` 按题持有 `AttachmentPreparationState`，Reply AttachmentMenu 换页保留处理任务与状态，结束草稿取消；其他表单的附件菜单仍保留原取消行为。发送中的原表单暂不可编辑，其他请求不受影响。未改变线协议或 Mac 的请求协调。
- `RequestScrollPosition` 用公开 UIKit 视图锚点与 KVO 保存／恢复位置，等待正文 Markdown 就绪，不替换 scroll delegate 或获取焦点。
- `advance` 继续使用现有全收件箱目标规则。以导航／操作代次识别用户已切走，不能只比较请求 ID，以免切走后又回来被旧发送回调推进。
- 自动检查覆盖：筛选与全部入口、稳定顺序、新到／结束、首尾／单条、跨 Mac 同名 ID、草稿与附件隔离、阅读恢复、发送后台完成与失败，以及原自动前进目标规则不变。
- 原生 UI 已覆盖一次点按、返回不累积、键盘／组合文字、Web Markdown 长表单阅读恢复、确认页、单条、动态字号与深色、iOS 18.5 回退，以及到达动效共同出现时的按钮可用性。后台上传与筛选等状态分支由 Core 集成测试验证；真机／媒体选择器／真实网络边界以计划记录为准。
- 功能实现后按仓库要求编译、安装和验收；原型证据不能代替正式接入验证，不调用真实付费 Agent 作为必要条件。

## 7. 原型与决策记录

- A／B／C 分别为顶部抽屉入口、底部快切栏、底部单入口；用户认为底部复杂或仍需多次点按，全部否决。整页横滑也已明确否决。
- D／E 为居中箭头与居中下一条；用户要求原生 Liquid Glass、左右箭头、靠右。
- F 原生外观获认可；经[工具栏顺序案例研究](../investigations/ios-request-switch-toolbar-order.md)，最终选择 G：箭头在更多左侧，更多最右。
- 浏览器候选：`demo/ios-request-switch/index.html`；原生样机：`demo/ios-request-switch/native/`。后者实际构建并运行于 iOS 26.2，底栏复用正式 `BottomBar.swift`；`DesignMoreLast` 默认使用 G，传 NO 可重现 F 对照。
- `output/g-native-reading.png` 与 `g-native-keyboard.png` 是最终外观截图；生成文件被 git 忽略。独立样机不连接 backend／配对／上传／Agent，也未上传 TestFlight。
- 浏览器检查仅确认候选切换、草稿隔离和无运行错误；原生样机构建与截图确认系统材质及位置。正式接入另有 Swift 与中英文原生 UI 验证，见实施计划；不以原型代替功能证据。
