> 状态：2026-10-27 起草，**同日评审通过**（结论见 §14、§17；第 8 轮把「历史清空」改为全局清空，见 T16）；已开工，进度见计划 §10 与 `docs/PROGRESS.md`
> 关联计划：`docs/plans/todo-sync.md`（决策编号 T1–T16 均指本文 §3）
> 前置资料：`docs/specs/todo-whats-next.md`（项目待办队列、whats-next、GUI 待办窗口）、`docs/specs/todo-attachments.md`（附件）。可行性 spike（下称 S0）的结果摘要见附录 A；spike 工程在仓库外（`~/Developer/AskHuman-TodoSync-Spike/`，复现方法见其中的 `RUNBOOK.txt`）

## 1. 背景与目标

2026-10-26 用户提出：

> 「我想支持跨设备的 todo 列表，比如说通过 CloudKit 来进行在多个 Mac 之间的共享。帮我分析一下。」

之后经过一轮可行性 spike（S0）和七轮 AskHuman 问答，范围与方案已定（§3）。

**一句话**：`todos.json` 仍是每台 Mac 自己的工作副本，所有入口照旧读它；一个**与传输无关的 Rust 同步核心**把各台 Mac 的副本合并成一致；一个只会「拉 / 推 / 提示有变化」的 **CloudKit helper** 负责和 iCloud 说话；whats-next 弹出前会先确认本地副本足够新。

**目标**

1. 同一 Apple ID 的多台 Mac 共享项目待办与执行历史：任何一台、任何一个目录上的增删改排、完成、恢复，其余全部自动跟上。
2. **不用手动刷新**：whats-next（含 ⚡ 自动执行路径）以及 Stop 卡、弹窗待办区、CLI、IM、待办窗口都能看到其他 Mac 的新待办；尤其 whats-next 弹出的那一刻，本地副本相对 iCloud 的陈旧度有上限（§6.3）。
3. **本地优先**：CLI 与 whats-next 永不被网络阻塞；断网时一切照常；不开同步时的行为与数据格式不变。
4. 「存储模式」改为 iCloud 后能看到**所有项目**的待办（含本机没有该仓库的项目）；待办窗口界面统一改为侧栏，**打开不得卡顿**（§9）。
5. 先自用：自己两台 Mac，本机 Xcode 构建签名、手动拷贝到另一台；稳定后再单独评审随正式版发布（T1）。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 同步核心 | Rust 模块（`todo_sync`）：本地变更检测、合并、物化、排序、元数据、何时拉；与传输无关，可用内存传输做测试 |
| helper | 单独的小 App（登录项，Swift，非沙盒，Developer ID + 描述文件），**只**和 CloudKit 说话：拉、推、提示有变化。没有业务逻辑，无状态 |
| 旁路元数据（sidecar） | `~/.askhuman/state/todo-sync/` 下的同步状态：设备 id、变更令牌、每条待办的同步版本、链接表、脏标记等。`todos.json` 的格式不动 |
| 云端项目 | 以「项目身份」为键的一组待办与历史，存在 iCloud 里 |
| 项目身份 | 规范化后的 git remote「主机/路径」，如 `github.com/naituw/humaninloop`（§5.1） |
| 副本 | 本机某个目录（项目 key）下的队列与历史。同一仓库的每个目录 / worktree 都是同一份云端项目的副本（T3） |
| 链接 | 「本机项目 key → 项目身份」的映射，由同步核心维护并缓存 |
| 仅云端 | 云端项目在本机没有任何链接的目录（本机没有这个仓库） |
| 仅本机 | 没有项目身份的目录（无 remote / 非 git），不同步（T4） |
| 实体 | 一条待办（含它的状态：待办 / 已执行 / 已删除）。云端记录名 = 待办 id |
| 墓碑 | `state = deleted` 的实体：删除也是一次可合并的修改，不真删云端记录 |
| HLC | 混合逻辑时钟（墙钟毫秒 + 计数器 + 设备 id），用来给每次修改定先后，不依赖各机墙钟一致 |
| tick | 同步核心的一轮：本地阶段（变更检测、合并、物化）+ 网络阶段（拉、推）。幂等，可被任何触发源调用 |
| 陈旧度 | 本地副本距离「上一次成功拉取」的时间 |
| 设备记录 | 每台 Mac 在云端的一条小记录：名称、最近同步时间、已链接的项目；用来显示「N 台 Mac」「最后同步」 |

## 3. 已确认决策（用户经 AskHuman 定案）

以下来自 2026-10-26 ~ 27 的第 1–7 轮问答（题目与用户原话见 §17）。

| 编号 | 决策项 | 结论 |
|---|---|---|
| T1 | 范围与节奏 | 只做**同一 Apple ID 的自己的多台 Mac**。分两步：先自用（本机 Xcode 构建签名、另一台手动拷贝，不公证、不对外发布）；稳定后再**单独评审**「随正式版发布」（公证、自更新下发、第二个大陆 iCloud 账号复测）。先做 S0 可行性 spike（已完成） |

| T3 | 副本语义 | 同一仓库的**每个本地目录 / worktree 都是同一份待办的副本**：任何一个目录、任何一台 Mac 上增删改排，其余全部跟上，本机几个 worktree 的队列也因此趋同 |
| T4 | 无 remote / 非 git | 不同步，保持本机独立队列；待办窗口标「仅本机」。让用户手动指定同步名以后再考虑 |
| T5 | ⚡ 自动执行 | **不跨机**：⚡ 只在本机生效；其他 Mac 把同一条待办当普通待办（`auto` 不进云端、不被远端覆盖） |
| T6 | 附件 | v1 **不同步附件**：文字、顺序、增删跨机；其他 Mac 上这条待办没有附件，待办窗口提示「附件在其他 Mac 上」。附件同步后置 |
| T7 | 执行历史 | **同步**：任意 Mac 都能看到全部历史并一键恢复（用户：「就像苹果的提醒事项一样」） |
| T8 | 存储模式 | 设置里「存储位置」有两档：**仅本机**（默认，现状）/ **iCloud 同步**。iCloud 模式下能看到**所有项目**的待办，含本机没有该仓库的项目 |
| T9 | 界面 | 待办窗口**统一改为侧栏**（本机与 iCloud 两种模式同一套组件）。用户要求：「统一弄这栏是不是以后更好维护？如果是的话就改成统一吧……你需要保证打开的时候不能卡顿」。评估结论见 §9.1；「不卡顿」的硬约束与度量见 §9.9 |
| T10 | 同步架构 | **Rust 同步核心 + 薄 CloudKit 适配器**：helper 只调普通 CloudKit 接口（拉 / 推 / 订阅），**推送只当「有变化」的提示**；不使用 `CKSyncEngine`（它没有「现在就拉」，也不补拉，无法在 whats-next 那一刻保证新鲜，S0 实测） |
| T11 | 新鲜度 | 四层、全自动：推送提示、轮询兜底、唤醒 / 解锁 / 联网恢复立即拉、**whats-next 前「过期才拉」**——上次成功拉取超过 20 秒才拉，最多等 1.5 秒，超时或离线直接用本地（§6） |
| T12 | 实时性 | 实时性要求不高：空闲 Mac 的推送延迟分钟级可以接受；但 whats-next 弹出时必须自动是新的，不用手动打开待办窗口 |

## 4. 总体架构

```
┌────────────────────────── Mac A ──────────────────────────┐         ┌────── Mac B ──────┐
│ CLI / whats-next / 待办窗口 / 弹窗 / Stop 卡 / IM / iOS 网关 │         │  …同样的一套…      │
│          │ 读写（路径不变，不依赖 daemon）                   │         │                    │
│          ▼                                                 │         │                    │
│  todos.json（本机副本 = 事实来源）                          │         │                    │
│          ▲ 合并 / 物化                                      │         │                    │
│  todo-sync 核心（Rust，与传输无关）＋ state/todo-sync/ 旁路元数据 │         │                    │
│          ▲ RPC（本机 unix 套接字，拉 / 推 / 状态）           │         │                    │
│  CloudKit helper（Swift 登录项，无业务逻辑）                 │         │                    │
└──────────┬─────────────────────────────────────────────────┘         └─────────┬──────────┘
           └────────────── iCloud（CloudKit 私有库，Production）───────────────────┘
```

- **同步核心不常驻**：它是一段库代码，被「tick」调用。tick 可以由 helper 触发（拉起 `AskHuman todo-sync tick` 子进程）、由 CLI 在 whats-next 前内联调用、由待办窗口触发。同一时刻只有一个 tick 在跑（`todo-sync.lock`）。没有「必须常驻的 Rust 进程」。
- **helper 无状态**：它只暴露 `hello / status / fetch / save / subscribe` 几个 RPC，并把推送、轮询、唤醒、联网恢复、`todos.json` 变化这几类事件翻译成「请核心跑一次 tick」。变更令牌由核心持久化，helper 崩溃或升级不丢状态。
- **传输可替换**：核心只依赖一个很小的传输接口（拉变更 / 推记录 / 有变化的通知）。将来换成 MQTT（Mac 互通）或「同步文件夹」，核心不动（§12）。
- **为什么不把 CloudKit 直接链进 `AskHuman`**：CloudKit 是受限 entitlement，必须有描述文件，裸可执行文件内嵌不了；放进主应用会让所有开发构建因缺描述文件而无法启动。独立 helper 把风险隔离在可选功能里。
- **旧二进制安全**：旧版 `AskHuman` 重写 `todos.json` 时会丢掉未知字段，所以同步元数据一律放旁路；本地变更靠 diff 检测，旧二进制写的文件照样被正确同步。

## 5. 数据模型与合并语义

### 5.1 项目身份（T2）

输入：目录所在 git 仓库的远程列表。读取 `.git/config`（worktree 的 `.git` 是文件，经 `gitdir:` / `commondir` 找到主仓配置），**不 fork `git` 子进程**；结果与配置文件的修改时间一起缓存在旁路元数据里。

选择：`origin` → `upstream` → 其余按名字字典序的第一个。只考虑「带主机名」的地址（scp 式 `user@host:path`、`ssh://`、`https://`、`http://`、`git://`）；本地路径与 `file://` 不合格，跳过，看下一个远程。

规范化为「主机/路径」：全部小写；去协议与 `user@`；去端口；去末尾的 `/` 与 `.git`；scp 式的 `:` 换成 `/`。

| 远程地址 | 项目身份 |
|---|---|
| `git@github.com:NaituW/HumanInLoop.git` | `github.com/naituw/humaninloop` |
| `https://github.com/naituw/HumanInLoop` | `github.com/naituw/humaninloop`（与上一行同一项目） |
| `https://user@github.com/naituw/HumanInLoop.git/` | 同上 |
| `ssh://git@gitlab.corp.example:2222/team/api.git` | `gitlab.corp.example/team/api` |
| `/Users/x/repos/bare.git`、`file:///…` | 不合格，跳过 |

- 显示名取路径最后一段；同名冲突时前面补一段（`owner/repo`）。
- 没有任何合格远程，或不是 git 目录 → 没有项目身份 → **仅本机**（T4）。
- 子模块、monorepo 沿用现有项目 key 规则（每个 git 根一个 key）；key 的规则本需求不改。
- **已知限制**：忽略大小写与端口意味着「只差大小写 / 端口」的两个不同仓库会被合并；极少见，v1 接受。

### 5.2 副本与链接（T3）

- 同步核心维护「本机项目 key → 项目身份」的**链接表**（缓存，窗口打开路径只读它）。
- 「已知目录」来自：`todos.json` 里的项目 key ∪ 最近 workspace 索引 ∪ 活跃 Agent 的目录 ∪ 当前读取待办的目录。
- **物化**：每个已链接目录的队列与历史，都要与它的云端项目一致：缺的补上，本机多出来的算本机新增并上传。同一台 Mac 上同一仓库的多个目录，每个目录里各有一份相同 id 的条目；任何一个目录里的改动，经本地阶段传到其余目录，**不依赖网络**。
- **新目录第一次读取**（比如新建 worktree 后第一次 whats-next）：读取钩子先做本地阶段，把该目录链接并物化，所以不会出现「云端有待办、新 worktree 里却是空的」。
- 物化到副本里的远端待办：`auto = false`，没有附件；已存在的条目只更新文本与顺序，**保留本机的 `auto` 与附件**。
- 本机副本之间的附件**不互相复制**（附件各留在添加它的目录副本里）：v1 的已知限制，与「附件不同步」同时后置（T6）。

### 5.3 云端记录

- 容器（建议命名，待用户确认，§14）：`iCloud.com.naituw.humaninloop.todosync`；私有库；单一自定义区 `Todos`。
- 记录类型两个：`Todo`（记录名 = 待办 id）与 `Device`（记录名 = 设备 id）。
- **每条记录只有一个加密字段 `payload`**（JSON，内含 schema 版本 `v`）；不建索引、不做查询，只用「区变更」。理由：Production 的 schema 需要用户在 Dashboard 手动部署，且只增不减；把所有内容放进 `payload` 后，以后加字段只改 JSON，**不用再部署 schema**。项目身份、文本等都在加密字段里，iCloud 服务端看不到明文。
- `payload` 含：项目身份、文本、顺序键、状态（待办 / 已执行 / 已删除）、创建信息（时间、设备、Agent 家族）、执行信息（时间、设备）、附件提示（数量、文件名、所在设备）、以及每个可变字段各自的 HLC。
- 单条待办文本超过 256 KB 时不同步，并在窗口里标注（CloudKit 记录上限 1 MB，留足余量）；实际上几乎不会发生。

### 5.4 字段与合并

- **字段级合并**：`text`、`order`、`state`、附件提示各带一个 HLC；合并时每个字段取 HLC 较大的一方。S0 的记录级「后写者胜」会丢另一边对其他字段的修改，产品不用。
- **不依赖墙钟**：HLC = (墙钟毫秒, 计数器, 设备 id)。远端 HLC 的墙钟若比本机现在超前 24 小时以上，按 24 小时钳制（防某台 Mac 时钟错乱把别人的改动都压住）。
- **删除是墓碑**：`state = deleted` 与其他状态一样按 HLC 竞争，云端记录不删除。已删除的实体忽略对 `text`/`order` 的并发修改。**墓碑不清理**（体量可忽略，且避免离线很久的 Mac 把已删除的待办「复活」）。
- **状态机**：待办 → 已执行（执行出队 / 勾选完成）→ 待办（恢复，同时排到队尾）；待办 → 已删除。并发冲突按 `state` 字段的 HLC 取后者。
- **`auto` 不进云端**（T5）；附件文件不进云端（T6），只带「数量 + 文件名 + 所在设备」的提示字段。
- **历史**：已执行的实体即「历史」。每个 Mac 按本机的 `todo_history_limit` **只裁剪本机视图**，不产生云端删除；而「清空历史」是**全局**的（T16）：该项目云端全部已执行实体标为已删除，所有 Mac 随之清空（§5.5）。`todo_history_limit = 0`（停止新增历史）时，不把远端已执行的实体物化进本机历史。

### 5.5 本地变更检测（T14）

同步核心在本地阶段把 `todos.json` 与上次同步时记下的快照做 diff，推出「用户做了什么」：

| 本地观察到的变化 | 解释 | 同步动作 |
|---|---|---|
| 新 id 出现在待办队列 | 新增 | 建实体：状态待办，顺序键取队尾 |
| id 从队列消失，且出现在历史 | 执行出队 / 勾选完成 | `state = done`，执行时间取历史条目的 `doneAtMs` |
| id 从队列消失，也不在历史 | 删除 / 清空队列 / 历史上限为 0 时的出队 | `state = deleted`（墓碑） |
| id 从历史回到队列 | 恢复 | `state = pending`，顺序键取队尾 |
| 文本变化 | 编辑 | `text` 新 HLC |
| 条目相对顺序变化 | 拖拽排序 | 只给被移动的条目生成新顺序键 |
| 项目的历史由非空变为空，且消失的 id 都不在队列 | **清空历史**（T16） | 该项目云端**全部**已执行实体（含本机早已裁掉的）标为 `state = deleted` |
| 历史里最旧的若干条消失，历史仍非空 | 本机按 `todo_history_limit` 裁剪 | **不同步**（只影响本机视图） |
| `auto` 变化、附件变化 | | 不同步（附件只更新「附件提示」字段） |

同一实体在本机多个目录副本里发生的变化，合并成一个事件；若多个副本给出互相矛盾的变化（极少见），按项目 key 字典序依次采纳，后者的 HLC 更大。

**清空与裁剪怎么区分**：裁剪只会在新增一条历史的同时丢弃最旧的，所以历史**永远不会因为裁剪而变空**；清空一次清到空；`todo_history_limit = 0` 时既有历史保留、也不会被裁。这个判断只看 `todos.json` 的前后差别，不依赖 `todos.rs` 的写函数，所以旧版二进制执行的清空同样会被识别并同步。

### 5.6 顺序

- 现有队列没有排序键（顺序 = 数组位置）。每条待办在云端有一个**顺序键**（分数索引：可在任意两个键之间生成新键的字符串），按 `(顺序键, HLC, id)` 排序。
- 新增追加队尾；拖拽只更新被移动条目的键；键过长（> 32 字符）时由发起方一次性重排该项目全部键。
- 首次合并两条非空序列时，各自内部顺序保持不变，按 `createdAtMs` 归并交错。

### 5.7 启用、停止与清除

- **启用**：生成设备 id；确认 iCloud 账号可用；确保区与订阅存在；**首次完整拉取**；与本机内容做并集合并（§5.6），上传本机独有的；之后进入常态。全程后台、界面显示进度；失败则保持「仅本机」。
- **停止同步（保留本机副本）**：停掉 helper，旁路元数据保留；本机与 iCloud 的数据都不动。以后重新启用只做增量对账。
- **清除 iCloud 数据（危险，二次确认）**：删除云端区。其他 Mac 发现区不存在后**暂停同步并提示**：「iCloud 中的待办已被清除。用本机副本重新上传 / 停止同步」，不自动重传，避免互相覆盖。
- 关闭同步不影响本机任何功能，也不删除旁路元数据以外的东西。

### 5.8 账号

- 旁路元数据记录当前 iCloud 账号的哈希。helper 的 `hello` 返回当前账号；不一致（换了 Apple ID）→ **暂停并提示**：不会把旧账号的待办写进新账号，由用户选择「停止同步」或「用本机副本作为新账号的初始内容」。
- iCloud 未登录 / 受限 → 暂停，只用本机副本，登录后自动恢复。

## 6. 同步循环与新鲜度（T10、T11）

### 6.1 一次 tick

1. 取 `todo-sync.lock`（同一时刻一个 tick；后来者合并为一次）。
2. **本地阶段**（不碰网络）：在 `todos.lock` 内读 `todos.json` 与旁路元数据，做变更检测（§5.5）、链接新目录、物化。持锁时间毫秒级。
3. **网络阶段**（经 helper RPC，不持 `todos.lock`）：`fetch(since 令牌)` 取远端变更（含 `moreComing` 循环）→ 合并 → 在 `todos.lock` 内物化到 `todos.json` 并推进令牌 → `save` 推送本机脏实体；遇 `serverRecordChanged` 取回服务端记录，合并后重试（上限 5 次）。
4. 写回旁路元数据，释放锁。

**幂等**：合并是「取每个字段 HLC 较大者」的纯函数，同一批变更应用两次结果不变；崩溃后重跑 tick 即可，不需要事务。先写 `todos.json`、再推进令牌；令牌没推进就重拉同一批，安全。

### 6.2 触发源（默认值标「我定」的见 §13）

| 触发源 | 谁触发 | 时机 | 说明 |
|---|---|---|---|
| 推送提示 | helper | 收到 CloudKit 静默推送 | 活跃 Mac 约 1 秒；**空闲 Mac 可能延迟分钟级**（附录 A）。只当提示，不当保证 |
| 轮询兜底 | helper | 系统清醒时每 10 分钟 | 睡眠中不唤醒系统（我定，可配置） |
| 唤醒 / 解锁 / 联网恢复 | helper | 事件发生后去抖 2 秒 | 立即拉 |
| 本机改动 | helper（监听 `todos.json`） | 去抖 1 秒 | 把本机脏实体推上去；tick 自己写文件引起的事件要忽略 |
| 待办窗口打开 / 获得焦点 | GUI | 异步，不阻塞界面 | 陈旧度 > 20 秒才拉 |
| **whats-next（含 ⚡ 自动路径）** | CLI | 发起提问前，在构建待办选项**之前** | 见 §6.3 |
| CLI `todo`、Stop 卡、弹窗待办区、IM `/todo` | 各入口 | 读取前 | **只做本地阶段**，不碰网络 |
| 手动「立即同步」 | 设置 / 侧栏 | 用户点击 | 不设等待上限，显示进度 |

### 6.3 whats-next 前的新鲜度保证（T11）

whats-next 的待办卡片由 **CLI 进程自己**读 `todos.json` 现场构建（不经 daemon），所以钩子加在 CLI 构建待办选项之前，对 ⚡ 自动路径（`try_whats_next_auto`）同样生效：

1. **本地阶段**（始终执行，毫秒级）：链接当前目录并物化，保证新 worktree 不空。
2. 若未启用同步，或 helper 未运行 / 不可达 → 到此为止（helper 不在时顺手在后台拉起它，供下次用）。
3. 若陈旧度 ≤ 20 秒 → 到此为止（刚拉过，不重复）。
4. 否则拉取一次，**总等待上限 1.5 秒**：成功则物化后再构建；超时、离线、出错 → 直接用本地，**绝不阻塞或失败**；超时的那次拉取在后台继续（拉起一个脱离的 tick），数据随后落地。
5. 这一次构建出的卡片是静态的：弹出之后才到的远端变更不会改写已显示的选项（下一次 whats-next 会看到）。

由此得到的承诺：**在线时，whats-next 看到的待办相对 iCloud 的陈旧度不超过 20 秒**；离线时看到本机最后一次同步的结果。

### 6.4 失败与退避

| 情形 | 处理 |
|---|---|
| 离线 / 网络错误 | 本轮网络阶段放弃，本机照常；联网恢复事件或下一个触发源再试；指数退避，上限 30 分钟 |
| 限流 / 区忙 / 服务不可用 | 遵守服务端给出的重试间隔 |
| 变更令牌过期 | 丢弃令牌，从头完整拉取并合并（幂等） |
| 区不存在 | 暂停并提示（§5.7「清除」的对端表现，或账号被重置），不自动重建 |
| 配额已满 | 暂停并提示 |
| 未登录 / 账号变更 | 暂停并提示（§5.8） |
| 单条保存冲突 | 取回服务端记录，字段级合并后重试（≤ 5 次），仍失败留作脏实体 |
| helper 不可达 | tick 只做本地阶段；状态栏显示「同步程序未运行」+ 修复 |

### 6.5 边界

- **Dev Instance**（`ASKHUMAN_HOME` 非默认）：同步功能**恒关闭**（设置页该卡片置灰并说明），helper 只服务生产实例的 state 目录。各实例有各自的 `todos.json`（`todo-whats-next` D11 已成立），旁路元数据放在各自的 state 目录下。
- **多份安装**：helper 通过 `helper.json` 记录要调用的 `AskHuman` 路径与 state 目录；已有的「多份安装互顶」刹车不变。
- **跨 Mac 互斥不做**：两台 Mac 同时对同一条待办 whats-next → 沿用 `todo-whats-next` D11「文本照常送达、出队 best-effort」；单用户场景窗口极小。

## 7. helper（CloudKit 适配器）

- **形态**：独立 `.app`（建议 bundle id `com.naituw.humaninloop.todosync`），非沙盒，Developer ID 签名 + 内嵌描述文件（iCloud / CloudKit + 推送），Hardened Runtime；以登录项方式常驻（`SMAppService`），崩溃自动重启；不显示 Dock 图标。S0 已验证：能用 `open` / SMAppService 启动，手写 LaunchAgent 直跑内部二进制会被 CloudKit 自己拦截。
- **RPC**（本机 unix 套接字，权限 0600，JSON 行）：
  - `hello` → 协议版本、容器环境、账号哈希、helper 版本；
  - `status` → 账号状态、上次成功拉取时间、订阅状态；
  - `fetch {token?}` → `{changes[], deletions[], token, moreComing}`，token 为不透明值，由核心保存；
  - `save {records[]}` → 逐条结果：成功 / 服务端记录已变（附回服务端记录）/ 错误；
  - `subscribe` → 确保区订阅存在（幂等）。
- **事件**：推送、轮询定时器、系统唤醒、网络恢复、`todos.json` 变化 → 去抖后拉起 `AskHuman todo-sync tick --reason …`。helper 自己不合并、不存业务状态。
- **资源**：S0 实测常驻内存约 20–40 MB；正式版会去掉 spike 的调试日志，空闲 CPU 应远低于 spike 的约 1%（验收项，§16）。
- **最低系统版本**：不依赖 `CKSyncEngine`，目标 macOS 13+；自用阶段两台均为 macOS 27 beta，稳定版 macOS 上的行为需要复测（§15）。
- **自用阶段分发**：本机 Xcode 构建并签名，另一台手动拷贝安装；脚本见计划。**不公证**（需另行授权）。

## 8. 设置与 CLI

- **位置**：设置 → 实验 → 「iCloud 待办同步」卡片（与 iOS 渠道同处，稳定后再考虑提升）。仅 macOS 显示；Dev Instance 置灰。
- **卡片内容**（见 `settings.jpg`）：存储位置（仅本机 / iCloud 同步）、状态（已同步 N 条待办 · M 条历史 · 刚刚）、这台 Mac 的名称（默认系统的电脑名，可改）、已加入同步的 Mac 列表与各自「最后同步」、同步程序状态、「立即同步」、「停止同步（保留本机副本）」、「清除 iCloud 中的待办数据…」。
- **配置字段**（`config.json`）：`todoSync.enabled`、`todoSync.deviceName`、`todoSync.pollMinutes`（默认 10，不在界面暴露）。账号哈希、令牌等放旁路元数据，不进配置文件。
- **CLI**（隐藏子命令，不写进 Agent 帮助）：`AskHuman todo-sync status [--json]`、`tick`、`enable`、`disable`；用于排障与 helper 触发。
- **状态展示**只在侧栏底部一处（§9.7）；出错才变色。

## 9. 待办窗口界面（T8、T9）

### 9.1 为什么统一成侧栏（对用户问题「统一是不是更好维护」的评估）

结论：**是，统一更好维护**，所以采纳统一。

1. 一套导航组件、一套测试。两种模式只是数据不同（项目模型多几个字段与分组），没有 `v-if 模式` 的分叉。若保留下拉，iCloud 模式要另做一套侧栏，此后每个导航改动（分组、搜索、徽标、键盘导航）都要做两遍。
2. 侧栏本身就是本机模式的升级：现在的 `<select>` 做不了条数徽标、搜索、同名项目区分、「全部待办」。
3. 成本是**一次性重构**：把导航从 2656 行的 `TodosView.vue` 拆成 `TodosSidebar` + 项目视图模型，反而让主文件变短。
4. 风险点靠验收守住：窗口默认变宽（现 520×560）；首屏必须仍是纯本地数据（§9.9）。

### 9.2 布局（`local.jpg` 本机模式、`project.jpg` iCloud 模式）

- 左：侧栏（固定宽度约 208–218 px，顶部搜索框，底部同步状态）；右：项目头 + 列表 + 历史 + 底部添加区（沿用现有行样式、交互与快捷键）。
- 窗口默认约 760×580，最小约 560×360；窗口窄于约 640 时侧栏收成抽屉（同一组件、另一种呈现，用顶部按钮切换），不再另有一套下拉。
- 项目分组：
  - **本机模式**（`local.jpg`）：「全部待办」「有待办」「最近项目」，来源与排序同现在的下拉（有待办 ∪ 活跃 Agent ∪ 最近 workspace；工作中 → 空闲 → 置顶 → 其他最近）。同名目录用灰色后缀区分（`HumanInLoop · feature-a`）。底部显示「仅本机 · 启用 iCloud 同步…」（仅 macOS）。
  - **iCloud 模式**（`project.jpg`）：「全部待办」「iCloud 同步的项目」「无待办的项目（N）」（折叠）、「仅本机（不同步）」。同一仓库的多个本机目录合并成**一行**。

### 9.3 全部待办（`all.jpg`）

按项目分组的聚合视图，每组头带条数与「打开项目 ›」；仅云端 / 仅本机项目带标记；不提供添加框（添加必须先进入项目）。超过 50 行时折叠并「显示更多」。

### 9.4 项目头与仅云端项目（`remote.jpg`）

- 项目头：项目名、规范化后的仓库地址（本机模式显示路径）、「本机 N 个目录」「N 台 Mac」两个标签（悬停列出目录 / 设备与最后同步时间）、「⋯」菜单（复制仓库地址、在 Finder 中显示、从 iCloud 移除此项目…）。
- **仅云端**项目（本机没有该仓库）：侧栏行右侧是虚线云图标；顶部说明条「这台 Mac 上没有 X 的目录……」；照样可以查看、编辑、排序、完成、添加；⚡ 隐藏（没有本机目录，自动执行无意义）。这类项目在 `todos.json` 里以虚拟键 `icloud:<项目身份>` 存放（没有真实目录，副本由 tick 建立与回收；本机一旦有了该仓库的目录，待办改物化到那个目录），读写路径与普通项目完全一致，经 tick 推送。
- 「从 iCloud 移除此项目」：把该项目全部待办与历史标为已删除并同步到所有 Mac；二次确认并写明影响。

### 9.5 行内变化

- 其他 Mac 上创建的待办，meta 行显示设备名（本机创建的不显示）。
- ⚡ 只在本机生效；在别的 Mac 上同一条显示为关闭。
- 附件：本机没有附件、但云端提示有 → 显示虚线标签「N 个附件 · 在 X 上」。

### 9.6 历史

沿用现有折叠区；iCloud 模式下标注「所有 Mac 共享」，每条显示执行设备；恢复照旧。「清空历史」是全局的（T16）：确认框在 iCloud 模式下写明「将清空所有 Mac 与 iCloud 中该项目的执行历史（共 N 条），无法恢复」，并保持现有的模态二次确认。

### 9.7 状态（`settings.jpg` 下半部分）

只出现在侧栏底部一处：已同步 · 刚刚 / 正在同步… / 离线 · N 项待上传 / 未登录 iCloud / 同步程序未运行（修复）/ Apple ID 已更换（查看）。出错才变色。

### 9.8 添加待办落在哪个副本

在合并后的项目里添加 / 编辑，写入该项目在本机**最近使用的目录**的副本，再经本地阶段趋同到其他目录与云端；仅云端项目写它的虚拟键。

### 9.9 「打开不卡顿」的硬约束与度量（T9）

**不可违反项**：
1. 窗口打开路径上**禁止**：网络、helper RPC、`git` 子进程、daemon IPC。
2. 首屏数据只来自本机小文件：`todos.json`、旁路元数据里的链接表 / 云端项目缓存、workspace 索引。沿用现有「两段式加载」：先用本地快路径填满侧栏与当前项目，再在后台补充（`todos_projects_enriched` 的活跃 Agent 等）。
3. 同步状态、设备列表等云端补充信息**异步到达，只更新局部**；侧栏行高与徽标位置固定，不因它们到达而整体重排。
4. 「全部待办」按需渲染，超过 50 行折叠；侧栏搜索在前端过滤。
5. 项目身份（读 `.git/config`）只在 tick 里算并缓存，**不在窗口打开路径上现算**。

**度量**（目标值待计划 P0 量出现状基线后校准）：
- 先量改造前的基线：窗口创建到首屏渲染的耗时（冷 / 热各若干次，沿用 `perf` 里程碑 + 脚本的做法）；
- 改造后在本机真实数据（8 个项目 / 19 条待办 / 72 条历史）上 p95 不劣化超过基线 +10%（且绝对增量 ≤ 30 ms）；
- 压力数据（200 个项目 / 2000 条待办 / 2000 条历史）首屏 ≤ 300 ms；
- 读取钩子的本地阶段：真实数据 ≤ 20 ms，压力数据 ≤ 100 ms。

### 9.10 对既有 spec 的修订

`docs/specs/todo-whats-next.md` D9 的「带项目选择器（两个 `<optgroup>`）」改为本文的侧栏；其余 D9 能力（列表、新增、删除、勾选完成、清空、拖拽、⚡、历史、实时同步）不变。落地时在该 spec 加一行指向本文。

## 11. 性能、资源与成本

- 数据规模（2026-10-27 本机实测，只数条数）：8 个项目有待办、19 条待办、72 条历史、2 个附件，`todos.json` 32 KB。整份同步也是毫秒级，不需要增量技巧；增量拉取走变更令牌。
- 流量：每次 tick 一次 `fetch`（无变化时几百字节）；轮询 10 分钟一次 ≈ 每天 144 次；本机改动去抖后一次 `save`。
- CloudKit 配额：用的是用户自己的私有库，占用用户 iCloud 存储，数据量可以忽略。
- 本地：旁路元数据与 `todos.json` 同量级（含墓碑，随年计 KB）；每次本地阶段读两个小文件。
- helper：常驻内存约 20–40 MB（S0 实测）。

## 12. 非目标与后置

- **附件同步**（含同机多目录之间）：后置（T6）。
- **不同 Apple ID / 共享给别人**：不做（T1）。
- **iOS App 读写待办**：后置；同一容器日后可复用。
- **⚡ 跨机**、**跨 Mac 互斥取走**：不做（T5、§6.5）。
- **Windows / Linux 同步**：不做；界面侧栏共用。
- **空闲 Mac 的秒级推送**：做不到（附录 A），靠轮询 / 唤醒 / whats-next 前拉取兜底。
- **手动指定同步名、项目合并 / 改名工具**：后置（T4）。
- **云端历史 GC、墓碑 GC**：不做（§5.4）。
- **随正式版发布**（公证、helper 打进 `AskHuman.app`、自更新下发、第二个大陆 iCloud 账号复测）：另行评审（T1）。
- **其他传输**（MQTT / Mac 互通、同步文件夹）：架构留了位置（T10），本需求不做。

## 13. 我自行决定的项（请审阅，可否决）

1. 同步元数据放旁路目录，**不改 `todos.json` 格式**；本地变更靠 diff 检测，不在 `todos.rs` 写函数里加钩子。
2. 用 HLC 做字段级合并，而不是墙钟记录级；远端 HLC 超前 24 小时以上钳制。
3. 云端每条记录只有一个加密 `payload` 字段，不建索引（以后加字段免部署 schema）。
4. 墓碑永不清理；云端历史不清理。
5. 历史「裁剪」只影响本机、不产生云端删除；「清空」是全局的（用户第 8 轮改，T16），靠「历史由非空变为空」识别，确认框里写明。
6. 顺序用分数索引键；首次合并各自保持内部顺序，按 `createdAtMs` 交错。
7. 默认轮询 10 分钟（系统清醒时）；本机改动去抖 1 秒；唤醒 / 联网恢复去抖 2 秒。
8. 设备名默认取系统电脑名，可改；设备记录里带「最后同步」时间，设置页列出。
9. 同步默认关闭（仅本机），放在设置 → 实验；仅 macOS 显示。
10. 账号变更与区被清除时**暂停并问用户**，不自动重传或迁移。
11. Dev Instance 恒关闭同步；helper 只服务生产 state 目录。
12. 窗口默认约 760×580、最小约 560×360；窄于约 640 时侧栏收成抽屉。
13. 目录的 remote 发生变化（仓库迁移 / 新加 remote）：该目录副本里的待办**以新 id** 并入新项目（按首次合并规则），旧项目里的不动；v1 不做「移动实体」。
14. 超过 256 KB 的待办文本不同步并标注。
15. 容器 / bundle id 命名建议：`iCloud.com.naituw.humaninloop.todosync` / `com.naituw.humaninloop.todosync`（不复用 spike 的 `-spike` 容器；正式环境需要用户在开发者后台新建，见计划 §7）。
16. 「全部待办」视图不提供添加框；添加先进项目。
17. 仅云端项目的 ⚡ 隐藏；其他 Mac 上同一条待办的 ⚡ 显示为关闭。
18. 同机多目录之间的附件不复制（随附件同步一起后置）。

## 15. 风险与已知限制

1. **CloudKit Production 的 schema 需要用户在 Dashboard 手动部署且不可回退**：靠单一 `payload` 字段把部署次数降到一次。
2. **系统版本**：S0 全部在 macOS 27 beta 上做；`CKSyncEngine` 的怪异行为（不拉取）正是在 beta 上观察到的，换用普通 CloudKit 调用降低了对它的依赖，但稳定版上仍需复测。
3. **大陆 iCloud 账号未验证**：容器 / 用户层「初始化」是否需要手工打开 Dashboard；发布前必须用另一个大陆账号复测（T1 第二步）。
4. **空闲 Mac 的推送延迟**：系统策略（附录 A），靠四层新鲜度兜底；无法消除。
5. **helper 生命周期**：登录项首次注册会弹系统的「后台项目已添加」通知；升级后 helper 与 `AskHuman` 版本不一致要靠 `hello` 版本握手处理。
6. **同机多目录附件各留各的**：whats-next 在没有该附件的目录里送达时按现有降级逻辑（无附件）；随附件同步后置。
7. **忽略大小写 / 端口会合并极少数不同仓库**（§5.1）。
8. **待办文本进 iCloud**：用户主动开启才会发生；文本在 CloudKit 里是加密字段，但不等于端到端保护所有场景（取决于用户的 iCloud 设置，如高级数据保护）。
9. **时钟错乱**：HLC 钳制 24 小时；仍可能出现某台 Mac 的改动因时钟偏差「赢」过更晚的改动，但不会丢失数据。
10. **侧栏重构风险**：可能带来既有窗口的回归（拖拽排序、附件拖入、实时刷新等）；靠计划 P1 独立先合并、保留既有测试 + 性能门守住。
11. **helper 与 `todos.json` 事件的反馈环**：tick 写文件会触发监听；靠「忽略自身写入」与去抖避免空转（计划 P3）。
12. **未验证**：断网离线编辑后的重试、B 上关闭 Surge 后的空闲推送（附录 A）。

## 16. 验收标准

1. **传播**：两台 Mac 均在线且活跃时，A 上新增 / 编辑 / 排序 / 完成 / 恢复 / 删除，B 的 `todos.json` 在 5 秒内一致；B 空闲时在轮询周期 + 2 分钟内一致。
2. **whats-next 新鲜**：B 的陈旧度 > 20 秒时，A 刚新增的待办在 B 的下一次 whats-next 卡片里出现，且额外等待 ≤ 1.5 秒；离线时不阻塞、不报错。
3. **收敛**（属性测试）：多个副本上随机操作序列（含乱序、重复、丢失投递）最终所有副本状态完全一致；对任意合并顺序结果相同。
4. **崩溃安全**：在 tick 的任意位置随机 `kill -9`，重复数百次，不丢待办、不重复、下一轮收敛。
5. **离线**：两台都离线各自编辑 → 恢复后字段级合并；删除对并发编辑的结果符合 §5.4。
6. **同机多目录**：同仓库的多个 worktree 队列趋同，新建 worktree 第一次 whats-next 就有完整待办。
7. **性能**：§9.9 的各项度量。
8. **关闭同步零影响**：不启用时，`todos.json` 字节级格式与改造前一致；无 helper、无后台任务、无网络。
9. **隔离**：Dev Instance 无法启用；Windows / Linux 构建与测试不受影响（含侧栏界面）。
10. **账号保护**：换 Apple ID、区被清除、未登录三种情形都暂停并提示，不自动覆盖。
11. **helper 资源**：空闲常驻内存 ≤ 40 MB，空闲 CPU < 0.5%（`ps` / Activity Monitor 抽样）。
12. **重建**：删除旁路元数据后重新启用，能从 iCloud 重建而不丢待办。
13. **历史清空是全局的**（T16）：A 上清空某项目历史后，B 的该项目历史在下一次同步后也清空（含 B 本机早已裁掉、仍在云端的条目）；按 `todo_history_limit` 裁剪不产生任何云端删除；iCloud 模式下确认框写明会清空所有 Mac 与 iCloud 中的历史。

## 17. 反馈意见

### 2026-10-26 ~ 27 设计问答（第 1–6 轮，经 AskHuman）

- **起点**：「我想支持跨设备的 todo 列表，比如说通过 CloudKit 来进行在多个 Mac 之间的共享。帮我分析一下。」
- **第 1 轮**：都是自己的 Mac、同一个 Apple ID；先做 S0 可行性 spike；项目按 git remote 自动合并（同一仓库的所有 worktree 共用一份待办）；⚡ 自动执行不跨机，其他 Mac 当普通待办。
- **S0 期间的授权**：只建 Developer ID 描述文件并导出，不含公证；SSH 到 Mac B 仅用于 spike（用户给出了 B 的地址）；Production schema 由用户自己在 Dashboard 部署（「已部署（Todo、Ping 两个记录类型都部署到 Production 了）」）。
- **第 5 轮**：「你不推荐 sync Engine 只是因为它的延迟有十几分钟吗？我觉得这个完全可以接受。这个的实时性要求没这么高。是不是可以把你说的那些调用也支持？然后推送也支持？」；下一步选「先写 spec 与计划（不写代码），你评审后再开工 S1；同时问清 git remote 合并的边界情况」。
- **第 6 轮（边界）**：
  - Q1 每个目录都是同一份待办的副本：「任何一个目录、任何一台 Mac 上增删改排，其余全部跟上（本机几个 worktree 的队列也因此趋同）」；
  - Q2 「当待办的存储模式改成 iCloud 之后，我就可以看到所有项目的待办。你帮我设计一下界面。」；
  - Q3 无 remote / 非 git：「不同步，保持本机独立队列（待办窗口标『仅本机』）；手动同步名以后再考虑」；
  - Q4 「优先 origin，其次 upstream，再其次按名字排序的第一个；地址规范化成『主机/路径』（忽略协议、用户名、.git 后缀、大小写），ssh 和 https 地址算同一个仓库」；
  - Q5 「v1 不同步附件：文字、顺序、增删跨机；其他 Mac 上这条待办没有附件（待办窗口里提示『附件在其他 Mac 上』）；附件同步后置」；
  - Q6 「执行历史也同步：任意 Mac 都能看到全部历史并恢复」+「就像苹果的提醒事项一样。」；
  - Q7 分两步（先自用，稳定后再评审随正式版发布）+「同步方式，我觉得我们需要先聊清楚。不是我说一个方案，就直接照这个做，我们需要找到最佳方案。这种组合的方式，你觉得有什么问题吗？有没有其他更好的方式？我想解决的问题主要是，我们每次 What's next 也会显示待办。我不希望我需要去手动看一下待办，才能在这里显示出来，所以需要自动的同步机制。」
- **第 7 轮（同步方式与界面）**：向用户提出对混合方案的批评、备选方案对比（混合 / Rust 核心 + 薄适配器 / iCloud Drive / MQTT / git 或自建）与 5 张界面稿。结论：采纳 B′；whats-next 前「过期才拉」；界面问题用户反问并授权：「统一弄这栏是不是以后更好维护？如果是的话就改成统一吧，我不确定本地模式用侧栏成本会不会更高，你需要保证打开的时候不能卡顿之类的」。

- **第 8 轮（评审）**：用户通过需求与计划，并说「你自己全部搞定，我要上班了。」；命名采用建议；其余默认项全部接受，但提出：「但是历史清空是不是应该是全局清空？清空的时候你需要提示一下。」→ 改为全局清空（T16），确认框提示会清空所有 Mac 与 iCloud 中的历史。

## 附录 A：S0 可行性 spike 结果摘要（2026-10-27，两台 Mac，同一 Apple ID，macOS 27 beta）

spike 工程 `~/Developer/AskHuman-TodoSync-Spike/`（仓库外，XcodeGen），标识：bundle id `com.naituw.humaninloop.todosync-spike`，容器 `iCloud.com.naituw.humaninloop.todosync-spike`，Production 环境。

**通过**
- **能跑**：Developer ID + 描述文件的非沙盒 `.app`，`open` 启动，账号可用，建区成功，`encryptedValues` 对端可读。启动方式 `open` / exec / agent-open / SMAppService agent 都行；手写 LaunchAgent 直跑内部二进制会被 CloudKit 拦截（`BUG IN CLIENT OF CLOUDKIT … apsMachServiceName`）。只在 A 上做了完整启动方式矩阵，B 只验了 `open`。
- **收敛**：增删改 / 排序 / 完成双向 digest 一致（12/12）；冲突（基于旧版本保存 → `serverRecordChanged` → 合并 → 约 2 秒内重试）两边收敛（9/9）；带状态重启与清空状态重启都在 0.5–0.7 秒内追平（4/4）。
- **普通拉取好用**：`CKDatabase.recordZoneChanges(since:)` 增量约 0.1–0.2 秒（全量 21 条 0.34 秒）；B 每 20 秒轮询时可见时延 3.5–18 秒，期间零推送。

**不通过 / 需要绕开**
- **`CKSyncEngine` 没有可用的「现在就拉」**：`fetchChanges()` 不发请求，除非推送 / 启动已把区标脏（日志 `no zone IDs needing to be fetched`）；带已保存状态重启时引擎也不拉取（B 重启两次仍落后 4 条）。macOS 27 beta 上观察到，未在更老系统上验证。
- **空闲 Mac 上推送被延迟**：活跃 Mac 约 0.3–0.4 秒到、可见约 1.2 秒；空闲 Mac 上推送被存储转发，等 apsd 心跳（约 16–19 分钟）或别的「enabled」主题才一起到，且被合并。priority 10、`caffeinate` 都没用。
- **补充事实（B 上 apsd 日志 14 小时，只数条数）**：Apple 自己的「enabled」主题（照片、钥匙串、同步默认设置等）走同一条 APNs 连接约 0.1 秒到；它们的**后台型**主题（routined 中位数约 7 分钟、knowledge-agent 约 6 分钟、UsageTrackingAgent 最长约 16 分钟）与我们的容器（该窗口内 8 条：最快 4 秒、中位数约 2 分钟、最长约 4 分钟）同一量级。→ 这是系统对后台型 iCloud 推送的省电策略；**基本排除 Surge / TUN 的影响**（同一条连接上有的主题 0.1 秒到）。

**分发（G4）**：`syspolicy_check distribution` 只报「Notary Ticket Missing」，签名 / Hardened Runtime / entitlements / 描述文件通过；**未做公证上传**；描述文件 2044 年到期。

**没验证**：另一个大陆 iCloud 账号；B 关闭 Surge 后的空闲推送；断网离线编辑后的重试；B 上完整启动方式矩阵；稳定版 macOS 上的引擎行为。

**spike 的合并策略**是记录级「后写者胜 + done 粘性」，会丢另一边对其他字段的改动——产品改用字段级 HLC 合并（§5.4）。
