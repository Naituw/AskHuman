## 1. 用户目标与已确认决策

打开观察界面，一眼知道 Agent 现在在做什么，同时能稳定阅读它公开的思考。

| 编号 | 决策 | 行为 |
|---|---|---|
| O1 | 沿用现有布局 | 主文字区显示一段最新内容，下方继续展示已有工具调用 |
| O2 | 思考直接可见 | 正文与公开思考按来源顺序选最新一段，思考带小标签，内容默认可读 |
| O3 | 整段更新 | 生成中的内容在后台缓冲，段落定稿后成为可展示候选 |
| O4 | 密集更新合并 | 主文字区最多每 10 秒自动替换一次，期间只保留最新候选 |
| O5 | 阅读时暂停替换 | 手指（鼠标）落在文字上、在其上滚动或选字时固定当前内容，有更新显示「有新内容」；展开只改变窗口大小，不固定文字 |
| O6 | 阅读恢复 | 阅读是租约：手指离开文字后再固定 3 秒，之后新内容自动替换，展开的文字也一样；点击「有新内容」主动切到最新，收起回到概览时立即显示最新 |
| O7 | 稳定预览 | 默认约 4 行的固定高度预览，长内容支持展开 |
| O8 | 时间呈现 | 时间放进次级详情，主文字区以内容为重 |

用户先后否定了密集时间线和额外的「当前动作」主区，认为已有工具调用已经表达动作。
本轮定案为在原主文字区补齐思考，并控制文字替换的节奏。

示意中的中文是本地样本的意译，产品直接展示来源原文。

```text
思考

相机目前显示 4K / 60 FPS。
接下来打开规格面板，确认切换后日志与画面是否一致……

展开                          有新内容

◌ 执行命令  …
✓ 读取文件  …
```

「有新内容」仅在已有更新候选且当前显示被阅读固定（手指在文字上或租约内）时出现；展开本身不固定文字。已有状态、工具与 TODO 使用各自的更新路径。

## 3. 候选内容与定稿

### 3.1 选择规则

后端按来源顺序提供最近一段已定稿的助手正文或公开思考，附带类型与稳定身份。
新思考可接替旧正文，新正文也可接替旧思考。
工具更新独立进入现有工具区，工具本身不清空主文字区。

同一条来源记录原地增长时，只更新后台缓冲。空内容与纯签名字段跳过。
显示内容保留原文与原语言，思考使用轻量文本样式，正文沿用现有 Markdown 能力。

### 3.2 定稿依据

优先使用来源的明确完成事件或完成字段。Cursor 结合思考时长字段，以及同一主会话顺序中的后续工具调用、
新正文、下一段思考或回合结束，确认前一段的边界。
子 Agent 和并行分支的事件分别归属，避免用其他分支的工具误判主会话思考已经结束。

固定经过若干秒只能用于展示节流。来源缺少完成证据时，继续缓冲，等待可识别的边界。
最新候选为空时，可沿用上一段已定稿内容。来源明确报告仍在思考时，可带轻量状态提示。
记录过的思考与「当前正在思考」分别依据内容和实时状态表达。

### 3.3 预览与展开

概览默认保留约 4 行固定高度，正文与思考在预览和展开时是同一字号。思考优先取最近的完整末段，过长时展示末尾片段，并标明片段属性。
展开后显示该段已取得的有界内容，超出读取或传输预算时保留截断提示。
主文字区的折叠与展开只改变阅读方式，后台仍持续接收更新候选。

iPhone 上预览与展开是同一个窗口在变高，不是两棵视图互相替换：

- 内容放得下 4 行时没有「展开」，也不标「末尾片段」，窗口仍保持 4 行高，换文时下面的内容不跳（O7）。
- 放不下时才出现「展开」，窗口被裁掉的一侧渐隐，提示还有内容：正文预览从开头起，渐隐在下边；思考预览取末尾几行，渐隐在上边。
- 展开时窗口高度带动画长到全文，思考的文字随窗口变高从末尾对齐顺势滑回开头；收起则反向。
- 收起时如果全文的顶部已滚出屏幕（读到了页尾才收起），页面同时滚回，让这段文字回到视野，而不是把人留在页面下方。
- 点按区不小于 44 pt（2026-11-15）：「展开 / 收起」整行至少 44 pt 高、按钮至少 44 pt 宽，带向下 / 向上的箭头；「有新内容」同样。
  随辅助功能字号放大，整块区域都能点，不只是字所在的那一小块。
- 展开着一段放不下 4 行的文字时，文字上方有一行带「收起」（靠右；思考则与它的标签同一行），展开后不必滚到全文末尾才找得到收起；
  底部的按钮仍在。放得下 4 行的文字没有这一行。
- 展开着的文字被新段落替换时，展开状态保留，窗口高度带动画随新文字变高或变矮（§4）。页面不为这次替换滚动：
  新文字变短时页面按系统的规则停在新的页尾。

## 4. 自动更新与阅读租约

客户端分别保存当前显示内容、最新待显示候选、上次自动替换时刻与阅读状态。
Mac 与 iPhone 使用同一规则，各自维护本地阅读状态。

阅读是一份**租约**，不是永久的锁（2026-11-13 修订，见 §7.3）：手指在文字上时固定内容；离开后再固定 3 秒，
再次触碰重新计时；租约到期后新内容自动替换，不需要点「有新内容」。
展开只改变窗口大小，不固定文字（2026-11-15 修订，见 §7.4）：展开的文字与收起的一样，被手指或租约固定，其余时候按 10 秒窗口自动替换，
展开状态保留。刚点按「展开」的 3 秒内按租约处理（避免刚选中要读全文的这一段因为替换恰好到期而立刻被换走），之后不再固定。

| 场景 | 主文字区行为 |
|---|---|
| 首次打开或切换会话 | 有定稿内容则立即展示，重置该会话的本地展示状态 |
| 新候选到达且距上次自动替换已满 10 秒，且没有被阅读固定 | 直接替换为最新候选 |
| 新候选到达且尚未满 10 秒 | 覆盖待显示候选，原截止时刻到达后展示最新一段 |
| 到达截止时刻 | 有新候选且没有被阅读固定时替换，内容相同则保持 |
| 手指落在文字上并停留（超过 0.15 秒）或移动（含长按选字、在文字上滚动） | 固定当前文字；手指在时没有期限 |
| 手指离开文字 | 再固定 3 秒（租约）。再次触碰重新计时。租约结束后，待显示候选在 10 秒窗口允许时替换，不早于租约结束 |
| 点按「展开」 | 窗口变高，文字不再另行固定；点按后的 3 秒按租约处理（手指正按在文字上时不另算），租约结束后与收起时一样自动替换，展开状态保留 |
| 固定期间收到新候选 | 保留最新候选，显示一个「有新内容」入口；租约结束的那一刻入口随之消失，候选仍等 10 秒窗口 |
| 点击「有新内容」 | 明确切换至最新候选并结束租约；展开态保持展开，窗口随新文字变化 |
| 收起并回到概览 | 立即展示已有最新候选，重新开始节流窗口 |
| 页面其他位置的触碰、拖动、滚动 | 不固定文字。原先「页面任意处下拖就锁」已取消，它让文字在离开页面前一直不换 |
| 租约内没有复制就等到换文 | 选区随换文消失，这是租约的已知代价；要慢慢选或复制，手指按在文字上，选区变化（Mac）也会续租约。展开不再有这个作用 |
| 收到相同内容的重复帧 | 保持文字、选区、展开状态与节流截止时刻 |

10 秒窗口从上次实际替换计算，持续收到新候选不会把截止时刻向后推，避免一直等不到展示。
租约只会推迟替换，不会让替换早于 10 秒窗口。
用户主动点击更新或返回概览可即时切换。状态与工具区照常响应各自变化。
窗口重新聚焦、手机回前台时恢复读取与订阅，当前阅读状态仍属于该页面的本地状态。
页面关闭或切换会话后释放阅读状态，跨页面恢复时首先展示最新内容。

Mac 控制台把「手指」换成指针：在文字上按下（含拖选）算触碰，指针抬起、取消或窗口失焦算离开；
在文字上转动滚轮、文字的选区发生变化是瞬时的触碰，各自开始一段租约。页面其他位置的滚轮、按键、点击不固定文字。

## 5. 数据链路与预算

### 5.1 统一候选

活动聚合按来源顺序选出最新定稿文字，候选包含稳定身份、内容修订、`assistant / thinking` 类型、
有界原文、来源事件时间与截断标志。身份来自会话与来源记录，内容修订独立参与比较。
源内容与身份共同决定是否真的有新内容，纯轮询时间或接收时间走动不触发替换。

Mac `AgentDetailFrame` 与 iOS `watch.frame` 消费同一候选。展示节流和阅读租约留在客户端，
后端候选持续反映来源的最新已定稿内容。已有 `text / steps` 为旧客户端提供兼容投影。
新字段采用可缺省的增量格式，依照 overview 中的 IPC 协议号与 iOS 协议兼容规则实施。
缺少 `latestText` 字段表示旧 Mac，可回退旧文字；字段为 `null` 表示新 Mac 尚在缓冲定稿内容，此时保留当前文字。

### 5.2 有界读取

Cursor 数据库在抽样时约 12GB。通过消息目录尾部分块和 bubble 主键查询读取目标会话，
结合有界回看与缓存取得最近定稿内容。兼容旧目录、分块 generation 变化、同数量重建、
消息原地更新和分块暂缺；暂缺读取保留重试机会。
活动与完整会话共用目录和消息解码，缓存失效也需识别新目录 / checkpoint 的变化。

实施中进一步只读核实了 `generation` 的含义。同一会话在 3 秒内从 7639 条消息追加到 7641 条时，
generation 也随普通写入变化。它是写入版本，来源记录身份仍使用会话 ID 与 bubble ID。
尾部每拍重读，新增定稿消息增量消化；目录版本变化引起的较早消息重放最多每 10 秒一次。
目录收缩越过已消化边界或锚点被替换时立即重建缓存。消息目录和 bubble 读取使用同一 SQLite 只读事务。

沿用现有事件唤醒和工作中约 2 秒的兜底读取。只有候选内容、类型或状态确实变化时推送。
思考签名等无展示用途的字段留在源端。iOS 沿用既有 Watch 单帧预算，按最终序列化字节数限制内容，
避免把长思考作为高频增量全文发送。实施时明确截断位置与提示，展开沿用取得的有界内容。
同一段文字在两次内容变化之间仍会随每个因工具步骤而发出的帧重复；声明 `leanWatch` 的手机只在文字变化（及重新订阅）时收到整段，
其余帧只带引用，见 §7.3。

### 5.3 降级

旧 Mac 缺少 `latestText` 字段时，客户端沿用旧版文字字段。支持思考的来源按各自公开记录解析。
读取暂时失败时保留最后成功内容，读取状态单独表达。
回合空闲、等待回答或出错时，生命周期状态及时切换，已显示文字继续作为最近记录供阅读。
单纯长时间无内容变化仍按现有生命周期信号判断会话状态。

### 7.3 2026-11-13：阅读改为 3 秒租约，实时视图自愈，帧瘦身

用户反馈「思考内容不会及时更新，要切 agent 回来才更新」，但不希望一直刷浪费流量。排查出的原因和各自的处理：

1. **Mac 重启或断线重连后帧号回退**：已在 §7.2 修复（重新订阅前本地帧号归零）。
2. **阅读锁永不过期**：页面任意处下拖、手指落在文字上、展开，都把文字锁到「有新内容」被点或收起为止，手指早就走了，文字仍停在旧内容。
   改为租约（用户定 3 秒，Mac 控制台同一规则，规则见 §4）：
   - iPhone：`WatchTextPresentation` 以 `touching`（手指在文字上）与 `heldUntil`（离开后 3 秒）取代原来的 `reading` 布尔；
     `ReadingTouch` / `ReadingRecognizer` 除「开始」外还在手指离开、取消时回调「结束」，且只跟踪起点落在文字内的那根手指，
     另一根手指抬起不算结束。`AgentDetailScreen` 上「任意下拖就锁」的页面级手势与 `WatchCard` / `WatchText` 的 `reading` 绑定都已删除。
   - Mac 控制台：`useLatestAgentText.ts` 的 `holdBegin` / `holdEnd` / `holdBriefly` 与 `LatestAgentText.vue` 的指针、滚轮、选区、失焦监听；
     原先挂在所有可滚动父级上的 `pointerdown` / `wheel` / `keydown` 监听全部去掉。
   - 10 秒自动替换窗口不变，租约只会推迟、不会让替换提前。
3. **思考只在整段定稿后才出现**：这是 O3 的设计，不是缺陷，未改。
4. **订阅悄悄断掉**：frame 在路上丢了、Mac 忘了这个视图，手机会一直停在旧内容。「切走再切回来」之所以有效，是因为它重新向 Mac 要一次视图。
   `PhoneEngine` 的看门狗把这一步自动化（`PhoneEngine+Agents.swift`）：
   - 每 5 秒看一遍打开着的视图；仅在前台、与 Mac 已同步、视图没被 Mac 关闭时工作。
   - 触发条件之一：打开（或重新订阅）后 5 秒仍没有第一帧；之二：Agent 列表里该 Agent 的**状态、标题、步数或当前工具**变了，
     20 秒内没有任何新帧。仅「关注」「待送达消息数」之类帧里不显示的列表变化不算。
   - 触发时重发 `watch.open`，Mac 会回一帧完整的（含文字）。同一个视图最多每 60 秒问一次，所以最坏每分钟多一帧。
   - 触发和结果都写进诊断日志（开发者模式「复制诊断信息」，类别 `live`）：`a live view is asked for again: <原因>`，
     以及随后的 `the answer to the question had news / nothing new`（答复里有没有与手机已显示内容不同的东西，时钟类字段不比较）。
     日志里有 `news` 才说明真的补回了漏掉的内容；一直只有 `nothing new`，说明触发条件偏松，可以放宽。
5. **帧瘦身（Watch 流量）**：每次工具步骤变化都会发一整帧，而占大头的最新文字只在整段定稿时才变。
   手机在 `hello` 里声明 `leanWatch`（可缺省，缺省 = false，不升协议号），Mac 对这样的手机：
   - 省去旧版 `text` 投影（带 `latestText` 的帧里，新手机只读 `latestText`）。
   - 同一段文字（`kind` + `revision` 相同）整段只发一次；之后的帧里 `latestText` 换成 `{id, kind, revision, same: true}` 引用。
     重新订阅（`watch.open`）、Mac 重启、手机回前台都会重新整段发一次。
   - `latestText: null`（Mac 还在缓冲第一段）照旧发 null，不影响手机已持有的文字。
   手机在引擎里记住每个视图最近收到的整段文字，把引用还原后才交给界面。引用对不上（整段那一帧丢了）时，
   这一帧的其余内容照常显示，文字留空（界面保留当前显示），并立即重发 `watch.open` 要整段（最多每 5 秒一次）。
   旧手机不声明 `leanWatch`，收到的帧与以前完全一样；旧 Mac 不认识这个字段，照发完整帧，新手机照常显示。
   省下的量以文字长度为准：4000 字节上限的思考每帧 ≈ 4 KB 变成 ≈ 100 字节。

### 7.4 2026-11-15：展开不再固定文字，点按区放大，展开后随手可收

用户说 iPhone 上的 Watch「依然很奇怪」：收起展开不好点，有新内容了也不自己刷新，非得点一下按钮。排查到三个原因：

1. 「展开」是 24 × 14 pt 的纯文字，实际可点的区域约 24 × 25 pt（苹果的指引是 44 × 44）。
2. 展开长文后，「收起」在全文末尾，在 Duo 模拟器上实测落在屏幕下方约 270 pt 处，要先滚到全文末尾才找得到。
3. 展开固定文字，而且没有期限（O5 / O6 的原设计）。「有新内容」只在固定时才出现，于是点这个按钮成了刷新的唯一办法。
   用户确认的场景正是文字展开着、新一段到了却不换。

按用户定案（2026-11-15）改为：

- **展开只管窗口大小，不再固定文字。** 固定只看手指（按住时与松手后的 3 秒租约）。展开着的文字与收起的一样，
  新段落过了 10 秒窗口就自己换，展开状态保留，窗口随新文字变高或变矮（带动画）。
  已接受的代价：展开读长段时手不碰文字，最多 10 秒后会被新段落换掉，要慢慢读就把手指按在文字上；
  以前「要慢慢选字或复制，先展开」的办法随之取消。
- **刚点按「展开」的 3 秒内按租约处理**（`WatchTextPresentation.toggleExpanded`，手指正按在文字上时不另算）。
  这一条不是定案里的字面规则，是实现时补的：刚选中要读全文的这一段，不该因为替换恰好到期而在同一秒被换走。
  之后与规则一致，不再固定。
- **点按区放大**：「展开 / 收起」与「有新内容」整块至少 44 pt 高、44 pt 宽，不随字号放大（字放得进去，行再高只会让卡片更长）；
  「展开 / 收起」带箭头；「有新内容」是带底色的胶囊。点按区的角落也算（`contentShape`）。
- **展开后随手可收**：放不下 4 行的文字展开时，文字上方多一行带「收起」（`watch-text-collapse`），不用滚到全文末尾。
- **Mac 控制台同一规则**：`useLatestAgentText.ts` 的 `schedule()` 不再因展开而不替换，点击展开开始 3 秒租约，
  `LatestAgentText.vue` 的「有新内容」只在手指（指针）或租约固定时出现。Mac 上只改规则，没有加顶部的「收起」。

做过又去掉的：展开着的文字被替换时，让页面回滚到新文字顶部（`PageAnchor`，用在收起上的那套）。
实现后这条用例单跑通过，整组跑时有一次替换后页面停在新的页尾（失败截图里顶部的「收起」一行在屏幕上方）。那次失败同时混着用例自己量高度的竞争，
所以不能全部算在它头上；但滚动在这里确实依赖时机：替换时窗口高度是新文字量出来之后才变的，比滚动动画晚一步，
读到页尾时页面可能先被系统截到新的页尾，正在进行的滚动随之被打断（这是推测，没有逐帧确认）。收起时两者在同一个事务里，那条路径是稳的。
这里属于要靠时机凑的做法，按「不做补丁式绕法」的规则没有保留；替换后页面按系统的规则停在新的页尾，「收起」仍在屏幕上可点。

`WatchTextPresentation.wake`（租约结束与候选到期中较早的一个）取代 `deadline` 成为界面睡到的时刻。
我原先的单元测试在 9.9 秒处手动调了一次 `tick`，界面里并没有这次调用，所以没有测出来。

加了 `wake` 之后，「展开的文字自己换」那条用例在 Duo 27.2 上整组跑时连续两次失败（单跑通过），先怀疑是新的调度出了问题，
于是在界面里临时打了日志（已删）重跑：失败的那次运行里，页面收到的第一段文字已经是第二段（`answer`），根本没有「第一段」可换；
其余各次运行里租约结束、再到替换的日志（`woke` → `ticked` → 新的 `wake` → 替换）都正常。原因在用例，不在规则：mock 在页面打开后 0.3 秒（第三帧）
就说出第二段，机器忙的时候（负载 6 至 11）长文的首次渲染比这更慢，页面就直接显示了第二段。这条用例改为一秒一帧（`-AHWatchTick 1`），
第二段在页面打开 3 秒后才到；之后三套环境整组通过。既有的几条（手指固定、租约结束）靠 mock 默认的第二段文字，同样是 0.3 秒后到，余量一样窄，
这次的负载下没有失败，没有改。

没有验证的：真机的手感（点按区是否合手、10 秒窗口下读长段是否被换得太勤、点按「展开」后的 3 秒是否够用）；Mac 控制台只有单元测试，没有对着实窗看。
