## 1. 背景与目标

2026-11-04 为 Cursor 的 Max 开关出内测包 `0.1.0 (6)` 时，出包前只确认了 Max 一项，没有把「自 build 5 起 main 上所有 iOS 改动」列出来。
结果包里还带上了用户此前选过「先不出」的新版项目选择，以及「去掉 Agents 页需要关注分组与继续按钮」。这是流程上的疏漏：
出包技能要求「只包含用户要装的改动」，却没有一步让用户看到「包里到底有什么」。

目标：

1. 出包前列出「这个包里有什么」，让用户知道包里有什么：默认在出包后的汇报里给出，用户要求先看时则确认后才归档、上传（T12）。
2. 手机上的 TestFlight 在该构建下面显示同样的内容（中文、英文各一份），手机上也能看到这个构建带来了什么。
3. 每个构建对应一个可查询的源码提交，下次出包能自动算出「自上个构建以来」。

非目标：不改 App、不改 Mac 端；不进面向用户的发行说明（那是 Mac 自更新用 git-cliff 生成的那份）；不涉及外部测试与审核；
不回填 build 6 的测试内容；不推送标签；不改变上传的授权范围（仍是内部组 `AskHuman Internal`）。

## 3. 出包流程的新增步骤

在现有 skill 流程上增加：

**出包前（归档之前）**

1. 确定出包提交（T8）。用 `scripts/changes.mjs` 取基线并列清单（T2、T3）。
2. Agent 起草中英文测试内容（写法见下），默认不停下确认，直接继续（T12）。用户要求先看时，连同清单一起经 AskHuman 给用户确认（T6）；用户换出包提交点时按 T7 处理。
3. 用户要求先确认时，确认之前**不归档、不上传**。

**上传之后**

4. 等 Apple 状态 `VALID`（沿用现有检查）；然后用 helper 写入测试内容并读回核对（T9、T11）。
5. 在出包提交上创建本地标签 `ios-testflight-N`（T3）。标签是附注标签，信息含版本、构建号、Apple 构建 ID、日期。
6. 在 `docs/plans/ios-channel.md` 的出包记录里写明：源码提交、基线标签、清单要点、中文测试内容全文、Apple 构建 ID 与状态；给用户的汇报里同样写出出包提交、清单和两份测试内容（用户事先没有看过，T12）。

**测试内容的写法**

- 纯文本（TestFlight 不渲染 Markdown），列表符号用 `•`；总长不超过 4000 字（Apple 上限），目标 1500 字以内。
- 第一行：`构建 N · 源码 <7 位提交>` / `Build N · source <7 位提交>`。
- 正文每条一句，写用户视角的变化（做了什么、在哪里看），同一功能的多个提交合并成一条；test／refactor／chore 只在影响行为时写；正文不写提交哈希。
- 「请重点看」1–3 条：本次变化里需要真机验证的点，可取自 `docs/PROGRESS.md` 的待验收项。
- 中英文条目一一对应；如果这个包带上了用户此前选择「先不出」的改动，要明确写出来。
- 不写密钥、本机路径、未公开的信息：内部测试员都能看到。

确认门的消息内容（用户要求先确认时）：构建号与版本；基线标签与出包提交；全部提交清单（短哈希、日期、标题，Agent 可按功能分组）；两份测试内容草稿全文。默认不经确认门时，出包后的汇报给出同样的内容。

## 4. helper 的 `notes` 操作（边界）

helper 是唯一能读 Keychain 凭据的程序（见 [secret-storage-keychain](secret-storage-keychain.md) 与 skill 的 `references/signing-and-recovery.md`）。
`notes` 只在它已有的边界内增加一条窄路径：

- **只作用于本 App**（App ID `6828712684`）的一个指定构建号；该构建必须存在、`processingState=VALID`、未过期。
- **只允许两种语言** `zh-Hans`、`en-US`；每种 1–4000 个字符的纯文本（按 UTF-16 单元计，是几种计法里最严的）。换行统一为 `\n`，去掉整段末尾连续的空格（U+0020）与换行（其他空白字符，如不换行空格，原样保留），拒绝除换行外的控制字符；超长直接拒绝，不截断。
- **只调用固定的几个接口**：按 App 与构建号查询构建；`betaBuildLocalizations` 的读取、创建、修改；以及仅在 `probe` 模式下对**自己刚创建的那一条**的删除。不开放任意网址或方法。
- **输入来自 `0600` 临时文件**（启动器创建、结束后删除），不走命令行参数或环境变量；输出只含构建号、Apple 构建 ID、各语言的动作与字数（`read` 模式另含现有文本，不是机密），**从不输出令牌或凭据**。
- **幂等且必读回**：文本与线上相同则不写（`unchanged`）；每次写入之后都读回并逐字比对，不一致即失败。
- 三个模式：
  - `read`：列出该构建现有的语言与文本，不写；
  - `write`：对输入里给出的语言创建或修改，读回核对；
  - `probe`：对该构建上**当前没有文本**的允许语言，各创建一条标记文本（两行，含项目符号与中文，用来验证换行与非 ASCII 字符能原样读回）→读回→删除→确认已不存在；两种语言都已有文本时拒绝，从不删除不是自己刚创建的条目；中途失败时尽力删除，并在输出里报告残留的资源 ID。
- 修改类模式（`write`、`probe`）与导出共用 helper 现有的互斥锁，同一时刻只有一个修改操作。
- 令牌沿用现有的 5 分钟内存签名；Keychain 授权、helper 标识与 Developer ID 签名都不变。

## 5. 失败与边界

| 情形 | 处理 |
| --- | --- |
| 基线标签缺失、不是出包提交的祖先、或 Apple 最大构建号与最大标签号不一致 | 停下，说明原因，问用户 |
| 自基线起 `ios/` 没有任何提交 | 告诉用户「没有 iOS 改动」，由用户决定是否仍出包 |
| 工作树有未提交改动 | 停下问用户（T8） |
| 用户选「修改文字」（只会出现在用户要求先确认时，T12） | Agent 改后重新给用户确认 |
| 排除项夹在中间（T7） | 停下问用户，不拼包 |
| 上传成功后写测试内容失败 | 不重传；401／403 视为授权问题交给用户；其余把 Apple 的原文报告给用户；确认原因后只重试 `notes` |
| 目标标签已存在 | 不覆盖，停下问用户 |
| 构建最终 `INVALID`／失败 | 不写测试内容、不打标签；按现有规则调查 |
| `probe` 的任何一步与预期不符 | 停下、报告（含残留 ID），不换参数重试 |

- 在线（均已由用户批准，逐步进行，任一步不符即停）：helper 换新后 `status` 与 `upload.py <archive> --check-signing` 正常；对 build 6 先 `read`，再 `probe`（创建→读回→删除），事后 `read` 确认没有残留。
- 首次真用在 build 7：出包前清单与确认门、上传后写入并读回、打标签、记录，全部走一遍。**2026-11-04 已走完**：确认门走了一次（用户看过清单与两份文案后选「按清单出包」）；归档预检通过、上传成功，约 2.5 分钟后 Apple 状态 `VALID` 并进入内部组（这也是 Apple 第一次校验 iPad 构建，没有新的校验错误）；两种语言的测试内容 `created`、读回逐字一致；标签 `ios-testflight-7` 指向出包提交；`changes.mjs` 事后以它为基线、清单为空。出包记录见 [ios-channel](../plans/ios-channel.md) 的「TestFlight 内部构建 7」。没有验证的：多行中英文测试内容在手机 TestFlight 里的实际显示（只验到 API 读回），等用户在手机上看。
