# 调用方断开时保住弹窗里没提交的内容

> 状态：已评审通过，实施中（2026-11-16）。用户选定：只把草稿记进历史、窗口照旧立刻关闭；
> Agent 重发同一个问题时自动载入草稿；§6 的五个默认值全部按默认；在主工作区执行。
> 依赖 / 复用：`docs/specs/reply-history.md`（历史只在汇聚点记一次）、`docs/specs/duplicate-ask-coalescing.md`
> （会话键、提问指纹、引用计数取消）、`docs/specs/popup-request-inbox.md`（合并窗口与按请求草稿）、
> `docs/specs/daemon-live-update.md`（Handoff 保留草稿）。关联计划：`docs/plans/popup-draft-on-cancel.md`。

## 1. 问题

Cursor 出错或中断时，可能把 AskHuman 的 MCP server 关掉。MCP server 一收到取消通知或退出，就杀掉它拉起的
`AskHuman` CLI 子进程——这是有意的，否则弹窗会变成没人读答案的孤儿卡。daemon 看到 CLI 断开、没有其他等待者，
就取消请求，弹窗收到 `Cancel` 立即关闭。**正在输入的内容只存在弹窗网页的内存里，随窗口一起没了。**

链路（代码）：

1. `mcp/ask.rs`：MCP 取消通知或进程退出 → 杀 CLI 子进程。
2. `daemon/runtime/mod.rs`（CLI 连接断开处）：没有其他等待者 → `Coordinator::cancel_request(caller, "caller")`，
   随后立刻把请求从登记表摘掉（这样 Agent 马上重发不会合流到一个已终结的请求）。
3. `cancel_request`：先让每个渠道 `interrupt`，再写一条取消历史（有提问、`answers` 为空）。
4. `GuiHelperPopupChannel::interrupt` 发 `ServerMsg::Cancel` → 弹窗宿主 `Inbox::finish` → 前端移除卡片。

同一份草稿，各条路径的待遇并不一致：

| 路径 | 草稿 |
| --- | --- |
| 用户自己关窗 / 取消 | 二次确认「将丢弃 N 份未提交草稿」 |
| daemon 即时换新（Handoff） | 保留，卡片与草稿原样续上 |
| Agent 重发而旧 CLI 没被杀 | 合流到旧卡，草稿保留（coalescing D3，「绝不作废旧卡」） |
| **调用方断开 / 系统取消（本篇）** | **无保护、无提示，直接丢** |

这条路径不罕见：本机历史里 11-14 至 11-16 共有 26 条调用方取消（`answers` 全空；其中一部分是开发实验留下的，
没有逐条核对来源）。

## 2. 需求

1. 调用方断开、daemon 关停时，弹窗里已经输入的内容不丢。
2. 窗口照旧立刻关闭，不加提示、不保留卡片（用户选定）。
3. Agent 在同一会话重发同一个问题时，新卡自动带出这份内容，并提示「已载入上次未提交的内容」。
4. 其余路径一概不变：用户取消、被别处抢答、Handoff、合流。
5. 契约不变：CLI / MCP 输出、退出码、IPC 协议号。

## 3. 设计定案

### D1 保存条件：取消来源决定

取消来源分三类：**人**（用户在某个渠道点了取消）、**调用方**（CLI 断开且无其他等待者，coalescing D4）、
**系统**（daemon 关停时的 `cancel_all_requests`）。

- 保存：调用方、系统。
- 不保存：人（用户亲手取消，弹窗里本来就有二次确认）；被别的渠道抢答（用户已在别处答了）；Handoff（草稿本来就保留）。
- 只对 Ask 类交互（普通提问、whats-next、严格选择、Stop 确认；它们都有答题表单）。权限卡（Confirm）不存。

### D2 草稿内容

每题的：选中的选项（文本）、文字、图片、回复文件（路径）；加上对 message / 题干的批注。
字段与历史里的回答同形（`HistoryAnswer`、`UserAnnotation`）。

不存：弹窗折叠待办区里选的待办（按当时队列生成，重发时队列可能已变；待办在「开始执行」时才出队，没有丢）、
快速回复指令（armed directive）、权限卡备注。没有任何内容时不写草稿（记录与今天完全一样）。

### D3 存哪：取消记录上的 `draft` 字段

调用方 / 系统取消本来就会写一条历史（id 即请求 id）。草稿挂在这条记录上，作为新的可选字段，**不放进 `answers`**：

```jsonc
{
  "id": "<请求 id>", "action": "cancel", "channel": "caller", /* …既有字段… */
  "draft": {
    "key": { "sessionKey": "sid:…", "fingerprint": "<合流指纹>" },  // 重发时用来对上号；没有会话键则只有 fingerprint
    "answers": [{ "selectedOptions": [], "userInput": "…", "images": ["/tmp/askhuman/<id>/q1/img-1.png"], "files": [] }],
    "annotations": [{ "quote": "…", "note": "…" }],
    "claimedBy": "<载入它的新请求 id>"                              // 载入后写入（D6）
  }
}
```

理由：`answers` 的含义保持「用户真的发送了什么」，`--show-last`、会话「最近回答」、iOS 会话历史只认 `action=send`
的记录，本来就不会读到草稿；历史的容量、搜索、删除规则无需另立一套。

### D4 写入时序与进程分工

- daemon：
  - `cancel_request` **先写取消记录，再 interrupt 各渠道**（现在是反过来）。这样弹窗宿主收到 `Cancel` 时记录一定已在。
  - 弹窗渠道发出的 `Cancel` 对调用方 / 系统取消带 `keepDraft: true`，其余来源为 `false`。
  - Ask 类请求的 `ShowPayload` 带 `draftKey`（会话键 + 合流指纹，只是标识，不含内容）。
- 弹窗宿主：收到 `Cancel{keepDraft: true}` → 向前端要草稿（D5）→ 把图片落盘（与回复图片同一个写法）→
  `history::attach_draft(请求 id, 草稿)`，在历史文件的跨进程锁内把草稿并进已有的取消记录；草稿的 `key` 取自该请求
  `ShowPayload.draftKey`。
- 记录不存在（历史条数为 0、该请求不记历史）→ 什么也不做，写一行日志。
- 为什么由宿主写、不回传给 daemon：草稿在弹窗网页里，回传需要新的 `ClientMsg` 变体，按 AGENTS.md 要升协议号；
  历史窗口的删除本来就是别的进程改同一个历史文件，宿主直接改不动协议。

### D5 前端采集与宿主等待

- `Inbox::finish` 遇到 `keepDraft` 时把请求放进「待存草稿」集合，`popup-inbox-terminal` 事件带 `keepDraft: true`。
- 前端在这个事件的监听里**同步**读取该请求卡片的草稿（此时卡片还在），**不等保存完成**，卡片照常移除——窗口关闭的时机与
  今天一致。读不到（卡片没挂载、没有内容）就回传 `null`。提交进行中也照读：此时回答没有送达，内容仍在表单里。
- 宿主在退出路径（空闲退出 `PopupHostIdleAck keep_warm=false`、`PopupHostShutdown`）上等「待存草稿」集合清空，
  **最多 3 秒**（有界等待，不是轮询重试）；超时写日志并照常退出。
- 保存尽力而为：写盘、历史锁等任何失败只写日志，不影响关窗，也不影响其他路径。

### D6 重发载入：在宿主里匹配、认领、一次性

载入也在弹窗宿主里完成，不经 daemon。原因：「调用方断开 → Agent 立刻重发」时，daemon 先发 `Cancel`、紧接着发新请求的
`Show`；这两件事（保存上一份草稿、给新卡找草稿）若分在两个进程，新卡可能赶在草稿落盘之前去查而落空。放在同一个宿主进程里，
`Cancel` 先到、`Show` 后到，前端按到达顺序处理，保存与载入就是串行的两步，不需要 daemon 等、也不需要轮询。
（即使顺序被打乱，后果也只是这次没载入：草稿仍在历史里、未被认领，下一次重发会载入，不会丢。）

- 时机：前端取到这张卡的 `popup_init` 之后，向宿主调用新命令 `popup_draft_claim`（卡片实例化时，比 `Show` 到达更接近真正
  展示；`popup_init` 本身不动，预热与独立窗口路径不受影响）。若宿主里还有同键的「待存草稿」，命令先等它完成（有界，同样最多
  3 秒）再查；这一步只会拖慢这一张卡的草稿载入，不阻塞别的消息，也不阻塞卡片本身的显示。
- 匹配：**同会话键 + 同合流指纹**。会话键规则同 coalescing D1（agent session 优先，MCP 实例兜底，两者都没有就不匹配）；
  指纹用 `coalesce_fingerprint`，所以 whats-next / Stop 卡里待办队列变了也算同一个问题（coalescing D2 的例外同理）。
- 取最新的一条「有草稿且未被认领」的记录，**认领**它（写 `draft.claimedBy = 新请求 id`）；每份草稿至多载入一次。
  同一请求重复收到 `Show`（宿主被替换后重新下发）时，已被本请求认领的草稿原样再给一次。
- 草稿跟着问题走：载入后若新卡又被取消而且仍有内容，新记录里存一份新草稿；旧记录保留为「已载入」，历史里仍可见。
- 不设有效期；草稿随历史记录被裁剪或删除而消失。
- 只给弹窗：IM 与 iOS 渠道不下发（iOS 有自己的草稿库，IM 卡没有预填入口）。若用户在手机上答了，草稿已被认领、留在历史里，
  不再载入。
- 与重放（coalescing D5 / D6）无关：载入只是预填，要你自己点发送；取消仍不重放。

### D7 载入后的界面

- 新卡带出内容：选项（按文本匹配，新卡里没有的丢弃）、文字、图片（读保存的文件，文件已被系统清理的跳过）、
  回复文件（路径还在才带）、批注（按引文重新定位，找不到的排在清单最后，与 iOS 一致）。
- 卡片顶部一行提示「已载入上次未提交的内容」，可关闭。如果有图片因文件已被清理而没带出来，提示里写明张数。
- 之后和手输的草稿完全一样：侧栏「草稿」标记、关窗二次确认都照常。不自动提交，不抢焦点。
- 草稿到达时用户若已在这张新卡里输入了内容，不覆盖，只补空着的部分（提示照常显示）。

### D8 历史窗口

- 带草稿的取消记录：徽标仍是「调用方取消」，另加「草稿」标记；详情里每题下只读显示草稿（选项、文字、图片、文件）和批注，
  带复制按钮；状态行写明「调用方断开时未提交的内容」及是否「已载入新提问」。
- 搜索覆盖草稿文字——没有重发时，这是找回内容的入口。
- 删除、清空、按条数裁剪与别的记录一样，草稿随记录消失。

### D9 历史被关闭时不保存

`historyLimit = 0` 或该请求不记历史（如引导页的测试题）：没有取消记录可挂，草稿不保存、也不提示。
尊重「不留记录」的设置，不另开第二条存储通道。

### D10 兼容与协议

- 新增的跨进程字段只有两个：`ServerMsg::Cancel.keepDraft`、`ShowPayload.draftKey`，外加历史文件里的 `HistoryEntry.draft`。
  都是带 `#[serde(default)]` 的新增字段、没有值时不序列化。按 AGENTS.md「IPC 协议号」的规则**不升** `PROTOCOL_VERSION`，
  既有序列化与恢复存储的哈希不变（计划里逐项核对）。草稿内容不经过 daemon IPC；载入给前端走宿主进程内的 `popup_draft_claim` 命令。
- 新旧混用：新宿主 + 旧 daemon 没有 `keepDraft` / `draftKey`，与今天一样不保存也不载入；旧宿主 + 新 daemon 忽略这两个字段，
  同样不保存；旧版本重写历史文件时会丢掉 `draft`（只丢草稿本身，记录保留）。
- 不动 SQLite 恢复存储。

### D11 不留开关

行为是纯保护（少丢一次内容），默认始终生效，不加配置项。

## 4. 不做的事

- 不保留卡片、不弹系统通知（用户选定「窗口照旧立刻关闭」）。已知取舍：没有重发时，要去历史窗口找。
- 不连续写盘（不是每次按键都存）：弹窗进程本身崩溃或被杀仍会丢，本篇只覆盖「调用方走了」。
- 不做跨会话匹配，不做模糊匹配。
- 不把草稿当答案送给 Agent：没人在等，也不替用户发送。
- 独立窗口模式（`channels.popup.windowMode=independent`）本期不做：它的窗口走另一套取消处理
  （`dismiss_from_daemon`），你的配置也是合并模式。
- 不处理「SIGKILL 杀掉 MCP server 后 CLI 子进程成孤儿、卡片留着但答案无处可送」，那是另一类问题。
- 不存待办区选择和权限卡备注（D2）。

## 5. 验收

1. 一张卡里输入文字、选一个选项、粘一张图、拖一个文件、加一条批注；杀掉调用方 → 窗口立刻关闭（时机与今天一致）；
   历史里该取消记录带「草稿」，五样内容都在；`--show-last` 与会话「最近回答」不受影响。
2. 同一会话重发同一条命令 → 新卡带出五样内容和提示；可以直接发送；历史里旧记录标「已载入」；第三次重发不再载入。
3. message 差一个字、或换了会话 → 不载入。
4. 用户自己关窗（确认丢弃）、在手机 / IM 上答了、在 IM 上点取消 → 不保存草稿。
5. 历史条数为 0 → 不保存，没有报错。没有内容 → 记录里没有 `draft`。
6. whats-next 卡里输入文字后调用方断开，待办队列变了再重发 → 仍载入。
7. 调用方断开后**立刻**重发（间隔小于一次保存）→ 仍载入，不落空。
8. daemon `stop` 时有未提交草稿 → 尽力保存（3 秒内）；宿主退出不被无限拖住。
9. 新旧混用（新宿主 + 旧 daemon，旧宿主 + 新 daemon）：不崩溃、不保存。
10. 草稿里的图片文件已不存在 → 载入时跳过并在提示里写明张数，其余内容照常带出。

## 6. 默认值（用户已确认：全部按默认）

这些是评审时替用户定的默认，上面的设计已按它们写：

1. **Stop 确认卡也保存。** 我上一条说「权限卡、Stop 确认卡不存」不准确：Stop 确认卡和普通提问一样是 Ask 类、有文字框，
   在里面输入的内容同样会随调用方断开丢掉。只有权限卡（没有自由输入）不存。
2. **不设草稿有效期。** 只靠「被载入一次」「被新记录顶替」「历史裁剪 / 删除」让它消失。
3. **图片落系统临时目录**，与回复图片同一个写法；macOS 过几天会清理，之后载入时跳过缺失的图片并说明张数。
4. **独立窗口模式本期不做**（它走另一套取消处理）。
5. **载入提示是卡片顶部一行、可关闭**，不提供专门的「清除已载入内容」按钮（照常编辑 / 清空即可）。

  提交只按明确路径，安装前先问用户怎么处理它们）。
- 评审前用户提出的两点已并入设计：草稿记在取消的历史记录上（D3）、重发时自动载入（D6、D7）。
