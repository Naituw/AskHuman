# Agent 生命周期结果与原会话继续

> 状态：已实现并通过自动验证；Mac 已安装，iOS 尚未分发。
> 日期：2026-10-31。
> 范围：Codex／Grok 生命周期补齐、所有 Agent 的上轮结果展示，以及手机向空闲会话发消息和要求继续。
> 关联：[现有生命周期](agent-lifecycle-tracking.md)、[iOS 渠道](ios-channel.md)、
> [结果通知](ios-follow-narrowing.md)、[Codex Desktop](codex-desktop-session-integration.md)、
> [Pi 集成](../plans/pi-agent-integration.md)。

## 1. 问题与目标

电脑创建的 Cursor 会话失败后，会从手机 Agents 的「运行中」移到「空闲」，但没有失败提示。
当前 `stop(status=error)` 已能上报失败；`AgentState.swift` 却只在 `state=ended` 时显示
`lastTurnFailed`，普通回合失败后的 `idle` 一律显示「空闲」。失败标记还只在网关内存中保存。

同时，上游 Codex 已提供 `Interrupt`／`SessionEnd`，Grok 已提供 `StopCancelled`，现有集成未接入。
生命周期事件只携带 `failed: bool`，把 Cursor／Pi 的用户中断与正常完成混在一起。

本设计将会话运行状态、上轮结果和消息提交状态分开，保留失败原因，提供两种原会话入口。
开发与验证过程中禁止用 Cursor 实测，包括启动测试会话、发送真实请求或附加运行中的 Cursor
进行行为探测；Cursor 结论仅来自文档、安装文件静态分析和隔离替身测试。

## 2. 已确认的使用行为

| 场景 | 行为 |
| --- | --- |
| 用户主动停止、取消或拒绝权限 | 上轮结果为「已中断」，会话空闲；撤销待发完成通知，不发完成／失败提醒，不弹 Stop 确认 |
| 运行达到上限、无进展而自行终止 | 上轮结果为「未完成」，保留原因；符合通知条件时发「任务未完成」提醒 |
| 明确的运行错误 | 上轮结果为「失败」，保留原因；符合通知条件时发失败提醒 |
| 明确完成 | 上轮结果为「完成」；符合通知条件时发完成提醒 |
| 原因无法确定或仅观察到空闲 | 不推断为完成或失败；显示已有结果，或「结果未知」 |
| 所有来源的失败／未完成会话 | 在手机 Agents 靠前的「需要处理」分组显示；不要求任务从手机创建 |
| 空闲会话发消息 | 在详情页输入并发送，自由输入不要求上一轮失败 |
| 失败／未完成会话继续 | 独立按钮，文案固定为 **「要求继续」**；点一次直接提交默认指令 |
| 从手机发送或要求继续 | 该次操作真正启动的新一轮进入一次性结果通知范围，包括原先在电脑创建的会话 |
| 首版恢复覆盖 | 桌面 Codex、桌面 Cursor、Pi；按会话实际能力开放，其它会话显示具体不可用原因 |

通知沿用 Mac 空闲门槛、手机前台展示、Mac 再次活动后撤销等既有规则。用户主动中断不算一个
需要投递的结果；本次待通知资格保留到后续明确结果或会话结束，不因为中断而发送成功提醒。
同一轮已处理的结果不因重复回调、手机重连或 daemon 重启再次通知。

## 3. 状态与结果

### 3.1 独立保存两个维度

会话状态保留现有 `working / idle / ended`；`waiting` 仍从在途 AskHuman 请求派生。
上轮结果另存为 `completed / failed / interrupted / incomplete / unknown`。
「空闲且上轮失败」是正常组合，失败不意味着进程退出，会话退出也不意味着任务完成。

结果记录包含：原生回合 ID（可选）、结果类别、规范原因码、来源、观察时间和有界原因摘要。
保留原生原因码用于诊断，展示使用本地化文案；不把整段 Hook 输入、提示词或转录存进结果。
历史记录缺失结果时保持未记录，不从 `idle`／`ended` 倒推出成功。

结果由 `AgentRegistry` 随 `agents.json` 持久化，网关只消费统一结果。新的一轮真正开始后，
当前结果标记清除；发送按钮被点击、服务端受理、普通活跃心跳都不能提前清除它。
退出会话时保留结果供最近结束列表展示，沿用现有有界历史保留，不建立新的无限结果档案。

### 3.2 手机列表

分组顺序为「等待回答 → 需要处理 → 运行中 → 空闲 → 已结束」。需要处理收纳当前不在工作、
且最新结果为失败或未完成的会话；会话只出现一次。在途提问、真实运行状态优先于旧结果分组。

- 失败使用红色「上轮失败」，未完成使用橙色「未完成」，同行显示简短原因。
- 详情页同时显示运行状态、结果、原因和发生时间，不把空闲换成一个虚假的运行状态。
- 已中断留在空闲分组，显示中性的「已中断」；成功／未知不进入需要处理分组。
- 原会话已结束时仍展示其最后结果，并说明会话已结束；恢复按钮按实际控制能力判定。
- 下一轮开始后离开需要处理，转入运行中。仅打开详情不会清除结果。

这套展示规则覆盖所有 Agent，与是否有一次性通知资格分离。桌面控制台、托盘、IM 与 Watch
消费者也须能继续读取原有会话状态，不因新增结果把失败解释成会话死亡。

## 4. 回调补齐与映射

| 来源 | 事件 | 归一化含义 |
| --- | --- | --- |
| Codex | `UserPromptSubmit`／工具活动 | 原回合 ID 下的开始／活动 |
| Codex | `Stop` | 正常结束候选，沿用共享 Stop handler 的 continuation 裁决 |
| Codex | `Interrupt` | 活动主回合被用户中断；结果 interrupted，不走结束确认 |
| Codex | `SessionEnd` | 会话结束；保留已有结果，不生成一个成功结果 |
| Grok | `UserPromptSubmit` | 记录当前 `promptId`，进入运行中 |
| Grok | `Stop` | `reason=end_turn` 的正常结束候选；会话关闭的 Stop 不算成功 |
| Grok | `StopFailure` | failed，保留规范错误类别 |
| Grok | `StopCancelled` | 用户原因 → interrupted；`max_turns / no_progress` → incomplete；未知原因 → unknown |
| Grok | `Notification(idle_prompt)` | 会话已空闲的补漏；不凭该通知断言完成 |
| Grok | `SessionEnd` | 会话结束，保留已有结果 |
| Claude | 现有 `Stop`／`StopFailure` | 接入统一结果；用户中断仍保留既有兜底，不能声称已获得完整回调 |
| Cursor | `stop.status` | completed／error／aborted 分别对应完成候选／失败／已中断 |
| Pi | `agent_settled` + 本轮 `stopReason` | stop／error／aborted 分别对应完成／失败／已中断；缺失原因不算成功 |

Codex 的 Interrupt 仅覆盖活动主会话，SessionEnd 也不等于切换聊天：正常关闭、归档／删除
已打开会话、或无人订阅且空闲 30 分钟后的卸载才是上游描述的结束点。API 错误尚无对应的
独立失败 Hook；本设计不将 Interrupt 当成 API 错误。可从已接入的原生运行结果补充结果，
其它情况保持未知与状态兜底。

Grok 的 `Stop` 是可阻止结束的 gate。检测到其它 Stop handler 时，不能凭一次被动 Stop 观察
认定整轮最终完成：优先用原生终态确认；无可确认终态时，等待空闲补漏，只更新已确认的状态。
这类场景可能延迟约一分钟，无法确认结果时不发完成通知。时间超时永远不能合成成功。
`subagentType` 存在的 Grok 子代理事件不修改主会话状态。

### 4.1 关联、乱序与重复

Codex 保留 `turn_id`，Grok 保留 `promptId`；ID 是会话内不透明标识，不按字符串或时间排序。
完整 JSON 与大载荷摘要读取路径都必须保留回合 ID、结果、取消者与原因，避免大工具输出改变语义。

- 开始、活动、终态关联同一回合；旧回合迟到的结束不能把新回合从运行中改为空闲，也不能触发新通知。
- 重复回调幂等。同一回合的完成候选可被随后到达的中断／失败撤销，撤销待投递的完成提醒。
- 终态先于对应开始到达时保留有界关联记录，迟到开始不能复活已经结束的那一轮。
- Grok 无 `promptId` 的会话级空闲补漏可以校正会话状态，但不会覆盖已有明确结果。
- Hook 时间戳是分发时间，不能用来压过另一个回合；新会话／重载使用独立会话代际，避免旧控制连接回报串入。

## 5. 两个操作入口

### 5.1 空闲消息

详情页在原生通道就绪且会话确实空闲时显示可发送输入栏；沿用已有消息与附件交付契约。
发送的是普通用户消息，沿用目标会话的模型、思考强度和权限设置，不创建新任务或 Fork。
仍在工作的会话沿用现有可用的运行中补充消息能力；等待回答时先显示当前待答请求。

### 5.2 要求继续

需要处理的会话在列表行提供「要求继续」按钮，详情页也提供同名动作。它与空闲输入栏独立。
只有失败／未完成、没有在途提问且控制通道可用时允许提交；无需先编辑一段提示或再次确认。

默认指令的语义固定为：检查上一轮失败／未完成的原因和已经完成的步骤，从当前进度继续原任务；
避免重复已成功的操作；仍受阻时说明原因并按现有 AskHuman 协议请求帮助。
可引用有界的上一轮规范原因，不把原始错误当作可执行命令。不自动提权、换模型或绕过权限。

两个入口共用一个消息提交服务；「要求继续」只是带预期结果 ID 和默认指令的普通原会话发送。
按钮与输入栏的禁用、等待开始、失败与结果不明状态一致。

### 5.3 实际可用能力

| 会话 | 首版路线 | 就绪判定与限制 |
| --- | --- | --- |
| Codex Desktop | 复用 `Operation::Send` 与持久操作回执 | 原生连接、准确会话身份与可发送状态均成立 |
| Cursor Desktop | 扩展用户私有控制桥，调用原会话原生消息提交 | 安装文件存在 `composerChatService.submitChatMaybeAbortCurrent`；仍需版本契约、窗口／会话归属和原子空闲检查；不是现成已验证功能 |
| Pi | 受管扩展增加空闲时的消息接收，用原生 `pi.sendUserMessage` | 扩展以真实 session/generation 注册连接；会话关闭／切换时撤销，重连不能重复提交 |
| 普通 Codex／Claude／Cursor／Grok 终端会话 | 首版保留状态与结果观察 | 现有工具前插话无法唤醒空闲进程；没有接入通道时显示原因 |
| Antigravity | 首版无控制入口 | 尚无 AskHuman 生命周期／控制适配器 |

Cursor 的公开 SDK 具有独立持久化和 resume 能力，不能据此认定能接管已打开的 IDE 聊天。
首版不另开 CLI／SDK 进程替代原桌面会话，也不向终端盲打按键。Cursor 消息控制不应依赖
用户开启「禁止后台完成后自动续跑」的偏好；两种能力分别探测与启停。

## 6. 提交与结果的竞态

每次操作使用手机作用域的稳定操作 ID，并绑定目标会话及预期回合／结果版本。双击、超时重试、
重连都复用这个 ID；客户端不能因一次超时直接生成新 ID 再提交。

1. 服务端检查目标身份、代际、通道与最新状态。
2. 在原生提交锁或同等原子边界内再次检查空闲。已在运行则返回状态变化，不替用户停止新回合。
   Cursor 名称中带 `MaybeAbortCurrent` 的函数尤其不能无保护调用。
3. 原生接受后记录回执，UI 显示「已送达，等待开始」；受理不等于已经运行。
4. 观察到关联的新回合开始后，清除旧结果，转入运行中；为这台手机登记本轮的一次性通知资格。
   其它入口或电脑自行启动的新回合不借用本次资格。
5. 明确拒绝时保留草稿／原结果；结果不明时保留操作 ID 和原结果，提示检查原会话，不自动重发。

先到的新回合、后到的接受回执同样能关联。进程或窗口重启后，恢复持久回执而不重放已提交操作。
「要求继续」不能把仍在等待权限或 AskHuman 作答的会话当作失败后空闲；应先处理原请求。

## 7. 通知与兼容

结果展示来自持久会话记录，是否通知来自手机的本轮操作登记；两者不能共用一个失败 HashSet。
已有手机创建任务的一次性通知继续有效。手机发送／要求继续只让发起的手机获得本轮资格，
重复操作不占多个名额；继续遵守现有通知集上限，并明确反馈未能登记通知的情况。

失败、未完成、成功各使用匹配的本地化通知。用户中断和未知不发结果推送；回合取代、继续运行
和会话结束按既有撤销规则清理待投递结果。重启重载结果用于展示，不自动补发历史提醒。

IPC 优先在现有消息中增加带默认值的可选回合／结果字段，保留旧字段投影；不重命名原状态。
但「旧端能解码」不足以保证语义兼容：旧 daemon 会把 `failed=false` 的 turn-end 当成功。
新版报告器必须确认 daemon 声明支持结果分类，才发送中断／未完成的富结果；遇到旧端时不发送
会被误认成成功的替代事件，保留旧状态兜底并给出集成更新诊断。

新增能力通过可选 capability 字段协商；未完成提醒和需要处理分组需要新版手机。
旧手机不得把新类别误显示为完成或得到未翻译的推送键；未声明能力的手机不投递新类别的通知。
实施前须覆盖新旧 CLI、daemon、App 和同协议不同构建的组合。若必须新增旧端可接收的消息枚举，
按主 overview 的 IPC 规则提升协议号，不以「增量」为由绕过兼容要求。

新 Hook 仅对有证据支持的 Agent 版本安装，状态检查与安装使用相同能力集合；版本不明时不能
盲写未知事件。本机静态基线为 Codex CLI 0.163.0、Grok 1.0.70、Cursor Desktop 3.27.12、
Pi 0.84.2；这是观察基线，不宣称是首次支持版本。Codex 的信任标签、短超时归一化与哈希要
一起更新，Interrupt／SessionEnd 的超时遵守上游 1–3 秒限制。

## 8. 实施与验收边界

先实现统一结果与回合关联，再补 Codex／Grok Hook、持久状态与全 Agent 展示，最后接入空闲
发送／要求继续和本轮通知。桌面原生结果与 Hook 按同一会话／回合合流，不能重复通知。

必须验证：

1. 所有 Agent 的成功、明确错误、用户中断、运行时中止和未知原因映射；工具失败后恢复不算整轮失败。
2. 新回合开始后旧终态迟到、终态先于开始、重复回调、子代理隔离、会话代际更换。
3. daemon 重启后仍有失败原因；空闲失败显示在需要处理，下一轮实际开始后移回运行中。
4. 空闲自由消息与要求继续共用准确原会话，保留模型／权限；同时启动新回合时拒绝重复继续。
5. 双击、请求丢失、接受回执丢失、服务端重启、原生结果不明均不重复提交。
6. 手机接续电脑会话后的本轮通知资格、Mac 空闲门槛、中断静默、未完成提醒与旧 App 降级。
7. Codex／Grok 新旧能力集合、JSONC 保留与卸载、信任哈希和实际有效超时。
8. iOS 原生 mock 界面的分组、原因、要求继续、发送中／待开始／不可用状态和中英文本。

功能实现后遵循项目规则运行相关检查、`./scripts/install.sh` 和新安装的 AskHuman。
Cursor 使用静态契约与隔离替身验证；不得为验收解除本设计中的实测限制，也不能把替身通过
写成真实 Cursor 验收完成。手机分发与功能实现是后续工作，本设计稿不代表已经部署。

## 实现地图与运行边界

- `agents/result.rs` 分类结果；`agents/registry.rs` 在同一锁内处理回合关联、重复与迟到事件，随 `agents.json` 保存。
- `agents/control.rs` 保存手机范围的一次性消息回执；`daemon/runtime/agent_control.rs` 复用原生通道并等待实际开始证明。
- Codex Desktop 从 canonical turn 状态与原用户消息 ID 补充结果；Cursor 的消息桥只在显式发送时附加，使用独立身份与原生提交锁，不改变后台完成抑制桥的版本与内容。
- Pi 的控制轮询只连接已有 daemon，不唤醒或保活它；重载会更换代际。受控 Stop continuation 尚未报告最终结果时，继续使用同一逻辑回合身份，普通后续用户消息使用新身份。
- Codex 新事件使用本机已验证的 0.163.0 门槛；Grok 使用 1.0.70 门槛。这是已验证基线，不声称是上游首个支持版本。版本未知保守保留兼容集，降级安装只移除本工具的不支持项。
- Grok 的 Stop 无法排除后续 gate 时保守等待 idle_prompt；新工具活动会作废先前候选。只有空闲而无有效结果候选时保留 unknown。
- IPC 保持协议 4，只增默认／可选字段；富结果要求 `agentLifecycleVersion`，手机新通知类别要求 `lifecycleResults`。
- 会话关闭、回到 Mac、以及有新活动时按既有规则撤销未投递提醒；重启恢复结果展示，不自动补发历史提醒。
- iOS 改动需要新版 App；本轮尚未分发 TestFlight。Cursor 仅做静态与隔离替身验证，未启动会话、发送真实请求或附加运行实例。
