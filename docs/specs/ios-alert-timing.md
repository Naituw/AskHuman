# 需求：iOS 提问不再受活跃槽约束，Mac 空闲一阵后才推送

> 状态：**已实现，自动化验证通过，待真机一轮**（2026-10-26 经多轮 AskHuman 讨论起草，同日用户批准草案并完成实现；待验项见 `docs/PROGRESS.md`）。
>
> 痛点：开启「IM 渠道按需发送」（`channels.autoActivation`）后，iOS 渠道和 IM 一样受**活跃槽**约束。
> 每次在 Mac 上答完题，槽就回到本地弹窗；离开 Mac、拿起手机之前必须记得去「接管」，忘了就收不到推送，
> 连手机的待答列表里都没有这道题。
>
> 目标：手机**不用激活**——所有待答题始终在手机的待答列表里；**推送**只在 Mac 真的空闲了一阵
> （默认 15 分钟）、而你又没看过这道题时才发一次，不再提醒。
>
> 关联计划：`docs/plans/ios-alert-timing.md`。同步修订 `docs/specs/ios-channel.md`
> （D11、§6.7、§6.10、§6.11、§7 第 2 / 6 条）与 `docs/overview-ios.md`。
> 范围**只含 iOS**；IM（飞书 / 钉钉 / Telegram / Slack）继续按活跃槽 / `/here`。

## 背景

- 活跃槽（`docs/plans/im-channel-activation.md`）是为 IM 设计的：IM 只能靠推送送达，消息一发就留在聊天记录里，
  所以只给「当前活跃的一个渠道」发。iOS 渠道复用了这套规则（`ios-channel.md` D11）。
- 槽在每次作答后都会重置：`finish_request_bookkeeping` 把槽设为答题的渠道，在 Mac 弹窗答完就回到 `popup`，
  iOS 随即被排除在投递之外。要重新接管得「打开 App → Macs → 这台 Mac → 把提问发到这部手机」。
- 这个失败是**静默**的：槽不是手机时，题不进手机的待答列表、也不推送，Agent 一直等。
- iOS 是我们自己的 App：内容可以按需拉取，推送又便宜，要权衡的只剩「打扰」——不需要 IM 那种「按需发送」的克制。

> 用户原话（2026-10-26）：「我理解我们现在可以自己控制 iOS 端之后，不需要这种激活策略。这种激活策略的坏处是，
> 每次我离开我的 Mac，拿起我的手机，我都需要想起来去激活一下我手机上的渠道。我觉得这个还是不够自然，
> 有的时候我忘了，可能我就收不到通知了。」

## 决策记录（用户经 AskHuman 定案）

- **D1 iOS 脱离活跃槽**：每道待答题（含权限 / Stop 确认）无条件挂到已配对手机的待答列表，不再看 `autoActivation`
  与活跃槽。IM 不变。
- **D2 通知与内容传输分开**（用户原话：「发通知是一个相对比较廉价的事情，我们只需要考虑打扰的问题。然后手机活跃的时候，
  才是实际需要把这些内容传输到手机的时候。」）：
  - **传输**由「手机活跃」决定，沿用现状：手机活跃时实时 `request.new`；手机一打开（hello）就收到全部待答题的摘要快照，
    点开某题再 `request.get` 取全文。
  - **通知**只管「要不要打扰」，规则见 D3。
- **D3 推送只在 Mac 真的闲了一阵之后才发**：人在 Mac 前操作时一律不推——**即使这道题没人看**也不推
  （用户原话：「如果我在电脑前正在操作，然后我的手机又没有打开，那你肯定不需要往我的手机发通知啊。
  即使我没有看这个提问，你也不应该给我推到手机上。」）。因此**没有**「题在 Mac 上放了一阵没人理就推」这类缩短规则
  （那是被放弃的方案，见文末）。
- **D4 阈值 D 取较长值**：用户提议 15 分钟或半小时（「用完电脑之后，过 15 分钟，我的手机才会收到推送」）；
  D 之前打开手机，立即就能看到全部待答题。默认取 15 分钟，可调。
- **D5 不再提醒**：每道题对每部手机**最多推一次**（用户原话：「如果我忽略了，那我想看我再去 APP 里看就行了，
  你不需要一直提醒我做这种打扰的事情。」）。
- **D6 先只做手机**：IM 没有「手机活跃」这类事件，也没有「已打开」回执，统一的事以后再议。
- **D7 流程**：先出规格 / 计划草案给用户审，批准后再动代码。
- **D8 默认值与档位**：D 默认 **15 分钟**；设置里的档位为 立即 / 5 / 15 / 30 / 60 分钟。
- **D9 积压的多道题逐条推**：D 到点时，每道没看过的题各推一条（iOS 里按 Mac 叠成一组）；实机嫌吵再合并。
- **D10 不加保底封顶**：Mac 被判定为「在用」时一直不推，不设题龄兜底；靠设置页的「Mac 已空闲 N 分钟」观察检测是否失灵。
- **D11 其余按草案推荐**：空闲信号只用键鼠，不叠加锁屏 / 显示器休眠；不做「有待答题时保持唤醒」；接受默认行为变化（局限 7）；
  设置页显示「Mac 已空闲 N 分钟」；被关注的 Agent **不**绕过 D，Follow 的去留另议。

## 术语

| 术语 | 含义 |
|---|---|
| 手机活跃 | 在线 ∧ App 在前台 ∧ 已发 hello（Gateway 的 `is_live`；`inactive` 有 10 秒宽限）。**硬信号**：App 是我们写的，状态精确。 |
| Mac 空闲时长 | 距离 Mac 上最近一次键盘 / 鼠标 / 触控板输入的时间。**软信号**：由输入推断，会错。 |
| D | 空闲阈值，配置项 `channels.ios.alertAfterSecs`。 |
| 已打开 | 手机在 App 里点开了这道题（现有的 `request.seen`）。 |
| 待通知 | 一道题对某部手机的状态：仍在等答、手机不活跃、没打开过、还没推过。 |

设计原则：**硬信号（手机活跃）管贵的事——内容传输；软信号（Mac 空闲）只管便宜的事——推送的时机。**
软信号判断错了，最坏是少推或多推一次，题本身不会丢：Mac 在线时，打开 App 总能拉到。

## 行为规格

### 三层

| 层 | 管什么 | 由谁决定 | 本期 |
|---|---|---|---|
| ① 可见 | 待答题是否在手机的待答列表里 | 无条件（iOS 渠道可用、已有配对手机） | **去掉活跃槽门控** |
| ② 传输 | 内容何时真正传到手机 | 手机活跃 | 不变 |
| ③ 通知 | 要不要推送 | Mac 空闲 ≥ D，且手机不活跃、没打开过这道题 | **新规则** |

推送只是提醒，不是送达手段：推送没发 / 没到 / 被专注模式压掉，打开 App 仍能看到所有待答题。

### 通知规则

对每道待答题、每部手机**各自**判断（确认请求同样适用）：

| 事件 | 结果 |
|---|---|
| 题到达，手机活跃 | 实时投递（现状），不推 |
| 题到达，手机不活跃 | 进入「待通知」；若此刻 Mac 已空闲 ≥ D（或 D = 0）则立即推 |
| 「待通知」期间 Mac 有键鼠输入 | 空闲清零，D 重新计 |
| 「待通知」期间 Mac 空闲达到 D | 推一次，此后不再提醒 |
| 手机变活跃（打开 App） | 全部待答题经 hello 快照补给它；它的「待通知」清空 |
| 手机打开了某题 | 该题不再「待通知」 |
| 手机由活跃变为不活跃，仍有没打开、没推过的题 | 这些题回到「待通知」 |
| 已推过的题在别处被答，手机没打开过 | 沿用现有「已在 X 回答」替换推送（无声） |
| 还没推的题被答 / 取消 / 过期 | 什么都不发（从未推过，也无需替换） |
| 手机前台但 3 秒没确认收到（现有补推） | **不变**，仍立即推：这是「你正在用手机却没收到」的兜底，与 Mac 空闲无关 |

多部手机、多台 Mac 互不影响：每台 Mac 只为自己的题、按自己的空闲时长决定推不推。

### Mac 空闲时长怎么取

- macOS：系统级「距最近一次键盘 / 鼠标 / 触控板输入的秒数」（`CGEventSourceSecondsSinceLastEventType`），**不需要任何权限**；
  已在用户的 Mac 上实测，读数与 `ioreg` 的 `HIDIdleTime` 吻合；装机后 daemon 进程里读到的值也与独立读数一致、随停手增长
  （`AskHuman channel ios status` 会打印「Mac 已空闲」）。
- 只看这一个信号，**不看**锁屏 / 显示器休眠 / 亮度：用户习惯是不锁屏（锁屏会收紧 Agent 的权限）、只调暗亮度或关外接显示器让
  Agent 干活，这些信号常常不触发或误判（D11）。
- 其他平台本期不实现 → 视为「未知」→ 按旧行为**立即推**（宁可多打扰也不丢通知）。

### 手机端表现

- Mac 对手机上报「未启用自动激活」（`slot.autoActivation = false`），现有 App 的 Mac 详情页因此显示「每个提问都会发到这部手机」，
  不再出现「接管提问」。**App 不用改。**
- 手机上的待答列表、通知文案、点击行为都不变。
- 预期顺带消除一个死胡同：被关注的 Agent 显示「在等你」、点「去回答」却发现请求不在手机上——现在每道题都在手机上。

### 设置（Mac 设置页 → 实验 → iOS 卡片）

- 新增「推送时机」：下拉「立即 / 5 分钟 / 15 分钟（默认）/ 30 分钟 / 1 小时」，说明：
  「Mac 空闲这么久之后，你还没看过的提问才会推送到手机。在此之前，打开手机 App 随时能看到所有待答提问。」
- 同一卡片显示「Mac 已空闲 N 分钟」，一眼看出检测在不在工作。

## 配置

| 字段 | 默认 | 说明 |
|---|---|---|
| `channels.ios.alertAfterSecs` | `900` | `0` = 立即推（旧行为）；读取时限制在 `0..=86400`；老配置缺字段按默认；改它**不**触发网关重连 |

- `channels.autoActivation` 的语义改为「只管 IM」。
- 不新增 IPC 消息；设置页读空闲时长走既有的 iOS 状态查询，只给状态结构体加一个带 `#[serde(default)]` 的可选字段，
  **不升 `PROTOCOL_VERSION`**。iOS 线协议（`ios/Fixtures/wire-v1/`）与推送中继不变。

## 已知局限与后果

1. **第一条推送最晚在「你最后一次操作 + D」才发**：你离开后 D 内，Agent 在空等。这是 D3 / D4 的直接后果
   （你选了「不打扰」优先）；嫌慢就把 D 调小。
2. **空闲时钟被合成输入清零**：某些 Agent 工具、鼠标抖动器会产生输入事件，让空闲一直为 0 → 一直不推。拉取不受影响，
   设置页的「Mac 已空闲」能看出来。**没有封顶**（D10）。已实测：`CGEventPost` 发出的 mouse-moved 事件确实把空闲清零。
3. **被动在场**：看视频 / 读文档 D 分钟没碰键鼠，会被当成走开，推一次。可接受。
4. **Mac 在 D 之前睡眠**：睡眠期间 daemon 与 Agent 都被挂起，不推；唤醒后按届时的空闲读数判断。用户机器接电永不睡，
   电池下 1 分钟睡眠但 Cursor 持有「防空闲睡眠」断言，影响小；别的环境若 D 比睡眠时间长，推送发不出去。
   本期不加「有待答题时保持唤醒」（D11）。
5. **D 到点时积压的多道题**：逐条推（N 条）；同一台 Mac 的通知按 `thread-id` 在 iOS 里叠成一组（D9）。
6. **推送被错过没有第二次**（D5）：专注模式 / 静音 / 没看到，只能靠自己打开 App。
7. **默认行为变化**：今天 `autoActivation = false`（默认）时，手机不活跃就**立即**收到推送；改后默认要等 Mac 空闲 15 分钟。
   想要旧行为：设为「立即」。
8. **与关注（Follow）**：「被关注的 Agent 在等你」那类推送只在这道题**没**投给手机时才发（`agents.rs::tick_waiting` 跳过
   已在 Gateway 待答表里的请求）；现在每道题都挂在手机上，它不会再触发。「完成 / 失败」不受影响。Follow 的去留另议。
9. **未在真机验证**：已送达的通知被同 `collapse-id` 的新推送改写成「已在 X 回答」（既有行为，`PROGRESS.md` 真机矩阵
   「跨渠道同时回答」）；远程桌面 / 屏幕共享时输入是否计入空闲；daemon 由 SSH 等非图形会话拉起时读到的空闲值是否可靠。
10. **非 macOS**：空闲未知 → 立即推；Windows 以后可用 `GetLastInputInfo`（同样无需权限）。

## 被放弃的方案（供回看）

「短 T + 无人理睬就推 + 再提醒」：T = 90 秒，「键鼠 T 秒没动 **或** 这道题等了 T 秒没人答」就推，之后最多再提醒 3 次；
锁屏 / 显示器休眠算一直没动。

- 放弃原因（用户 2026-10-26）：人在电脑前、故意不理这道题时也会被推，还会反复提醒——与「在电脑前不要打扰」冲突。
- 它的优势：**推送不依赖空闲检测**（题龄分支兜底，检测失灵也会推）；首条通知快（约 90 秒）。
- 它的代价：规则多（T、再提醒的次数与节奏、锁屏 / 显示器信号）；打扰多（最多 4 次 / 题）。

## 后续（本期不做）

讨论过、需要时再开的事，记在这里免得丢（未完成的跟踪见 `docs/PROGRESS.md`）：

- **Follow 的去留 / 绕过 D**：让被关注的 Agent 的提问不等 D、立即推，给「关注」一个清晰的新用途；「完成 / 失败」通知保留。
- **IM 统一**：每个 IM 渠道各自的「提醒时机」；前提是 IM 要有「手机活跃」类的事件。
- **保底封顶**：若实机发现空闲检测常被误判，再加「题龄 ≥ X 小时仍推一次」。
- **有待答题时保持唤醒**（可选开关）。
- **合并通知**：D 到点时把多道题合成一条「N 个提问在等你」。
- Time Sensitive 通知、通知扩展送达回执、划掉追踪、手机上展示 Mac 在用 / 空闲。

## 验收要点

- 在 Mac 上连续有输入时，提问不会推送到手机；打开手机 App 立刻看得到、答得了。
- 键鼠停下超过 D 后，没看过的题恰好推一次；再等多久也不再推。
- 提问到达时 Mac 已空闲 ≥ D：立即推。`D = 0` 或空闲未知：立即推。
- 手机在前台（活跃）：只有应用内提示，不推；切到后台且没打开过：空闲到点才推。
- 推送之后在 Mac 上答：通知被改写成「已在 Mac 回答」；推送之前答：什么都不发。
- 手机上不再出现「接管提问」。设置页能看到「Mac 已空闲 N 分钟」。
