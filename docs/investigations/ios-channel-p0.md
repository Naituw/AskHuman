## 1. EMQX（国内站，实例 AskHumanCN，阿里云杭州）

### 1.1 账号与授权规则

- 认证：一个用户名 / 密码（密码由用户在控制台自己输入，Agent 不读取）。
- 授权（控制台「客户端授权」）：
  - 「用户名」规则：`ah/<用户名>/#`，动作「发布 & 订阅」，允许。
  - 「全部用户」规则：`#`，动作「发布 & 订阅」，**不允许**。
- 实例的授权模式是 **默认黑名单（未命中规则一律放行）**，控制台页面会有橙色提示建议改白名单。所以「全部用户 `#` 拒绝」这一条
  是账号隔离的**唯一兜底**：删掉它，没有规则的账号将能读写一切。给朋友新开账号时，每人各加一条自己的 `ah/<用户名>/#`，
  不要动这条兜底。
- 同一个「添加授权信息」对话框里，一个用户只放一行「发布 & 订阅」；在同一对话框里再加别的行会触发「动作冲突」校验。

### 1.2 可达性与延迟（从开发 Mac，家用网络）

探针：[`ios/Tools/broker-probe/probe.cjs`](../../ios/Tools/broker-probe/probe.cjs)（零依赖，不需要账号：每轮新开连接、发不带凭据的
MQTT CONNECT、计时，broker 回「用户名或密码错误」即算通）。100 轮、每轮间隔 400 ms，2026-10-25：

| 路径 | 成功 | 整个往返 p50 / p95 / max | 连上之前 p50 / p95 | CONNECT→回复（一个网络往返）p50 / p95 |
|---|---|---|---|---|
| TLS 8883（MQTT） | 100 / 100 | 125 / 146 / 175 ms | 87 / 106 ms | 38 / 44 ms |
| WSS 8084（WebSocket） | 100 / 100 | 166 / 214 / 268 ms | 129 / 173 ms | 38 / 44 ms |

无任何超时或错误。原始逐次数据：[`ios-channel-p0-mac-broker-probe.json`](ios-channel-p0-mac-broker-probe.json)。

环境说明：这台 Mac 开着 TUN 代理（Fake-IP DNS）；`*.emqx.com.cn` 域名的 TLS 会失败，而实例域名
`*.emqxsl.cn` 与控制台 `cloud.emqx.com` 正常，所以不要用 `emqx.com.cn` 的地址。

公司网络的端口是否放行，需要在那个网络运行同一个探针（`node probe.cjs --host <实例域名>`，只需要 Node 22+）。

### 1.3 产品内连接测试

设置页「测试连接」：`Connected via tls (164 ms). The broker accepted the credentials and routed a test message.`
命令行 `AskHuman channel test ios` 连续三次：163 / 186 / 195 ms，同样结论。Mac 网关随后显示 `Broker: connected via tls`。

### 1.4 账号隔离

脚本：[`ios/Tools/broker-probe/acl-check.cjs`](../../ios/Tools/broker-probe/acl-check.cjs)（MQTT 5；需要在该目录 `npm install`）。
它登录**一个**账号，先确认能在自己的 `ah/<用户>/` 里订阅、发布并收回消息，再尝试越界，期望全部被拒。

做法：在控制台临时建一个测试账号（名字 `ahprobe…`，随机密码只存在 Agent 的临时文件里）并按 §1.1 给它一条自己的规则，运行

```bash
AH_PROBE_PASSWORD=… node acl-check.cjs --host <实例域名> --user <测试账号> --other <正式账号>
```

结果（2026-10-25）12 项全部符合预期，`PASS`：

- 自己的命名空间：订阅 + 发布 + 收回自己的消息 ✓；App 用的存在性通配订阅 `ah/<用户>/s/+` ✓。
- 越界全部被拒：订阅别的账号的 `ah/<正式账号>/#` 与单个话题（SUBACK `0x87`）、向它发布（PUBACK `0x87`）、`ah/+/…`、`ah/#`、`#`、
  `$SYS/#`、`ah/` 之外的话题、名字以自己开头的相邻账号（订阅与发布）。

测完已在控制台删除这个测试账号及它的规则，并确认它无法再登录（返回 `0x87`）。脚本对本地 broker 也跑过（含「把 `--other` 设成自己」
的反向对照，能正确报 `FAIL`）。

## 3. 腾讯云函数中继

### 3.1 部署（2026-10-25）

控制台表单由 Agent 在 Cursor 内置浏览器里操作；登录、选 zip 文件、两个机密环境变量由用户亲自完成。

- 函数 `askhuman-relay`：Web 函数、Node.js 20.19、中国香港（`ap-hongkong`）、监听端口 9000、内存 128 MB、执行超时 15 s、日志投递关闭
  （不引入额外计费项）。
- 代码包：`relay/scripts/build-zip.sh` 产出的 `askhuman-relay.zip`（6,856 字节：`scf_bootstrap`、`src/core.js`、`src/adapters/scf.js`，
  零 npm 依赖），由用户在系统文件选择框里选定。控制台把「启动命令」标成必填，填的是与 zip 里 `scf_bootstrap` 相同的脚本。
- 环境变量 5 个：`APNS_KEY_ID`、`APNS_TEAM_ID`、`APNS_TOPIC` 由 Agent 填写；机密的 `APNS_KEY_P8`（单行，换行写成字面 `\n`）与
  `RELAY_HANDLE_KEY`（32 字节随机数的 base64）由用户自己粘贴，Agent 只核对过字符数、没有读取内容，剪贴板事后已清空。
- 函数 URL：公网访问、授权类型「开放」（鉴权由中继自己做：句柄是 AES-GCM 不透明串，`/v1/register` 只收 `APNS_TOPIC` 的 Bundle ID）。
  这个 URL 带账号的 APPID，**不写进文档与提交**，只存在 Mac 的本机配置里（`AskHuman channel set ios --relay-url …`）。
- 端点：TLS 1.3、HTTP/1.1（服务端不协商 h2）、通配证书 `*.tencentscf.com`（DigiCert OV）。

### 3.2 `/v1/health`：成功率与延迟（Mac，家用网络，2026-10-25）

100 轮，每轮新开 TCP + TLS 连接，间隔 500 ms，`curl` 计时。原始数据：
[`ios-channel-p0-mac-relay-health.json`](ios-channel-p0-mac-relay-health.json)。

| 口径 | 成功 | p50 | p95 | p99 / max |
|---|---|---|---|---|
| 整个请求（连接 + TLS + 首字节） | 100 / 100 | 820 ms | **1401 ms** | 3282 / 3282 ms |
| 其中 TLS 握手（TLS 1.3，一个往返） | | 472 ms | 518 ms | 1392 ms |
| 其中请求往返（函数处理 + 回包） | | 338 ms | 912 ms | 2678 ms |

计划门禁（成功率 ≥ 99%、p95 ≤ 1.5 s）在这条路径上达标，但 p95 只剩 99 ms 余量；超过 1.5 s 的 4 轮（2806 / 2112 / 3282 / 3276 ms）
是**连续的第 59–63 轮**，像一次短暂的网络 / 代理抖动或函数实例切换，不是均匀分布，而超过 1 s 的共 7 轮。

**口径警告**：这台 Mac 的流量经过 TUN 代理和旁路由——TCP 连接 7 ms 就完成，说明握手被本地 / 网关的透明代理接走；TLS 握手却要 472 ms，
说明真实路径的往返约 470 ms。所以这组数只是「家用网络，默认路由」的参考，**不是计划要求的「关闭代理」口径**；关闭代理的证据
等手机在蜂窝网络上测（第 0.3 项）。

创建函数后的第一个请求约 4 s（冷启动 + TLS 握手），此后稳定在 1 s 以内。空闲约 3 小时之后（2026-10-26）的第一次请求（产品内「测试连接」里的中继检查，同一条经代理的路径）用了 1305 ms，
没有再出现创建时的 4 s 量级冷启动；这是一个样本，空闲后第一条真推送（含 APNs）的耗时仍要在真机上量。

### 3.3 中继到 APNs（假 token 验证提供方凭据与出口）

用随机 64 位十六进制当设备 token 走一遍 `/v1/register` → `/v1/push`。APNs 先验证提供方 JWT（`.p8`、Key ID、Team ID）、再验证 token：
回 `BadDeviceToken` 就说明密钥链路对、**香港函数到 APNs 的 HTTP/2 出口可用**；密钥或 Team ID 不对会是 403 `InvalidProviderToken`（中继映射为 502）。

| 用例 | 结果 |
|---|---|
| 沙盒：`register` → `push`（假 token） | 200（1103 ms）→ 410 `gone` / `BadDeviceToken`（1151 ms） |
| 生产：`register` → `push`（假 token） | 200（332 ms）→ 410 `gone` / `BadDeviceToken`（472 ms） |
| 乱码句柄 | 401 `bad_handle` |
| 其他 Bundle ID 注册 | 400 `bad_request` |
| `locKey` 不在白名单 | 400 `bad_request` |
| 载荷超过 4096 字节 | 413 `too_large` |
| 未知路径 | 404 `not_found` |

沙盒和生产两个环境 APNs 都接受，说明 Team Scoped 的「Sandbox & Production」密钥按预期通用。**真 token 的送达**：模拟器上的真 token 已验证（§3.7）；真机的送达与耗时分布仍待真机（第 0.4 项）。

### 3.6 真实服务端到端（一次性 Mac + macOS 上的手机引擎，2026-10-25）

（只在测试进程的内存里，不显示、不落盘），手机侧是真正的 `PhoneEngine` + `MQTTBrokerClient`。**33 项全部通过**（本地 broker 上 30 项，另有 3 项只在真实服务上跑）。

| 检查 | 结果 |

| 配对、问答、多题与自由文本、附件上下行、确认、取消、多手机抢答、多 Mac、手机 / Mac 重启、撤销、Agents / 插话 / Follow / 任务 / 提问权 | 通过 |

### 3.7 模拟器上的真 App 对真实服务（一次性 Mac + 真 EMQX + 真中继 + 真 APNs 沙盒，2026-10-25）

不再用 macOS 上的手机引擎，而是在 iOS 27 模拟器上跑真正的 App（真钥匙串、真通知扩展），XCUITest 驱动；一次性 Mac 在宿主进程里（做法见
[`docs/overview-ios.md`](../overview-ios.md) 的「验证」）。场景全程走真实服务：配对（两端校验码一致）→ 通知权限 → 模拟器的真 token →
中继登记 → Mac 持有句柄 → 前台单题 → 多题 + 自由文本 → Agent 的权限确认（一次允许、一次带理由拒绝）→ 一个 `__agent-hook` 会话（Agents 列表、实时观看、
关注、插话与读取回执、列表里的当前工具、应用内「Agent 已完成」横幅）→ Mac 关着 Agent 任务时的新任务表单提示 → App 退到后台 → 一次真 APNs 沙盒推送 →
通知扩展解密出标题 / 副标题 / 正文 → 点击横幅打开请求 → 回答 → 被关注的 Agent 在手机离开时结束回合的推送（`follow.done`）→ 点击打开 Agent 页 → 历史 → 手机侧解除配对。
**基础场景（到解除配对为止，不含 Agents / 权限确认 / 关注推送）连续三次通过**（各约 2 分钟；第三次在提交后的最终代码上），**含这些的完整场景又通过两次**（172 s、195 s）。
下表是基础场景三次的数字；完整场景两次的同口径数字在同一范围内（显示请求 1.19–1.21 s，发送 → 消失 1.11–1.13 s，Mac 察觉离开 0.43–0.73 s，问题推送 2.1–2.2 s）。

| 量 | 第一次 | 第二次 | 第三次 | 口径与目标 |
|---|---|---|---|---|
| 登记：点「允许」并打开「Mac」页后，推送状态行显示「On」（token → 中继登记完成） | 394 ms | 383 ms | 359 ms | 起点是状态行出现，之前的弹窗、配对页关闭不计 |
| Mac 提问 → UI 里出现请求行 | 1218 ms | 1148 ms | 1162 ms | 含 XCUITest 轮询，是上界；D10 ③ 目标 p95 ≤ 1.5 s |
| 点发送 → 请求行消失（Mac 已确认） | 1125 ms | 1128 ms | 1129 ms | 含 XCUITest 轮询，是上界；D10 ① 目标 p95 ≤ 1 s（引擎口径见 §3.6：p95 195 ms） |
| 手机退到后台 → Mac 看到 `foreground: false` | 757 ms | 431 ms | 707 ms | — |
| Mac 提问（手机在后台）→ 横幅出现 | 2129 ms | 2258 ms | 2233 ms | D10 ④ 目标 p50 ≤ 3 s；仅三个样本 |

横幅文本是扩展解密后的：标题「项目 · 会话名」、副标题「Mac 名」、正文「问题」，没有退回通用文案。关注推送（`follow.done`）的横幅是「Claude Code · project / E2E Mac / Finished: Claude Code」，
从 Mac 回合结束到横幅 4.3–4.5 s（两次），其中 3 s 是 Mac 的完成去抖（防止回合间隙误报）。

结论与边界：
- **模拟器收得到真 APNs 沙盒推送，且会运行通知扩展**（`simctl push` 不会运行扩展，所以场景不用它）。真 token → 中继 → APNs → 手机 → 扩展解密整条链路通了。
- 这些是**单样本**，不是计划要的分布（≥ 30 次 APNs、往返 ×100）；手机在蜂窝 / 真机上的延迟与送达差异、锁屏 / 强退下的行为仍要真机。
- 这次运行抓到四个真实缺陷（点击横幅崩溃、扩展解不开中继的信封、快速 inactive → active 后永久断线、推送句柄没可靠送到 Mac），已修复，见计划 §13。
- 观察到的取舍：系统弹窗会让 App 经历 `inactive` → 断开重连一次；真机上证实是缺陷并已修，见 §3.8。

### 3.8 真机：iPhone Air + 真 EMQX + 真中继 + 真 APNs 沙盒（2026-10-26，手工）

设备 iPhone Air（iOS 27.0.1），Debug 构建（开发签名，走 APNs 沙盒），Mac 是 worktree 的 Dev Instance。配对由用户在终端运行 `channel ios pair` 并扫码完成

| 场景 | 结果 |

**缺陷：系统界面盖在 App 上也会让连接断开（真机上找到，已修）。** `scenePhase` 在控制中心、通知中心、多任务界面、系统弹窗盖在 App 上时只是 `.inactive`（App 仍在屏幕上），
锁屏与回主屏才是 `.background`。旧构建一变成 `.inactive` 就告别，偏离规格里的「手机只在前台保持连接，退到后台即断开」。监测 Mac 看到的手机在线状态（用户在前台依次做三项）：

| 操作 | Mac 看到离线 | 恢复在线 | 离线窗口 |
|---|---|---|---|
| 下拉控制中心 | 08:44:55.7 | 08:45:01.6 | 5.9 s |
| 下拉通知中心 | 08:45:05.7 | 08:45:11.6 | 5.9 s |
| 上划进多任务界面 | 08:45:16.8 | 08:45:23.7 | 6.9 s |

窗口里到达的请求会被当成「手机不在前台」直接推送，而用户还在看着 App。用户在 2026-10-26 03:25 的回答已有条件授权（「装完如果的确是 bug 就要改」）。

修法：`PhoneEngine.setInactive()` 起一个 `inactiveGrace`（10 s）的定时器，到期仍未回到前台才告别；`.background` 与锁屏仍立即告别（`setForeground(false)`）；
回到前台则取消定时器、保留连接。`AskHumanApp` 只把 `scenePhase` 映射到 `setInactive` / `setForeground`。提交 `fix(ios): keep the connection while the app is only inactive`，新增 5 个测试；每处保护去掉后都有测试变红
（整个修复 3 个、离开后不起定时器 1 个、返回时取消定时器 2 个）。

新构建上的真机数据（09:09–09:10；用户在 App 前台做了几次系统界面停留，自述控制中心、通知中心、多任务界面**三项都超过 10 s**）：离线窗口 2.3 / 14.4 / 2.3 / 2.8 s，
每次都在用户回来后恢复在线，最后一次（09:10:34）离线后直到监测结束（约 09:15）都没再上线；旧构建同样的停留是整段离线。手机侧没有时间线，每次停留的起点只能推断，
所以这组数据只说明「离线晚于停留开始、窗口远短于停留」，**不能精确核对 10 s**。09:06 还有一轮记录（离线窗口 8.2 s，最后一次离线后没再上线），但当时没有逐项记下停留时长，不引用。

**没有在真机上验证的**（用户 2026-10-26 决定不再手测，按未验证记）：
1. 停留**短于** 10 s 时不离线——只有单元测试（`ConnectionTests`）覆盖；
2. 锁屏 / 回主屏后 Mac 多快看到离线——告别从 `inactive` 挪到了 `background`，估计晚 0.1–0.3 s，没量；最坏是 Mac 晚几秒才发现手机已走，此时「3 秒无应用层确认再补发推送」（规格 §7）兜底，不会丢通知；
3. 强退后 Mac 多久看到离线——靠 Last Will，没量。

## 真机手测备忘（2026-10-26）

- **用户不想被反复叫去测**：真机手测要一次设计好、合并成尽量少的几轮；能用 `devicectl`（`device install app`、`device process launch`、`device process terminate --pid … --kill`）
  自己做的自己做，只有必须用手的动作才叫用户。这次一个 `inactive` 修复的真机复测拖成四轮，用户明确说这很浪费时间。
- **监测脚本要作为独立的后台任务启动并确认存活**：塞在前台命令里的 `nohup … &` 会在命令结束时被一并结束（有一轮用户做完的步骤因此没有记录，整轮作废）。
- **让用户做的动作要天然限时**（「下拉后马上收起」），不要写「停约 5 秒」：实际会停得更久（用户把三项都停了 10 秒以上），数据就对不上想测的情形。
- 只有 Mac 侧的在线状态时，每次停留的起点和终点只能推断；要精确核对计时需要手机侧的时间线（DEBUG 构建里记录 `scenePhase` 与连接事件，再用
  `devicectl device copy from` 取回）。这属于 P0 手机侧测量方式的决定，须先经 AskHuman 与用户确认，不要直接加。
- **测之前数一数别的会话在等多少条**（2026-10-27 界面冒烟时踩到）：别的 Agent 的提问进同一个手机收件箱，会让「已全部处理」出不来，也会成为自动切换的目标
  （按创建时间新→旧、先选未读）。`AskHuman daemon status` 的 `requests N active` 减去自己发的条数，再用 `ps -axo pid,lstart,command | rg AskHuman` 看是谁在等；
  提问正文里要写明有别人的那一条，别写「此时没有别的待答」这类会被现实推翻的断言。
- **发出去的真机提问不要撤回重发**：`AskHuman channel ios status` 里「N 台在线」可能下一秒就从 0 变 1（用户刚解锁并打开 App），撤回会让他正在看的那条变成已结束。
