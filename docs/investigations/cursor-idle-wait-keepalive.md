# Cursor 长等待期“保活”（避免“无进展”规则中止回合）

> 状态：想法已记录，待与用户讨论；**尚未实现**，没有修改任何托管规则 / 代码
>
> 调查日期：2026-10-26（同日补充了“失败率随年龄 / 是否成簇”的统计，见 §2.3；以及 checkpoint 产生时机和计费口径的核对，见 §2.2b、§2.4）
>
> 调查方式：静态阅读 Cursor 3.27.12 `cursor-agent-host` 打包源码 + 只读分析本机 Cursor 日志；
> 未发起任何 Cursor Agent 请求，没有产生额外计费。受控的计费验证见 §5，需用户明确批准后才能做

## 1. 问题与结论

AskHuman 长时间阻塞等待用户回答时，Cursor Agent 回合内没有新的模型步骤，也就没有新的
checkpoint。网络在途中断开（`socket_reset` / `ECONNRESET`）后，Cursor 会自动“续跑”（resume），但
**连续两次**续跑“流已建立却没有产生 checkpoint”时，Cursor 会主动放弃自动续跑：

- 日志：`[nal_agent_retries] Resume attempts are streaming but not producing checkpoints; stopping automatic resume`
- UI：`Agent stopped retrying …`，需要用户手动 Retry；手动 Retry 本身又是一次计费请求。

于是“等用户回答”的长回合会在数小时内被 Cursor 自己中止，而不是一直等到用户作答。

想法：让**等待期周期性地产生 checkpoint**（“保活”），使无进展计数不断清零。它不减少断线次数，只防止回合被
无进展规则杀掉（见 §4 的上限与权衡）。对计费的影响见 §2.4：**空等中的续跑很可能本来不计费，保活会让每次续跑
都变成有模型调用的计费请求**（假设，待核对）。

## 2. 机制（Cursor 3.27.12，`extensions/cursor-agent-host/dist/main.js`）

### 2.1 重试循环

- 每次尝试使用新的 `x-request-id`，同一回合共享原始 request id；每次尝试开始时重置“本次尝试是否收到
  checkpoint”（`u`）与“流是否已建立”（`S`）。
- 停滞检测：约 30 s 没有任何入站消息视为断线；停滞类重试若累计 ≥180 s 仍未恢复，同样终止回合。
  退避：`min(1000·2^n, 60000)` ms 加抖动。
- 上限 `ot = {serverCap: 3, transportCap: 10}`：同一回合累计 10 次传输错误即抛出，**回合内不会因进展清零**。
  `endlessRetries` 开启时不受该上限约束，但本机观察到的回合（10 次后终止）说明它没有生效。
- 自动重试受服务端控制的开关 `nal_agent_retries` 约束，未找到用户可调设置。

### 2.2 “无进展”规则（决定性）

每次失败且分类为“可重试”后：

```text
if 本次尝试收到过 checkpoint        -> noProgress = 0
else if 本次尝试是 resumeAction 且流已建立 -> noProgress++
noProgress >= 2                      -> 抛出 "Agent turn stopped after repeated resume attempts made no progress"
```

要点：只有“流已建立”的**续跑**尝试才计数；首次尝试、以及连接都没建立的失败不计数；一次有 checkpoint 的
失败就会清零。AskHuman 等待期的入站流量只有心跳（本机 48 次失败里 29 次的最后一条入站消息是心跳），所以
等待期的续跑天然是“无进展”。

### 2.2b checkpoint 何时产生、续跑从哪里开始

- **谁产生**：server loop（`connect`）里由服务端在“一步（step）”结束时下发 `conversationCheckpointUpdate`；
  客户端只是收下并交给存储（`handleCheckpoint`）。本机源码里没有找到客户端 / 用户侧“手动创建”的入口。
- **顺序**：本机 58 份停滞检测缓冲里有 7 份带 checkpoint（`<` 入站、`>` 出站，按时间正序，已去掉心跳）：
  - `<kvServerMessage×3 >setBlobResult×3 >shellStream <checkpoint`：一次 shell 工具调用（如 AskHuman）开始时。
  - `<toolCallCompleted:shellToolCall <tokenDelta <kvServerMessage… >setBlobResult… <checkpoint`：工具完成后，
    下一步结束时。
  - `<kvServerMessage×7 >setBlobResult×7 <checkpoint×2 <stepCompleted`：一步结束，checkpoint 在 `stepCompleted` 之前。
  - `<checkpoint <tokenDelta×11`：下一步开始前。

  规律：先让客户端存 blob，再发 checkpoint，然后进入工具执行或下一步。**没有新的模型步骤的空等期间（只有心跳）
  不产生 checkpoint**；一次 AskHuman 调用只在“发出调用的那一步”结束时产生一次（推断）。
- **终端 checkpoint**：`turnEnded` 之后到达的 checkpoint 标记为 `ineligible_terminal_turn`，不能用来续跑；
  如果可重试错误之前已经收到终端 checkpoint，Cursor 直接结束，不自动续跑。
- **续跑从哪里开始**（源码）：失败的那次尝试里收到过 checkpoint → 下一次尝试以它为状态、动作改为
  `resumeAction`；没收到 → 状态和动作都不变（首次尝试就是原样重放用户消息，续跑就是再从旧 checkpoint 续一次）。
  所以“这次尝试里没有 checkpoint”意味着这段时间做的事没有存下来。
- UI 里的 “Restore checkpoint”（文件回滚点）是另一套机制，和这里的会话 checkpoint 无关。

### 2.3 本机证据（2026-10-25 11:00 → 10-26 08:52）

数字来自一份只读脚本 `cursor_disconnect_report.py` 的输出（脚本放在给另一台机器做对照分析的交接包里，**未入库**；
口径可复现，早先用 grep 手工统计的“47 次 / WebSocket 中位 46 min”等数字以此为准修正）。

- 传输层失败 48 次（35 次 WebSocket、13 次 HTTP/1 回退，均为 `socket_reset`），另有 1 次服务端
  `resource_exhausted`（不计入）。总暴露约 56 流小时（并发流平均 2.7 条、最多 6 条；仍在运行的流按截止时刻
  计入），平均 0.85 次/流小时。
  断线时连接是健康的（服务端心跳年龄中位 6 s、最大 21 s），不是停滞检测触发。WebSocket 最终抛错事件的关闭
  诊断一律是 code 1006（abnormal，没有 close frame，`phase=accepted`）：TCP 层直接断开，不是应用层的有序关闭。
- **失败率随流的年龄上升**（仍存活的流计入风险时间，所以无偏）：

| 流的年龄 | 风险时间（流小时） | 失败数 | 失败率（次/小时） |
| --- | --- | --- | --- |
| 0–30 min | 23.5 | 12 | 0.51 |
| 30–60 min | 16.1 | 11 | 0.68 |
| 60–90 min | 10.5 | 11 | 1.04 |
| 90–120 min | 5.4 | 10 | 1.85 |
| 120–150 min | 0.9 | 3 | 3.20 |

  年龄 <60 min 为 0.58 次/小时，≥60 min 为 1.48 次/小时（比值 2.5，单侧精确二项检验 p≈0.001）。所以不是纯随机
  掐断，更像“活得越久越容易断”（最大寿命 / TTL / 某一跳的会话上限一类机制）；本机数据区分不了它来自 Cursor
  服务端还是本机代理链路，需要另一条网络路径做对照。
- **不成簇**：相邻失败间隔 ≤180 s 的有 5 对，按“并发流数加权的独立事件”模拟期望 6.5 对（p≈0.83）。不同流不是
  同时被掐，没有共同的全局事件。早先“存在成簇现象”的说法不成立，已更正。
- 一次 attempt 的存活时间就是它那条 WebSocket 的存活时间（最终事件的 `agentWsElapsedMs` 与 attempt 起止相差
  不到 2 s）。断线时最后一条入站消息是心跳（基本在空等，n=29）的流，年龄中位 77 min；最后入站是 token / 工具
  调用等（流在忙，n=19）的中位 43 min。
- 失败与传输重建（`Transports rebuilt`，含 auth token 刷新触发）无时间重合。

| 回合（request id 前缀） | 起始 | 失败次数 | 结局 |
| --- | --- | --- | --- |
| `fce47980` | 10-25 11:34 | 11 | 22:10 因 `transportCap=10` 终止 |
| `cdae2461` | 10-25 18:19 | 10 | 10-26 05:55 无进展规则终止 |
| `e4651f2f` | 10-25 21:19 | 6 | 10-26 04:23 无进展规则终止 |
| `d454fbf2` | 10-25 21:48 | 7 | 10-26 06:37 无进展规则终止 |
| `54d90e96` | 10-26 00:15 | 3 | 10-26 04:57 无进展规则终止 |
| `35b72d5b` | 10-25 22:18 | 11 | 10-26 07:54 因 `transportCap=10` 终止 |

被无进展规则终止的 4 个回合，最后两次连续续跑共撑了约 1.6–3.8 h。

### 2.4 计费

**计费单位是“一条带模型调用的请求流（一次尝试）”，不是一步，也不是一个 checkpoint。**

- 对账（Dashboard 导出 `usage-events-2026-10-25.csv`，只到 10-26 00:47:38）：日志里 10-25 11:34 → 00:47 的
  30 次尝试起始（6 个 prompt + 24 次续跑）与 CSV 的 30 条事件一一对上，事件晚于尝试起始 0.54–2.35 s（中位
  1.22 s）；事件都是 `Included`、`Requests=1`。
- 事件里的 Token 是**整条流**的总和：每条 31 万–8750 万（中位 2284 万），与该次尝试的时长强相关（Spearman
  ρ≈0.73）；例如一次 120 min 的尝试只有 1 条事件，7462 万 Token、69 万输出。同一时期这几个会话共约 3,900 条
  助手消息（每条是一步，对应至少一个 checkpoint；含窗口前的部分），而请求至多 53 个。所以步骤 / checkpoint
  不单独计费。
- **早先“≈7 个 prompt + 42 次续跑 ≈ 49 条事件（约 86% 是续跑）”只是按日志里的尝试起始数估的**，只有 00:47 之前
  的 30 条被 CSV 证实；之后到 08:52 的 23 次起始（19 次续跑 + 4 个 prompt）没有 CSV 可对。
- **线索：空等的续跑可能不计费。** 10-19 的回合 `c132b143` 有 8 次尝试，6 次有事件；没有事件的是第 6、7 次，
  它们结束前（失败 / 被用户取消）停滞检测缓冲里只有心跳。另外 CSV 里存在 `Requests=0` 的记录（10-11 00:15，所有 Token
  列为空）。已核对的 30 次尝试都有模型调用（最小一条 31 万 Token ≈ 1 次调用）。样本只有 2 个，所以只是假设（H*）：
  **一条流里没有模型调用，就没有计费事件（或 `Requests=0`）**。
- 若 H* 成立：①“每次续跑计一次”应改成“每次**有模型调用的**续跑计一次”，空等期间的续跑（正是被无进展规则杀掉的
  那类）可能是免费的；②保活会让每条续跑流里都出现模型调用，**反而把免费的空等续跑变成计费请求**（按
  0.85 次/小时、`transportCap=10`，一个回合最多多约 10 个）；③被无进展规则中止之后，用户手动 Retry 才是确定的
  一次计费。
- **零成本验证**：重新导出一份 Dashboard CSV（覆盖 10-26 00:47 之后），用同一口径数这 23 次起始里有多少条有
  事件：事件数≈起始数 → H* 被否定；明显少于起始数 → H* 成立，缺的那些应能对上“空等”的续跑。

## 3. 候选方案

目标：让回合内每次尝试在失败前尽量已经收到至少一个 checkpoint。

### 方案 ①：规则层（Agent 分段等待）

改 Cursor 的托管规则：AskHuman 放到后台运行（`block_until_ms: 0`），Agent 用 Cursor 内置 `AwaitShell`
按固定周期轮询，直到 AskHuman 返回。每次 `AwaitShell` 返回就是一个新的模型步骤，期望由此产生 checkpoint。

- `AwaitShell` 单次最长 7,140,000 ms（119 min）；工具说明建议避开“整 5 分钟”：60–270 s（保持 prompt cache
  热）或 1200 s 以上（一次 cache miss 换一次长等待）。保活周期取 ≤270 s 同时满足两点。
- 现行规则要求把 AskHuman 的超时设为 24 h；改为后台 + 分段后不再依赖单次长阻塞。
- 不需要改 AskHuman 程序，但完全依赖模型遵守规则，且规则文本需区分 Cursor 与其他 Agent。

### 方案 ②：程序层（AskHuman 分段返回）

AskHuman CLI 每 N 分钟返回一条“仍在等待，请重跑同一条命令”的状态，daemon 保持同一个问题挂起（不重复弹窗 /
不重复发 IM）。每次返回是一次工具结果，同样产生新的模型步骤。

- 规则只需一句“看到‘仍在等待’就重跑原命令”，不依赖 `AwaitShell` 语义。
- 需要 CLI 与 daemon 之间的“重新接入在途请求”能力（稳定请求身份 + 重连），与 PROGRESS 中“daemon 即时换新与
  在途提问恢复”共享同一块基础设施；改 IPC 时按 AGENTS.md 判断是否需要抬 `PROTOCOL_VERSION`。
- 同样依赖模型照做；用户以外的宿主（Codex / Claude 等）也会看到这个状态，需要确认不会副作用。

### 粗略效果估算

只有“本次尝试还没有 checkpoint”的窗口内发生失败才有风险；窗口长度≈保活周期 N（续跑后第一个保活步骤最迟 N
之后到来）。需要**连续两次**这样的失败才会终止，所以每次失败导致终止的概率≈p²。

续跑后的新流处在最“年轻”的阶段，失败率约 0.51 次/小时（§2.3 的 0–30 min 档）；不考虑年龄效应的平均值是
0.85 次/小时，可作保守上界：

| N | p（年轻流 0.51 次/小时） | p² | p（平均 0.85 次/小时） | p² |
| --- | --- | --- | --- | --- |
| 5 min | ≈4% | ≈0.2% | ≈7% | ≈0.5% |
| 10 min | ≈8% | ≈0.7% | ≈13% | ≈2% |
| 30 min | ≈23% | ≈5% | ≈35% | ≈12% |

假设不同尝试的失败相互独立（§2.3 的成簇检验没有发现相关性）。

## 4. 共同的限制与未决问题

- **`transportCap=10` 仍是硬上限**：按 0.9 次/小时约 11 h 触顶（实测 `fce47980` 就是 11 次失败、10.6 h）。
  保活只能把“被无进展规则提前杀掉”推迟到“触顶”，要继续延长必须降低断线频率。
- 保活**不会重置底层连接的年龄**：同一条连接上多一个模型步骤，连接照样越活越老、失败率照样上升；只有失败后重连
  才会回到“年轻流”。所以保活不能降低断线频率，只能让断线后的续跑不被无进展规则杀掉。
- 每个周期多一个模型步骤：Token 成本、上下文增长。N=270 s 时 24 h 约 320 个周期，可能加快上下文压缩，需要
  结合 `docs/plans/agent-context-compaction-retention.md` 的恢复机制评估。单个保活步骤不是单独的请求（§2.4：
  步骤数远多于请求数），但保活会让每条续跑流里都有模型调用——若 H* 成立，每次断线就多 1 个计费请求。
- 带宽：本机网关的字节计数显示，一条 agent 流入站可达约 450 KB/min（按步骤推送的 checkpoint 可能占大头，
  未验证），Cursor 在一天内经代理链路的流量可达数百 MB。保活会增加步骤数，周期越短带宽越大；若用户的代理
  链路有流量配额，需要先校准每个 checkpoint 的大小再选 N。
- 未验证：①`AwaitShell` 返回之后是否确实产生 `conversationCheckpointUpdate`（§2.2b 里“工具完成 → 下一步结束 →
  checkpoint”的顺序是间接证据，没有 `AwaitShell` 的样本）；②保活是否真的把无进展
  计数清零（源码读下来如此，缺少实测）；③是否存在每回合最大步骤数限制（本机源码未找到）。
- 待讨论：方案 ① / ② / 混合；周期 N；是否保留 24 h 阻塞作为非 Cursor 宿主的默认；是否要在 AskHuman 里按宿主
  区分行为。

## 5. 验证计划（需用户明确批准后才可执行）

仓库先例（`docs/specs/im-agent-task-launch.md` D27）：任何可能计费的真实 Agent 测试都要先问用户。

0. **先做零成本的一步**：重新导出 Dashboard CSV 核对 H*（§2.4），不需要发起任何 Cursor 请求；结果会改变下面
   第 3 步的成本估计和是否值得做保活。
1. 新开一个短测试回合，按所选方案等待至少一个保活周期。
2. 用网关 / 代理工具主动终止该回合的 agent 连接制造一次确定性的断线（例如 Surge 的
   `surge-cli kill <connection-id>`），观察日志是否出现 `Resuming from checkpoint`、且**没有**
   `stopping automatic resume`；再连续制造两次断线对照“无保活”的行为。
3. 预计成本：1 个 prompt + 1–3 次续跑 ≈ 2–4 条计费事件。

## 6. 相关但不在本文范围

- 降低断线频率：`cursor.general.disableHttp2`（UI 的 HTTP Compatibility Mode）及其自动降级后不会自动恢复的
  “棘轮”、HTTP/2 对比实验、本机代理链路的对账。断线的来源（本机链路 vs Cursor 服务端）仍未确定；本机网关侧在
  上述窗口内没有重启 / 重载 / 节点切换记录，但网关只保留最近几百条连接记录，无法回溯逐条断线的“谁先关闭”，
  需要前向记录。§2.3 的新证据（失败率随年龄上升、不同流不成簇）说明更像“单条连接活得越久越容易被掐”，
  而不是全局网络抖动；下一步是在另一条网络路径（另一台机器）上跑同一份只读统计做对照：若对方的长流能稳定活过
  2.5 h，问题在本机链路；若同样在 1–2 h 衰减，问题更可能在 Cursor 服务端。
- 其他宿主（Codex / Claude Code 等）的长等待行为不同，本文只针对 Cursor。
