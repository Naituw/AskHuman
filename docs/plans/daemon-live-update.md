> 体验取舍已确认并进入实施，进度与未完成验收见 [PROGRESS](../PROGRESS.md)。

> 现行换新行为见 [优雅排空](../specs/daemon-graceful-drain.md)、

## 1. 问题与当前实现

用户可能在 iOS 或 IM 上保留暂时不想回答的问题，同时继续处理其他 Agent 的问题。
当前安装新版会让旧 daemon 进入 graceful drain，直到所有计入排空的请求结束才换新。
新提问在 CLI 内无限等待，尚未进入 daemon registry，桌面、iOS 与 IM 都无法收到。
一个长期待答问题因此阻塞全部会话的新提问。

关键实现入口如下。

| 环节 | 当前行为与代码 |
| --- | --- |
| 更新检测与排空 | `daemon/runtime/mod.rs` 的 `check_pending_update`、Hello 分支与 `begin_drain` |
| 新提问等待 | `client/mod.rs` 的 `run_ask_observed`、`wait_for_drain`，每 30 秒向 stderr 提示 |
| MCP 可见性 | `mcp/ask.rs` 捕获子 CLI 的 stdout/stderr，运行中的等待提示没有实时展示给用户 |
| 请求状态 | `daemon/request.rs` 的 `RequestRegistry`、等待者与 Coordinator 主要保存在内存中 |
| 已受理 CLI | 连接中断后返回退出码 3，当前没有恢复原请求的路径 |
| 共享窗口 | `app/popup_inbox.rs` 在 IPC EOF/错误时退出，表单状态主要保存在已挂载的前端实例中 |
| 多渠道首答 | `app/coordinator.rs`、`app/confirm_coordinator.rs` 在内存中决定唯一终态并执行后续处理 |
| 重复题合流 | `daemon/ask_dedup.rs`、`RequestRegistry::try_attach`，答案重放缓存只在内存中 |
| iOS | 手机已有持久草稿、outbox、消息 ID 重发；Mac 有 journal，但普通待答请求没有完整恢复记录 |
| IM | Router 的卡片路由、渠道逐题流程和部分选择状态保存在内存中 |

桌面已有待更新横条和菜单状态，但手机缺少更新过程说明。现有弹窗文案
“新版本将在所有弹窗回复完成后生效，请尽快回复”也没有解释新问题正在等待。

## 2. 已确认的目标体验

2026-11-08 通过 AskHuman 确认以下取舍。

| 编号 | 用户决定 |
| --- | --- |
| U1 | 旧问题保留、新问题正常收到，后台及时换成新版，接受较大的实现改造 |
| U2 | iOS App 与飞书、钉钉、Telegram、Slack 等 IM 都属于目标渠道 |
| U3 | 接受短暂显示“正在更新，自动恢复”，期间保留输入，提交有明确反馈，恢复后自动继续 |
| U4 | 桌面优先保留当前窗口和输入位置，由窗口重连新版后台，窗口程序可稍后更新 |
| U5 | IM 原卡片继续可回答，已选内容尽量保持，同一题恢复时避免重复推送 |
| U6 | 面向普通用户收敛更新体验，恢复由程序负责；技术排障信息记录在内部日志 |
| U7 | 更新暂时恢复失败时保留原题和 Agent 等待，由程序自动恢复 |

目标流程为“保存待答状态 → 短暂交接 → 新版恢复原题并接收新题”。
普通问题仍可长期待答，更新只等待机器完成交接。
切换耗时以本机和真实渠道测量为准，验收分别统计后台恢复、新请求受理与各渠道恢复的耗时。

## 3. 方案取舍

| 方向 | 收益 | 代价与限制 |
| --- | --- | --- |
| 补排空提示及处理入口 | 用户能够理解当前等待原因 | 新问题继续受旧问题阻塞 |
| 旧 daemon 继续接题，空闲后更新 | 兼容请求可以及时到达 | 持续繁忙时更新可能长期挂起，新版请求还需要语义兼容判定 |
| 请求与终态可靠保存，CLI/窗口重连，各渠道接管 | 符合 U1–U5，换新与用户作答时间解耦 | 涉及完整请求生命周期、协议兼容及四渠道恢复 |

采用第三个方向作为实施目标。现有单 daemon、单渠道连接与自动接班机制作为基础。

## 4. 请求身份与可靠状态

### 4.1 身份和等待者

- CLI 在首次提交前生成稳定的调用身份，提交重试沿用该身份。
- daemon 的请求身份跨重启保留；同一调用再次提交时返回原请求或原终态。
- 沿用会话键和内容指纹做重复提问合流。调用身份、合流身份与请求身份分别表示一次调用、
  内容相同的等待关系与用户面前的一张卡，恢复时保留这些关联。
- 每个原始 CLI 和合流 CLI 有独立的等待者身份与恢复凭证，分别记录结果交付进度。
- 恢复凭证仅供对应用户实例使用。现有一次性 Popup token 消费后已失效，需要专门的宿主恢复凭证。
- 重连要识别安装实例、运行代际与请求身份。exec 可保留 PID，因此 PID 只承担辅助诊断。

### 4.2 建议保存模型

优先评估复用已有 `rusqlite` 依赖，为恢复状态建立单一事务存储。
实施前核对同步落盘方式、损坏处理、schema 迁移和写入时延，再确定最终存储布局。

| 记录 | 必须覆盖的内容 |
| --- | --- |
| 请求 | 完整规范化载荷、身份、创建顺序/时间、类型、Agent/项目绑定、原始期限、合流指纹 |
| 等待者 | 调用身份、恢复凭证校验材料、是否取消、重连及结果交付状态 |
| 答案与终态 | 胜出渠道、提交身份、规范化答案、原始终态时间、渲染结果与交付进度 |
| 渠道交互 | 消息/卡片标识、精确路由、逐题进度、部分答案、可恢复选择、附件与投递阶段 |
| iOS 投递 | 手机接收/确认/推送事实、通知去重身份，以及现有 journal 到请求终态的关联 |
| 副作用 | 历史、待办出队、回复文件、指令和权限记忆的执行身份及完成状态 |
| 交接 | 交接 ID、目标构建、schema/恢复能力、阶段与最近失败原因 |

存储写入失败必须可观测。请求受理、答案成功确认和交接完成都以相应可靠记录完成为前提。
记录按现有用户私有目录和权限规则保存。引用的上传文件与临时文件需有跨交接的所有权与清理时机，
提问附件原路径的语义继续沿用现有行为，文件缺失时保留明确提示。

### 4.3 请求状态与答案提交

建议把以下阶段显式建模。

```text
待答 → 答案已可靠接受 → 副作用处理与结果准备 → 结果待交付 → 各等待者完成交付
  └→ 用户/调用方取消，或沿用原确认期限到期
```

- 终态竞争在可靠状态上串行决定，iOS、IM、Popup 同时提交仍只有一个胜出答案。
- 同一提交重复到达时返回同一回执。其他渠道提交时得到已回答的明确反馈。
- 先保存胜出答案，再向渠道确认成功。任何恢复步骤都可从已记录阶段继续。
- 历史、待办、文件及指令等副作用各自按稳定身份去重，完成记录与外部操作之间的中断需要逐项处理。
  涉及不同文件/存储的操作应明确可重试语义，发送结果不确定的操作保留待核实状态。
- 请求关闭后仍保留尚未领取的结果。结果领取记录与现有 5 分钟内容重放缓存分别管理。
- 同一存活 CLI 在重连后只向自己的 stdout 输出一次，保持原来的结果格式与退出码。
  CLI 已退出或 Agent 重试时，按调用身份与现有合流/重放规则恢复交付。

### 4.4 断线与真正取消

连接暂断、用户取消和 Agent 结束需要独立处理。
CLI 在受控交接期间保持存活与原 stdout 管道，重连恢复自己的等待者。
MCP 取消仍能终止子 CLI，并使其等待者离场；最后一个真实等待者取消时按原请求语义收尾。
受控交接中保存的等待者不能仅因 socket EOF 被取消。

实施时需收敛等待者租约、CLI 存活证明、恢复宽限期与失联后的处理，
同时覆盖原始调用先离场、follower 留存和交接期间取消的情况。
普通题原有长期等待能力、确认题原始截止时间分别保留。

## 5. 更新交接与故障路径

### 5.1 建议阶段

1. 检测新版并校验目标、保存格式与请求/宿主恢复能力，给各端发布更新状态。
2. 在最终切换前建立写入屏障，停止接受会改变快照的操作，等待进行中的状态提交到达可恢复边界。
3. 保存交接阶段和全部待恢复关系，验证已保存状态可由目标版本接管。
4. 为请求和渠道执行专门的交接收尾，释放旧监听与长连接，保留待答与原卡的有效性。
5. 复用当前 macOS/Linux exec 安装入口和 Windows 接班进程机制启动新版。
6. 新版取得单实例所有权，恢复请求、终态、路由与宿主关联，再发布对应就绪状态。
7. CLI/窗口重连，iOS 完成新的 epoch 同步，IM 接管原卡，新请求恢复受理和投递。

当前关停会调用 `cancel_all_requests`、关闭 Popup、把 IM 卡片置为取消。
实现中需要明确区分交接收尾和终止请求的收尾，逐个检查后台任务、Drop 和渠道失联分支。
保存后的旧任务也必须被写入屏障约束，防止在快照之后提交答案或继续修改卡片。

### 5.2 可恢复失败

| 失败点 | 建议处理 |
| --- | --- |
| 保存、兼容校验或交接准备失败，旧服务仍完整 | 撤销切换准备，旧服务继续运行，展示待更新与失败原因 |
| 已释放部分资源但旧进程仍在 | 根据记录的阶段重新建立旧服务，或进入明确的恢复失败状态 |
| exec/新进程启动失败 | 保留请求记录和客户端草稿，由程序协调恢复；技术原因记录在内部日志 |
| 新版已启动但请求恢复失败 | 显示恢复失败与具体请求状态，阻止空快照覆盖原待答状态 |
| 渠道恢复失败，其他部分已可用 | 分渠道显示重连/失败状态，其余已就绪渠道继续服务 |

自动退回旧构建需要旧镜像可执行且能够理解当前存储格式。
回滚能力需在 schema 与安装布局设计时验证，无法满足时明确报告并保留恢复材料。
单轮恢复尝试应有界，重试由程序协调。用户只需看到简明的更新/恢复状态，
详细版本、阶段与技术原因记录在内部日志。

### 5.3 连续更新与退出意图

沿用已有 `ReplaceOwnBinary`、`YieldToClient`、`Stop` 的意图边界和停止优先规则。
连续安装时通过交接 ID、构建指纹和目标兼容性选择后继，防止旧交接记录覆盖后来成功的交接。
单实例锁、启动串行化、Dev Instance 路由与多安装 hold 需纳入回归。
管理命令 stop/restart、SIGTERM、force 与自然闲退需要分别定义其与可恢复更新的关系，
保留用户明确停止及原有强制操作的含义。

## 6. 桌面与各渠道恢复

### 6.1 Popup Host

- 首选保留当前 Host 及其已挂载表单，IPC 断连后切换为重连状态。
- 恢复认证成功后，按请求 ID 对账，在原组件上更新数据，保留草稿、附件、选区、滚动、
  批注和“稍后回答”标记，避免重新触发到达动效及提示音。
- 受控交接时未确认的提交沿用原提交 ID，窗口区分待发送与等待确认。
- 宿主代际和恢复租约需适配 daemon 换代，防止旧代际 EOF 或延迟消息退出已经恢复的窗口。
- 窗口程序在空闲时更新。若其能力无法承载新请求，需有明确的兼容安排。
  要求重建窗口的场景先保存完整草稿，再恢复表单和附件，并向用户说明。
- 合并模式与独立窗口模式都需要覆盖。

### 6.2 iOS

- 复用 `DraftStore`、持久 outbox、`clientMsgId` 与 Mac journal，恢复原请求 ID。
- 新 daemon 在待答数据恢复完毕后提供 inbox snapshot，防止 `onInboxSnapshot` 把原题误收尾。
- 更新 epoch 后重新同步，用原请求身份保留草稿和已缓存正文。
- 已答而未收到 ACK 的提交再次到达时，可从持久终态查回原回执。
- 保存每题每手机的投递与推送事实，恢复原题时继续通知去重。
- 手机前台的更新状态按配对 Mac 展示，问题页给出该 Mac 的状态。
  提交过程区分待发送、待确认、已接受及重试反馈。
- 更新提示字段需走现有能力协商和线协议夹具流程，旧手机端的行为需单独验证。

### 6.3 IM 原卡接管

需要同时恢复公共会话进度与各平台路由。

| 层次 | 恢复内容 |
| --- | --- |
| 公共逐题流程 | 当前题号、前面已完成的答案、共享正文投递状态、原创建时间 |
| 精确卡片路由 | 平台消息/卡片 ID、请求/题号、用户与聊天绑定、终态版本 |
| 交互输入 | 已收到的选择、文字、图片和文件，以及当前步骤的可恢复表单状态 |
| 自由文字归属 | 各渠道当前活动请求与聊天槽，沿用现有选择规则，防止回复进入另一题 |
| 外部事件去重 | 回调、消息和提交身份，重发后返回原回执 |
| 投递结果不确定 | 发卡请求成功但响应丢失时的核实方式，防止恢复时重复发卡 |

恢复优先重新挂接原消息。需要更新显示时就地修改原卡。
Telegram 长轮询消费位置及飞书、钉钉、Slack 的事件确认时机，需结合现有实现逐项核对。
切换期间原卡点击的成功确认必须对应已保存的操作，各平台重发与失败反馈通过真实渠道验收。
尚未到达 Mac 的手机 IM 编辑框输入，其恢复能力以平台行为为准。

### 6.4 权限确认、Stop 与 daemon 自持卡

普通 ask、whats-next、Stop 卡和结构化权限确认共享恢复基础，分别保留各自的终态与输出契约。
权限确认恢复沿用原始有效期，权限记忆和编辑差异的处理需要专门的幂等边界。
现有错误卡已有 24 小时持久记录，接入时保留原期限与接续回执，确定与新存储的权威关系，
避免两份记录分别恢复成重复卡片。

## 7. 兼容与首次上线

### 7.1 已经挂起的旧版请求

旧 CLI 遇断连会退出，旧 Host 遇 EOF 会退出，安装文件替换无法改变这些进程已经运行的代码。
首次上线时，已有旧题仍需走现行安全排空；后续由支持恢复的版本建立的请求才能完成可恢复更新。
判断条件应覆盖每个等待者、窗口和渠道的能力。
过渡期向 iOS、桌面和可达 IM 解释阻塞来自旧版请求，并列出可定位的待处理项。

### 7.2 建议的兼容设计

- 将恢复能力、宿主能力、请求语义与保存格式版本分别表达，避免只用二进制指纹判断可否重连。
- 当前 Hello 要求全局协议号相等，版本不匹配会让位。需设计稳定的恢复握手，
  让兼容的旧 CLI/Host 能连接新 daemon，避免旧进程把 daemon 再次换回旧构建。
- 兼容的已存请求可继续恢复，新请求按双方支持的能力校验。
- 恢复数据在交接前验证。发现不支持的请求或 schema 时保留旧服务并明确说明原因，
  相关特殊升级的兼容边界需在发布前审定。
- 改动 `ipc/mod.rs` 前遵守 overview 的协议号规则。新增旧端可收到的枚举变体按规则升号，
  只有可选字段且缺省安全的改动才可沿用协议号。
- 旧手机 App、旧 MCP server 新拉起的子 CLI、旧 GUI Host 与多个安装入口都属于兼容矩阵。

## 8. 状态与提示

建议统一生成更新状态，再映射到各界面和 CLI。

| 阶段 | 用户需要看到的内容 |
| --- | --- |
| 准备切换 | 新版已安装、待答问题已保留 |
| 正在交接 | 正在更新、自动恢复，输入可保留，当前提交处于什么状态 |
| 后台就绪/渠道重连 | 哪些渠道已恢复，哪些仍在连接 |
| 完成 | 当前运行版本，随后收起过程提示 |
| 失败 | 问题和输入已保留，以及简明的恢复状态 |
| 首次迁移或不兼容 | 正在等待哪些旧版请求，为什么需要等待 |

CLI 的 stderr 与内部日志保留排障信息。手机和桌面通过现有界面展示简明状态。
IM 根据平台能力就地更新卡片状态或提供状态查询，避免周期性发送过程消息。
有多张旧题时，把更新状态作为 Mac/服务级信息呈现，同时允许从问题定位，避免反复催答。

## 9. 实施顺序与落点

| 阶段 | 交付 | 主要落点与完成条件 |
| --- | --- | --- |
| P0 设计收敛 | 恢复消息、存储 schema、各状态的成功条件、兼容与故障策略 | 明确 §11 的问题，补对应需求规格，接口评审后进入实现 |
| P1 请求与终态存储 | 稳定调用身份、等待者、可靠首答、结果交付及副作用恢复 | `daemon/request.rs`、`ask_dedup.rs`、两个 Coordinator、结果与副作用模块，故障注入通过 |
| P2 CLI 与受控交接 | 提交幂等、CLI 重连、写入屏障、独立交接清理、接班就绪 | `client/mod.rs`、`ipc/mod.rs`、`daemon/runtime/mod.rs`、`daemon/handoff.rs`、生命周期与启动代码 |
| P3 Popup 与 iOS | Host 重连、原表单保留、手机状态、快照屏障、ACK 与通知去重 | `app/popup_inbox.rs`、`daemon/popup_inbox.rs`、前端 inbox、iOS gateway/wire、Swift engine 与请求界面 |
| P4 四渠道接管 | 原卡、逐题进度、回调与自由文字路由恢复 | `channels/conversation.rs`、四渠道 adapter/Router、回调与附件处理，真实渠道逐一验收 |
| P5 启用与交付 | 恢复条件判定、过渡提示、安装/更新入口与跨平台回归 | 自动更新与外部安装两入口闭环，完整恢复条件满足后启用相应路径 |

各阶段可分批开发，自动切换的启用条件始终覆盖该请求实际使用的等待者、宿主与渠道。
P0 需确定提交/交付回执顺序和 schema 迁移，再开始 P1/P2。
实施任务开始时按项目规则选择主工作树或独立 Dev Worktree，并遵循对应安装验收流程。

## 10. 验收矩阵

| 场景 | 必须证明 |
| --- | --- |
| A 题挂起数小时，安装新版后提交 B 题 | A 保留，后台完成换新，B 自动到达，耗时与 A 的作答时间解耦 |
| 同时有多个 Agent 与多个合流等待者 | 请求身份、卡片数量与等待关系保持一致 |
| Submit 已保存、Accepted 尚未收到就切换 | 重试返回同一请求，卡片与 ask-received 只发生一次 |
| 答案提交前后每个持久化边界触发切换 | 已确认答案可恢复，唯一胜者与待交付结果一致 |
| 已发送 Final、CLI 输出/回执边界切换 | 同一存活 CLI 输出一次，未领取结果可再次取得 |
| iOS 提交已接受，ACK 丢失 | 原 clientMsgId 重试查回原回执，副作用只执行一次 |
| Popup 有草稿、附件、批注、选区与滚动位置 | 保留窗口重连，状态完整，延迟旧代际消息不关闭窗口 |
| iOS 在后台、前台、离线返回及新 epoch 同步 | 原题草稿保留，空快照不会提前收尾，恢复不重复推送 |
| IM 多题已答前几题、当前题已选部分选项 | 原卡继续完成，前面答案保留，新题从正确进度继续 |
| 切换期间点击 IM 原卡、输入自由文字或传附件 | 成功确认有可靠记录，重发去重，文字归属正确 |
| 发卡外部成功但响应丢失 | 可核实原投递或明确待核实，恢复不盲目重复发卡 |
| 两个渠道同时作答或重复回调 | 唯一终态，落败端反馈一致 |
| 原始 CLI 离场、follower 留存，或 MCP 在交接中取消 | 正确维持/释放等待者，最后离场才按约定取消 |
| 权限确认接近原截止时间 | 原期限与权限记忆语义保持，恢复不延长授权窗口 |
| 历史、待办、文件或指令执行中断 | 恢复后的结果与副作用一致，有不确定状态的可见处理 |
| 保存失败、schema 不兼容、目标损坏、接班失败 | 旧服务可保留时继续服务，其他情况有诊断且保留恢复材料 |
| 同一次交接连续安装、多个 CLI 同时启动 | 单实例、正确后继，成功状态不被旧记录覆盖 |
| exec 保留 PID | 按运行代际、指纹与恢复就绪判定完成 |
| 显式停止、force、SIGTERM、闲退、auto-restart=0 | 按既定退出意图处理，明确停止优先 |
| 首次从旧版升级、协议号跨代、多安装 hold | 旧请求安全处理且原因可见，兼容恢复客户端不反向顶替新版 |
| macOS/Linux/Windows、Direct/npm 与外部安装 | 对应原生接班及入口行为成立，Windows exe 文件锁有实机证据 |

先用隔离 daemon、伪造 Agent 及渠道替身做可重复的故障注入，再做真实 iOS/IM 验收。
每项记录后台恢复、请求受理、渠道可交互与结果交付时间，外部网络重连单列。
功能改动后的构建/测试先运行 `node scripts/machine-health.mjs`，安装执行 `./scripts/install.sh`
或 Windows 对应脚本，再通过新安装 AskHuman 完成验收。Dev Instance 按项目显式验证路由操作。
iOS 发布和手机安装使用项目 `ios-testflight` skill，并核对新旧手机版本互通。

## 11. 实施前需要收敛的技术问题

1. 恢复握手如何与现有严格协议号、指纹让位和 hold 共同工作，旧 Host 能支持哪些新请求。
2. 事务存储的最终 schema、可靠落盘要求、迁移与旧镜像回滚支持范围。
3. 等待者租约、原调用取消证明、恢复宽限期与终态领取记录的保留策略。
4. 历史、待办、文件、权限记忆和指令逐项如何跨存储去重及处理不确定结果。
5. 四种 IM 的原卡接管能力、未提交输入可恢复范围、事件重发与发卡结果核实方式。
6. Host 必须升级时的草稿保存格式，以及失效文件/上传中附件的恢复与生命周期。
7. 各阶段的耗时目标、程序自动恢复策略与简明的用户状态反馈。

这些问题在 P0 根据代码调查细化。影响 U1–U5 或需要缩减恢复渠道的取舍通过 AskHuman 确认。
