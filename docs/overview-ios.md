# iOS 渠道概览

可恢复后台更新由 `daemon/recovery.rs` 与 Gateway 共同处理。原题持久身份、答案/回执事务、
通知事实与上传检查点跨交接保存，Gateway 等原 iOS 待答面全部恢复再发快照。
AHCore 保留更新期间的草稿和原提交 ID，完成新 epoch 同步后自动续送。
`Caps.liveUpdate` 与 Presence 可选 `u` 保持旧手机互通，详细契约见 [即时换新](specs/daemon-live-update.md)。


> 本文是 `docs/overview.md` 的专题补充，记录 iOS 渠道（实验功能）当前的实现地图与不变量；需求决策见 `docs/specs/ios-channel.md`，实现步骤见 `docs/plans/ios-channel.md`，用户使用说明见 `docs/wiki/ios-setup.md`。

## 形态

```
Agent / CLI ─► Daemon ── IosGateway（一个 actor）──► MQTT（TLS 8883 / WSS 8084）──► EMQX Serverless ──► iOS App
                                │                                                                  ▲
                                └────── 推送中继（无状态云函数，持有 APNs 密钥）──► APNs ───────────┘
```

- iOS 是 Daemon 里的又一个渠道（`channels/ios.rs`），受 `experimental.enabled` 隐藏；一个 Mac 一份 broker 凭据，多台 Mac 共用同一份（连接串可导入导出），手机经二维码配对。
- **端到端加密**：每个配对一对方向密钥（ChaCha20-Poly1305），broker 只见密文；配对用一次性票据 + 6 位校验码，由 Mac 用户在设置页或 CLI 上放行。推送预览同样加密，由手机上的通知扩展解密。
- **Mac 不持有 APNs 密钥**：Mac 把加密后的信封和手机的不透明句柄交给中继，中继按固定白名单拼出提醒并转给 APNs。
- 手机能做的事：回答问题 / 确认（含多题、推荐、附件；回答时还能从该项目的待办里选几条随回答发给 Agent，What's next 能看到完整队列，`docs/specs/special-replies.md` D28 / D29）、看 Agent 列表（App 里没有手动关注：手机新建任务或原会话接续的新一轮出结果时 Mac 会通知，列表行与详情页只读地标出）、实时观察（Watch，≤2 路、仅前台）、给 Agent 插话、新建 Agent 任务（Face ID 确认）、管理待办（「待办」标签：来源是某台 Mac 或「iCloud」，浏览项目、增 / 改 / 勾 / 删 / 排序、⚡ 自动执行、看执行历史；`docs/specs/ios-todos.md`）；请求页里出现的每一份待办清单（提问页「待办」卡、What's next 与 Stop 的队列行）都能完成 / 删除 / 添加：右滑完成、左滑删除（也有长按菜单与 VoiceOver 操作），清单末尾「＋ 添加待办」只有文字、写到该请求所在的那台 Mac（`docs/specs/todo-list-actions.md`，取代了请求页「⋯」→「添加待办…」的半屏页）；可选的开发者模式（Macs 标签里的开关，默认关）：全局浮动按钮，按住滑到条目松手，v1 只有「快速添加待办」，不用离开当前界面（`docs/specs/ios-developer-mode.md`）。
- **投递与通知分开**（`docs/specs/ios-alert-timing.md`）：iOS 不参与 IM 的活跃槽，`attach_im_channels` / `confirm_im_candidates` 在选完 IM 候选后用 `with_ios` 把它并进来，每个提问 / 确认都挂给所有已配对手机，手机一连上就从 hello 快照（`request.get`）拉到。手机在看（在线 + 前台 + 已 hello）时经 MQTT 实时送达、不推送；不在看时只有系统推送能打扰人，而它要等 Mac 键盘 / 鼠标空闲满 `channels.ios.alertAfterSecs`（默认 900 秒，`0` = 立即）才发，每题每手机最多一条，没有提醒。


生命周期结果与原会话控制见 [统一结果与接续](specs/agent-lifecycle-results-and-recovery.md)：
`AgentView.lastTurnResult` 独立于空闲／运行／结束状态；手机 Agents 页只显示结果与原因，不设「需要处理」分组，
失败的处理动作只在收件箱的错误卡（[决定](specs/agent-failure-inbox.md)），可接收消息的空闲会话另有详情页自由消息。
`daemon/runtime/agent_control.rs` 将原生新回合证明关联到手机；`PhoneRecord.followTurns` 将通知绑定该轮，
`lifecycleResults` 能力声明避免旧手机收到不认识的未完成推送。用户中断静默，结果随 `agents.json` 保留。

## 推送中继（`relay/`）

零依赖 Node.js（`http` / `http2` / `crypto`），为腾讯云云函数 Web 函数而写：`src/core.js`（句柄编解码、请求校验、载荷白名单、ES256 JWT、错误映射、令牌桶）与 `src/adapters/scf.js`（HTTP 服务、环境变量、HTTP/2 到 APNs）。接口 `GET /v1/health`、`POST /v1/register`、`POST /v1/push`。密钥只在云函数环境变量里（`APNS_KEY_P8` 等），仓库与日志里没有任何密钥。`scripts/build-zip.sh` 产出上传用的 zip，`npm test` 跑 `node --test`。

## iOS App（`ios/`）

- 工程用 XcodeGen（`ios/project.yml`），`*.xcodeproj` 不入库；新增文件后 `xcodegen generate`。iOS 17+，SwiftUI，Swift 5 语言模式 + 严格并发。Team `DMJXDB9H6Q`，Bundle ID `com.naituw.humaninloop.ios`，通知扩展 `…ios.notification`，共享钥匙串组 `…ios.shared`。
- 业务全部在本地 Swift Package `ios/Packages/AskHumanKit`，UI 只是它的薄壳：

  | Target | 内容 |
  |---|---|
  | `AHProtocol` | 与 Rust 对应的线协议、加解密、信封（通知扩展也链接它，所以保持极小） |
  | `AHStore` | 文件型 JSON 存储（历史、草稿、发件箱、流量）、钥匙串 `Vault`、`PushDecryptor`（通知扩展用） |
  | `AHTransport` | `BrokerClient` 抽象、`MQTTBrokerClient`（CocoaMQTT）、进程内 `LoopbackBroker` |
  | `AHCore` | `PhoneEngine`（actor：连接、配对、同步、发件箱重试、推送登记、Agents / Watch / 插话 / 任务 / 待办请求）、`TodosStore`（待办标签的状态：来源与 iCloud 接入 Mac、多台 Mac 开着同步时合并成 iCloud 一个来源、项目行上取自 Agents 页状态的点、「Mac 最后的回答 + 用户未被应答的写入」叠加出屏幕上的列表、写入队列）与 `AppStore`（`@MainActor @Observable`，UI 的唯一入口）及各 Composer；开发者模式的逻辑也在这里（`DeveloperTools`：开关、按钮位置、提示，`DeveloperGeometry` 的位置 / 吸附几何，`QuickTodoComposer`），还有「复制诊断信息」用的日志与报告分节 `Diagnostics`；`QuickTodoComposer` 用 `TodoAddCall` 发送并「丢回包重发一次」；离开模式由 `AwayStore`（`AppStore+Away.swift` · `AwayModels.swift`：把各 Mac 的 `away.state` 汇总成常驻条、开启页与会话行的视图；`PhoneEngine+Away.swift` 发 `away.set` / `away.session.set`）管，待发指令与快捷回复的合成在 `AnswerComposer`（`directive`、`quickReplyFills(_:)`、`items(uploads:fillingWith:)`——只用**这条请求自带的**预设填充）；请求页的待办清单由 `RequestTodoPicker` 管（按请求缓存，读 `todo.list.get`；选中的 id 存在 `AnswerComposer.todoIds` 里随回答的 `todoIds` 发出，`caps.answerTodos` 缺失的旧 Mac 不显示；还能完成 / 删除 / 添加 / 撤销完成，写入走 `todo.op`，与 `TodosStore` 同一种「Mac 最后的回答 + 未被应答的写入」叠加、`clientMsgId` 幂等与丢回包重发一次，`AskView.listsTodoQueue = whatsNext || todoQueue` 决定待办是不是选项本体——What's next 与 Stop 确认卡都是），请求页的「此会话的历史」由 `SessionThread` 管（`@MainActor @Observable`，页面拥有、不缓存不落盘、同一时间只有一个读取在飞；`AppStore+SessionHistory.swift` 的 `sessionHistoryAvailable(for:)` 决定入口，`PhoneEngine+SessionHistory.swift` 复用待办的邮箱与超时读 `history.session.get`，Mac 声明 `caps.historyPictures` 时带 `pictures`；同一个文件的 `sessionExchange(macId:id:)` 与 `AppStore.historyExchange(for:)` 给「历史」Tab 详情页按 id 读单条往来的图，邮箱键 `x|macId|reqId`，Mac 不会就是 `nil`），都不依赖 UIKit，能在 macOS 上 `swift test` |
  | `AHMarkdown` | Markdown 块解析，供原生渲染（题干、列表摘要、Watch 卡片、附件预览，以及网页渲染不可用时的回落）；请求正文平时由网页渲染（见下） |
  | `AHMock` | `MockBackend`：演示数据与可编程故障，UI 测试和截图都跑在它上面 |

- 新建任务的 Mac 在手动选择时即保存为这部手机的本地偏好，取消或重启 App 也保留；打开时优先入口指定的 Mac，否则恢复可用的已记忆 Mac，再临时回退第一台可用 Mac，回退不覆盖记忆（`AppStore+Agents.swift`；`ios-channel.md` §6.8）。
- 新建任务的 `TaskComposer` 在点击「开始」时，将模型 / 强度按 Agent 存为这部手机的本地偏好，所有 Mac / 工作区共用；取消不更新。
  打开表单或切换 Mac / Agent 时恢复，缺少已保存模型的 Mac 临时回默认并保留原偏好。完整约定见 `docs/specs/ios-task-model.md` M3。
- Agent 消息对 Codex Desktop 走原生 `Operation::Send`（运行中补充／空闲时继续，继承线程设置）；其余走原有工作中 Hook 队列。
  Desktop 断开绝不回退队列；Gateway 后台发送并去重，成功只代表 App 接受。手机对不明结果保留消息 ID 与草稿，经用户检查原聊天后才能解除。见 `ios-channel.md` §6.7。
- Codex 新任务可逐次开启 Fast（桌面 App／CLI 均支持），默认关闭且关闭明确传标准速度；速度不保存，模型／强度的偏好规则不变。
  能力取对应 Codex 目录的逐模型声明，旧 Mac 隐藏开关；进度显示所选速度，详情仅显示会话有证据的速度配置。见 `docs/specs/ios-task-speed.md`。
- 回复、插话与新任务共用 `Views/Attachments/ReplyAttachments.swift` 的附件菜单：相册允许照片 / 视频混选，视频通过文件型 `Transferable` 读取。
  `AHCore/VideoAttachmentPreparer.swift` 保留限额内原视频，超限时先预估可用压缩档位，只有预估 ≤8 MB 才尝试；编码一次后核对实际体积与完整时长。回答区、插话栏与新任务表单直接显示压缩进度及取消按钮，由用户决定是否继续等待。
  导出器的状态与取消约束在 MainActor，原文件 / 导出临时目录按生命周期清理；三个 Composer 用准备任务的 token 集合阻止处理期间发送。验证办法见 `docs/plans/ios-video-attachments.md`。
- 提问附件列表与预览支持拖出（[规格](specs/ios-attachment-drag-export.md)）：`AttachmentDrag` 接入 SwiftUI 的列表／文件预览及 UIKit 图片拖拽；`AHCore/AttachmentFilePromise` 通过 `NSItemProvider` 的异步文件表示，在接收 App 请求时才调用 `downloadForExport`，导出带原名的文件副本。具体类型优先，并提供通用文件表示供不认识该类型的接收方读取；不导出路径字符串。provider 持有交付临时目录，页面离开不删除；取消与错误不交付空文件。实际加载申请有期限的系统后台任务，`PhoneEngine.assetExports` 仅在导出期间保留后台 MQTT，presence 为 `fg=0`、Watch 停止，最后一份导出结束后恢复断连。普通预览仍走原下载入口；没有新增线协议。

`-AHAdvanceSettle <秒>` 拉长回执与换页的时间，方便截图 / 录屏；`-AHNotify <请求 id>` 模拟点开该请求的推送（页面立刻打开，不等同步，带一段虚构的通知文字）；`-AHArrival <会话标题|none>` 启动约 2 秒后模拟一条前台实时新提问（到达动效），`none` 表示该会话没有标题；`-AHArrivalCount <N>` - XCUITest 经验：**`WKWebView` 里的内容在无障碍树里是一串平铺的普通元素**（StaticText / Link / Image / Button，Link 的标签是链接文字，**没有 WebView 节点**，`app.webViews` 永远找不到），所以测网页渲染要靠只有网页才有的标志（复制按钮标签「Copy」、Mermaid 图是带图中文字的 `Image`），原生渲染的对应物是「Copy code」与源码文字；链接文字折行时 Link 的 frame 是整块包围盒，点它的中心可能点到别的链接，测试挑单行的那个。容器 view 上的 `accessibilityIdentifier` 需要 `.accessibilityElement(children: .contain/.combine)` 才找得到子元素；Form / List 的懒加载行需要滚动到附近才存在；详情页保留系统 TabBar，底部操作栏统一经 `.actionBar` 的 `safeAreaBar` / `safeAreaInset` 避让；验证要检查按钮与标签栏、键盘互不遮挡，不要用标签栏是否存在判断已返回列表。挂在容器上的 `accessibilityIdentifier` 会盖住子元素自己的标识，要查子元素就把标识挂在叶子视图上；判断「被盖住」用 `isHittable`（被 `.accessibilityHidden` 的元素仍然 `exists`）。推送横幅是 springboard 里的 `BannerNotification`（标识 `NotificationShortLookView`），权限弹窗按钮是 `springboard.alerts.buttons["Allow"]`；合并后的 `push-status` 行标签形如 `Notifications, On`，判断用 `hasSuffix`。 `AskHumanUITests` 里按序号点底部标签的 `tab(_:)`：收件箱 0、Agents 1、待办 2、历史 3、Mac 4（加标签时要回头改这里的序号）。开发者模式的 UI 测试（`AskHumanDeveloperUITests`）：按住再滑动用 `XCUICoordinate.press(forDuration:thenDragTo:withVelocity:thenHoldForDuration:)` 且两端都用坐标（系统菜单的行在手势开始时还不存在，位置先用一次轻点读出来）；系统菜单的条目没有 `accessibilityIdentifier`，按标题找（`app.buttons` 里 label 等于条目标题），点菜单外面收起菜单的那一下由系统吃掉、不会传给下面的控件，iOS 26 上菜单打开时按钮被菜单取代，要读 `dev-button` 的 frame 得等菜单收起；手指按着时的画面在测试线程里拍不了（线程停在 `press(…thenHoldForDuration:)` 里），要看就在测试里长按、另开 shell 循环 `xcrun simctl io <udid> screenshot` 从外面拍；`dev-button`、工具栏按钮等同一标识也会出现在内层文字上，要用 `app.buttons` 取；改了 UI 测试之后的第一次运行偶尔会跑到旧的测试包（输出 `Executed 0 tests` 或跑出旧行为），先看 `Executed N tests` 与用例名，不对就原样重跑。`Failed to get matching snapshots: Timed out while evaluating UI query`（约 2 分钟）多半是 App 主线程被布局死循环占满：把测试放到后台跑（输出重定向到文件），等它卡住后 `sample <App 的 pid> 3 -file …` 看主线程。待办的 UI 测试在 iOS 18.5 的模拟器上跑 `testAddingFinishingEditingAndRestoringATodo` 会卡住：拖动待办页把键盘收起（`dismissKeyboard()`）之后，每一个动作都要等满 60 秒的「App animations complete notification not received」才继续，整个类跑上 20 分钟也不结束，而此时 App 空闲（CPU 约 0、主线程停在 run loop）；同一份构建在 iOS 27.0 的模拟器上约 1.5 分钟通过。所以跑待办的 UI 测试用 iOS 27.0 的模拟器；这只是在一个环境里的观察，没有查到 18.5 上的根因。

CI（`.github/workflows/build.yml`）只跑上表的「Swift 包」与「中继」两行，各占一个 job（`ios-kit`：`macos-26` 上 `swift test`；`relay`：`npm test`），与四平台构建矩阵并行；不跑 `xcodebuild`（App 本体与 UI 测试要模拟器）、真实 daemon 端到端和真实服务场景（端到端缺环境变量会自动跳过）。Rust 侧的 `ios::` 测试已包含在矩阵里的 `cargo test`。

端到端测试台会起**一台一次性的 Mac**：独立 `ASKHUMAN_HOME`、`HOME`、`ASKHUMAN_NO_KEYCHAIN=1`，加本地 Node broker；`agentTasks.enabled` 保持关闭，所以不会真的启动任何终端。伪造的 Agent 会话通过隐藏命令 `AskHuman __agent-hook <agent> <event>` 注入。

真实服务模式不起本地 broker：一次性 Mac 用 `channel ios export` 取出实例的连接串（只在测试进程的内存里，经 stdin 交给 `channel set ios --connection-stdin`，不显示、不落盘），手机侧是 macOS 上真正的 `PhoneEngine` + `MQTTBrokerClient`。每个用例的 Mac / 手机 ID 都是新生成的，话题互不重叠（共用同一个 EMQX 账号），但会消耗真实 EMQX 的流量与中继调用。`AH_E2E_REPORT=<json>` 写入延迟统计，`AH_E2E_KEEP_LOGS=<目录>` 让失败的用例留下 Mac 的 daemon 日志与手机侧摘要（都不含秘密）。

模拟器场景（`SimulatorLiveTests` + `AskHumanLiveUITests`）把一次性 Mac 留在宿主进程里，手机侧是 `xcodebuild test-without-building` 启动的 XCUITest，两边用 `ui/` `host/` 目录里的「会合点」文件互相等待。它走完：配对与校验码 → 通知权限 → token → 中继登记 → Mac 持有句柄 → 前台单题 / 多题 → 权限确认（允许；带理由拒绝）→ 一个 `__agent-hook` 会话（App 以 `-AHFollowAgent` 启动，所以这个会话「会通知你」）：列表、实时观看、详情页的那行说明与列表行上的铃铛（没有关注按钮）、插话与读取回执 → 任务被关闭时新任务表单的提示 → App 离开前台 → 一次真 APNs 沙盒推送（模拟器收得到，扩展会运行；`simctl push` 不会运行扩展）→ 点击横幅 → 该 Agent 第一次结束回合的推送（一次性：之后会话移出通知集）→ 点击打开 Agent 页 → 历史 → 解除配对。一次性 Mac 的 `alertAfterSecs` 播种为 `0`（真实服务模式的 `RealBroker.settings()`），推送不依赖这台机器此刻是否空闲。配对码含 broker 密码，只经命名管道从宿主交给 UI 测试（不落文件、不进环境变量 / 剪贴板，码在屏幕上时不截图），`xcresult` 结束时删除，并在日志与模拟器键盘日志里扫描配对码。模拟器默认只卸载 App + `simctl keychain reset` + 等 CPU 静下来；`AH_E2E_SIM_ERASE=1` 才抹掉设备（首次开机要占满一个核好几分钟）。`AH_E2E_SHOTS=<目录>` 保留截图。

## 不变量与注意点

- **请求详情不能把重连误报为 Mac 离线**：作答／确认页共用 `EngineState.requestConnection(macId:)` 与 `RequestConnectionNotice`，先判断手机连接阶段，再判断当前请求的目标 Mac。连接／重试中显示中性进度；仅在手机已连通且目标 `MacLink.macOffline` 时显示 Mac 离线。连接恢复保留页面和草稿，发送继续受就绪状态约束；见 `docs/specs/ios-answer-flow.md` §3.6。

- **新请求的前台动效**：仅对已同步后有效的前台实时新增播放，收件箱与其他页面一致；所有快照补齐均静默，回来不补播。`AppStore.requestArrivals` 以手机单调接收时刻过滤旧活动期事件，状态／事件乱序时等请求进入 inbox 后一起释放动画和原有震动，不生成旧的大横幅；打开、处理、失活时清理，动画完成不改未读。Agent 完成等其他横幅保留。
  `Views/Arrival/ArrivalSceneHost.swift` 通过根视图的零尺寸 attachment 绑定真实 `UIWindowScene`，以不可成为 key、`hitTest` 恒为空且禁用交互的透明装饰窗口覆盖 App 页面／弹层。它不操作真实输入框；只有 Debug + mock 专属组合态测试 fixture 会准备 marked text。**气泡在第一次被画出来之前必须不可见**：新建的 `UIView` 落在窗口原点且不透明，窗口显示与第一次 display link 回调之间只要有一次画面提交，屏幕上就先有一个气泡停在角上、随后才跳到中间（用户反馈的「先在角上出来再闪到中间」）。所以气泡创建即 `alpha = 0` 并先摆在第 0 毫秒那一帧的位置，动效计时从第一次画出它那一帧起算（不是创建时刻），显示装饰窗口前先把它的 frame 对齐到来源窗口当下的 frame；诊断串里的 `stray=` 数「第一次画出来时就已可见」的气泡，恒为 0，`AskHumanArrivalUITests.testABubbleIsNotSeenBeforeItsFirstFrameIsPainted` 守着。
  `ArrivalLayout.swift` 从真实底栏、导航栏、安全区和键盘测量锚点；底栏可用飞收件箱，否则落顶部短暂提示，移动锚点平滑跟随。宽窗口里收件箱是分栏的一栏时，新请求那一行若在列表可见区域内，气泡改飞进那一行的未读蓝点（与 Mac 一致）：分栏列表的行（`InboxRow(landsArrival:)`）在蓝点后面放一个看不见的 `ArrivalDotMarker`，向 `Views/Arrival/ArrivalDots.swift` 登记，控制器每帧用它找行的位置，蓝点在气泡落下之前被藏起来；找不到行时仍按上面的规则落标签或标题。`AHCore/ArrivalMotion.swift` 与 Mac 共用 `ios/Fixtures/arrival-motion.json` 数值参考，使用原轨迹；SVG／PDF 位于 `ios/Tools/arrival-motion/` 与 assets。减少动态效果只显示静态提示，后台停止 display link。规格见 `docs/specs/ios-arrival-motion.md`。

- **开发者模式的窗口规则**（`docs/specs/ios-developer-mode.md` §5.5）：窗口层级相对主窗口——到达动效 +1、浮动按钮 +2、快速添加页 +3。**按钮窗口不得 `makeKeyAndVisible`**（只设 `isHidden = false`，`canBecomeKey = false`）：成为 key 会让正在编辑的输入框失去键盘；它的 `hitTest` 只在按钮上返回视图，其余触摸原样穿透；菜单是按钮的系统 `UIMenu`，由系统呈现在所有窗口之上、不属于任何 App 窗口（所以没有收起层，也不会抢走键盘）。只有快速添加窗口会成为 key（要弹键盘），所以它的收尾 `QuickTodoPresenter.finish` 是**唯一的出口**（取消、添加成功、系统下拉、关开关、场景结束都走它），必须把主窗口恢复为 key、让原来的第一响应者重新编辑。拖动与菜单谁先到由系统决定（按下后立刻移动 = 拖动，按住不动 = 菜单），没有手势常量；`DeveloperMetrics` 放按钮直径、贴边与空闲降透明。`AskHumanDeveloperUITests` 守着这些（盖住 sheet 与它的键盘、盖住图片查看器、与到达动效共存、焦点恢复）。
- **隔离**：任何隔离运行的 Mac / daemon 必须设置 `ASKHUMAN_HOME`（只改 `HOME` 时 daemon 标签虽已独立，但 GUI Host 登录项与 Agent hook 文件仍会碰到真实环境）；测试台在启动前断言它位于临时目录。
- **IPC 协议号**：当前为 5（`ClientMsg::Ios` / `ServerMsg::Ios` 是 4 带来的，离开模式的 `ClientMsg::Away` / `ServerMsg::Away` 在 0.17.0 发布前并入 5，现已发布）。给 `IosOp` / `IosResult` 加带 `#[serde(default)]` 的字段不 +1；规则见 `docs/overview.md` 的「IPC 协议号」。手机线协议自己的 `PROTO` 没动：离开模式与快捷回复只加了可选字段与新消息，能力靠 `Caps` 位协商。
- **线协议**：`ios/wire.rs` 与 `AHProtocol` 的限额常量（信封 ≤ 900,000 B、分块 192 KB、附件 ≤ 10 MB、每次回复 ≤ 5 个附件、令牌桶 6/s 突发 10、Follow ≤ 5、任务正文 ≤ 3000 字、插话 ≤ 20,000 字、Watch 间隔 ≥ 2 s 且每手机 ≤ 2 路）两边必须一致；改任何一边先改夹具。
- **幂等**：状态变更消息（回答、插话、`task.create` 等）按 `msgId` 进幂等日志，重放返回同一结果、同 ID 不同内容被拒绝。
- **「活着」的手机**：Gateway 只向「在线 + 前台 + 已 hello」的手机实时投递。App 在首次同步之后才发布前台状态，所以 hello 与前台状态之间的变化（新请求、Agent、Follow）不会被实时发出；`Actor::on_presence` 在手机由此变为「活着」时补发四个快照。改动这一段先看 `tests_requests` / `tests_agents` 里 `…between_hello_and_the_foreground_presence…` 两个用例。
- **「待通知」是推导出来的，不存标志位**：一道题对某部手机是否还在等推送 = `!seen && !pushed && !(is_live && connected) && can_push`，由 `flush_due_notifications`（`deliver()` 末尾与每 250 ms 的 `tick_requests`）判断；手机上下线、broker 抖动、`request.seen` 都不必逐个维护状态，推过一次 `pushed` 置位后条件不再成立，所以天然没有提醒。3 秒补推（前台手机没确认）不受等待时长约束；读不到空闲时长按「够久了」处理；`alert_after_secs` 不在 `ConnKey` 里，改设置不重连网关。改这一段先看 `tests_requests.rs` 的「push timing」一节。
- **最终失败卡**（`docs/specs/agent-failure-confirmation.md`）：daemon 复用普通 Ask 发到手机收件箱，沿用问题的空闲门槛，不要求手机发起资格；网关按结果 ID 暂停同轮 `follow.failed`，建卡基础设施失败时恢复原结果提醒。已处理卡片消耗旧通知资格，从手机要求继续则依实际新回合重新登记一次性通知；手机身份从网关现有作答回执取得，不新增手机线协议。
- **Follow 的「做完 / 出错」走同一条等待规则，但是显式排队**（`docs/specs/ios-follow-narrowing.md`）：结果没有长期存在的对象可推导，所以 `announce` 把它排进 `Live.follow_notices`（内存，每部手机每个 Agent 至多一条），由 `flush_follow_notices`（`announce` 末尾与每 250 ms 的 `tick`）判断：Agent 又开始工作 / 会话结束 → 作废并继续关注；手机变成在看、或结果之后 Mac 有了新输入 → 作废；空闲满 D（或 `D = 0`、读不到空闲）→ 推一次。除「Agent 又开始工作」外，推出或作废都会把该 Agent 移出关注集（一次性），所以重启 daemon 会丢掉还没推出的通知。改这一段先看 `tests_agents.rs` 里 “A result (done / failed)” 那一节。
- **App 没有关注入口，但 `setFollow` / `FollowSet` / `FollowState` / `FollowEvent` / `Wire.maxFollow` 都留着**：旧版 Mac 与旧版 App 还在用它们（旧版 App 的星标连新版 Mac 照常能加，只是同样一次性、同样遵守 D），`-AHFollowAgent` 也靠 `setFollow`。把它们当死代码清掉之前，先看 `docs/specs/ios-follow-narrowing.md` 的「兼容」。App 只读地展示 `AgentView.followed`：列表行铃铛、详情页 `follow-note`；Mac 拒绝（名额满）时静默，不弹提示。
- **推送信封没有 `v`**：中继转给 APNs 的 `ah` 只有 `{f,k,n,c}`（Mac 封装时的 `v` 不转发），`PushDecryptor` 缺 `v` 时按本协议处理、带了别的版本则拒绝。改推送载荷或中继的白名单时，同步改 `PushDecryptorTests` 里「中继的形状」，否则单元测试与真实推送会各说各话。
- **通知代理方法必须在主 actor 上**：`AppDelegate` 的 `UNUserNotificationCenterDelegate` 方法是 `@MainActor`（一致性标 `@preconcurrency`）；写成 `nonisolated async` 时系统的完成回调落在协作线程池，iOS 27 上点推送横幅会崩溃。
- **每次握手都把推送句柄再给 Mac**：`PhoneEngine` 在每次 `hello.ack` 清空 `pushSent` 并重发，发送失败要回滚标记，token 在 ack 与首个快照之间到达也立即发；Mac 只会回 `push.state` 的 `ok` / `gone`，不会反过来索要句柄。
- **手机自己能从「握手卡住 / 连接半死」里恢复，不靠 Mac**（`docs/specs/ios-alert-timing.md` D12）：`hello` 一轮 3 次（各 5 秒）没人应后不放弃，按 `helloRetryDelays`（30 / 60 / 120 秒封顶）继续问；`hello.ack` 认本会话最近 8 条 `hello`（`MacRuntime.helloNonces`）中的任何一条，`resetSession` 清空名单，所以旧会话的随机数没用，握手完成后晚到的 ack 也被忽略；下拉刷新对没握手的 Mac 重新握手（`restartHello`），不再只发会被忽略的 `Resync`。App 在前台收到收件箱里没有的请求的推送时（`AppDelegate.willPresent` → `AppStore.noteUnknownRequest`，`resolved` 与 `follow.*` 不算）走 `PhoneEngine.checkLink`：向手机**自己的下行主题**发一个随机令牌，**只有这条回声**算连接健康（PUBACK 不证明下行，Mac 的流量不证明上行）；`probeTimeout`（4 秒）内没回来或发布直接失败就 `reconnectNow()`（不等退避），回来了就重新握手或 `Resync("inbox")`；同一台 Mac 10 秒内只处理一次。探测发布不能 `await` 在看门狗之前——`MQTTBrokerClient.publish` 最多等 10 秒 PUBACK。改这一段先看 `SessionTests` 里 hello 的重试 / 迟到确认用例与 `ConnectionTests` 的 “link check” 一节（`LoopbackClient.dropsInbound` 模拟看着活着却什么都收不到的连接）；`AHE2ETests/LinkCheckE2ETests` 在真实 daemon + 真实 MQTT 客户端 + 本地 broker 上证明回声走得通（自发自收经 CocoaMQTT 与 Aedes 都成立；EMQX 的自发自收见 P0 记录），以及「聋」连接（`ObservedBroker.goDeaf()`）会被换掉、漏掉的请求随后补上。
- **离开 / 返回前台的竞态**：`setForeground(false)` 在 `goodbye()` 处挂起，goodbye 之后若应在前台必须重连（`ConnectionTests.testComingBackWhileTheGoodbyeIsOnItsWayStillReconnects`）。`scenePhase == .inactive`（控制中心、通知中心、多任务界面、系统弹窗——App 仍在屏幕上）**不算离开**：`PhoneEngine.setInactive()` 给 `inactiveGrace`（10 s）的宽限期，超过才告别，期间回到前台则取消计时、保留连接；`.background`（锁屏、回主屏）仍立即告别；`AskHumanApp` 只做 `scenePhase` → `setInactive` / `setForeground` 的映射（`ConnectionTests` 里 5 个 inactive 用例，每处保护去掉都会变红）。强退没有任何 `scenePhase` 回调，靠 Last Will 兜底。真机上只验证了「停留超过 10 s 时离线窗口远短于停留」，短停留不离线、锁屏 / 回主屏与强退后 Mac 多快看到离线都**没在真机上验证**（见 P0 记录 §3.8）。
- **`AppStore` 的状态流与事件流没有先后**：`AppStore` 在两个独立任务里分别消费 `states` 与 `events`，同一次变化的两者谁先到不确定。`AHAppTests` 里不要假设顺序，每个条件各自用 `eventually` 等。模拟「别处已作答」用 `MockBackend.simulateFinishedElsewhere`（结束事件带 `by`，页面保留请求并显示提示；要别的结果——取消、超时、结束——用同一处的 `simulateFinished(outcome:by:)`）；不要用自己提交的回答代替——它的结束事件没有 `by`，App 会前进到下一个请求并忘掉提示，结果取决于哪条流先到（曾因此在 CI 上偶发失败三个用例）。
- **iOS 26 的顶部滚动边缘效果**：别用 `safeAreaInset(edge: .top)` 在列表上方固定自绘的栏——它会落进导航栏下的模糊带，让导航栏高到约三倍（曾经的筛选条）。需要的控件放进 toolbar（筛选是 `Menu`），状态文字放 `.principal` 的标题位。
- **「没有数据」与「还没加载」是两回事**：`EngineState.listReadiness`（`ready` / `loading` / `unreachable`）与 `syncStatus`（`upToDate` / `updating` / `reconnecting` / `refused`）由 `EngineState`（`AHCore/Models.swift`）从连接阶段与各 Mac 的 `link` 推导，`MacLink.connecting` 是唯一的「还不知道」状态。UI 只有在 `ready` 时才显示「已全部处理」类的空状态，`loading` 显示缓存或骨架行（15 秒仍无应答才显示「等待 Mac 响应」）；同步提示放标题位且延迟约 0.6 秒才出现，只有需要用户处理的问题（Broker 拒绝、时钟偏差、流量、Mac 离线）才在列表顶部出现提示卡。新增列表页时沿用这套，别自己写 `isEmpty → 空状态`。
- **多题表单的「发送」要等看过最后一题，而「下一题」只看屏幕位置**：`AnswerComposer` 记录每题是否「看过」（题卡底边进入过可视区，已作答的算看过；一旦看过最后一题就不再收回），多题时 `hasReachedEnd` 之前底部是「下一题」，之后是「发送」（屏幕下方还有题时，「发送」旁多一个「下一题」图标按钮；纯选择题表单没选全时，计数下的提示可点，跳到第一道没选的题）；与弹窗的 V1 / V2（`docs/specs/multi-question-vertical.md`）一致，改一边要同步改另一边。「下一题」落到哪张卡由 `QuestionNavigator`（AHCore，纯函数）按题卡与可视区的**当前**位置算——第一张底边还在可视区下方的卡，放得下就整张露出，放不下先对齐顶部、再按一次看底部——**不看「看过」的历史**，所以往回滑后再点不会跳过看过但没答的题（同弹窗的 `goNext`）。**正在输入时例外**：键盘在哪一题，就从那一题往后（`QuestionNavigator.next(after:in:)`，同弹窗 H4），下一题是纯文本题时键盘接力过去（焦点直接移过去、键盘不收，页面滑到那一题；由 UIKit 交接：`InlineTextView.takeTheKeyboard()`，**不要**靠 SwiftUI 的 `focused` 绑定在 `updateUIView` 里让旧输入框 resign、新输入框 become——resign 的嵌套布局会把新的 become 撤销，键盘留着却没有谁在输入）；要收键盘（下一题有选项）时由按钮的动作直接 `resignFirstResponder` 再**等布局排完**才算位置、开始滚——不要把收键盘放进 SwiftUI 的更新过程（`CaretTextView.updateUIView` 里置空 `focused`）再固定等一会儿：键盘在更新中途退出，布局会卡在键盘时的几何上（底栏下面一条空白），量到的位置也不可信（`docs/specs/ios-answer-flow.md` §2.5）。**同样不能在更新过程里同步 `resignFirstResponder` / `isEditable = false`**：UIKit 会回头问宿主视图「能不能接管 responder」，这同步重跑一遍视图图，图里有 `ViewThatFits`（底栏的计数块）时成环，主线程卡一分钟以上（多题表单打完字点「发送」时出现过）；这两个动作都挪到下一轮主线程（`InlineTextView.setEditable`、`CaretTextView.updateUIView`，G13）。选项行点按即时选中，不做渐变（`OptionRow`）。规格与弹窗对照见 `docs/specs/ios-answer-flow.md`。
- **提问页 / 确认页的底栏：iOS 26 起是浮动的 Liquid Glass 栏，之前是经典栏**（`Views/Common/BottomBar.swift`，规格 `docs/specs/ios-answer-flow.md` §3.4）：`.actionBar { … }` 在 iOS 26+ 用 `scrollEdgeEffectStyle(.soft, for: .bottom)` + `safeAreaBar`——栏自己**没有底板也没有分隔线**，内容滚到它后面，可读性靠系统的柔和渐隐（`.soft` 要显式写，自动样式在有的系统版本上是带硬边的色带）；iOS 17–25 回退到 `safeAreaInset` + `classicBarBacking()`（`.bar` 材质 + 分隔线）。栏里不是控件的文字（计数、提示、上传进度、确认页的状态行）一律过 `barStatusChip()` 放进玻璃小块——直接放在渐隐上，滚过来的内容会和它叠在一起读不清；**一行里的计数块与按钮同高**（两边的标签 `maxHeight: .infinity`，行高由最高的那块定；只在浮动栏、非辅助字号下），所以提示（它会折成两三行）不放进计数块，单独成行上方的一小条（`barStatusChip(compact: true)`），行的高度不随提示变——左右两块高度不一样会很难看，用户反馈过；**这一行由 `CountAndButtons`（`AnswerScreen.swift` 里的自定义 `Layout`）排，不是 `HStack`**：先量出行高（按钮行与计数块里高的那个），再用这个高度量按钮行；按钮行（`ButtonRow`，同样是自定义 `Layout`）里，快捷回复与「下一题」图标是**与「发送」同高的圆**（直径 = 行高，字号变大随之变大，G13；圆的宽要等行高定了才知道，`HStack` 做不到），「发送」拿剩下的宽；按钮行先取自己的理想宽度、从不被压缩，计数块拿剩下的——放得下「Answered 0/3」就并排；放不下，计数块自己缩成「0/3」（`ViewThatFits`）；还放不下，挪到按钮行上方单独一行。同高的行里「谁被压窄」不能交给 `HStack`：计数文字被挤得折成三四行，行就变高，吃满行高的按钮跟着被拉高（375 pt 的 iPhone SE 上出过，`docs/specs/ios-answer-flow.md` G12；`AskHumanBarUITests` 用字号档位把栏变窄来盯着它）；**可点的小块（会跳去未答题的提示）要把玻璃包在按钮外面、内边距留在标签里**（`barChipButtonLabel()` + `barChipButtonGlass()`）：玻璃放进按钮的标签里，iOS 26.2 上点它没有反应（27.0 上有）；按钮用 `barPrimaryButton()` / `barSecondaryButton()`（iOS 26 起 `.glassProminent` / `.glass`，之前 `borderedProminent` / `bordered`）；一栏里的玻璃放进同一个 `GlassGroup`（`GlassEffectContainer`），栏内各块的间距要大于它的 `spacing`，否则相邻的玻璃会融成一块。**「下一题 → 发送」是同一个 `Button`**（`SendBar.primaryButton`，只换文字与标识 `next-button` ↔ `send-button`）：换成两个按钮时，玻璃样式下换身份的那几帧会闪出一个空胶囊。新加底栏沿用 `.actionBar`，不要自己写 `safeAreaInset` + `.background(.bar)`；带输入框的栏见下一条。

- **已结束页的自动前进**（`ios-answer-flow.md` §3.8）：`prepareEndedCountdown` 只记录待显示资格；当前 `EndedStrip` 真正挂载且 App 可见、无键盘／弹层时用 `endedNoticeDisplayed` 开始 3 秒。输入保护只认实际可编辑的原生输入框，不能将点按只读网页后成为第一响应者的 `WKContentView`（也符合 `UITextInput`）误作键盘。开始后切后台不打断，重现横幅不重置；「停留」、换页、切标签与关开关仍取消。`RequestPageTransition` 在换到下一条前保存旧页内容区的临时原生快照，再与发送成功共用 `RequestScreen.Arrival` 的横滑；动画结束／离开释放，不落盘、不假造发送回执。Mock 的 `-AHEndInBackground YES` 等待 App 真正进入后台后再按 `-AHEndAfter` 延迟结束请求；两条后台 UI 回归通过激活系统设置再返回，断言 App 确实处于后台；Duo runtime 的 XCTest Home 键可能不生效，不能把按过 Home 当作已后台化。
- **阅读和附件准备归请求拥有**：`RequestScrollPosition` 观察原生滚动几何，用 `RequestReadingAnchor` 记录题卡／正文锚点与相对偏移，Markdown 就绪后恢复；每请求位置保存在 AppStore 的非观察缓存，用户新滚动会结束恢复。它不替换 scroll delegate、不设置输入焦点。`AnswerComposer` 按题保留 `AttachmentPreparationState`，请求换页不取消准备，其他 AttachmentMenu 用法仍在离开时取消；结束草稿会取消其准备。发送中的原表单不可编辑，其他请求不受影响；失败说明按请求 ID 保存，不在别条表单上弹错。
- **提交后的换页是一个小状态机**（`AppStore.advance` → `moveOn`）：收到 Mac 的确认后先设 `receipt`（`RequestScreen` 盖上全页「已发送」回执；它带着 `summary`——请求一关闭页面就没有详情了，回执自己记着是谁问的）；`AdvanceTiming.hold` 之后栈**一步**从 `[a]` 换成 `[b]`（栈里始终只有一页），回执记下 `next = b`，并出「已发送 · 还剩 N 条」提示条；位移由页面自己做（`RequestScreen.swift` 里的 `Arrival`，只有 `next` 指向它的页面才接手回执：回执的一份副本留在原地并略向左让，新页从右边滑进来盖住它，约 0.45 秒；新页的版面第一次排好后才开始动，否则长表单首次排版的卡顿会吃掉动画；「减少动态效果」下改成淡入）；`receipt` 一直留到 `settle`（0.8 秒）之后才清，回到列表时被弹出的那页也还在用它。**不用系统的推入**：它要把已发送页留在栈里、推完再拿掉，而 `NavigationStack` 按位置认页面，拿掉一页等于把第 0 位那页「改成」下一条——那页最后一帧（回执）会再闪两帧，它的滚动位置与 `@State`（阅读进度，决定底栏写「下一题」还是「发送」）也被沿用；而原地替换栈顶（`[a] → [b]`）在 iOS 27.0 上只有交叉淡入、在 18.5 上没有动画，两边都没有位移，所以位移放在页面里，并且每条请求一个独立页面（`RequestScreen` 上 `.id(id)`）。回执期间用户自己离开页面则 `cancelAdvance()`。UI 测试用 `AdvanceTiming.immediate` / `-AHAdvanceHold`；看这个动画要用不带 XCUITest 的 `simctl io recordVideo`（XCUITest 的无障碍快照会让过渡画面出现重影，长表单上一次查询要几秒，期间应用主线程被占住、动画被吞掉；录屏也是变帧率，只有帧的先后顺序可信）；模拟器场景 `single`（只剩一条）与 `longs`（两条长表单）就是为这条流程准备的。
- **回答与创建任务的多行输入**共用 `Views/Common/CaretTextView.swift`：原生输入保留选区与中文组合态，在输入、选区、布局或键盘变化后只滚动露出光标所需的距离，视口扣除键盘和操作栏；行数上限后框内滚动。绑定驱动的焦点获取与释放都由 Coordinator 合并到下一轮主线程，执行时读取最新绑定与启用状态；不能在 `updateUIView` 中同步 `becomeFirstResponder`，它也会重入 SwiftUI 的视图图。按钮动作里的 UIKit 键盘接力仍沿用上文规则。原生 UI 测试只在 Debug mock 的 `-AHInputCaretDiagnostics YES` 下读取真实光标几何，规格见 `docs/specs/ios-answer-flow.md` §3.5。
- **空状态按稳定的底部安全区居中**：列表与详情均保留 TabBar，系统临时更新底部安全区时仍要保持空状态位置稳定。列表页的空状态 / 骨架提示一律经 `.emptyState { … }`（`Views/Common/ListChrome.swift`，记住这个宽度下见过的最大底部边距）摆放，不要直接 `.overlay { ContentUnavailableView }`。
- **请求附带的图片：缩略图是 1:1 方块，查看器一条消息一个**（`Views/Attachments/`）：`AssetList` 里图片缩略图的格子大小由一块 `Color` + `.aspectRatio(1, contentMode: .fit)` 决定，图片放进它的 `overlay` 里 `scaledToFill` 再裁切；不要把 `scaledToFill` 的图片直接放进 `.frame(height:)`——它的布局宽度按图片比例撑大，宽图会溢出网格格子、叠到邻格上。点任一张图都打开 `ImageGalleryViewer`（这条消息的全部图片，左右滑动；非图片文件仍由 `AssetViewer` 单独打开），它用 iOS 17 的分页 `ScrollView`（非惰性 `HStack` + `scrollTargetLayout` + `.paging` + `scrollPosition(id:)`），不用 `TabView(.page)`（UI 测试里第一次滑动常被吞，疑似邻页刚被创建）；`scrollPosition(id:)` 的初值不会把非惰性的栈滚到那一页，所以开页时另用 `ScrollViewReader.scrollTo`。**每页的尺寸取自外层的 `GeometryReader`（`.ignoresSafeArea()`，整张 sheet 的大小），不要改回 `containerRelativeFrame`**：开发者模式的快速添加页在查看器上方弹出键盘时，滚动视图的容器尺寸被键盘反复改动，分页永远排不稳（页面高度随键盘一路变大，卡死的那次是在 824.33 ↔ 824.67 pt 之间来回），App 主线程被布局占满、整个卡死（采样里是 `ScrollStateRequestTransform` / `PagingScrollTargetBehavior` / `RelativeFrameModifier`）；只改忽略的安全区范围（滚动视图上或 `NavigationStack` 外面加 `.ignoresSafeArea(.keyboard)`、只忽略容器那一层）都没有用。守着它的是 `AskHumanDeveloperUITests.testTheButtonIsAboveAFullScreenImageViewer…`：改前它会卡死；动查看器的布局后要连跑多次（`-test-iterations 8 -run-tests-until-failure`），一次通过说明不了问题。**图片自己躲开顶栏**：每页再按外层 `GeometryReader` 读到的上、左、右安全区做 `.padding`（顶栏的高度，iPad 的表单 sheet 也一样），所以竖长的图从栏的下沿开始，不会躲在关闭 / 文件名 / 分享按钮（iOS 26 是玻璃胶囊）后面；读安全区必须在**不**忽略它的那一层——里面那层 `.ignoresSafeArea()` 的 `GeometryReader` 读到的永远是 0。外层只忽略底部：底部是另一个窗口的键盘出现的地方，页面不能跟着它动，所以底部不读也不留，`ZoomableImage` 的底边一直到 sheet 底；放大后的图被裁在栏的下沿。守着它的是 `testATallPictureStartsBelowTheBarOfTheViewer`（比较 `viewer-picture-<assetId>` 与栏的位置）。只有当前页与左右相邻页会下载并打开图片（`AssetPage(near:)`）。规格与取舍见 `docs/specs/ios-channel.md` §15（2026-10-29）；模拟器场景 `gallery` 与 `testPictureThumbnails…` / `testThePictureViewerPages…` 等四个 UI 用例守着它。
- **待办只是 Mac 的遥控与展示**（`docs/specs/ios-todos.md`）：权威状态仍是 Mac 的 `todos.json`；线上项目只有不透明 id（key 的 SHA-256 前 8 字节十六进制）与最少的上层目录名，没有路径；手机不把待办内容落盘（只在内存里缓存），也不进推送；写操作按待办 id 定位、带 `clientMsgId` 进幂等日志，应答附带该项目最新的整表，所以手机屏幕上的列表 = Mac 最后一次的回答 + 用户还没被应答的写入。「iCloud」只是一个**来源**（由一台开着同步且在线的 Mac 代答，掉线自动换），手机不直连 CloudKit（那要用户为 iOS App ID 开 iCloud 容器，见该 spec §11）。配对了多台 Mac 时，开着同步的 Mac 并进「iCloud」、不再单独出现在来源菜单里；它们各自「仅本机」的项目在 iCloud 视图里按 Mac 分段，点进去在那台 Mac 上读写。项目行上的 Agent 点不是 Mac 算的：手机拿 Agents 页已有的实时状态，按 Agent 项目信息里可选的 `repo`（仓库地址，Mac 开着同步时才带）或同一台 Mac 上的目录哈希对到行，所以跨 Mac 的点要那台 Mac 也装新版。项目列表的合并 / 分段 / 同名后缀在 Rust（`ios/todos_view.rs`）里有一份镜像桌面端 TS 的实现，改一边先看另一边的镜像用例；`todo.watch on` 会立刻回一条 `todo.changed` 作为基线。
- **会话历史只读 Mac，手机不落盘，滚动靠「记位置、插入、每次布局校正」**（`docs/specs/ios-session-history.md`）：权威是 Mac 的 `history.jsonl`；线上只有会话键 `{kind}:{sessionId}` 与往来的文字（附件、图片、附注只给数量，没有路径）；`SessionThread` 随页面丢弃，离开再回来总是从当前提问的顶部开始。分页游标是 `(beforeMs, beforeId)`，按 `(timestamp_ms, id)` 倒序，首页以请求的 `createdAt` 为锚（之后到的往来不算「更早」）；默认一页 8 条（≤ 20），整页 ≤ 256 KiB，超了 Mac 先丢最旧的（`more` 变 true）、再截短文本。界面上有三条别改的约束：线程区不要换成 `LazyVStack`（估算高度会让前插之后的位置漂）；SwiftUI 会按内容高度把 `UIScrollView.alwaysBounceVertical` 改回 `false`，而短页（多数请求）要靠它才拉得动，所以 `ThreadScrollCoordinator` 用 KVO 把它放回去；补偿必须在同一次布局里完成，不能改成「下一个 runloop 再 `setContentOffset`」（会有一帧错位；只有松手后回弹的起头放在下一个运行循环里）；下拉的空地不能用 `contentInset`（SwiftUI 约 10 ms 内改回去），要用页面内容里的一行加补偿，而且那次补偿要用 `setContentOffset(_, animated: false)` 才停得住 UIKit 自己的回弹。线程载入时 `RequestScrollPosition` 的 `intent` 令牌递增，让「恢复上次阅读位置」不把线程的插入当作用户新滚动。
- **回答里的指令与待办都以「这条回答赢得请求」为界**：`AnswerSubmit.directive`（离开 / 不再使用）与 `todoIds` 都在 Mac 网关里随回答一起校验，被别处抢先、被拒收（`invalid`：`todo gone` 等）的回答不应用指令、不让待办出队；`answer_hash` 只在 `todoIds` 非空、`annotations` 非空时才把它们算进去（附注是「引文 + 附注」按顺序并入），不带待办也不带附注的回答哈希与旧版逐字相同（旧发件箱里的重发不会被判成冲突）。手机把 `todo gone` 显示成可「重新选择」的提示，草稿保留。
- **成本红线**：EMQX 消费上限保持 0（额度用尽即停，不自动付费）；不创建管理 API Key。Mac 与手机分别统计自身实收与获 Broker 确认的发送，月累计通过手机合并并双向复制，按实例、UTC 月份、设备类型与稳定 ID 逐项取最大值后相加；解除配对保留已知用量。两端显示已记录报文流量与历史完整性，覆盖完整时显示额度占比，80% 免费额度时预警。见 [流量统计](specs/ios-traffic.md)。
- **保密**：broker 密码、配对码、方向密钥不得出现在日志、命令输出、文档与提交里；`E2ETests.testSecretsNeverReachTheLogsOrTheCommandOutput` 守着这条。
